# Integrations (Argus)

Services outside Legato can look up who owns work, hand that work to a task's agent, hear back from the agent, and show their cases in Attention. Argus, the person's operations service, is the first. It opens cases when CI fails and delegates them to the agent that owns the pull request. The contract was agreed with Argus's side. Argus documents it as `design.md` § D12 and § D19 in its own repository. Legato's changes are `openspec/changes/argus-integration` and `openspec/changes/argus-attention`.

```
Argus ──(lgi_ token)──► /api/integrations/owner              who owns acme/widget#12?
      ──(lgi_ token)──► /api/integrations/delegations        here is a brief
      ──(lgi_ token)──► /api/integrations/attention/{key}    this case needs Cameron
                              │ message / resume / start
                              ▼
                        the task's agent ──reply_case──► outbox ──(OAuth, argus:reply)──► Argus /api/cases/{id}/replies
```

## Scoped tokens

`legato integration token create argus --scope owner:read,delegate,attention` prints a token once (`lgi_` and 52 base32 characters). The database keeps only its SHA-256 (`integration_tokens`). `token list` shows names, scopes and dates; `token revoke <name>` stops it at once. A token has a kind (migration 083): `argus` for the tokens the CLI makes, `main` for a paired main instance's (see [Main instances and workers](#main-instances-and-workers)). A name is unique among live tokens of its kind, so a main named `argus` does not collide with Argus's token; `token list`, `token revoke` and Settings › Security › Integration tokens deal with `argus` tokens only. Settings › Integrations › Argus shows the connection; when `integrations.argus.url` is not pinned by config.yaml, an Argus that is not set up points to that field (its row just below) rather than to the file, and the card links to the tokens in Security.

The auth middleware (`internal/server/integrations.go`) lets a bearer token starting `lgi_` reach `/api/integrations/*` only:

- an unknown or revoked token gets 401 `unauthorized`;
- any other path gets 403 `forbidden`;
- a route whose scope it lacks gets 403 `missing_scope`.

The scope a route needs comes from the first segment of its path after `/api/integrations/` (`integrationScopes`): `owner` needs `owner:read`, `delegations` needs `delegate`, `attention` needs `attention`, and `handoff` needs `handoff`. A path in no group, such as `/api/integrations/ownership` or a new route nobody mapped, gets 403 `forbidden` whatever scopes the token holds: a new group must be given a scope before a scoped token can reach it.

`handoff` (`service.ScopeHandoff`) is for the routes a main instance uses to hand tasks to a worker instance. Only pairing a main gives it, alone (`IntegrationTokenService.CreateMain`): `token create` refuses it, and the CLI does not offer it. The WebSocket never takes a scoped token. The full web token works on the integration routes too, and acts as Argus there, but it is no main: handoff handlers refuse it (below). A request made with a scoped token carries its identity in its context (`integrationFrom`): kind, name, instance ID and scopes.

Integration routes answer errors as `{"error": "<code>", "message": "<text>"}`. The other routes keep `{"error": "<message>"}`.

## Main instances and workers

A main instance pairs with a worker instance by phrase, as a phone does, and gets a token that can only hand off ([GLOSSARY](../../GLOSSARY.md) § Instances and handoff). The spec is Burnlite LEG-15; this section covers pairing (LEG-18). Every Legato can be both.

**On the worker.** The person opens a pairing request for a main: Settings › Connections › Main instances › **Pair a main instance**, `legato pair --main`, or `POST /api/pairing {"purpose":"main"}`. It differs from a phone's request (see [Web UI](web-ui.md) § Pairing by phrase) in four ways:

- **Its own SPAKE2 identity.** The main is party A as `legato-main` (`pairing.MainProtocol`), so a phone cannot complete a main's request, nor a main a phone's: each gets 403 and uses an attempt. The phone's identities, labels, AAD and `testdata/exchange.json` are unchanged.
- **The main must say who it is.** Its sealed field (the `phone` field of `/api/pair/confirm`, sealed under `pairing.LabelMain`) is `{"name", "instance_id"}`. A field that is missing or does not open, a name with nothing left after normalising, or an instance ID that is not `srv-` and 16 hex digits fails the confirm with 400 (`ErrPairingClient`). The name is lowercased and every run of other characters becomes one dash, at most 40 (`service.NormaliseMainName`).
- **It mints a token.** `service.PairingSecrets.Secret` is the pairing service's secret callback in both runtimes; for a main it calls `CreateMain(name, instanceID)`: an `lgi_` token of kind `main` holding `handoff` and `reeve` (the second lets the main's Reeve message this one's; Settings › Connections › Main instances turns it off, `PUT /api/settings/mains/{instance_id}/reeve {enabled}`, and migration 103 gave it to mains paired before), carrying the main's instance ID. Re-pairing the same instance ID revokes its old token and stores the new one in one transaction (`store.ReplaceMainIntegrationToken`), so a lost confirmation or a renamed main just pairs again. Another live main with the same name is 409 (`ErrMainNameTaken`): unpair it first. The sealed secret is `{token, name, ca_certificate, instance_id}`, the last being the worker's instance ID (a phone's secret never has one).
- **No QR code.** The request's view has `purpose: "main"`, no `pair_uri`, and `address`: the address the browser used, else the first LAN address, for the person to type on the main.

A main is known by its instance ID, never its name. Settings › Connections › Main instances lists the live `main` tokens (`GET /api/settings/mains` → `{mains: [{name, instance_id, paired_at, last_pull_at?, open_handoffs, reeve}]}`, `last_pull_at` being the token's `last_used_at`; `open_handoffs` counts the main's handoffs not closed, `store.CountOpenHandoffsByMain`), and **Unpair** revokes one and closes its open handoffs, leaving their cards (`DELETE /api/settings/mains/{instance_id}`, 404 when neither paired nor holding handoffs; § Take back, Drop and Leave). `/api/meta` advertises `handoff_pairing: 1`, `handoff` (the protocol version, `service.HandoffProtocolVersion`: 2 since the Handoff call) and `sandbox` (whether agents can run in the sandbox here) when the server pairs mains, and `review_passes` (its defaults, adapters with tiers, and skills) while `review_passes.enabled` is on; a main shows the Hand off dialog's review section only to a worker that advertises it. See [Configuration](config.md).

**Handoff routes.** They live under `/api/integrations/handoff/` and act only for a paired main: a handler calls `requireHandoffMain(w, r)` (`internal/server/instance_pairing.go`), which returns the scoped identity (kind `main`, scope `handoff`, its `InstanceID`) or answers 403 `not_a_main` itself, for the full web token too. Handlers then act only on that main's records and answer `not_found` for another's. The first route is `GET /api/integrations/handoff/pairing` → `{worker_instance_id, main_instance_id, main_name, handoff}`: how the worker sees the pairing.

**On the main.** Settings › Connections › Workers › **Add a worker** takes the worker's address (https assumed without a scheme), the four words and this main's name on the worker (`POST /api/settings/workers {address, phrase, name}`; `GET` lists `{workers, instance_id, main_name}`, the last being the suggested name). `service.WorkerService.Pair`:

1. reads the worker's `/api/meta` and refuses one without `handoff_pairing` or with an older `handoff` (`ErrWorkerTooOld`, "update the worker", 409);
2. runs SPAKE2 as `legato-main` with its normalised name and instance ID sealed; until then it does not check the worker's certificate, since the phrase authenticates the exchange and the certificate to trust arrives sealed;
3. refuses a secret whose token is not `lgi_` (an old or wrong worker sending its full web token) or that has no instance ID (`ErrWorkerRefused`, 409);
4. calls the pairing route with the new token over the worker's certificate and checks the worker's instance ID;
5. keeps the token sealed in Legato's own secret store as `legato://handoff-worker-<worker instance ID>` (see [Credentials](credentials.md)), and the worker in `workers` (instance ID, address, name, this main's name there, CA, the secret's name, sandbox, protocol version, paired at, last pull). Pairing the same worker again replaces its record.

A wrong phrase or a closed request is `ErrWorkerRefused` with the worker's words; no answer is `ErrWorkerUnreachable` (502). `WorkerService.Client(ctx, instanceID)` is the client of a paired worker for later calls: `Call(ctx, method, path, body, into)` sends the main's token over the pinned certificate, and `CheckPairing` checks the worker still accepts this main and is the same instance.

### What a worker advertises

A main used to know three things of a worker before it handed work over: `handoff_pairing`, the protocol version and `sandbox`. Everything else showed only after the agent started. Since LEG-226 a worker advertises what its agent will have, and the main keeps it (`service.HandoffAdvert`, `internal/service/handoff_advert.go`).

- **Public, in `/api/meta`:** `handoff_features`, the handoff features this build supports by name (`service.HandoffFeatures`: `base`, `capabilities`, `drop`, `events`, `pushed_branch`, `return`, `review_override`, `ticket`). Features replace protocol bumps: `handoff` stays at 2, and a main refuses or degrades per feature. They are build facts, as the version already in `/api/meta` is.
- **Behind a main's token, `GET /api/integrations/handoff/capabilities`** (`service.HandoffCapabilitiesPath`, `requireHandoffMain`): `{version, commit?, features, sandbox, agents: [{name, installed, tiers, prompts_off}], default_agent, mcp_tools, mcp_connections, skills, repositories, refuses?, review_passes?}`. These name the worker's skills, MCP connections and repositories, so a stranger on the LAN does not get them from `/api/meta`. `HandoffWorkerService.Advert` builds it from the agent service (registered tools, `PromptsOffAdapter`) and `HandoffAdvertSources`, which `handoffAdvertSources` in `cmd/legato/handoff_advert_runtime.go` fills: the tool's command on `PATH` (`claude`, `chimera`, `codex`), `adapters.<tool>.tiers`, `agents.mcp.enabled`, the MCP connections that are on, the Legato-managed skills that are on and usable, and the repositories the credential broker's GitHub credentials list (`CredentialBroker.GitHubRepositories`, from `config.yaml` or a vault; `null` when the worker has no broker to ask, which a main does not second-guess, `[]` when it has no GitHub credential). A source that fails is logged and left empty. `commit` is `version.Commit()`, the build's `vcs.revision` (12 characters, `-dirty` for a modified tree), when the build has one.

The main reads it at pairing, after the token checks (`WorkerService.RefreshAdvert`; a failure does not stop pairing), and again after each pull on a connection or a manual sync (`WorkerConnections.refreshAdvert`), keeping the last good one when a read fails. It is stored as JSON in `workers.advert` with `advert_at` (migration 120) and listed in `GET /api/settings/workers` as `advert` and `advert_at` on each worker (`WorkerAdvert` in `web/src/lib/workers.ts`). A worker without the route (404 or 405) is an older Legato: it pairs, and has no `advert`.

**Feature-gated calls (LEG-228).** `TaskHandoffService.HandOff` reads the worker's `/api/meta` at each handoff (`WorkerMeta.HandoffFeatures`) and sends what goes beyond a local task on a new branch only when the worker lists its feature: a ticket (`ticket`), a pushed branch (`pushed_branch`), a review override (`review_override`; an override that only turns passes off is dropped instead, as it is for a worker without review passes). Otherwise it refuses with `ErrWorkerTooOld`, "<worker> is too old for <feature>: update it (it runs Legato <version>)", and sends nothing. A worker that lists no features was built before they were advertised: `workerFeatures` gives it what its release took on protocol 2 (`pushed_branch` from v0.7.0, `ticket` from v0.7.2, `review_override` from v0.9.0, all three for `dev` or an unknown version), so a v0.21.0 worker is still sent a ticket and a v0.7.1 one, which dropped it, is not. The worker decodes the Handoff call strictly (`DisallowUnknownFields`) and answers 400 `unknown_field` naming the field, so a newer main past the gate cannot lose data to a 201 either. Summary rows and pulls on the main stay lenient, so an older main still reads a newer worker. The return, drop and review routes are not gated: they act on tasks already away.

**Restarting a handed-off agent (LEG-231).** On a worker, the agent service holds `HandedOffAgents` (`SetHandedOffAgents`, the `HandoffWorkerService`). `restartAgentWith` asks it first: for a card with an open handoff, Switch sandbox and the host-network toggle are refused (`ErrAgentNotRestartable`, 409: "this agent was handed off from <main>; it always runs unattended in the sandbox"), and a plain Reload goes through `RestartHandedOff(HandedOffRestart{Note, Resources, Stop})`, which is `ResumeAuthor` with the `[legato reloaded]` note and the resources the reload carries: it finds the saved conversation the way a resume does, and only then calls `Stop`, so an agent that could not come back is refused (409) and left running; then prompts off, in its clone, the branch guidance kept and its branches granted to the new execution. `HandedOffFrom` returns an error other than "no open handoff", which refuses the restart rather than treat the card as the worker's own.

**Legato's tools on the worker (LEG-233).** The brief asks the agent to record its work with `add_task_note`, and a reviewer reports with `submit_review`: both are Legato's MCP tools, which a worker gives its agents only with `agents.mcp.enabled`. A worker with them off refuses every handoff (`Accept`: 422 `no_mcp_tools`, "turn on agents.mcp.enabled here"), lists it in its advert's `refuses`, and a main refuses before sending when the advert says `mcp_tools: false` ("turn on agents.mcp.enabled on legato-1: …"). The brief keeps naming the tools: falling back to `legato task note` was the alternative, but a reviewer has no CLI fallback for `submit_review`.

**The ticket's holder (LEG-232).** The worker's agent may claim, note and close its ticket on the provider (decision on LEG-225), under the main's task ID: the worker passes `AgentSpawnOptions.Holder` (the handoff's `main_task_id`, kept by `ResumeAuthor` and restarts), which sets `LEGATO_HOLDER`, and the brief's ticket section says so ("as holder LEG-33 … use it, not LEGATO_TASK_ID"; golden `*-jira.md`, `*-burnlite.md`), and that without access to the provider here the ticket is read only for this run. The provider access is the worker's own (its MCP config or connection); the main's never crosses. `docs/agents/issue-tracker.md`'s holder rule puts `LEGATO_HOLDER` first. On the main, a provider-backed task the provider moved while away (its status no longer the column it left) is brought home where the provider put it, not into the worker's column (`TaskHandoffService` return): the provider's state wins. One the provider did not move lands in the worker's column as before, and a later pull moves it if the provider says otherwise.

**A worker that can't take handoffs.** The advert's `refuses` lists why the worker would refuse every handoff now, each with what to do: no sandbox (Legato's sandbox needs Linux with bubblewrap on `PATH` and `agents.sandbox.enabled`; a macOS worker has none) and a board with no columns. The main sums them up as the worker's `cannot_take_handoffs` ("can't take handoffs: …"; from `sandbox` alone for a worker without an advert), which Settings › Connections › Workers shows under the worker and Add a worker says once paired. Pairing still succeeds. `legato serve` seeds `board.columns` at start when the board has none (`setup.SeedColumnsIfEmpty`), as the TUI's first-run wizard does, so a headless worker no longer needs `legato columns sync` first.

**Testing.** `internal/handofftest` runs a main and a worker in one Go test: each its own SQLite and real services, the worker's web server on an `httptest` TLS server (its certificate is the CA the main pins, the same at each restart), agents started in a `FakeTmux`, one injectable `Clock`. `StartWorker`, `NewMain`, `Pair(t, main, worker)`; `worker.Stop()` and `worker.Restart()` (same database, address and certificate); `WorkerOptions.Wire` gives the worker's server more routes before it serves. Its package comment shows how to use it.

## Handing off a task

A paired main hands one of its tasks to a worker, which makes a card for it and starts a briefed agent on it at once; the main keeps the task **away** and read-only. Spec LEG-15 § The protocol, § Accepting and starting on the worker, § The brief; this section covers the Handoff call (LEG-19): a local task, starting from a new branch. Pull and Events (LEG-24), return and recall (LEG-25), push grants (LEG-21), a pushed branch (LEG-22) and provider-backed tasks (Jira, LEG-27; any provider, LEG-35) build on it.

**Session history of an away task.** Each instance keeps and serves its own session history; a main makes no calls to a worker for it. On a main, an away card (the Away lane's panel and the detail panel) links to **Session history on <worker>**, `workerHistoryURL` (`web/src/lib/away.ts`: the origin of the card's `url`, the handoff summary's, then `/agents/history?task=<worker_task_id>`); a history entry whose task is away has state `away`, is not restorable (`RefuseAway` also refuses a restore), and carries `away_history_url`, built the same way by `service.WorkerHistoryURL` from the away task's row (`SessionHistoryOptions.AwayHistoryURL`).

**On the main.** `service.TaskHandoffService.HandOff(ctx, TaskHandoffRequest{TaskID, Worker, Purpose, Kind, Branch, Repo, AgentKind})`, which the web board's Hand off form reaches through `POST /api/tasks/{id}/handoff` (see [Web UI](web-ui.md) § Handing off a task; wired by `wirePairing`). Purpose is `make-change` or `find-out`; kind `new-branch` (the default) or `pushed-branch` with `Branch` naming a branch already on GitHub (below); repository `owner/name`; an empty agent tool means the worker's default. Before anything is sent it refuses (`ErrHandoffInput`) an archived or ephemeral task, a task of a provider other than Jira, a bad purpose or repository, and a pushed branch with no name or a name that is not a branch, refuses a task already away (`ErrTaskAway`) or whose agent runs here (`ErrHandoffAgentRunning`, "stop it first"), and reads the worker's `/api/meta` over its certificate without the token (`WorkerClient.Meta`): no answer is `ErrWorkerUnreachable`, a `handoff` below `HandoffProtocolVersion` is `ErrWorkerTooOld` ("update the worker"), no sandbox is `ErrWorkerRefused`. Errors from the worker name it, in words the web form shows as they are: "vm-1 did not answer, so nothing was sent", "vm-1 refused the handoff: <the worker's message>" (`WorkerClient.Call` returns a `*WorkerRefusal` carrying the worker's own words, which `errors.Is` matches to `ErrWorkerRefused`). Then it records the handoff in `away_tasks` as `sending` with a fresh handoff ID (`ho-` and 16 hex), sends the call, and on the worker's answer marks it `away` with the worker's task ID. A refusal deletes the row; no answer leaves it `sending`, which is not away, and the next handoff of that task to the same worker reuses its ID, so a worker that did get the first call answers with the card it made. The worker's answer (its state, `pending` as a rule, and any failure) is kept as the away task's first `last_summary` (`service.HandoffSummary`, `store.SetAwayTaskSummary`), the state the board shows until LEG-24's summary rows replace it. `Away(ctx, taskID)` and `ListAway(ctx)` read them as `service.AwayTask`, with `State`, `Failure`, `StateAt` and `WorkerURL` (the summary's link, else the worker's board with its card picked out); the board's cards carry it as `Away` (`away` in `GET /api/board`, which also lists the paired `workers`).

**Away is read-only.** `service.RefuseAway(ctx, db, taskID)` is a `*TaskAwayError` (`errors.Is(err, ErrTaskAway)`; "task X is away on vm-1: it can change only there until it comes back") for a task with an `away` handoff. It is asked where every surface changes a task: the board service's title, description, workspace, metadata, move (`moveCard`, so the sync service's `PushMove` too), reorder, delete and archive (`ArchiveDoneCards` and `store.ArchiveTasksByStatus` leave away tasks); the agent service's `SpawnAgent`; the CLI's `TaskUpdateFields` (`legato task update`, which agents reach through the broker; the other `legato task` setters go through the board service); and `HandOff`. The web API answers it 409 (`taskErrorStatus`), and `POST /api/tasks/{id}/agent` asks the board's `RefuseAway` before it starts a clone in the background. Notes can still be added: they stay on the main.

**The call.** `POST /api/integrations/handoff/tasks` (`service.HandoffCallPath`) with `service.HandoffCall`: `{handoff_id, main_task_id, title, details, ticket?: {provider, key, text, url?}, notes: [{id, body, created_at}], repo, purpose, kind, branch, agent_kind}`, `branch` being `legato/<main task id, lowercased>` for `new-branch` and the given branch for `pushed-branch`. It answers `{handoff_id, worker_task_id, worker_instance_id, state, failure?}`: 201 for a new card, 200 for the same handoff ID with the same body (the request hash), 409 `idempotency_conflict` for the same ID with another body. `GET /api/integrations/handoff/tasks/{handoff_id}` is one handoff as its main sees it; another main's is 404 `not_found`. Both need a main's handoff identity (`requireHandoffMain`). Refusals are 400 `bad_request`, or 422 with `no_sandbox`, `unknown_agent` (a tool the worker does not know, or cannot start with its prompts off; never a fallback), `cannot_clone` (`CloneChecker.CloneProblem`: the repository service, which needs a GitHub credential that can read the repository) or, from a worker older than LEG-27, `unsupported` for a provider-backed task; none makes anything. An older worker answers a `pushed-branch` call `unsupported`, which the main shows as "vm-1 refused the handoff: this worker cannot start from a pushed branch yet"; the protocol version is unchanged.

**On the worker.** `service.HandoffWorkerService` (`internal/service/task_handoff_worker.go`; wired by `wireTaskHandoffs` in `cmd/legato/task_handoff_runtime.go` for both web servers). `Accept` makes, in one transaction (`store.CreateHandoffCard`), an ordinary card in the main's workspace (`store.EnsureMainWorkspace`: made on demand, named after the main, or with the end of its instance ID when the name is taken, and found by the instance ID afterwards, `main_workspaces`), in the column named Doing or In Progress, else the first; the main's notes as `task_notes` with `source` `main` and `remote_id` the main's note ID; and the handoff record, `pending`. Then it starts the agent in the background (`start`): it claims the start (`store.ClaimHandoffStart`, so two Legatos on one database do not both start it; a claim older than 15 minutes is stale), composes the brief, and calls `SpawnAgent` with the repository, the branch, the agent tool, the brief as `Assignment` and `Unattended` (below). Success makes the handoff `in_progress`; an error makes it `failed` with the error as its reason (a clone that failed, the sandbox missing). `ResumePending` starts the pending handoffs no Legato is starting; the process that serves the broker runs it at start and every minute. `Reconcile` makes an `in_progress` handoff `done` while its card is in a column named Done, and `in_progress` again when it leaves; `StartEventLoop` runs it on every card event and every 30 seconds. State changes publish `EventHandoffChanged` (payload: the worker's task ID). The board's cards carry `HandedOffFrom` (`handoff_from: {main, main_task_id}` in `GET /api/board`), which the web card shows as "from workstation · K7Q2M9XA".

**The agent.** `AgentSpawnOptions.Unattended` runs it in Legato's sandbox whatever `Unsandboxed` says, refused when the sandbox is off, with its tool's permission prompts off: an adapter that is a `service.PromptsOffAdapter` adds `PromptsOffArgs()` to its launch command (Claude Code `--dangerously-skip-permissions`; Codex `-c approval_policy="never" -c sandbox_mode="danger-full-access"`, configuration its native bridge also gives the app server; Chimera `--auto-approve all`). A tool that is not one cannot take a handoff. The brief (`service.HandoffBrief`, `task_handoff_brief.go`) is the text settled in LEG-7: work alone, decide and note the decision, no progress notes; for make-a-change, work on the branch, stack on `legato/<main task id>-<a few words>`, and open PRs as the repository's pull request mode on the worker says (`HandoffBriefInput.PullRequests`, set by `HandoffWorkerOptions.PullRequests` for make-a-change; `handoffPRLine`): drafts with no mode, as before, drafts that Legato enforces with `draft`, ready for review with `ready`, the agent's choice with `agent`; for find-out, answer in notes and push nothing; finish with an outcome note and move the card to Done (`legato task update --status Done`), then stay. Text people wrote is fenced in tags so the agent can tell it from the brief: the ticket's copy in `<ticket provider="…" key="…">`, the Legato details in `<task-details>`, each of the main's notes in its own `<note>`, after a line saying headings inside a tag belong to that text. A closing tag of the fence's name inside the text, in any case, is escaped (`<\/ticket`, `fenced`), so the text cannot end its fence early. Its golden files are `internal/service/testdata/handoff_brief/`; `go test ./internal/service -run TestTheHandoffBrief -update` rewrites them. The brief says pushing is already allowed, and for make-a-change it is: once the agent has started, the worker grants its session pushes to `legato/<main task id>` and `legato/<main task id>-*` and draft pull requests from them (and pull requests that are not drafts, when the mode is `ready` or `agent`), and its credential and stack guidance name those branches (`HandoffWorkerOptions.Grants`; see [Credentials](credentials.md) § Handed-off sessions). A find-out handoff is granted nothing.

**Fetching first.** Every handoff fetches the worker's repository cache before its clone, whatever `repository_cache.max_age` says: a handoff can start long after the person last pushed, and a new branch must start from GitHub's default branch as it is then. A new-branch start calls `HandoffRepositories.Refresh(ctx, repo)` (`RepositoryService.Refresh`) before the spawn, so the clone's own `Ensure` finds the cache fresh; a fetch that fails makes the handoff `failed` with git's reason and no clone. A pushed-branch start fetches in `PushedBranch` (below).

**From the main's base branch (LEG-236).** The main's repository presets decide the intent: `TaskHandoffOptions.BaseBranch` (`presetBaseBranch` in `cmd/legato/worker_connections_runtime.go`, the first preset of the repository naming a `base_branch`) gives a new-branch handoff its `base`, sent only to a worker with the `base` feature (else `ErrWorkerTooOld`, "too old for base"). The worker keeps it in `handoffs.base` (migration 121; refused with `bad_request` on a pushed-branch call or when it is no branch name). At start it fetches and checks GitHub has the branch (`HandoffRepositories.PushedBranch`); one GitHub does not have makes the handoff `failed` with "origin has no branch develop, the base branch <main> gave for <repo>", and nothing is cloned. The spawn passes it as `AgentSpawnOptions.Ref`, so the job clone makes `legato/<main task id>` at it, and the brief says "Starts from: a new branch off develop" and to open PRs against it (`HandoffBriefInput.Base`; golden files `*-new-branch-base-local.md`). Without a base, the new branch starts from GitHub's default branch as before. The worker's own presets decide only access and the clone address.

**From a pushed branch.** A `pushed-branch` handoff starts on work the person began and pushed (Burnlite LEG-22). Before the agent starts, the worker fetches its repository cache, whatever `repository_cache.max_age` says, and looks for the branch there (`HandoffWorkerOptions.Repositories` is a `service.HandoffRepositories`: `CloneProblem`, `Refresh(ctx, repo)` and `PushedBranch(ctx, repo, branch) (base, err)`, which `RepositoryService.PushedBranch` is: `Refresh`, then `gitrepo.Runner.HasBranch` on the cache, then its default branch). A branch GitHub does not have makes the handoff `failed` with "branch not on GitHub: acme/widget has no branch fix/x" (`service.ErrBranchNotOnGitHub`); the repository's default branch fails it too ("main is the default branch of acme/widget: hand off a branch of your own"). Neither makes a clone or a branch. Otherwise the spawn passes `AgentSpawnOptions.PushedBranch`, which becomes `JobCloneRequest.PushedBranch`: the job clone checks out GitHub's branch, tracking it, and `JobClone` refuses with `ErrBranchNotOnGitHub` rather than make a new branch of that name should it have gone since the fetch. The brief's pushed-branch form says "Starts from: the pushed branch <branch>" and, for make-a-change, to read its commits against the default branch first (`HandoffBriefInput.Base`), then only add commits, never rebase, amend or force-push it, and reuse its PR, stacking new `legato/<main task id>-…` branches on top of it; for find-out, to read its commits first. The grant names the given branch beside the session's own (`HandoffGrantBranches(mainTaskID, given)`), and `SessionBranches.Given` tells the credential and stack guidance (`BranchToolsPromptAdapter.ToolsPromptFor(base, given, granted)` for Codex and Chimera; the MCP server reads it from the handoff for Claude Code).

**Handed-off cards stay.** A worker refuses to archive or delete a card whose handoff is open: `service.RefuseHandedOff(ctx, db, taskID)` is a `*TaskHandedOffError` (`errors.Is(err, ErrTaskHandedOff)`; "this task belongs to workstation; return or recall it from there"), asked by the board service's `DeleteTask` and `ArchiveTask`, while `ArchiveDoneCards` and `store.ArchiveTasksByStatus` leave such cards in Done (`store.OpenHandoffForTask`). The web API answers it 409 (`taskErrorStatus`), and the web board shows the words. Moving, editing, notes and the agent work as usual. Whatever closes a handoff (return, recall, Drop, unpairing) closes it before it archives the card, or archives through the store.

**Provider-backed tasks.** A task from a ticket provider (Jira, Burnlite, any later one; Burnlite LEG-27 for Jira, LEG-35 for the rest) travels in two parts: `details` are its Legato details (`description_md`, the part a person edits in Legato), and `ticket` (`service.HandoffTicket{Provider, Key, Text, URL}`; its presence says the task is provider-backed) is the main's provider name (`jira`, `burnlite`; a copy handed on names the provider it came from), the ticket's key (`remote_id`), its text as the main last synced it (`remote_description_md`: Jira's description, or Burnlite's Description, Plan and Checklist) and its address (`remote_meta.url`); `title` is the ticket's name. The main reads all of it from the task the same way whatever the provider (`handoffTicket` in `task_handoff.go`), and refuses only a provider-backed task with no `remote_id` (`ErrHandoffInput`, "has no Burnlite key"), besides archived and ephemeral ones. The main keeps the link, its sync and the ticket's text: nothing of them changes on the main while the task is away or when it comes back (its sync still refreshes the title and the text meanwhile; `RefuseAway` keeps everything else). The worker never talks to the provider: its card keeps the copy with Legato's two-part model for provider-backed tasks, under the provider `<provider>-copy` (`service.HandoffCopyProvider`; `HandoffCopyOf` and `IsHandoffCopy` read it back), which no ticket source has, so no sync pulls it and no move pushes a transition. `remote_id` is the key, `remote_description_md` the copy, `remote_meta` only `{url}`. The worker answers 400 `bad_request`, making nothing, for a `ticket.provider` that is not a lowercase name (`[a-z][a-z0-9_-]`, at most 50), a key that is empty or longer than 200 characters, text over 256 KiB, or a `url` that is not an http or https address. So the board service refuses its title (`UpdateTaskTitle`: `ErrRemoteTaskReadOnly`, as do the CLI and the TUI's `t`), `UpdateTaskDescription` changes only the Legato details, the web detail panel shows the copy as "From Burnlite LEG-33 (read only)" (the provider by `providerLabel`, which names any `*-copy` by the provider it came from) with "Edit Legato details" and no title edit, the TUI names and draws it as its provider (`theme.ProviderName`, `Icons.Provider`), and the effective description agents read (`legato task show`) is the ticket's text, then `## Legato details`. The brief gives the copy as `### From <Provider> <KEY> (read only)` before `### Details` (`HandoffBriefInput.TicketProvider`, `TicketKey`, `TicketText`, read from the card, the provider named by `service.TicketProviderLabel`; golden files `*-jira.md` and `*-burnlite.md`). Only the Legato details come back: step 1 answers `details` from the card's `description_md`, and the main applies no title to a provider-backed task (`store.AwayReturn.Title` empty keeps the task's). The card keeps its `*-copy` provider after its handoff closes, so on a worker that unpaired its main it stays a read-only copy with editable details.

**Testing.** The harness's worker now has a `HandoffWorkerService` (`worker.Handoffs`), a fake repository cache (`worker.Repos`: `Refuse(repo, why)`, `Fail(repo, err)`, `Clones()`, `Push(repo, branch)` for a branch on GitHub, `Refreshes()` for the fetches `Refresh` and `PushedBranch` made; clones are empty folders, every default branch is `main`), a fake sandbox backend (launch lines start `SANDBOX`), and two fake agent tools, `claude-code` (the default) and `codex`, whose launch command is their name and whose prompts-off argument is `--<name>-prompts-off`. `worker.Settle()` waits for agent starts, `worker.HoldStarts(true)` accepts without starting (a worker that stopped right after accepting), and `WorkerOptions.Handler` wraps the worker's server to stand in for an old worker or a lost answer. The main has `main.Handoffs`. See `internal/handofftest/handoff_test.go`, `pushed_branch_test.go`, `fresh_fetch_test.go`, `handed_off_card_test.go` and `jira_test.go` (a fake Jira, `TicketProvider`, behind each instance's sync service, recording every call); the cache's fetch and checkout of a pushed branch are tested against local bare repositories in `internal/service/repository_pushed_branch_test.go`.

### Resuming the author

`HandoffWorkerService.ResumeAuthor(ctx, cardTaskID)` (`task_handoff_resume.go`) brings back the author of a card's open handoff when it is not running, for the review loop. It reconciles sessions first (a worker restart or a crash leaves a `running` row whose tmux is gone), and does nothing while the main slot's agent runs. Otherwise it resumes the main slot's saved conversation of the handoff's agent tool (`GetTaskResumeSession`: Claude Code's and Codex's provider session, Chimera's selector) with what the first start had and a plain resume loses: `Unattended` (prompts off), `Repo` (so the spawn joins the task's live job clone, where it is recorded, and checks it is the folder the conversation was saved in: `prepareTaskResume` leaves the working directory to the clone when one is asked for), the branch guidance (`Branches`), and, after the spawn, the same `GrantBranches` grant for the new execution. With no saved conversation, or a failed resume, it returns `ErrAuthorNotResumable` with the reason; it never starts a fresh author.

## Review passes

`service.ReviewPassService` (`review_pass*.go`) is the review-pass engine: it moves review loops on, and knows nothing of who started one. Each loop is a `ReviewLoop` (`review_pass_caller.go`): the task it is keyed on (the loop record it hosts, read and written through the store's task-keyed view of it, `HandoffReview` despite the name; its reviewer slot; its job clone; see [Database](database.md) § Loop record › The engine's view), the repository, the author's task (`AuthorTaskID`, whose main-slot agent is told of each round and resumed; empty for a person, who reads GitHub and is never messaged) and `CountComments` and `CountChecks` (whether comments from people and bots, and counted checks, are items too: handoff loops and agent-authored run loops both, comments from pass 1 on for the latter (LEG-590, reversing LEG-255 for them), person-authored run loops neither). A **caller** (`ReviewCaller`, registered with `AddCaller`) lists its loops that move on (`Loops`), finds one by task (`Loop`, for a submission, a post or a queued pass), says when the author has finished a round (`AuthorDone`), is told of each stage (`Stage`: a pass started, feedback for the author, clean), resumes the author (`ResumeAuthor`, `ErrCannotResumeAuthor`), hears of every phase change (`Changed`) and names what the reviewer reviews (`Subject`, the brief's opening). The engine is built in every host process (`legato serve`, and the TUI whether or not it serves the web UI) with `review_passes.enabled` ([Configuration](config.md)) and the credential channels, handoffs or not (`startReviewEngine` in `cmd/legato/review_pass_runtime.go`, before the web server; `wireIntegrations` takes it as `integrationDeps.engine`), with the reviewer App's `ReviewPublisher` ([Credentials](credentials.md) § The reviewer App) and `GitReviewCheckout`. It **runs only in the broker holder** (spec LEG-559 D9): `Tick` is called at start, on card moves, `gap` after a run changes and every 15 seconds, and does anything only while the process serves the broker; with no caller's loop a tick does nothing. While it ticks, the holder holds `<data_dir>/review-engine.lock` (`reviewEngineLock`, an exclusive `flock`, which the operating system releases when the process ends), so any process can ask whether some Legato on the data folder runs the engine: `reviewEngineRunning(dataDir)` (`cmd/legato/review_engine_lock.go`; a shared lock that is refused means it runs). A process without the engine (not the holder, review passes off in it, or no credential broker) never opens, moves on or fails a loop: what it starts waits for the holder, and when the holder changes (the TUI exits, `serve` takes the broker) the new holder's first tick picks up every waiting loop.

The **handoff caller** (`HandoffReviewCaller`, `review_pass_handoff.go`) registers when the engine is built (`startReviewEngine` builds the process's one `HandoffWorkerService`, `newHandoffWorker`, and calls `wireHandoffReviewCaller`; `wireTaskHandoffs` serves that same service), so a process that holds the broker without the web UI still moves handoff loops on. It is what the handoff side asks of review passes (`HandoffWorkerService.SetReviews`, `HandoffReviews`). Its loops are the open make-a-change handoffs with review passes on, started and not returning, keyed on the card, with the card's agent as author and `CountComments` and `CountChecks` on. The card's column drives it: in Done the author is done; a pass moves the card to `review_column`, feedback to the work column, clean to Done; a dead author is resumed with `HandoffWorkerService.ResumeAuthor`; each change publishes `EventHandoffChanged`. A handoff is `done` only after a clean pass whose counted checks passed or were answered by a reply (`Reconcile` asks the caller's `DoneAllowed`). The rest of this section is the engine as the handoff caller drives it.

- **The loop** (the loop record the card hosts, one per card, owner `handoff`, its card the agent author, as a loop converted from before the record is; see [Database](database.md) § The engine's view): phase `""` (the author works), `ready`, `waiting_for_reviewer`, `reviewing`, `waiting_for_author`, `clean`, `stuck` (with `reason`), or `skipped` (no pull request to review), the pass count and the mismatch count. Its `settings` are the handoff's `ReviewPassSettings` (the worker's defaults; a main's override, LEG-75).
- **Trigger.** When the card is in Done the loop is `ready`. Once the author is idle (its main slot's activity anything but `working` or `waiting`, or not running: a `background` job, which may never end, holds nothing back, since the tip and clean-tree check below catches work it leaves unpushed), `ReviewCheckout.Branches` names the job clone and its local branches (`stackgraph`, else the checked-out branch), and `FindReviewStack` (`review_pass_stack.go`) follows GitHub's base→head chain from them and the handoff's branch (`ReviewGitHub.OpenPulls`, GET-only as the reviewer App): down from each seed's open pull request base by base until a base has none (the default branch), and up through open pull requests whose base is a head already in the stack. A fork is kept as a tree, walked depth first, bottom up; only pull requests from the repository itself by an author of the seeds' pull requests are kept; closed and merged layers are skipped (GitHub retargets the next one); at most `MaxReviewStack` (20), and a longer stack is cut short and logged. A Staccato graph only orders siblings. A discovered layer the clone has no branch of is fetched into the repository cache (`HandoffReviewCallerOptions.FetchPR`, `RepositoryService.PullHead`), marked `Fetched`, reviewed at its pinned head and not compared as a mismatch. `Pushed` counts a pull request added to the stack as a push. Comments and checks are polled on the caller's `OpenPRs`. None is `skipped`. Each branch's local tip must be its pull request's head on GitHub and the tree clean (ignored files aside, `git status --porcelain`); a mismatch types one `[legato review pass] Push or discard before review: …` line to the author, and a second (after the author worked, or 10 minutes) is stuck. `max_passes` reached is stuck. A reviewer slot is an in-flight pass (`reviewing`, `submitted` or `posting`) of an open loop, whatever the loop's phase, so a stuck loop whose post was never confirmed keeps its slot until Another pass or End. Past `max_concurrent` slots taken the loop waits as `waiting_for_reviewer`, oldest first: the tick reads the count (`store.ReviewPassesInFlight`, `slotsFull`) before it pins anything, and the pass start takes its slot atomically in the transaction that writes the pass and the loop (`StartHandoffReviewPass`), so two loops starting at once never pass `max_concurrent`; one that loses the last slot there (`ErrReviewSlotsFull`) waits as `waiting_for_reviewer` too. What a `ready` loop waits on is kept in memory (`setWaiting`) and said in the block's `waiting_on`; a `PullRequests` failure is logged once per distinct error (`logGitHubError`) and tried again next tick.
- **Posting** (`post`, in the background, and retried by `Tick` while the pass is `submitted`): `beforePost` checks again: HEAD, the tree and every layer's head on GitHub before the first post, and each layer's head just before its own post (or, for a layer whose approval stands, just before it is recorded `kept`), so a head that moved after submit posts nothing (a head that moves after a lower layer's review is posted leaves that review and discards the rest; the window between the read and the post is accepted). A read that fails leaves the pass `submitted` for the next tick. **Last, nearest each write, the loop must still be open and its owner's** (D11, LEG-563; `mayWrite`, `review_pass_write.go`): `store.CheckHandoffReviewWrite` reads, in one transaction, that the loop has not `ended`, that the pass (for a pass's writes) is still `submitted`, and that its owner (`ReviewLoop.Owner`, a `store.HandoffReviewOwner`: a run's step attempt, or the handoff's main and handoff ID; checked against the loop record's owner as `CheckReviewLoopOwner` checks it, in `store.CheckReviewLoopWrite`) still holds it: the attempt still `waiting` in a run not ended, or the handoff open on this worker and `in_progress` or `done` (not `returning`). Every GitHub write goes through it: each layer's review (in `beforePost`), each ruling reply and thread resolve, each author answer (`postAnswers`), and the approval once checks settle (`approveSettled`). A refusal drops that write and every later one: a pass in flight is `discarded` and its reviewer stopped, and a loop whose owner left (a run cancelled where no engine runs, a handoff recalled) ends (`EndHandoffReview`, reason `cancelled` for a run, `closed` for a handoff), freeing its reviewer slot. The check runs once more after the last write, before the pass is recorded `posted`, so a loop closed while a write was under way does not move on (a cancelled run never ends `succeeded`). **The remaining window is accepted:** a close that lands between the check and GitHub's answer does not stop that one write (a review, an answer, a reply), only the ones after it; what GitHub took stays there, and the pass is set aside. Then one review per pull request, each its own event (`prClean`): `APPROVE` when no blocking finding of the pass and no earlier finding ruled still `open` sits on that pull request (and, when the loop counts checks, no counted check fails on it, one answered by a reply aside), `COMMENT` otherwise, so a clean lower layer can merge while a layer above is fixed. On a person-authored loop (a run without `agent_author`: `AuthorTaskID` empty) a clean pull request whose author is outside the repository (any `author_association` but `OWNER`, `MEMBER` or `COLLABORATOR`: `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER`, `NONE`, or none read) gets a `COMMENT` opening "clean; not approved: the author is outside the repository" (`ReviewOutsideAuthor`, `outsideAuthor`, read from GitHub just before the post; a failed read leaves the pass `submitted`), so an injection the reviewer obeyed cannot buy an outsider an approval (X2, LEG-570). The loop's verdict is still clean, and a run's outcome is still `approved`; the run says the approval was withheld (`approval_withheld`, below), derived from the record with no column of its own: on an approved run loop that is person-authored, a `COMMENT` (the pin's `event` in `review_loop_passes.pins`) of the last pass can only be this one, since such loops count no checks. Agent-authored and handoff loops are approved whatever the author App's association (it reads `NONE`, below); the loop's verdict, Done gating and the run's `approved` stay stack-wide. A later pass posts nothing on a pull request whose last review approved it, whose head has not moved and on which the pass has no finding or ruling: its pin's `event` is `kept` (`review_loop_passes.pins`; `handoff_review_prs.event` from migration 127 until the loop record: `APPROVE`, `COMMENT`, `kept`, or `''` before posting), and the block's `links` give each pull request's latest posted review (`latestReviews`) with the pass's findings, the rulings of findings that had no thread in the body, a footer naming the reviewer's tool, model and skill, and the marker `<key>/pass-<n>/pr-<number>` (`passReviewMarker`; `<key>/pass-<n>.<attempt>/pr-<number>` for a pass pinned again). `<key>` is the loop record's `marker_key` (`HandoffReview.MarkerKey`, `HandoffReviewPass.MarkerKey`): the loop's own ID for a loop opened since LEG-605, the old task ID for one converted by migration 148. So two loops on one task (two review steps of a run, a card handed off again) never share a marker, and the second never takes the first's review on GitHub for its own; a converted loop still finds what it posted before. The inline comments' IDs are kept on their findings, so a later ruling replies in the thread ("Resolved in pass N: …", "Still open in pass N: …") and a resolved one resolves it; a reply or resolve that fails is kept in the pass's `reason`. A rate limit leaves the pass for the next tick, uncounted. **A 4xx refusal** (GitHub saw the post and took nothing) ends the pass `unable` (`unable`: the reviewer stops, the pass holds no reviewer slot, it still counts toward `max_passes`, and the reviews of layers posted before it stay recorded with its findings) and makes the loop stuck, "GitHub refused the review of #N: …". **A post whose outcome is unknown** (D12, LEG-561: a 5xx, a timeout, a network error, a head read that failed, or a review GitHub took whose inline comments could not be read) leaves the pass `submitted`; the next tick first looks for each unposted layer's marker (`ReviewGitHub.FindReview`) and records a review it finds with its inline comment IDs, matched to its findings by their text, so later rulings reply in their threads; only a layer not found is posted again, with the same marker. The heads are checked (`beforePost`) even when every layer was found: a review found stays recorded, but a head that moved discards the pass and pins it again, as when a head moves after a lower layer's post, so a pass is never finished, clean or not, on heads that moved. `review_loop_passes.posting_started_at` (the first try) and `attempts` (tries whose outcome was unknown; `post_attempts` of `handoff_review_passes` from migration 147 until the loop record, written only by `SetHandoffReviewPassPosting`) bound it: at ten such tries, or an hour after the first, the loop is stuck (`postFailed`; the reviewer stops), its reason naming the pass and the pull requests not confirmed, which raises one needs-you item (the run's waiting step, or the handoff's `handoff_review_stuck`). No other pass starts: Another pass on such a loop (its pass still `submitted`) puts it back to `reviewing` with a fresh budget, so the same pass is looked for and posted again; after a 4xx refusal the pass is `unable` and Another pass starts a new pass as before. Markers are distinct per kind, all in the `legato-review-pass` space, and the publisher matches a marker's whole line: the pass's review `<key>/pass-<n>/pr-<number>`, the later APPROVE once checks settle `…/checks` (`laterReviewMarker(…, LaterApprove)`), and the later held COMMENT of the sign-off seam `…/held` (`LaterHeldComment`). Then the reviewer is stopped: clean moves the card to Done (the handoff becomes `done`), changes to Doing and the loop to `waiting_for_author`. From pass 3, a changes pass that raised new blocking findings after a pass that also did (`notConverging`) lowers the loop's `max_passes` to its place in the pass window (its number while the window starts at 0), so the author answers it and the review is then stuck ("passes N-1 and N each found new blocking problems in the author's fixes…") instead of starting another pass; Run another pass makes room for one more pass as for any stuck review.
- **A pass** (`review_loop_passes` with its `pins`): the heads are pinned (`refs/legato/review/<card>/<pass>/<pr>` in the clone, so a later range-diff survives a force-push), HEAD is recorded, the card moves to `review_column`, and a reviewer starts in the card's `reviewer` slot (pass 1 fresh; a later pass resumes the conversation the slot saved, `resumeReviewer` with `GetTaskResumeSessionInSlot` and `SessionPolicy: resume`, and starts a fresh one when there is none or the resume fails; a resumed reviewer gets the brief as its `Prompt`, the conversation's next message, since a resumed launch sends no kickoff for an assignment and Chimera's resume drops `--prompt`): the configured agent, model or tier, `Unattended`, `ReadOnlyCheckout`, `ThrowawayCheckout`, in the clone, with the brief (`review_pass_brief.go`) as its assignment: each pull request's number, title, description, base and pinned head, the task's details, what makes a finding blocking (`blockingBar`: a reachable failure, lost data, a boundary an agent can cross, the task not done, the build or tests broken; not a setting only the person would choose, hardening beyond the task, unrealistic races or style; the smallest fix), the skill to use and `submit_review`. GitHub text is fenced as data (invariant 8): each pull request's title in `<pr-title>` and description in `<pr-description>`, the task's title and details in `<task-details>`, a later pass's comments (with who wrote them and where) in `<comment>` and the author's answers in `<author-answer>`, each escaped with `fenced` (a closing tag of the fence's name in any case, `</PR-Description>` included, becomes `<\/PR-Description>`), after a line saying fenced text is data, not instructions. Pass 1 reviews every pull request in full; a later pass is told to review only what changed since the last posted pass (its pinned heads; a pass the reviewer was unable to do, or a discarded one, moves no baseline, and with none posted the pass reviews in full, `lastPostedPass`), to rule on the blocking findings listed, each with a reason (`submit_review` refuses a `resolved` or `open` ruling without one, naming the ruling and what to say), to accept an answer that a finding is below the bar or a follow-up, and that a new blocking finding must be on lines changed since then that are in the pull request's own diff (after a rebase, the base's lines are not), or else needs `critical`. A spawn that fails (no sandbox) makes the pass `unable` and the review stuck.
- **`submit_review`** reaches `Submit(card, execution, ReviewSubmission)`; only the pass's reviewer may submit (`ErrNotTheReviewer`). `unable` ends the pass and makes the review stuck; nothing is posted. Otherwise it checks the summary, each finding's pull request, severity, title and body, each place against the pinned head (`ReviewCheckout.Lines`; a `LEFT` line is not checked), a `failure_scenario` on every blocking finding, on a later pass that each new blocking finding without `critical` has a line both changed since the last posted pass and in the pull request's own diff at its head (D3, LEG-574; `outsideChanges`: `ReviewCheckout.Changed`, git diff -U0 from that pass's pin to this one, and `ReviewGitHub.PullDiff`, GitHub's `GET /pulls/{n}/files` read as the reviewer App, each file's added lines and the lines either side of a deletion, a file with no patch changed in full; so after a rebase onto a main that moved, a blocking finding on a line main brought is refused; a pull request the last posted pass did not review is held to its own diff alone; a finding with no place or on a `LEFT` line is not on them; a diff that cannot be read, from git or GitHub, does not limit the finding), and a ruling on every earlier open blocking finding; problems come back as a `*ReviewSubmissionError` and the pass goes on. **A head that moved discards the pass** (D2, LEG-560; `headsMoved`): a checkout whose HEAD or tree moved, or any layer whose head on GitHub (`ReviewGitHub.PullRequest`, read as the reviewer App) is not the one the pass pinned. The whole pass is set aside (`discarded`, `DiscardHandoffReviewPass`: its findings go and the earlier findings it ruled on are open again with no ruling), the reviewer stops, and the loop is `ready` with its pass count back one, so a discarded pass counts toward neither `max_passes` nor the passes the main sees or a run's `passes` output. The next tick pins the same pass number again at the heads GitHub has then (`InsertHandoffReviewPass` replaces a discarded row, `attempt` one past it, migration 143), so pushes made meanwhile fold into it; its reviews' markers are `<key>/pass-<n>.<attempt>/pr-<number>`, never a discarded attempt's. A GitHub read that fails at submit accepts the result and leaves the decision to the check before posting. The failure scenario and any `critical` reason are added to the finding's body. The findings are kept with stable IDs (`review_loop_findings`, `f-…`), rulings on the earlier ones, and the verdict derived: `changes` with any blocking finding or open ruling, else `clean`.
- **Feedback** (`review_pass_feedback.go`, `review_loop_items`). A changes pass raises an item for each of its findings (blocking and nit; the finding's ID, its thread) and raises again, version moved on and answer cleared, each earlier finding its rulings kept open. Once the author is idle (`deliver`; a dead author is resumed through its caller (`ReviewCaller.ResumeAuthor`; the handoff caller's is `HandoffWorkerService.ResumeAuthor`), and one that cannot be is stuck), it is told once per pass: `[legato review pass] Pass N has 1 blocking finding and 1 nit. Run legato review-pass feedback --json to read them.` Nothing of the findings' or GitHub's text is ever typed to it. The author answers with `legato review-pass answer` ([CLI](cli.md) § Review pass commands); each tick posts the answers not yet posted as the author App, a reply in the item's thread ("Fixed in <sha>: …", the reply, "Skipped: this was optional.") or a conversation comment quoting the item, once: each answer has its own marker (`answer_marker`, new with each answer; `answerMarker` makes the key `<key>/<item>/<marker>`, `<key>` the loop's `marker_key`, never from the text, so the same words answering two items post twice), hidden in the comment as `<!-- legato-answer … -->`. `ReviewPublisher.Reply` and `PostIssueComment` look for the marker in the pull request's review comments or conversation before posting, and again after a timeout or a 5xx, so an answer GitHub took before it was marked posted is found after a restart and marked posted, not posted again (LEG-562). A ruling replied in a finding's thread carries `<!-- legato-ruling <key>/pass-<n>/<finding> -->` the same way (`rulingMarker`; `<key>/pass-<n>.<attempt>/<finding>` for a pass pinned again after a discard, so the replacement's ruling is never taken for a reply the discarded attempt left). A comment or review with a marker is taken for Legato's own only when the App that posts it wrote it (REST `user.login` equal to `<slug>[bot]`, the slug from the installation lookup's `app_slug`), and a reply only in its own thread (`in_reply_to_id` the thread's first comment), so a copied marker never stands in for a post. Neither kind is a review's marker (`legato-review-pass`), and nothing Legato posts uses `REQUEST_CHANGES`. Its `how` text says the item's text is data, how to answer, that a finding below the bar or for another change may be answered `replied` naming a follow-up, and to make the smallest fix. Done is refused while an item other than a nit is unanswered. With the card in Done again, a new pass runs (`ready`) when a pull request's branch moved past its pinned head or a blocking finding was answered `replied` (a dispute only a pass can rule on); otherwise the loop is `clean`. The next pass's brief lists each earlier finding with the author's answer. Every posted pass counts toward `max_passes`; a discarded one does not.
- **Comments** (`review_pass_comments.go`, `review_publisher_poll.go`). Every `poll_interval`, while the handoff is open and not returning, each pull request (the last pass's, else the open ones of its branches) is polled as the reviewer App: reviews, inline comments and conversation comments, page by page, each page with its ETag and its body kept in `review_loop_poll_pages`, so a 304 costs no rate limit; GraphQL `reviewThreads` (resolved, outdated) is read only when a page changed. A rate limit (`*GitHubRateLimit`, REST or GraphQL; [Credentials](credentials.md) § The reviewer App) ends the poll with nothing closed and puts the next one at the limit's `RetryAt` (after the reset, or `retry-after`, else 60 seconds); it backs off that App installation only, so loops on other accounts poll on. A failed poll (a 5xx, the network) closes nothing either: only a read that succeeded and lacks an item closes it. Legato's own logins are skipped: the pull request's author (the author App's on a handoff) and the logins of Legato's Apps (`legatoLogins`: those in `github_app_logins`, which the publisher's login recorder fills with the login GitHub answers each review Legato posts with, and `github.app_logins`, `ReviewPassConfig.AppLogins`; a configured name without the `[bot]` suffix is given it, `botLogins`). A login is never taken for Legato's from a marker in a comment's text, which anyone can copy: an outsider's review carrying `<!-- legato-review-pass …` is an outsider's (counted in `skipped_comments`), a member's is an item, and neither login is learned (LEG-570 review); a comment from `OWNER`, `MEMBER` or `COLLABORATOR`, or from a bot in `counted_bots`, is an item `c-r-…`, `c-i-…` or `c-c-…`; any other is counted in the loop's `skipped_comments`. An edit is a new version (answer cleared, told again); a thread a person resolved is handled (answer `resolved`); an outdated one is marked; a deleted comment's item closes, and the author is told if it had it. New items wait for `quiet_time` with nothing new, are held during a pass, and are told once the author is idle (`[legato review pass] 2 new comments on your pull requests. …`; each item's `delivered` flag outlives restarts). An unanswered comment stays in every round until answered; Done is refused while one is open, also before the first pass. A comment after a clean pass takes the loop back to `waiting_for_author` and the card to Doing, so the handoff is no longer done; a reply alone then makes it clean again, a push runs a new pass. The next brief lists the comments and the author's answers as context; the reviewer gives them no ruling.
- **Required checks** (`review_pass_checks.go`, `review_publisher_checks.go`). The counted checks of a pull request are the required checks of branch protection on its base (`GET /branches/{base}/protection/required_status_checks` with a `pr.protection` token; a refused token, a 404 or a 403 means none), else `required_checks`. `ReviewPublisher.Checks` reads them on a head, as check runs then commit statuses, each `pending` until it reports, `passing` (`success`, `neutral`, `skipped`) or `failing`, with the run's title and summary, its link and up to ten annotations (`path:line: message`) as the excerpt. From the first pass on, every `poll_interval` (and at once when a pass pins heads not read yet) the loop reads them at the pull requests' heads on GitHub (the loop record's `checks_polled_at`, `checks_heads`, `checks_pending`). A pass runs without waiting for CI. A failing check is an item `k-<pr>-<name>` (title "Check build: failure on <sha>", body summary and excerpt, untrusted like all of GitHub's text); passing on a later head closes it; failing again on a later head after `--fixed`, or after it passed, is a new version. A `--replied` answer handles it (the main sees how many, `checks_replied`); `--fixed` alone does not: a clean loop whose reviewed heads still fail the check clears that answer and goes back to `waiting_for_author` with the card in Doing, as an unanswered failing check does. Failing checks are told with new comments (`… 1 failing check on your pull requests …`, after `quiet_time`). They do not refuse the author's move to Done; they hold `DoneAllowed`, which also needs the checks read on the last pass's pinned heads with none pending. In a GitHub stack of this repository, a lower PR's `go`, `web`, `packages` and `docs` are `skipped` (passing), and the commit status `ci/stack` stands for its CI, `pending` until the top PR's build passes: so `required_checks` (or branch protection) should name `ci/stack`, `paths`, `migrations`, `go`, `web`, `packages` and `docs`; see the note "CI on a GitHub stack" in [Development notes](dev-notes.md).
- **The steward's watch** (`review_watch.go`, `review_publisher_watch.go`; spec LEG-559 C7, LEG-589). The reads the steward routes (below). Each `Tick`, before the loops move on, `watchLoops` takes every open loop record with `steward` on whose watch is due and reads it as the reviewer App, never with the operator's token, in one `ReviewWatchSession` (`ReviewPublisher.WatchSession(repo)`): one token, made on its first read, for every read of that loop in that tick, let go by `Close`. `Watch(ctx, numbers)` is one GraphQL query of every layer (aliases `p0`, `p1`, …): `state` (`open`, `closed`, `merged`), `isDraft`, the head (`headRefOid`, `headRefName`), `baseRefName`, `mergeable` and `mergeStateStatus` (GitHub's words), `reviewDecision` (`""` when none is required), and the head's `statusCheckRollup` as `PRWatch.Rollup` (`passing`, `failing`, `pending`, `""` with no checks) with its first 100 checks (`WatchCheck`: check runs and commit statuses, `isRequired` for this pull request, `ChecksTruncated` past 100); a pull request GitHub does not have is an error. Each open layer's comments are then read by ETag (`PollComments` of the same session: the comment poll's lists, kept apart from it as `watch/<list>` pages in `review_loop_poll_pages`, so a 304 costs no rate limit and neither poll hides a change from the other). The result is kept in memory per loop (`ReviewPassService.Watched(loopID)`: `ReviewLoopWatch` with the layers, each open layer's `CommentPoll`, `Changed` and `Err`); a failed read keeps what was read before and sets `Err` (a failed poll closes nothing). **Cadence** (`ReviewWatchSchedule`, keyed by loop ID, in memory; `ReviewPassOptions.WatchCadence`, `DefaultReviewWatchCadence`): every minute for an hour after a change, then every five minutes. A change is a read whose layers differ from the last one's (head, state, draft, merge state, review decision, checks; not `updatedAt`) or whose comments changed; until one is seen the loop's making counts (a restart reads every loop on its first tick), and `ReviewWatchSchedule.Changed` records one the caller saw itself. `EventPRStatusUpdated` (which names no pull request) brings every loop's next watch forward (`StartWatchEvents`, started with the engine in `startReviewEngine`; `BringWatchesForward`), never closer than 30 seconds to its last read. A `*GitHubRateLimit` (REST or GraphQL; [Credentials](credentials.md) § The reviewer App) holds that loop's watch until `RetryAt`, and the installation's back-off holds every other read of it. Loops without `steward` are not read, so the watch spends no rate limit until the steward turns it on.
- **The steward** (`review_steward.go`; spec LEG-559 § The steward, LEG-590). An agent-authored run loop opened with `steward` (the open step refuses it without `agent_author`) carries on after approval. **It starts watching** when its run's `github.pr.review.wait` in mode `watch` first finds the loop approved (`observeWatch` → `beginWatch`): the record's `idle_deadline` is set (now + `StewardIdleAfter`, seven days; moved on by each push, dispute or new item, and by each watch read whose layers or comments differ from the last one's, held too (`stillActive`; `watchLoop`'s `sameWatch` and `sameComments`, not a list's new ETag alone)), which is what `stewarding(rec)` reads (steward, open, deadline set), and the loop's last watch read is dropped (`forgetWatch`, also after every approval of a steward loop in `confirm`) so only a read taken after the approval is compared with the approved heads. Before that, as during the review, the loop is a review loop like any other (a failing check at the first approval still sends it back, `approved`'s check gate). **While stewarding**, `moveLoops` reads the watch instead of polling (`routeWatch`: no `pollComments`/`pollChecks`, so one App token per loop per tick): a layer `closed` (not merged) ends the loop (`ReviewStageClosed` → the run caller's `finish` with outcome `closed`); each new read (`watchRouted`, in memory) is routed once (`routeItems`): each open layer's `CommentPoll` through `countPolled` (shared with `pollComments`; counted comments and reviews, edits a new version, Legato's own and outsiders' skipped) and `closeUnseen`, and each counted check (`countedWatchChecks`: those `isRequired` for the pull request, else `required_checks`) through `applyCheck` (shared with `readChecks`: a failing one is item `k-<pr>-<name>`, title "Check go: FAILURE on <sha>", a passing one closes it); new items set `last_new_at`. The loop's phase does not change: routing starts no pass. In the approved phase (clean, confirmed), `step` calls `watching`: `approveSettled` (a layer a re-entry's clean pass left at a COMMENT for a failing check gets its `APPROVE` once it settles), then `deliverComments` once the author is idle after `quiet_time`, tagged `[legato steward] 1 failing check on your pull requests. Run legato review-pass feedback --json to read them: each item names the operation a fix may need, and nothing is granted ahead.` (each item once, its `delivered` flag), then **re-entry**: when the read finds any open layer's head past its `clean_head`, `reenter` puts the loop `ready` and counts one re-entry (`reentries`, `last_wake` `pushed`, `last_wake_at`) in one transition, however many layers moved; `ready` starts the pass once the author is idle, pinning every head then, and pushes during it fold in (the moved-head discard, D2). **The re-entry budget** (`review_steward_hold.go`, LEG-592): a push found when `reentries` has reached `max_reentries` makes the loop stuck at its watch instead (`reentryBudgetReason`; no pass, no fresh agent, the approval stands, so `approvalStands` holds), and its watch step waits. The pass is a later pass (it reviews what changed since the last posted one) and a clean one is approved only by `Confirm` at the new heads, with a fresh `APPROVE`; `approved` does not hold a re-entry's approval on checks. After a re-entry pass with changes the loop waits for its author as usual, but `agentDone` waits only for blocking findings to be answered (never checks or comments, and `feedback` skips `RefuseUnansweredReview`), and needs a push or a dispute: a reply alone starts no pass, a blocking finding answered `replied` (or disputed on GitHub, `disputed`) does, recorded as `last_wake` `disputed`. Everything the engine tells the author while stewarding opens `[legato steward]` (`authorTag`: the pass's findings, comments and checks, deleted comments). The author's `review-pass feedback` finds the loop while it is approved too (`reviewLoopTask`), and each check and comment item has `operation` (not stored; `stewardOperation`): a push (`git.push`, `git.push-workflows` for `.github/workflows`), and for a check one re-run of a job that failed before its tests ran (`gh run rerun <run-id> --failed`, `actions.write`), nothing granted ahead ([Credentials](credentials.md) § The reviewer App); `how` adds `stewardHow`. **Held, Watch again, End and the idle end** (LEG-592). The operator's actions reach the steward's waiting step (`ActOnLoop`, through the run caller's `reviewStewardActor` while the step that owns the loop waits). `stop_watching` sets the record's `held` on a steward that watches an approved pull request (`confirmed`; refused `ErrStewardNotWatching` during a re-entry's review, when stuck or already held). While held, or stuck, `routeWatch` still ends the loop on a closed pull request but routes nothing (`stewardHolds`: no items, no deliveries), and `watching` returns at once (no `approveSettled`, no delivery, no re-entry); the watch keeps reading, so its reads still move the idle deadline. `watch_again` clears `held`: the next tick routes the newest read, and a head moved since approval re-enters once, however many pushes came while held. On a steward stuck at its watch it sets `max_reentries` to one past the re-entries used (never lower than it was) and the phase back to clean, so the push that went past re-enters and the next is stuck again (refused `ErrStewardNotHeld` otherwise). `end` on any stewarding loop closes it with outcome `ended` (the run caller's `endOn` → `finish`), and the steps waiting on it complete (`endedState`). **The idle end**: in `step`, a stewarding loop whose approval stands (approved, held, or stuck at its watch) past its `idle_deadline` closes with outcome `idle` (`idlePast`, `endSteward`); a loop in a re-entry's review never goes idle. While any open agent-authored loop holds a PR, the workflow trigger `pr.changes_requested` skips it, recorded as `held by review loop rl-…` (LEG-595; [Workflows](workflows.md) § pr.changes_requested), so an address-feedback run never acts beside the loop. Mergeability items and merged lower layers are LEG-591. ### Opening and closing a loop

The engine's **Open** and **Close** (`review_loop_lifecycle.go`; spec LEG-559 § Loop record schema and claims, § Lifetime; LEG-580) are the only ways a loop record opens or closes, for both callers.

- **`ReviewPassService.Open(ctx, store.ReviewLoopOpen)`** writes the record and the claims on its pull requests in one transaction (`store.OpenReviewLoop`; SQLite's `_txlock=immediate` serializes two at once, so one wins and the other is refused). It is idempotent per owner: a run's step (run ID, step path) or a handoff (main instance, handoff ID, card) that opened a loop before gets it back, open or closed, `created` false; another handoff of the same card is another owner and gets a loop of its own (`hostedLoop` opens it on a write once the card's newest loop is a closed one of an earlier handoff). On an agent-authored loop each layer's `author_task` is the board task that tracks its pull request (`ListTrackedTaskBranches`), else the loop's author task: never an input. A workflow run has at most one open loop (`ErrRunLoopActive`, also the partial unique index). It does no GitHub or agent work: the caller discovers the stack first.
- **Refusals are typed** (`ReviewRefusalCode`): `*ReviewLoopActiveError` (`review_loop_active`: the pull request, and the other loop's `LoopID`, `Name` and `Link`, "run wr-…" `/workflows/runs/wr-…` or "handed-off task X" `/board?highlight_task=X`) and `*AuthorLoopActiveError` (`author_loop_active`: the author task and the other loop). Workflow step errors carry no `error_code` yet (LEG-486/489), so the message starts with the code: "review_loop_active: pull request #12 of acme/widget already has an active review loop: run wr-1 (/workflows/runs/wr-1), loop rl-…". A step still waiting to open has no loop yet, so a refusal naming one has no `, loop` part.
- **Who holds a pull request** (`activeLoopOn`): the loop that claims it (`store.ActiveReviewLoop`, `claimedLoopOn`) first, then the callers' loops as before (for a loop with no claim yet), then (only at `Start`, not when the tick opens) a step waiting to open on it. `Start` and opening leave out the run's own task, whose failed attempt keeps its loop claimed for Retry (D1). The tick opens waiting steps one at a time with `heldLoopOn` (no waiting steps), so of two steps started at once on one pull request the first opened takes it and the other fails naming that loop.
- **Handoff loops** (those opened before LEG-600; a new one belongs to its review-loop run, § Handoffs run review-loop) are opened by the handoff caller through `Open` (`openLoop`, `store.HandoffReviewLoopOpen`: owner `handoff`, the card the host and agent author, `YieldAuthor` so a card whose agent authors a run's loop still reviews with `agent_author` false): at accept with review settings (`HandoffReviewCaller.SetSettings`) and in the holder's tick for each reviewed handoff with no loop of its own (`HandoffReviewCaller.OpenWaiting`). The stack is unknown at accept, so a handoff loop opens with no layers: each pass makes every pull request it pins a layer and claims it in the pass's transaction (`holdReviewLoopLayer`, from `StartHandoffReviewPass`). A pull request another loop holds then makes the loop stuck, naming that loop. A handoff loop that is approved (`clean` and confirmed by `Confirm`), `skipped` or `ended` lets go of its claims while its card stays open (`writeReviewLoop`, `handoffLoopLetsGo`), so it no longer counts as active, as before the loop record; a later pass claims them again. A clean pass not yet confirmed (`confirm_clean`, such as one whose confirm read GitHub failed) keeps its claims, so `GET /api/review-loops` finds the loop that `heldLoopOn` still counts as active.
- **`ReviewPassService.Close(ctx, loopID, outcome)`** is one transaction (`store.EndReviewLoop`: the claims released, the loop closed with its outcome, a pass in flight discarded; an outcome other than `approved` also sets phase `ended` with the outcome as its reason), then side effects that a crash may skip and the tick sweeps up: the reviewer slot stops (not for `approved`), and each `reviewLoopCloser` caller's own (the run caller removes the reviewer's clone, `loopClosed`). `sweepClosed`, each tick, stops a reviewer that still runs an execution of a loop closed in the last day whose task hosts no open loop; the job-clone sweep removes clones no open loop uses. The run caller's `endLoop` (approved, closed, cancelled, and `closeEnded`) goes through `Close`; a handoff loop closes when its handoff does (`CloseReviewLoopsOfClosedHandoffs`).
- **The owning run's end closes its loop** (spec LEG-559 B3, D1; LEG-581). The run caller is a listener of the workflow service's run-ended hook ([Workflows](workflows.md) § The run-ended hook), subscribed by `ReviewRunCaller.SetWorkflows`. `RunEnded` closes, through `Close` (`closeRunLoop`, outcome `cancelled`), every open loop the run owns when it ends `succeeded`, `cancelled` or `stopped`, or is gone: the claims go in Close's transaction, then the reviewer stops and the clone is removed. A `failed` run keeps its loop open and claimed until Retry (which adopts it), Cancel or End (`closesLoop`). `RunsHeld` is the runs that own an open loop, so the hook's sweep closes the loop of a run that ended in another process or while Legato was down: at the start of a host's advance loop, on every workflow change it hears, and every 30 seconds. The holder's tick keeps its own sweep (`closeEnded`): it closes, the same way, the loops of runs that have ended and those whose review step finished while the run goes on. `RunEnded` takes none of the engine's locks, since it is told inside a tick when the tick's step completes a run, and hearing of an end twice changes nothing. Today the step's own ends already close its loop (`finish`, `Cancel`); the hook is what closes one a step no longer holds (LEG-585's open and close steps) and one whose run ended where no run caller was.

### Handoffs run review-loop

Since LEG-600 (spec LEG-559 § Handoffs, D10, Q1, M4 to M6) a worker runs the built-in `review-loop` for each make-a-change handoff with review passes. `review_loop_handoff_run.go` holds the start and the binding; the handoff caller still moves the loop on.

- **Starting.** `HandoffReviewCaller.StartReview` (from `HandoffWorkerService.Accept`, for a handoff accepted without an override), `SetSettings` (with one; review passes it turns off open a handoff-owned record that only holds the settings, as before) and `OpenWaiting` (in the holder's tick, for a reviewed handoff with no loop: a crash between the card and the run, or an accept in a process without workflows) call `openLoop`, which with `HandoffReviewCallerOptions.Runs` (the `WorkflowService`; `wireHandoffReviewCaller` sets it when the run caller is attached) calls `startRun`. That is `WorkflowService.StartHandoffReviewLoop(HandoffReviewLoopStart)`: a top-level run of the built-in with `repo` and `ready` (LEG-456: `HandoffReviewCallerOptions.PullRequests.ReadyAfterReview(repo)`, true only when the worker's most specific `pull_requests.rules` match for the repository is a `draft` rule with `ready_after_review`; read at the start, so a rule changed later reaches the next handoff), its `RelatedTaskID` the card, and before its first step starts, `Bind` writes **the handoff binding**: a loop record opened through `Open` (`store.HandoffRunReviewLoopOpen`: owner `run`, the run and step path `open`, hosted by the card, the card's agent the author with `YieldAuthor`, `handoff_id`, `main_instance_id`, and `handoff_columns`, the card's work, review and done columns as JSON from `review_passes`, and `ready` as the run's, so the author's feedback says the run marks its pull requests ready). Only this path writes it: `steward: true` is refused with `handoff_input_refused` before anything is recorded, and a `handoff` input from a file (the engine's check), a launcher or the API (`parseReviewOpen`) is refused too. A run whose binding cannot be written is cancelled.
- **The open step adopts it.** `reviewOpenExecutor.Start` finds the step's loop by `(run, step path)` and waits without reading `repo`/`pr_number` (a handoff's loop opens with no pull requests); the holder's `openSteps` makes the step's attempt the loop's `attempt_id` (`adoptHandoffLoop`, again refusing a steward) and completes it with `loop_id` and no `prs`.
- **Who moves it.** `handoffBound` (owner `run` with a `handoff_id`) loops are the handoff caller's: its `Loops`/`Loop` list them while open (never once closed, and a card with no record yet waits for its run), with owner `HandoffReviewOwner{RunID}`; the run caller's `Loop`, `stepLoops` and `ownsLoop` pass them by, and `reviewRunCard` reads them as a handoff's (brief, feedback). So passes, the card's columns (read from the binding, `HandoffReviewCaller.columns`), comments and checks from open, Done gating, `ResumeAuthor` and the review block are as in the Go loop, and the run's steps observe the record: pass 1 waits for the card in Done. The confirm step reports `approved` only once `checksHandled` (as `DoneAllowed`); a failing check is sent back to the author meanwhile. A handoff's loop with nothing to review (`skipped`) closes with outcome `closed`, its phase kept (`closeKeepingPhase`), so `DoneAllowed` still reads it.
- **Writes.** `CheckReviewLoopWrite` owns a bound loop while its run runs and its handoff is open on this worker, `in_progress` or `done`: a Return, Recall or Drop that lands before the run is cancelled stops the write too. A bound loop lets go of its claims at approval, skipped or ended (`handoffLoopLetsGo`), as a handoff's does.
- **Ready.** With `ready`, once the confirm step reports `approved` the built-in's `ready` step (`github.pr.ready`, LEG-588) flips every open draft layer bottom up, host-side as the author App. A layer that will not flip fails it with `ready_failed`, and its `on_failure` (`pause`) pauses the handoff's run on the worker's Workflows page; the card stays in Done and the handoff is done, as the review approved. Without it the step is skipped and the stack stays draft. Legato never merges or turns on auto-merge. Tested in `internal/handofftest/review_handoff_ready_test.go`.
- **Ending.** The loop ends at `approved`: the run's close step closes it (claims released) and the run succeeds; `DoneAllowed` reads the closed record. `HandoffReviewCaller.StopReview` (Recall, Drop, Leave, unpair and an allowed Return; Return stays refused mid-review) ends the review as before and then cancels the run, whose end closes the loop (outcome `cancelled`). `stopRuns`, in the holder's tick, cancels the run of a bound loop whose handoff closed or is returning, for an end that never reached a run. End on a bound loop is refused (`ErrHandoffLoopEnds`), the run's Attention for it offers only Message the author, and `--loop` Another pass acts on it only when stuck.
- **Seen as.** `GET /api/review-loops` reports a bound loop as kind `handoff` with the card's link and no run or step; refusals name "handed-off task X" (`reviewLoopName`). The run is on the worker's Workflows page, related to the card. The main's review block and routes are unchanged (`review_contract_test.go`).
- **Old loops.** A loop the handoff owns (opened before LEG-600, or converted) keeps running on the Go loop until LEG-601 adopts it.

### The engine's operations

Beside Open and Close, Tick and Submit, the engine has the operations the five review steps will call (spec LEG-559 § Modules, § The five steps; LEG-582; `review_loop_ops.go`). The inline step (`ReviewRunCaller`) and the Go handoff loop (`HandoffReviewCaller`) are orchestrations over them: neither keeps loop state of its own (the author-mode wait's in-memory quiet-time marks, `runAuthorStops`, are the engine's, `ReviewPassService.authorStops`). Each takes a loop ID; an unknown one is `*ReviewLoopError` with code `loop_not_found`, a closed one `loop_closed` (`ReviewRefusalCode`; it unwraps to `store.ErrNotFound`, `store.ErrReviewLoopClosed`).

- **`Pass(ctx, loopID)`** and **`Wait(ctx, loopID)`** (author mode) say where the loop stands, and write nothing: the holder's tick pins, reviews, posts and delivers. `Pass` is `ReviewPassResult{Pass, State, Verdict}`, `State` `pending` (to start, waiting for a reviewer slot, or running), `posted` (with the pass's verdict, `clean` or `changes`), `stuck` or `none` (nothing to review). `Wait` is `pending` while the loop waits for its author, `ready` once the author is done (it pushed, disputed, or there is nothing more to wait for), `closed` (the pull requests closed, or a loop that closed with outcome `closed`) or `stuck`.
- **`Confirm(ctx, loopID)`** (invariant 9: no caller reports approved before it) reads GitHub's heads of the clean pass's layers. Every open layer's head equal to its pin records the loop approved in one transition (`store.ConfirmReviewLoop`: `confirmed_at`, `clean_pass`, `window_start` reset to the pass, `confirm_clean` cleared, each layer's `clean_head`), `approved`; a head that moved puts the loop to `ready` for a new pass (`moved`); none open is `closed`. It does not wait for pending checks. A read GitHub fails is an error, and the loop stays unconfirmed. Every write of phase `clean` (`post`, and `feedback` when there is nothing to review again) sets `confirm_clean` with it, so a loop is only approved once confirmed (`confirmed`: phase `clean`, not `confirm_clean`, `confirmed_at` set and `clean_pass` the loop's pass, open or closed; a loop closed while `clean` before Confirm found its heads, such as a run cancelled or a handoff closed between the clean post and Confirm, or one the conversion closed so, is not approved: its run page says it ended ("Cancelled", "Closed") and its `ReviewBlock` reads `ended`). The tick confirms a clean unconfirmed loop first (`confirmLoop`, right after the post in the same tick, and on each later tick while GitHub does not answer) and only then tells the caller `ReviewStageClean`. So the handoff caller moves the card to Done only once confirmed; `DoneAllowed` needs `confirmed` and the checks handled; a handoff loop's `ReviewBlock` reads `reviewing` with `waiting_on` `github` ("Waiting for GitHub") until then; a run's step completes `approved` only from `Stage` clean, and its run page says "Clean · waiting for GitHub to confirm the heads" until then. A handoff whose pull requests all closed before the confirm is `skipped`, and its card goes to Done (`Stage` none).
- **The operator's actions by loop ID**: `AnotherPassOn`, `MessageAuthorOn`, `EndOn`, or `ActOnLoop(ctx, loopID, action, text)` with `another_pass`, `message`, `end` (`ReviewLoopAction*`). The engine finds the caller that owns the loop's kind (`reviewLoopActor`) and it acts: on a run's loop, only while the step attempt that owns it waits (`ErrReviewNotWaiting`, `ErrReviewNotStuck` for End), Another pass reviews again past the limit of a stuck loop or at once on one waiting for its author, Message the author queues `[legato review pass] From the operator: …` for an agent author (resumed first), and End completes a stuck loop's step `stuck`; on a handoff's loop, Another pass runs one more pass of a stuck loop, Message the author queues `[legato main] …`, and End is refused (`ErrHandoffLoopEnds`: a handoff's loop ends with its handoff). Another pass only writes the record; the tick starts the pass. The step's `Act`, `ReviewRunCaller.AnotherPass(runID, stepID)` (the run page's route) and the handoff side's task-keyed `AnotherPass` and `MessageAuthor` resolve the loop's ID and call these, so `legato review-pass … --loop` (LEG-583) can too.
- **The author's `Feedback` and `Answer`** (`OwnReviewFeedback`, `AnswerOwnReviewItem`), found by the caller's identity (`ReviewAnswerer`), and **`ActiveLoop(ctx, repo, pr)`**: the loop record that claims a pull request (`store.ActiveReviewLoop`), nil when none does; `ActiveLoopOn` also counts a step waiting to open.

## Review loops on any pull request

The **run caller** (`ReviewRunCaller`, `review_pass_run.go`; LEG-268) is the engine's second caller: the workflow step `github.pr.review_passes` (`ReviewPassesStepType`), which the embedded example `review-pr-passes` uses. Every workflow service registers the step as `ReviewPassesStep` (`reviewPassesStep` in `cmd/legato/workflow_runtime.go`), and `attachReviewRuns` (`cmd/legato/review_run_runtime.go`, from `startReviewEngine`, with `integrationDeps.workflows`) attaches the caller to it where the engine is built. **Starting the step only writes it** (spec LEG-559 D9): `Start` checks the inputs' shape (`reviewStepPR`: `repo`, `pr_number`, `scope`), refuses while `review_passes.enabled` is off in this process (`ReviewPassesStep.SetEnabled`: no Legato on the folder runs the engine then), and, with the caller attached, refuses a pull request an active loop holds or another step waiting to open names (`ActiveLoopOn`, which also asks each `reviewOpener`'s `waitingToOpenOn`, so a handoff's pass and the review prompt see such a step too), with the same `*ReviewLoopActiveError`; then the step is `waiting`. No GitHub or agent work happens there, so a start from the TUI, the CLI's own workflow service (`legato workflow run`) or a process advancing a `serve`-started run never fails the step for want of an engine. The holder's tick opens it (`OpenWaiting`, called by `ReviewPassService.Tick` before it takes its lock, one opening at a time): each waiting attempt whose task hosts no run loop, or one another attempt opened (`opened`), is opened with its step's resolved inputs (`waitingStep`), and a refusal there fails the step with `WorkflowService.FailWaiting` and the words below. An attempt cancelled while it opened is undone (`Cancel`). Until it opens, `Loops`, `authoredLoop`, `Attention` and `Act` pass it by (a retried step's record of its earlier attempt is not its own), `Cancel` has nothing to end, and `Details` says phase `opening`, "Waiting for the review engine, which runs in the Legato that serves the broker". So a review loop runs with the holder's reviewer App (LEG-257).

- **Opening** (`ReviewRunCaller.open`, in the holder's tick). The preflight refuses, in order: review passes off; the reviewer App cannot read the repository (`ReviewRunGitHub.Installed`: `ReviewPublisher` makes a read token for it and reads `GET /repos/{repo}`; the error names the three causes GitHub cannot tell apart, not installed on the account, not among the installation's selected repositories, no such repository, and points to the find-only `review-pr`; `ErrReviewAppMissing`); the pull request not open (`PullRequest`: `open`, `closed` or `merged`); an unknown `scope` (`reviewScope`: `stack`, the default, or `pr`). With `stack`, `runStack` finds the stack from the pull request's branch (`FindReviewStack`; the pull request alone when it is in none, a fork's say); every pull request of it is checked next; an active loop on the pull request (LEG-276: `ReviewPassService.ActiveLoopOn` looks through every caller's `Loops`, skipping a loop that is approved (`confirmed`), `skipped` or `ended` (a clean pass `Confirm` has yet to confirm still counts), for one in the repository whose `ReviewLoop.PR` or last pass's pinned pull requests name it, and refuses with `*ReviewLoopActiveError` naming the loop, its ID and its link (claims first, `heldLoopOn`), `ReviewLoop.Name`/`Link`: "run wr-…" `/workflows/runs/wr-…`, or "handed-off task X" `/board?highlight_task=X`; a handoff loop is known by its pull requests only from its first pass, so the engine checks again before every pass: `ready` makes a loop stuck, naming the other, when `activeLoopOn` finds another loop on one of its pull requests); `agent_author` on a pull request no board task links (a task tracking the pull request on one of its branches, `ListTrackedTaskBranches`, first, so a stack's middle pull request links its card; else `OwnerLookupService.Lookup` by repository, number and head branch; the first match is `linked_task`). With `agent_author` and no link, the caller first asks `ReviewRunOptions.Discover` (`DiscoverRepository`, PR tracking; [PR tracking](pr-tracking.md) § Agents' branches) to look again in the repository, since an agent may have opened the pull request since the last poll, and looks for the link once more; the refusal then says the pull request is not linked to any board task yet and how to link it (`legato task link <task-id> --repo <repo> --branch <head>`, or `p` on the card), or to run without `agent_author`. A task's agent authors one live loop at a time (`authoredLoop`): its feedback commands find one loop, so a second `agent_author` start for the same task is refused with `*AuthorLoopActiveError` (`author_loop_active`), naming the first run and its loop. With `agent_author` on a linked one, the linked task is the author (LEG-273): `reviewRun.AuthorTask`, `ReviewLoop.AuthorTaskID`. Its round is done (`agentDone`) when it is idle, delivered, every non-nit item answered, and it pushed or disputed, besides the person triggers. `ResumeAuthor` reconciles sessions, then resumes the main slot's saved conversation (`GetTaskResumeSessionInSlot` with the tool of `LatestAgentSessionForTask`, `SessionPolicy: resume`, in the conversation's folder); with none it errors, and the engine makes the loop stuck. `review-pass feedback` and `answer` find the loop of the author's task through `reviewLoopTask`: the loop its task hosts (a handoff's card), else the newest live run loop whose `author_task` names it (`store.ListRunReviewLoopsAuthoredBy`). Answers post as the author App through the engine's `postAnswers`. A stuck loop's Attention item adds `message` (`WorkflowStepAttention` returns the extra action IDs, kept on `WorkflowStepAttempt.AttentionActions`), which `Act` turns into a queued `[legato review pass] From the operator: <text>` after resuming the author. Then `ReviewRunClones.PullHead` fetches `refs/pull/<n>/head` into the repository's cache (`RepositoryService.PullHead`, `gitrepo.Runner.FetchRef`), so a fork's head can be cloned, and `JobClone` makes a job clone of the reviewer's own for the run's task at the head SHA (`JobCloneRequest.Own`, LEG-613: never the run task's live clone, which an earlier `agent.run` with `repo` made and its author may still work in; the reviewer resets its clone before every pass and removes it when the loop ends; execution folder: the attempt ID). Each pull request is checked out on its head branch's name on GitHub, so `git status` names it (`reviewRunBranches`), or on `legato-review/pr-<n>` when its head is in a fork (`ReviewGitHubPR.HeadRepo`, read from `head.repo.full_name`), the name is not a valid branch, or it is a base of the stack that is no layer's head. `Checkout` sets `ReviewGitHubPR.LocalBranch` to that branch and leaves `Branch` as GitHub's head branch: the pins keep both (`local_branch`, `head_repo` in `review_loop_passes.pins`; the layer's `review_loop_prs.local_branch`), the brief names the head branch (with its fork) and says "Your checkout is on `<local>` at `<sha>`", the tip check reads `checkoutBranch()`, and feedback's `prs[].branch` stays GitHub's, which the author pushes. Each layer of a stack is fetched too and gets its own branch (`reviewRun.Stack`, bottom first; `Checkout` resets each open layer to its head before every pass, bottom up, so HEAD ends at the top), and the run is retitled after the stack (`store.RetitleWorkflowRun`, "Review loop on owner/name#137–#141"). The loop's record, `reviewRun` (run, step and attempt IDs, repository, number, branch, clone ID and path, linked task, `scope`, `stack`; a record with no `stack` is a stack of one, `prs()`), is kept on the loop record the run task hosts (`readReviewRun`, `saveReviewRun`; no longer the task's metadata): the step's attempt opens it with the engine's `Open` (`reviewRunOpen`; see § Opening and closing a loop), owner `run`, its pull requests claimed and each layer's reviewer-clone branch kept as `local_branch`, `marker_key` the loop's own ID (so a later step's loop on the run's task never finds this one's reviews), in phase `ready`, in one transaction, with the loop's settings (LEG-277, `ReviewRunCaller.settings`): the instance's `review_passes` defaults, or, when the step's `max_passes` (a number, 0 for the setting) or `reviewer` (`tool` or `tool:tier`) is set, `ReviewPassService.Override` with them, the same advert check a main's handoff override gets; an unknown reviewer is refused with the advert's tools listed, so pass 1 starts on the next tick, and the step returns `waiting` ([Workflows](workflows.md)).
- **The loop.** `Loops` are the run tasks whose step attempt is `waiting` (`WorkflowService.WaitingAttempts`). Each is keyed on the run's own task, which hosts its loop record (one open loop per run, LEG-256; a closed one is passed by), its author is a person (`AuthorTaskID` empty: never messaged, never resumed), and both counts are off: only the reviewer's findings, no comments or checks (LEG-255). With `agent_author` the run counts checks (`CountChecks`, LEG-305; comments stay off): a failing counted check is an item `k-<pr>-<name>` on its pull request, which posts `COMMENT` instead of `APPROVE` (`prClean`); it never blocks a pass. A clean pass with a failing check does not end the run: once `Confirm` approves it, the caller (`approved`) sends the loop back to the author (`checksReopen`) and the check is delivered once quiet. Once each failing check passes or is answered `--replied` (`agentDone` takes a round of replied checks alone as done, and `feedback` then stages the loop clean), `approveSettled` posts `APPROVE` on each pull request left at `COMMENT` for a check alone (marker `…/pr-<n>/checks`, `laterReviewMarker`) and the run ends `approved`. A handoff loop's clean phase runs `approveSettled` too. `Checkout` reads the pull request again, fetches its head and resets the clone's branch to it (`Reset`: `git checkout --force -B`, then `git clean -fd`, with hooks and fsmonitor off), so the engine's tip check passes; a pull request no longer open gives nothing to review. `AuthorDone` (LEG-269) reads the run's pull requests each tick (`openRunPRs`; a layer that merged or closed drops out): none left open ends the loop `closed` (`finish`, which also stops a running reviewer without the engine's lock); any head that differs from the last pass's pin records all the heads (`headsKey`) in `reviewRun.SeenHead`/`SeenAt`, and any different head again (a restack moves several) restarts the wait, so the author is done once the head stayed still for `quiet_time`; with no push, `disputed` polls the comments (`PollComments` with the loop's stored pages) and takes a reply in the thread of an unanswered blocking item as that item's `replied` answer (marked posted, kept in `reviewRun.Replies`, so it counts once). Only a reply that may dispute counts (D7 as narrowed by X2, LEG-570): from the pull request's author (`ReviewGitHubPR.Author`, whatever its association), an `OWNER`, `MEMBER` or `COLLABORATOR` (`insideRepository`), or a counted bot (`review_passes.counted_bots`), never Legato's own, known by who posted it and never by a marker in its text, which anyone can write (the author of a thread's root, whose ID Legato recorded as the finding's comment when it posted it, or a login of Legato's Apps, `legatoLogins` as for the comment poll; a stranger's `<!-- legato-…` reply after the author's neither advances the cutoff below nor passes as Legato's); and made after the pass that raised the finding or raised it again: its ID above Legato's newest comment in the thread (the finding, or its "Still open in pass N" ruling), and not dated by GitHub (`PRComment.CreatedAt`, `created_at`, a review's `submitted_at`) before that pass's `started_at` (the guard when the ruling's post failed). Logins compare with `sameLogin`, as `postedBy` does: REST's logins equal ignoring case, the `[bot]` suffix kept, so a person whose login is an App's slug (`legato-reviewer`) is never the App (`legato-reviewer[bot]`), neither Legato's own nor the author App as the pull request's author nor a counted bot. Every login compared there is REST's, or a configured bot name (`github.app_logins`, `review_passes.counted_bots`) given the `[bot]` suffix when it has none (`botLogins`: `cubic-dev-ai` is the bot `cubic-dev-ai[bot]`, never a person `cubic-dev-ai`; a name already ending in `[bot]`, in any case, is kept); no GraphQL login (which drops the suffix) is compared. A stranger's reply is skipped, so an outsider can neither force a pass nor put text in front of the reviewer. `disputed` polls each open layer; `Pushed` and the engine's `Confirm` compare each open layer's head with its pin; `ReviewLoop.PRs` names every layer, so `ActiveLoopOn` refuses a run on any of them (the engine's `pushedSince` asks the caller). A ready loop with no open pull request (`ReviewStageNone`) ends `closed` too. Run another pass is `ReviewRunCaller.AnotherPass(run, step)` → `ReviewPassService.NextPass` (the loop must be `waiting_for_author`, else `ErrReviewNotWaiting`), served at `POST /api/workflow-runs/{run_id}/steps/{step_id}/another-pass` (change class; `internal/server/review_runs.go`, `Server.SetReviewRuns`, 409 when refused, 503 without review loops) and the run page's button. No card moves; `Changed` publishes `EventWorkflowChanged` for the run.
- **Ends.** A clean pass is confirmed against GitHub by the engine's `Confirm` (§ The engine's operations) before the run caller hears of it: a head that is no longer the pull request's (a push after the pass's last head check; one while the reviewer worked discards the pass first) sends the loop to the next pass, none open ends it `closed` (`Stage` none), and a read GitHub fails leaves the loop unconfirmed (`confirm_clean`) for the next tick, approving nothing meanwhile. Only a confirmed loop reaches `Stage` clean (`approved`): an agent author's loop then sends a counted check that fails back to the author, and posts the APPROVE of a pull request its clean pass left at a COMMENT for a check now settled (`approveSettled`); a post that fails is not approved, and the loop is confirmed again and the APPROVE tried again on the next tick (`confirmAgain`). Then it completes the step (`WorkflowService.CompleteWaiting`) with `outcome` `approved`, `passes`, `findings` (how many), `reviews` (`[{pass, pr, url, event, approved}]`: `event` as posted, `APPROVE` or `COMMENT`, and `approved` only for an `APPROVE`; the outside-author `COMMENT` of the clean pass adds `approval_withheld: true` and `withheld_reason: "outside_author"`, `postedReviews`, `WithheldOutsideAuthor`), `approval_withheld` (true when any pull request of the approved loop got that `COMMENT`, else false; the run page's `ReviewRunDetails` carries it too, with the line "Clean · approval withheld: the author is outside the repository" for "Approved", and the summary names it on that review's line), `summary_path` (`<data_dir>/artifacts/review-summaries/<run>/review-summary.md`) and `linked_task`, then the note step adds the summary to the linked task or skips (`optional: true`). Cancelling the run calls the step's `Cancel`: the loop record ends `ended` with reason `cancelled` and closes with outcome `cancelled`, releasing its claims (`ReviewPhaseEnded`, `endLoop`, `store.CloseHostedReviewLoop`) first, whatever its phase and before the engine's lock, so a post or an answer under way in a tick finds it ended at its next check; then the reviewer stops and a pass in flight is discarded (`StopReview`), and nothing more is posted. A Cancel in a process with no engine only cancels the run: the holder's next write finds the attempt no longer `waiting`, drops it, discards the pass and ends the loop (`mayWrite`), and the run-ended hook's sweep in a host's advance loop (or the holder's next tick, `closeEnded`) closes the loop record of a run that is gone, cancelled, stopped or succeeded, as the holder's tick also does for one whose step is done, so its pull requests are free and its clone goes. Every end of the step closes the loop record (an approved one with outcome `approved`). Every end removes the clone. Failing the step (`legato workflow fail`) calls `FailStep` instead, which keeps the loop for Retry; Retry adopts it with a fresh clone ([Workflows](workflows.md), LEG-567).

## Live away state

The main hears of its away tasks as they change, without polling (spec LEG-15 § The protocol, Pull and Events, and § Connection lifecycle on the main; decisions in Burnlite LEG-9; built in LEG-24). The main opens every connection: the worker never reaches the main.

**Summary rows.** A worker describes each open handoff of a main as a `service.HandoffSummary`: `{handoff_id, worker_task_id, state, failure?, url, activity?, column, title, branches?, stage?, stage_reason?}`. `stage` and `stage_reason` are the worker card's main slot stage ([Agent states](agent-states.md) § Stages); a stage change (`EventAgentStageChanged`) wakes the Events stream at once, not debounced as activity is, and the main keeps it in `last_summary` and shows it on the away card (`AwayTask.Stage`). Both fields are optional: an older main ignores them, and a new main with an older worker shows none. `state` is the handoff's (`pending`, `in_progress`, `done`, `failed`, and `returning` once LEG-25 makes it); `activity` is the agent's, from its running session (`working`, `waiting` for waiting on the person, `idle`, or `ended` when no agent runs; none while pending; `service.HandoffActivity*`); `column` and `title` are the card's on the worker; `url` is a path on the worker's web UI (`/board?highlight_task=<worker task id>`), which the main puts after the worker's address. `branches` are the branches pushed for the task, in stack order, read from git's files without running git (`stackgraph.OnRemote`: a branch with a remote-tracking ref, whatever commit it records): in each live job clone of the task and in its agent's working directory, the clone's Staccato stack (`stackgraph.Read`) when it keeps one, else the handoff's branch; once no clone is left, the pushed branches of the stacks recorded for the task (`clone_stacks`). A stack a review loop found on GitHub comes first, in GitHub's order: the handoff caller records it on the card as tracked branches of source `review` (`TrackTaskBranches`, `BranchSourceReview`) each time it follows the chain, and building a row reads them from the database, so a stack built with plain branches (no graph) is reported whole without a GitHub call per rescan. The worker does no PR tracking; the main adds these branches to the away task's tracked branches and finds their PRs at once (see [PR tracking](pr-tracking.md) § Away tasks).

**Pull.** `GET /api/integrations/handoff/pull` (`service.HandoffPullPath`, a main's handoff token only, `requireHandoffMain`) answers `service.HandoffPull{worker_instance_id, handoffs: [rows]}`: every handoff of the calling main not closed, oldest first (`HandoffWorkerService.Pull`). Another main's are never listed.

**Events.** `GET /api/integrations/handoff/events` (`service.HandoffEventsPath`) is a WebSocket the main opens with its handoff token as a bearer header (not `?token=`, which only the web UI's `/ws` takes; the route is under `/api/integrations/`, so the scoped-token middleware checks it like any other handoff route). Messages are `service.HandoffStreamMessage` JSON: the main sends `{"type":"pull"}` once it has made the calls it owes the worker; the worker answers `{"type":"pull", worker_instance_id, handoffs}`, then sends `{"type":"row", worker_instance_id, row}` whenever a row changes, and `{"type":"gone", worker_instance_id, handoff_id}` for a handoff that is no longer open (its card deleted, the handoff closed). `HandoffWorkerService.Stream` builds the rows again on `EventHandoffChanged`, the agent events, the card events, and every `HandoffWorkerOptions.StreamRescan` (5 seconds; an agent's activity set by another process may tell this one nothing, though `legato serve` now puts the CLI's `agent_state` and `task_update` messages on its bus). A row that differs from the last one sent only in its activity waits until a second has passed since that one; any other change goes at once, and the pull does not count, so the first change after it goes at once. The route checks the token again every 5 seconds (`Server.SetHandoffReauthEvery`) and on each pull asked for, which also keeps the worker's "last pull" (the token's `last_used_at`) current; once the main is unpaired it closes the connection with status 4401 (`service.HandoffStreamRefused`). A server shutting down closes its Events connections (`RegisterOnShutdown`), so its mains reconnect.

**The main's connections.** `service.WorkerConnections` (`internal/service/worker_connections.go`), one per process, built and started by `startMainHandoffs` in `cmd/legato/worker_connections_runtime.go`, which also builds the main's `WorkerService` and `TaskHandoffService` that `wirePairing` gives both web servers. It keeps a connection loop for each paired worker that holds away tasks of this main or is owed a call (`WorkerOwedCalls.Owes`), and stops the loop when neither holds; it looks again on `EventCardsRefreshed`, on `Kick()` and every second. Each connection (`session`):

1. dials the Events route over HTTP/1.1 with the main's token and the worker's pinned certificate (`WorkerClient.dialEvents`);
2. makes the owed calls, `WorkerOwedCalls.SendOwed(ctx, client)`, before anything else (the main's handoff service sends step 2 of a return the worker did not confirm, § Return and recall, then each Drop owed, and Leave to a removed worker, § Take back, Drop and Leave). A removed worker is never dialled: its session makes only the owed calls over HTTP;
3. lists the tasks away on the worker, then asks for the pull and applies it: each row becomes its away task's `last_summary` (`store.SetAwayTaskSummary`, which also clears a lost mark) when the handoff is this main's, open and on that worker; each task away before the pull was asked for and missing from it is marked lost (`store.SetAwayTaskLost`: "vm-1 no longer has this task"). A handoff answered after the pull was taken is not in that list, so it is never lost by a race;
4. applies each row as it arrives, and marks lost a handoff the worker says is gone. Applying a row also tracks the branches it brings and, when one is new, looks for their PRs off this loop ([PR tracking](pr-tracking.md) § Away tasks).

Every message carries the worker's instance ID; one that does not match the worker's record marks every task away there lost ("vm-1 now answers as another Legato (srv-…), not srv-…") and drops the connection. Applying a row publishes `EventCardUpdated`, and a change in a worker's reach `EventCardsRefreshed`, so the web board (`cards_changed`) and the TUI refresh as for any other card change. `HandOff` keeps the worker's answer as the first summary only when no row came first (`store.SetAwayTaskSummaryIfNone`).

**Reach.** A pull, a row or a pong records that the main heard from the worker: `workers.last_pull_at` is then, and `unreachable_since` and `refused_at` are cleared (`store.SetWorkerHeard`). Pings go every 15 seconds; two in a row without a pong drop the connection. A dropped connection is retried after 1s, doubling to 60s, with jitter (half the wait to all of it; `service.WorkerBackoff`); the wait goes back to 1s after a connection that pulled. While it reconnects, cards stay as they were. `CheckReach` (every second, on the injected clock) marks the worker `unreachable_since` the time it dropped once it has been down 30 seconds (`store.SetWorkerUnreachable`, which keeps the first time). A Handoff call that got no answer marks it at once (`WorkerService.MarkUnreachable`, which LEG-25 calls for Return and Recall too). A 401 at dial, a 401 on a pull, or the 4401 close marks it `refused_at` ("the worker no longer accepts this main; pair again"; `store.SetWorkerRefused`), keeps every last summary, and retries only every 60 seconds; pairing again clears it (`SaveWorker`). The main never takes a task back by itself: a lost or unreachable task stays away until the person acts.

**What the main shows.** `service.AwayTask` gains the row's `Activity`, `WorkerColumn`, `WorkerTitle` and `Branches`, `Lost`/`LostAt`, the worker's `WorkerUnreachableSince` and `WorkerRefusedAt`, and `View`, one of `service.AwayView*`: the main's own view first (`lost`, `not_accepted`, `unreachable`), then the state (`coming_back`, `failed`, `done`, `starting` while pending), then the activity (`working`, `needs_you`, `ended`, else `idle`). The board API carries all of them in `away`, and `unreachable_since` and `refused_at` on each of its `workers`; Settings › Connections › Workers lists them too.

**A manual sync.** The web board's sync (`POST /api/board/sync`) and the TUI's `r` run the process's `ProviderSyncService`, built with `service.SyncWorkersToo(connections)`: `WorkerConnections.SyncWorkers` drops and reopens every connection at once and waits for its pull, and pulls once over HTTP each worker it keeps no connection to. The result names `workers`: completed, or failed with each worker it could not pull ("vm-2: the worker did not answer").

**For later tickets.** Return and Recall (LEG-25) mark the worker at once with `WorkerService.MarkUnreachable` when a call gets no answer, and should close the away task before the worker's `gone` arrives (a closed away task is never marked lost). Drop and Leave (LEG-26) are in `WorkerOwedCalls`; the connections list workers with `store.ListAllWorkers`, which keeps a removed worker owed a Leave. The Attention producer `handoff` reads the away tasks' last known state, `Lost`, and the workers' `unreachable_since` (15 minutes) and `refused_at`, following `EventCardUpdated`/`EventCardsRefreshed`; see [Attention](attention.md) § Handoff. Two Legato processes on one database (the TUI and `legato serve`) each keep their own connections to a worker; the rows they write are the same, and `handoff_notices` makes them notify the phone once.

**Testing.** `internal/handofftest/live_test.go` and `web_live_test.go`: the harness's main has `Connections` (backoff from 20ms, checks every 20ms; `MainOptions.Connections` changes them) and `StartConnections()`; the worker rescans every 50ms and checks tokens every 50ms; `worker.Stop()` closes its Events connections as a process ending does.

## Return and recall

The person brings an away task home (spec LEG-15 § The protocol, Return / recall, § Away tasks on the main; decisions in Burnlite LEG-6; built in LEG-25). **Return** brings back a task its worker finished; **Recall** brings back one in any state, with whatever exists so far, and adds a note naming the worker and the state; **Return all done** returns every done task of one worker. All three are the same two calls to the worker, which takes them in any state; each step is safe to repeat.

**On the worker.** `HandoffWorkerService.Return(ctx, mainID, handoffID)` is step 1, `POST /api/integrations/handoff/tasks/{handoff_id}/return` (`service.HandoffReturnPath`): it marks the open handoff `returning` whatever its state (`store.MarkHandoffReturning`), stops its agent (`HandoffAgents.KillAgent`), and answers `service.HandoffReturn{handoff_id, worker_task_id, worker_instance_id, state, title, details, column, notes: [{id, body, created_at}], repo, branches, stack?}`: the card's title and Legato details (a local task's description) as they are now, its column, the worker's own notes with their IDs (never those with `source` `main`), the pushed branches in stack order (as in a summary row), and Staccato's st graph import document (`stack`, raw JSON) of the newest importable stack of the handoff's repository among the card's clones (`HandoffWorkerOptions.Stacks`, the task stack service; none when it is not set or no stack can be imported). A pending handoff's start is cancelled: `start` does nothing for a handoff no longer `pending`, and an agent that was starting meanwhile is stopped once its spawn returns. While `returning`, the card is frozen: `RefuseAway` is also a `*TaskReturningError` ("task X is going back to workstation: it no longer changes here", `errors.Is(err, ErrTaskAway)`), so moves, edits and agent starts are refused on every surface; notes still go on it. `Reconcile` leaves `returning` alone. `FinishReturn` is step 2, `POST .../tasks/{handoff_id}/archive` (`service.HandoffArchivePath`), answering `{handoff_id, worker_instance_id}`: it stops the agent should step 1 never have come, then closes the handoff and archives its card in one transaction (`store.CloseHandoffAndArchive`, which archives through the store, as `RefuseHandedOff` would refuse the board service); the job clone is left to the sweep. Step 1 after step 2 still answers, from the archived card. Both answer `not_found` for another main's handoff or none, and publish `EventHandoffChanged`, so the main's Events connection sends the `returning` row and then `gone`. The routes are wired by the `server.HandoffReturns` interface the worker's handoff service implements.

**On the main.** `TaskHandoffService.Return(ctx, taskID)`, `Recall(ctx, taskID)` and `ReturnAllDone(ctx, workerInstanceID)` (`internal/service/task_return.go`), each answering `service.ReturnedTask{task_id, column, recalled, branches}`. Return needs the worker's last state to be `done` (or `returning`, to finish one under way): a `failed` handoff is refused "the handoff failed on vm-1; recall it", any other "task X is not done on vm-1; recall it to bring back what there is" (`ErrReturnRefused`, as are a task not away and one lost on its worker: "vm-1 no longer has this task; take it back"). Recall takes any state. The request is kept on the away task (`return_asked_at`, and `recalled_from`, the state a recall was made from, which is the worker's view apart from the main's: `starting`, `working`, `needs_you`, `idle`, `ended`, `done`, `failed`), so a return the main finishes later still adds the recall note. Then `finishReturn`, which holds the handoff (one at a time in a process):

1. step 1; no answer marks the worker unreachable at once (`WorkerService.MarkUnreachable`) and is `ErrWorkerUnreachable` ("vm-1 did not answer, so the task is still away; trying again is safe"); `not_found` marks the task lost and is refused "take it back"; another refusal is `ErrWorkerRefused` and forgets the request. An answer from another instance ID is refused;
2. applies the answer in one transaction that also closes the away task (`store.ApplyAwayTaskReturn`, which does nothing for one closed already): the returned title (never for a provider-backed task, whose title is its provider's) and description (its Legato details: the ticket's text, the link and the sync are never touched); the worker's notes as `task_notes` with `source` `worker` (`service.NoteSourceWorker`) and `remote_id` the worker's note ID, each skipped when the task has a note of that source and ID, so none comes back twice and the main's own never come back; for a recall, a note "Recalled from vm-1, where its agent was working." (`where it had failed: <reason>`, `where it was done`, ...); the column: the main's column of the worker column's name (case aside), else the column it left, else the first; the code context: the repository, and the bottom branch of those returned, sourced `handoff`, the worker's folder dropped; the stack document, kept in `away_tasks.returned_stack`; and `archive_owed`. The away state ends there, before the worker's `gone` arrives, which a closed away task ignores. The returned branches are added in stack order with `service.AddTaskBranches` (source `api`); branches tracked while away keep their place and PRs, so adding them again changes nothing; Landing in another column than the task is in records a `task_transitions` row with source `handoff` in the same transaction (`AwayReturn.Move`, LEG-238), and the main publishes `EventCardMoved` with its `transition_id`, so its workflow triggers (the curator among them) act on a return as on any move. Landing where it already is records nothing. Nothing is pushed to a ticket provider and `LocalMoveAt` is not set: the provider's own state wins at the next pull.
3. step 2. A confirmation, or `not_found`, clears `archive_owed`. No answer leaves it owed: the task is home, and the call is made again (below).

`ReturnAllDone` returns each away task of the worker whose last state is `done` and that is not lost, oldest first; it goes on past a refusal, stops at a worker that does not answer, and returns those brought home with the errors joined.

**Finishing what was interrupted.** `TaskHandoffService` is the connections' `WorkerOwedCalls` (`startMainHandoffs` passes it to `SetOwedCalls`): `Owes` is true while a worker has an `archive_owed` task, so its connection stays wanted, and `SendOwed` sends those step 2 calls on every connect, before the pull; one that gets no answer ends the connection, which retries. `StartReturnLoop(ctx, every)` (30 seconds in `startMainHandoffs`) runs `FinishReturning` at start, on every `EventCardUpdated` and `EventCardsRefreshed` (each summary row applied, a pull among them) and every tick: each away task whose last row says `returning` (step 1 made, its answer lost, or this main stopped between the steps) gets `finishReturn`, unless a call of the person's holds it. Each tick, and at start, it also sends again the step 2 calls owed (`SendOwedArchives`), since a connection that stays up does not reconnect. A task handed off again after a return is a new handoff (a new handoff ID) and a new card on the worker; the notes that came back travel with it as the main's notes.

**On the web.** `POST /api/tasks/{id}/return` and `POST /api/tasks/{id}/recall` answer `{"returned": ReturnedTask}`; `POST /api/workers/{instance_id}/return-done` answers `{"returned": [...], "error"?: "..."}` (`server.MainReturns`, implemented by the main's handoff service). Refusals use the Hand off route's statuses: 409 for `ErrReturnRefused`, `ErrTaskAway`, `ErrWorkerTooOld`; 502 for a worker that did not answer; 422 for a refusal. `WorkerRefusal.Code` is the integration route's error code (`not_found`, ...), when it gave one. See [Web UI](web-ui.md) § Returning and recalling.

**Testing.** `internal/handofftest/return_test.go` and `web_return_test.go`: a return and a recall end to end, each step repeated, step 1 or step 2 answered by a dropped connection (`dropper` in the worker's `Handler`), a main that stopped between the steps, a failed handoff, a pending one, Return all done, and a second handoff after a return. The harness's main passes its handoff service to `SetOwedCalls`, and `StartConnections` also starts the return loop (every 50ms); the worker's handoff service reads stacks with a task stack service.

## Take back, Drop and Leave

The ways out when a worker is gone or no longer wanted (spec LEG-15 § The protocol, Drop and Leave, § Connection lifecycle on the main; decisions in Burnlite LEG-6 and LEG-9; built in LEG-26). The main never takes a task back on its own: only the person does, after confirming.

**Take back.** `TaskHandoffService.TakeBack(ctx, taskID)` (`internal/service/task_take_back.go`) ends a task's away state on the main alone, without the worker's results. It is allowed only when the worker cannot bring the task back: the view is `lost`, `unreachable` or `not_accepted`; any other is `ErrReturnRefused` ("vm-1 can still bring task X back; recall it"). In one transaction (`store.TakeBackAwayTask`) the away task closes with `taken_back_at` and `drop_owed = 1`, and the task gets a note "Taken back from vm-1 without its results: <why>. vm-1 is told to drop it when it can be reached." The task stays in the column it left (its status never changed while away); branches tracked while away stay. The answer is a `ReturnedTask` with `taken_back: true`. When the worker is not marked unreachable or refusing, the Drop is sent at once; otherwise it waits.

**Drop.** `POST /api/integrations/handoff/tasks/{handoff_id}/drop` (`service.HandoffDropPath`) → `HandoffWorkerService.Drop` (`internal/service/task_handoff_drop.go`): it stops the handoff's agent, then closes the handoff and archives its card with a note "workstation took this task back without its results, so it was archived here." in one transaction (`store.CloseHandoffWithNote`), and answers `service.HandoffDropped{handoff_id, worker_instance_id}`. A closed handoff answers the same; an unknown one `not_found`. On the main, a confirmation or any 404 (`not_found`, or a worker too old to know the route) clears `drop_owed` (`store.ClearDropOwed`); no answer leaves it owed.

**Owed calls.** `TaskHandoffService` stays the connections' `WorkerOwedCalls`. `Owes` is true while a worker has an `archive_owed` or `drop_owed` task, or was removed and not yet told to leave. `SendOwed` sends, on every connect before the pull, each step 2, then each Drop (`store.ListDropOwed`), then, to a removed worker, Leave; a call without an answer ends the connection, whose backoff is the retry. Drops are retried while the worker stays paired (or is a removed worker within its window); a worker refusing this main (401) keeps them owed. `StartReturnLoop` also sends the owed Drops at start and each tick (`SendOwedDrops`, skipping workers marked unreachable or refusing).

**Remove a worker.** `TaskHandoffService.RemoveWorker(ctx, workerInstanceID)` → `service.RemovedWorker{worker, recalled, taken_back, left}`; `ErrWorkerNotPaired` for one not paired (or removed already). For each task away there, oldest first, it recalls it (§ Return and recall) unless it is lost or the worker refuses this main; once a recall gets no answer it stops trying and takes back the rest, as it does each task it could not recall ("vm-1 was removed"). Then it hides the worker (`workers.leaving_until` = now + `service.WorkerLeaveWindow`, 30 days; `store.SetWorkerLeaving`) and, when the worker answered, sends the owed calls at once. **Leave** is `POST /api/integrations/handoff/leave` (`service.HandoffLeavePath`) → `HandoffWorkerService.Leave`, which unpairs the calling main as Unpair does and answers `service.HandoffLeft{worker_instance_id, closed}`. Once Leave is answered, or the worker answers 401 (it unpaired this main itself), the main forgets the worker: its row, its sealed token and every call owed it (`store.DeleteWorker`, `WorkerService.forget`); `left` says it happened during the call.

A hidden worker is not in `store.ListWorkers` (Settings › Connections › Workers, the board's groups, the manual sync, `Client`, which answers `ErrWorkerNotPaired`, so nothing can be handed to it), but is in `store.ListAllWorkers`, which the connections use; its session skips the Events connection and only sends the owed calls over HTTP. `Owes` forgets a hidden worker whose `leaving_until` has passed (on the injected clock), so after 30 days it is never told; it can still unpair the main itself. Pairing the same worker again clears `leaving_until` (`store.SaveWorker`).

**Unpair on the worker.** `HandoffWorkerService.UnpairMain(ctx, mainInstanceID)` revokes the main's token, then closes each of its open handoffs in one transaction (`store.CloseMainHandoffs`), leaving their cards as ordinary cards (not archived, agents running) with a note "workstation was unpaired from this Legato, so this task is an ordinary card here now: it no longer goes back to workstation." The server's `DELETE /api/settings/mains/{instance_id}` calls it when its `TaskHandoffs` implements `server.HandoffDrops` (a worker that takes handoffs), else `RevokeMain`. The Events connection checks the main's token before every message it sends, so an unpaired main hears only the 4401 close (not accepted), never the closed handoffs as `gone` (lost).

**On the web.** `POST /api/tasks/{id}/take-back` → `{"returned": ReturnedTask}` and `DELETE /api/settings/workers/{instance_id}` → `{"removed": RemovedWorker}` (404 when not paired) (`server.MainTakeBacks`, implemented by the main's handoff service; `internal/server/take_back.go`), with the Hand off route's statuses. `GET /api/settings/workers` gives each worker `away`, how many of this main's tasks it holds, which Remove warns of. See [Web UI](web-ui.md) § Returning and recalling.

**Storage.** Migration 087: `away_tasks.taken_back_at`, `away_tasks.drop_owed` (indexed by worker while 1), `workers.leaving_until`.

**Testing.** `internal/handofftest/take_back_test.go`: take back from an unreachable worker with the Drop sent on reconnect, a lost task, a Drop owed to a worker refusing this main, removing a reachable worker (one recalled, one lost taken back, Leave) and an unreachable one (Drop and Leave on its return, within 30 days), a removed worker forgotten after 30 days of the shared clock, Unpair on the worker, Drop and Leave repeated, and the web routes.

## Owner lookup

`GET /api/integrations/owner?repo=acme/widget&pr=12&branch=feat-x&sha=0123abc` (`service.OwnerLookupService`). `repo` is required with one of the others. The lookup covers tasks that are not archived and whose code context or linked PR names the repository (`store.ListTasksForRepository`, case-insensitive). It matches by PR number, then by head SHA (a prefix of 7 or more characters), then by branch. Within a rule, tasks with a running agent come first, then the most recently updated.

The answer is `{matches: [{task: {id, title, status, url?}, agents: [{id, kind, state}], worktree?: {branch}, pr?: {number, url, state}, match}]}`, or 404 `not_found`.

- **Agent states:** `working` (`background` counts as working), `waiting` (needs the person), `idle` and `error` for a running session; `stopped` for a saved conversation with no running session. A task with neither has `agents: []`.
- **`id`** is the execution ID.
- **`url`** needs `web.public_url`.

Working directories, descriptions and notes are never in the answer.

## Delegations

`service.DelegationService`, `POST /api/integrations/delegations`:

```json
{"caseId": "ci:acme/widget#12", "mode": "fix" | "find_out",
 "target": {"task": "a1b2c3d4"} | {"repo": "acme/widget", "pr": 12, "branch": "feat-x"} | {"repo": "acme/widget"},
 "brief": "<markdown>", "title": "Argus: …", "idempotencyKey": "argus-<uuid>"}
```

Limits: `caseId`, `title` and `idempotencyKey` at most 200 characters, `brief` 64 KiB, a body of at most 128 KiB. The answer is 201 `{delegationId, route, taskId, state}` for a new delegation, and 200 with the same delegation for a repeat. A key is scoped to the integration. The table keeps a hash of the request, so the same key with a different body is 409 `idempotency_conflict`.

**Routes.** The route is decided before answering, and a target that cannot be routed is refused, with nothing stored:

| Target | Route |
|---|---|
| `{task}` with a running agent, in any state | `message`: through `QueueMessage`, as `legato agent message` |
| `{task}` stopped with a saved conversation | `resume`: a spawn with `session_policy: resume`, the brief as its first message |
| `{task}` with neither | `start`: the tool of `integrations.argus.agent` in the task's worktree or code-context working directory; 422 `no_checkout` without one |
| `{task}` missing or archived | 404 `unknown_task` |
| `{task}` whose stopped agent a swarm or workflow ran | 422 `not_resumable`, no fallback to `start` |
| `{repo, pr}` that the owner lookup finds | as `{task}` for the best match |
| `{repo, pr, branch}` nobody owns, with Yggdrasil worktrees | a new task, a worktree on `branch`, `start` there |
| `{repo, pr}` nobody owns, no worktree possible | `find_out`: a new task, `start` in `primary_dir`; `fix`: 422 `no_checkout` |
| `{repo}` | a new task, `start` in `primary_dir` |
| a repository not in `repositories` with a `primary_dir` | 422 `unknown_repo` |

A new task is local, titled from `title` (default `Argus: <caseId>`), in the column named Doing or In Progress (else the first), in the first workspace its catalog entry names. Its code context records the repository, the branch and the working directory (`repo_source: integration`).

Legato does not read a PR's head branch from GitHub: a `{repo, pr}` target without `branch` gets no worktree. Argus sends `branch` when the case has one.

**Delivery** runs in the background and checks the route again first, since the agent may have stopped or started in the meantime. The agent receives:

```
[argus case <caseId> · delegation <dl-id> · fix|find out]

<brief, unchanged>

---
From Argus, not from the person. When you are done, have found something, have a question, or cannot do it, call the reply_case tool with delegation_id <dl-id>.
```

A delegation is `delivered` when `QueueMessage` returns, or when the spawn that carries the brief as its first message returns. A failure sets `failed` with a code (`spawn_failed`, `message_failed`, `no_checkout`, `not_resumable`, `unknown_task`) and raises Attention `delegation_failed`. Every change publishes `EventDelegationChanged`.

The process serving the broker takes over delegations left `pending` for more than 5 minutes (`ResumeStale`, every minute): ones whose Legato stopped before delivering.

**Find out, enforced.** For `find_out`, a `resume` or `start` spawns with `AgentSpawnOptions.ReadOnlyCheckout`:

- **Sandbox:** the agent runs in the sandbox even if asked not to (when `agents.sandbox` is configured), and `BuildSandboxPlan` mounts the working directory and its git folder read-only. The tool's state, caches and `/tmp` stay writable.
- **Credentials:** the execution is marked read-only (`executions.read_only`), and the credential broker refuses its `git.push*`, `git.delete-ref`, `pr.*` and `issue.*` operations whatever the rules say (`readOnlyRefusal`).
- **`enforced`** is `true` only when the started agent's session is sandboxed.

A message to a running agent changes nothing it can do: the delegation records `enforced: false`.

**Asking first.** With `integrations.argus.delivery: ask`, a delegation raises an approval of source `delegation` (Deliver / Refuse) and stays `awaiting_approval` with no timeout. Deliver routes again and delivers; Refuse sets `failed` with `denied`, which does not reach Attention since the person chose it. The default is `auto`, because Argus's own `delegate` policy is `propose`: the person already accepts each delegation in Argus.

**Status:** `GET /api/integrations/delegations/{id}` returns `{delegationId, state, route, taskId, agentId?, enforced, error?: {code, message}, createdAt, deliveredAt?}`. Another integration's delegation is 404.

**Follow-up messages:** `POST /api/integrations/delegations/{id}/messages {text, idempotencyKey}` delivers to the same task by `message`, or `resume` if it stopped, tagged `[argus case … · delegation … · message]`.

- **201** `{messageId, state}`; **200** for a repeated key.
- **409** `not_delivered` before delivery, **409** `closed` after a failure.
- A message whose agent ended without a saved conversation is answered with `state: failed`: a new agent would not know what it answers.

Argus uses these to answer an agent's `question`.

## Replies

**The tool.** `reply_case(delegation_id, outcome, text)` is a tool of `legato mcp serve` (`internal/cli/mcp_reply.go`).

- **Listed** in every session once `integrations.argus` is set: tools are listed when a session starts, and a delegation can reach an agent that is already running.
- **Outcomes:** `done`, `finding`, `question`, `cannot`. `text` is at most 16 KiB.
- **Checks:** `service.CaseReplyService.Reply` refuses a delegation that is not `delivered` to the caller's task. The execution may differ, for a resumed agent.
- **Sending:** the reply goes into `case_reply_outbox`, and the host tries it at once for up to 10 seconds. The tool answers sent, queued, or Argus's refusal.

**Sending.** Only the process that serves the broker sends, every 15 seconds (`whileBrokerOwner`). A `legato mcp serve` that reaches no broker only records its replies.

Each send is `POST <url>/api/cases/{caseId}/replies` with `{delegationId, outcome, text, agent: {taskId, agentId}}`, the bearer access token, and `Idempotency-Key: <outbox id>`. What happens next depends on the answer:

- **2xx:** sent. Argus answers 202, or 200 for a repeated key.
- **401:** refresh the token once and try again.
- **401 after a fresh token, or 403:** the connection is broken, not the reply. The integration becomes `disconnected` and the reply waits.
- **Any other 4xx** (`not_this_case`, `closed`, 404): failed for good.
- **5xx, network errors, timeouts:** tried again after 30 seconds, doubling up to an hour.

A reply not taken within 24 hours fails and raises Attention `case_reply_failed`.

**Tokens.** Legato is a public OAuth client of Argus (`internal/engine/oauthclient`).

- **Access token:** kept in memory and refreshed when it has less than a minute left.
- **Refresh token:** in Legato's sealed store as `legato://integration-argus-refresh` (type `oauth-refresh`). Argus rotates it on every use, so the new one is stored before the new access token is used.
- **`invalid_grant`:** the store is read again, in case another process rotated the token, and retried once. Otherwise the integration becomes `disconnected`, Attention raises `integration_disconnected`, and replies wait.

## Connecting

`legato integration connect argus [url] [--no-browser]`. The URL defaults to `integrations.argus.url`.

1. **Discovery:** `/.well-known/oauth-protected-resource`, then `/.well-known/oauth-authorization-server`. `resource` is taken from the first, exactly as given (`<origin>/mcp` for Argus).
2. **Registration** as a public client with the redirect `http://127.0.0.1/callback`. Argus matches a loopback redirect without its port.
3. **Consent:** the authorize address goes to the browser, with PKCE, a random `state`, `scope=argus:reply` and `resource`. The command waits up to 10 minutes on a loopback listener at a free port. On a host without a browser the redirect fails in a browser elsewhere; pasting the address it tried into the command finishes the flow.
4. **Storage:** the refresh token is sealed. `integrations` holds the issuer, token endpoint, resource and client ID.

The command refuses when the store's master key is unlocked by a passphrase: the refresh token is rewritten by a Legato nobody is watching.

`legato integration status argus` shows the connection and the outbox counts. `legato integration disconnect argus` forgets both.

The connection is not Argus's alone. `IntegrationConnector.BeginWith` takes the integration's name, its scope and where the browser comes back to: `""` is the loopback listener above, any other address is one of Legato's web server's (`StartRedirectAuthorization`, no listener; the server's callback finds the connection by its `State` and hands it the address with `Paste`). Each integration's refresh token is `legato://integration-<name>-refresh` (`IntegrationRefreshSecret`). Legato registers as a public client (`token_endpoint_auth_method: none`), but a server may give it a `client_secret` anyway and refuse token requests without it, as Burnlite does: the secret is then kept as `legato://integration-<name>-client-secret` (`IntegrationClientSecret`) and sent in the body of every code exchange and refresh (`oauthclient.WithClientSecret`, `client_secret_post`); a registration without one removes an old one. `OAuthTokens` gives any connected integration's access token with the refresh, rotation and `invalid_grant` handling above. Burnlite, a ticket provider, connects this way; see [Sync](sync.md) § Burnlite.

## Attention

Producer `integrations` (`service.IntegrationAttentionAdapter`, reconciled on `EventDelegationChanged`), registered when `integrations.argus` is set. It covers the last 7 days:

- `delegation_failed`: a delegation that did not reach its agent, opening the task;
- `case_reply_failed`: a reply Argus refused or never took, opening the task;
- `integration_disconnected`: Argus refused Legato's tokens, urgency high, saying to connect again.

## Cases in Attention

Argus pushes one Attention item per open case (`service.CaseAttentionService`, table `integration_attention`). Only the integration named `argus` may push; other tokens get 403 `forbidden`.

- **`PUT /api/integrations/attention/{key}`** takes `{revision, signal, title, reason, detail, urgency, target: {repo, pr, branch, sha}, link}`.
  - The key is `case-` and up to 96 letters, digits and dashes.
  - `signal` is `argus_case` or `argus_needs_you`; `urgency` is `low`, `normal` or `high`.
  - `link` must be on the origin of `integrations.argus.url` (https, or http to loopback), else 422 `invalid_link`.
  - Title (200 characters), reason (its first line, 300 characters) and detail (4 KiB) are cut with `…`, never refused.
  - It answers `{itemId, taskId, status}`; `status` is the Attention item's `open`, `dismissed` or `resolved`, and `itemId` is absent until the item exists.
- **`POST …/attention/{key}/resolve`** `{revision, reason}` closes it and records the revision; an unknown key is 404 `not_found`. An upsert at that same revision then changes nothing, so a late retry cannot reopen a closed case. Another revision reopens it.
- **`POST …/attention/sync`** `{keys}` (at most 10,000; body up to 512 KiB) resolves every open item not listed, at its current revision, and answers `{resolved: n}`. One invalid key refuses the call. Argus re-upserts its open cases and then syncs, at startup and hourly.

The producer `argus` (category `argus`) shows the open rows. At each reconcile it runs owner lookup on the target and puts the item on the best task and its workspace, so an item attaches when a task later takes on the PR. With no target or no match, the item has no task. It reconciles after every push, on `EventPRStatusUpdated` and `EventCardsRefreshed`, and at startup. It is registered without `integrations.argus` too, and then shows nothing, so removing Argus resolves its items. Revoking the token does not.

Its navigation is `{kind: "external", target: link}`, and it has no actions: proposals are accepted in Argus. The web dashboard puts `argus_case` in Merge blockers and `argus_needs_you` in Needs intervention, with "Open in Argus" (a new tab) and, for an item on a task, "Open task". The TUI's Enter opens the link in the browser.

While an open case targets a tracked PR (same repository and number), the `pull_requests` producer leaves "CI failing" out of that PR's item, and raises none when that was its only reason. Its revision gains `:argus`. When the case closes, the PR's own item comes back.

## Task activity

`GET /api/tasks/{id}/activity` has `delegations`: each with its case, mode, route, state, `enforced`, error, brief and the agent's `replies` (outcome, text, state). The web UI does not show them yet.

## Chat bots

A Slack bot and a Discord bot (LEG-624) that workflows start on (`chat.message`, `chat.mention`), post as (`chat.message.send`), react as (`chat.reaction.add`, `chat.reaction.remove`, LEG-633) and read threads as (`chat.thread.read`, LEG-635); see [Workflows](workflows.md) § chat.message and chat.mention. Each holds one outbound connection, Slack's Socket Mode and Discord's Gateway, so Legato needs no public address. In v1 a bot's name is its platform's (`slack`, `discord`); `bot` stays a name in files and the API so several bots per platform can come later.

- **Engine.** `internal/engine/slackbot` and `internal/engine/discordbot`, each a thin client on `nhooyr.io/websocket` and `net/http` (no SDK), each with its own event type; neither imports the other or Legato. The service adapts them (`chatbots_platforms.go`): `slackChatEvent` drops the bot's own messages (its `auth.test` user or bot ID), makes a mention of `<@self>`, an `app_mention` or a DM a mention, and sets `thread_id` to the thread's ts or the message's own; `discordChatEvent` drops the bot's own (READY's user ID), makes a mention of a message that mentions it or a DM, and sets `thread_id` to a thread channel's ID or the message's ID. `discordReplyTo` sends a `thread_id` other than the channel as a reply (`message_reference`). `ChatConnection.React` adds or removes the bot's reaction: Slack `reactions.add`/`reactions.remove` (bot scope `reactions:write`; `already_reacted` and `no_reaction` are success; `slackbot.APIError.Needed` names a missing scope), Discord `PUT`/`DELETE /channels/{c}/messages/{m}/reactions/{emoji}/@me` (Add Reactions and Read Message History; idempotent on Discord's side; `discordbot.Code*` tells the refusals apart). Both clients retry one short rate limit, as their sends do. The emoji is resolved per platform first (`chat_emoji.go`); see [Workflows](workflows.md) § chat.message and chat.mention. Both platforms' messages from other bots (on Slack, any with a `bot_id`, such as an incoming webhook's `bot_message`) carry `FromBot`, which triggers skip without `include_bots`.
- **Forwards** (LEG-634). Slack sends a forwarded or shared message as an attachment with `is_share` or `is_msg_unfurl` on a `message` (no subtype) or `app_mention` event; `slackbot.Event.Shares` (`shares.go`) holds each one's author, channel, `from_url` and text: the attachment's `text`, else its `message_blocks` rich text rendered plainly (`<@U…>`, `<#C…>`, `:emoji:`, a list as `- ` lines), else its `fallback`. Discord sends a forward as `message_snapshots` under a `message_reference` of type 1; `discordbot.Message.Forwards` holds the snapshot's content and the original's guild, channel and ID (a snapshot names no author, and its mentions are not the message's), and `ReferenceID` is set only for a reply. The adapters quote them into `ChatEvent.ForwardedText` (`chatbots_forwards.go`: `> Forwarded from <author> in #<channel>:` on Slack, `> Forwarded message from https://discord.com/channels/<guild or @me>/<channel>/<id>:` on Discord), set `Forwarded` and `ForwardedURL`, and keep `Text` the sender's own words, from which alone a mention is decided: a forward in a channel is a mention only when the note mentions the bot; a DM still is one.
- **Thread reads** (LEG-635). `ChatConnection.ReadThread(channel, threadID, max)` gives the parent first, then the rest oldest first, at most `ChatThreadReadMax` (1000). Slack: `slackbot.Client.Replies`, then `UserName` once per user (cached per read); the first failure, `missing_scope` without `users:read` above all, stops naming for the rest of the read, so `AuthorName` is empty and the transcript writes `<@U…>`; a bot's post is named by its `username` or `bot_profile.name`. Discord, `threadID == channel` (a thread): `ListMessages` pages newest first, then the starter: `GetMessage(parent channel, thread ID)` (a thread started on a message has its ID), else `GetMessage(thread, thread ID)` (a forum post), else the oldest message; only authored message types are kept (`discordAuthored`: 0, 19, and 20 and 23, application commands' responses, which are bots' messages for `include_bots`), so the type 21 stub and other system messages go. Any other `threadID` (a message): `GetMessage`, then each `ReferenceID` up, at most `discordReplyChainMax` (50) messages, a 404 ending the chain; reversed, so the root is the parent. Forwards go through `withForwards` as on `ChatEvent`. `ChatBots.ReadThread` refuses as `Send` does (`ready`), is bounded by `ReadTimeout` (30 s), drops `FromBot` messages unless `includeBots` (never the parent), keeps the parent and the newest `limit-1` others, and gives `ChatThread.LeftOut`, how many the limit dropped. Errors read `bot <name>: reading thread <id> in <channel>: …`, scrubbed of tokens.
- **Buttons and clicks** (LEG-636). `slackbot.Client.PostMessage` and `discordbot.Client.CreateMessage` take `...Button` (`buttons.go` in each): Slack sends the text as `section` blocks (at most 3,000 characters each, split at line ends, `text` kept as the fallback) then an `actions` block `buttons` with `button_<i>`; Discord one action row whose `custom_id`s are the values (`primary` 1, default 2, `danger` 4). A click: Slack's `interactive` envelope of type `block_actions`, acked like every envelope before `Handlers.Click` gets a `slackbot.Click` (with the message's text and blocks); Discord's `INTERACTION_CREATE` of type 3 and component type 2, answered with a deferred update (callback type 6) on a goroutine of its own, bounded at 2.5 s, before `Handlers.Interaction` gets a `discordbot.Interaction` (the user from `member.user` or `user`, the message's buttons). Both clients have `Serve(ctx, Handlers)`, `Run` being `Serve` with messages only. `Settle`: Slack `chat.update` with the actions block replaced by a `context` block of the line (Block Kit cannot disable buttons); Discord `PATCH /channels/{c}/messages/{m}` with the line as subtext (`-# `), every button `disabled`, the content cut to fit 2,000. The interaction token is a credential for 15 minutes: `RespondDeferredUpdate` takes it out of its errors, and the adapters keep it only inside `ChatClick`'s unexported `settle` closure, never in a trigger request. The adapters put the clicked message's text (`Click.Text`, `Interaction.Content`) in `ChatClick.MessageText` (LEG-641), which a `chat.button` trigger reads as `${{ event.message_text }}`. `ChatBots.Send` checks buttons against both platforms' limits (5; label 75; value 100, unique; style) and `ChatBots.SettleClick` bounds and scrubs the edit. Slack needs **Interactivity** on for the app (Socket Mode needs no request URL); Discord needs no intent.
- **Supervisor.** `service.ChatBots`: a loop per enabled bot. A session that ends after connecting with the platform's reconnect request (Slack's `disconnect` envelope, Discord's op 7, op 9, a missed heartbeat ACK) starts again at once; any other end backs off with full jitter from 1 s to 3 min, the ceiling doubling with each failure and starting over only after a session that lasted a minute (connecting alone does not reset it); a refusal (Slack `invalid_auth`, `token_revoked`, `link_disabled`…; Discord 4004, 4010–4014, 4014 telling the operator to turn on the Message Content intent) is `auth_failed` and tries no more until `Reconnect` (`POST /api/settings/integrations/chat-bots/{name}/reconnect`). A bot whose tokens are missing or of the wrong kind (`xapp-`, `xoxb-`) is `auth_failed` before it tries (`ChatBotSpec.Problem`). Messages queue (256) to one goroutine per bot that calls the trigger coordinator, so a slow run start never delays Slack's acks, which go out before the event is handled. `Stop` cancels and waits at most 5 s.
- **One process.** `startChatBots` (`cmd/legato/chatbots_runtime.go`) is called beside `startMQTT` by `legato serve` and the TUI; the process that takes `<data_dir>/chatbots.lock` connects the bots, and another one on the same data directory marks them `elsewhere`: two Slack Socket Mode connections would split the events between them and two Discord sessions would each get every one. Any process can send and react, since neither needs a session; short-lived commands never connect.
- **Status.** In memory, in the process: `GET /api/settings/integrations/chat-bots` (`{bots: [ChatBotStatus]}`: `name`, `platform`, `enabled`, `configured`, `default_channel`, `state`, `last_error`, `since`, `next_attempt`) and `chat_bots` in `GET /api/settings/integrations`. `last_error` has the bot's tokens replaced and every address's query taken out (Slack's socket address carries a ticket).
- **Settings.** `integrations.slack.{enabled,app_token,bot_token,default_channel}` and `integrations.discord.{enabled,token,intents,default_channel}`, all applied at restart; the tokens are secret settings (names of secrets). See [Credentials](credentials.md) § Chat bot tokens.

## Home Assistant MQTT

Optional `integrations.mqtt` publishes ten stable aggregate discovery entities when `enabled` is true. Independent `theme_control` enables one discovered theme select; there are no per-agent entities. Site guide: [Home Assistant](../../site/src/content/docs/integrations/home-assistant.md). `internal/engine/mqtt` uses Paho MQTT v5 over TCP or verified TLS; `service.MQTTPublisher` owns counts, privacy, change detection and reconnect. Both TUI (including web disabled) and serve call `startMQTT` after session/Attention reconciliation. Short-lived CLI commands and web constructors do not start it.

A per-data-directory `mqtt.lock` flock permits one publisher. A non-owner neither connects nor publishes availability; no automatic takeover. Both processes forward coalesced source invalidations via content-free `mqtt_changed` IPC. Incoming messages map to `EventMQTTInvalidated`, not a source event, so there is no rebroadcast loop. The MQTT service subscribes before its first snapshot. It reads existing agent, default-policy Attention and pending approval sources; it does not reconcile sources or call remote providers. Agent lifecycle/activity, Attention and approval events invalidate a snapshot. A fixed 100ms burst window cannot be extended by continuous events. A mutation during snapshot collection leaves another invalidation pending.

Each connection attempt reads its host-only `mqtt` userpass credential through `UseForLegato` (audited operation `connect`), or explicitly uses anonymous access. Decode JSON username/password; errors never include values. Credentials are not loaded by config parsing. The publisher keeps only dirty work, not a historical backlog. Every connect or HA birth (`<discovery_prefix>/status` payload `online`) republishes discovery and a fresh snapshot. Publish retained QoS 1 states and attributes before retained `online`. Source errors publish offline, preserve existing state and retry; connection failures retry with backoff capped at 30s. Stop publishes offline with a two-second deadline before transport Close; the retained offline Will covers unexpected connection loss.

Discovery identifiers and client identity come from persistent `InstanceID`, not display names/topics. Count every running session including slots, workflow and swarm agents, excluding Reeve by default. Attention/approvals remain instance-wide. Optional attributes export at most 20 fixed safe labels, sorted by signal kind, with total/truncated; unknown kinds become a generic fixed label. No raw titles or source metadata leave Legato. Disabled detail export clears the retained attribute topic and removes the discovery link. Disabling MQTT or changing roots does not delete old retained discovery/state; operators clean only their own topics and HA history.

### Server theme controller

`service.MQTTThemeController` (`internal/service/mqtt_theme.go`), wired by `cmd/legato/mqtt_runtime.go`, uses a separate clean MQTT v5 connection (`legato-<instance-id>-theme`) under the same publisher lock. With theme control off, aggregate subscriptions and ACLs are unchanged. Both switches off means no MQTT connection or credential read.

Authority is the explicit local broker-grant opt-in, not the host-only broker login identifying a publisher. Trust every broker-authorized writer of exact `<base>/theme/set`. No integration token, sender identity, individual publisher revocation or arbitrary setting/command execution is provided. Current code saves actor `mqtt:broker-grant`; only the latest actor/time is stored.

- Discover `<discovery_prefix>/select/<instance-id>/theme/config`, name **Server theme**, unique ID `<instance-id>_theme`, nonoptimistic, QoS 0, retain false. Options: `none`, `legato`, `dracula`, `ocular-light`, `ocular-dark`, `ocular-light-vivid`, `ocular-dark-vivid`.
- Command `<base>/theme/set`: strict UTF-8 JSON `{id, session, expected_revision, issued_at}` (all required, no null/duplicate/unknown fields or trailing JSON), at most 2 KiB. `issued_at` is integer Unix seconds, at most 30 seconds old or five seconds ahead. Keep controller/server clocks synchronized. `none` clears the preference; it is not a palette ID.
- A random 32-byte hex session nonce rotates at every connection and is embedded in discovery. HA's command template uses `this.attributes.revision` from authoritative state and `as_timestamp(now()) | int` at send time. Old sessions and stale revisions fail; every successful save advances revision, including reselecting the same ID.
- Subscribe at QoS 0 with Retain As Published and Retain Handling 2 (no retained replay); reject retained commands received while connected. Clean sessions, no offline command queue. The reader copies into a five-entry bounded queue; persistence runs outside it. Process at five commands/second, burst five; excess traffic is dropped, with no result for dropped traffic. Oversized envelopes enqueue no payload bytes and return `invalid` when processed.
- Publish retained QoS 1 authoritative `{id, revision}` to `<base>/theme/state` after commit (`none` for empty ID). Success/conflict rereads authority. Reconnect and HA birth republish discovery/state, never commands.
- Nonretained QoS 0 `<base>/theme/result` is `{code}`: `ok`, `conflict`, `retained`, `invalid`, `session`, `expired`, `unknown_theme`, or `unavailable`. Separate retained `<base>/theme/availability` uses `online`/`offline` and its own Will. Logs do not include raw command payloads or broker credentials.

Legato needs publish permission on that select discovery path and the theme state/result/availability topics, and subscriptions to exact theme set and `<discovery_prefix>/status`. HA needs those read subscriptions/discovery plus write permission only to theme set (and its existing birth topic). Preserve aggregate ACLs if also enabled. Use dedicated broker accounts and verified TLS; anonymous or broad wildcard write access grants the same theme authority. Restrict/revoke writers at the broker; disabling `theme_control` takes effect only at an operator-chosen restart. Retained command cleanup, obsolete discovery/state and HA history are operator-owned; never clear other instances' topics. Setup: site `integrations/home-assistant`.

## LEG-199 OAuth transaction foundation

`OAuthFlowService` supplies begin, bounded response delivery, status, confirmation, cancel and local disconnect against migration 118. Web mode binds an ephemeral IP-loopback listener before DCR, registers its actual address as a native client, and keeps the receiver alive independently of the initiating request. App mode accepts only an explicit IP-loopback `/callback` receiver profile: the desktop app's receiver (LEG-209) uses it; Android has none yet (LEG-219, after LEG-202 and LEG-210). Server-held state/PKCE/registration/tokens use `SealedIntegrationSecrets`; metadata contains hashes, not credentials. Status responses never contain authorization material. Delivery needs the authenticated caller's authority, initiating instance and receiver capability; HTTP handlers must supply authority, not accept it from JSON.

The existing authorization helper now rejects malformed/duplicate parameters and wrong state/issuer without consuming a legitimate attempt. An advertised RFC 9207 response issuer is required; an issuer supplied by any provider must match exactly. Provider denial descriptions are discarded, and unknown denial codes map to a fixed safe code. Existing integration CLI paste behavior is unchanged; there is no pasted-code path in the new service.

Atomic exchange claims prevent duplicate exchanges across processes. Confirmation advances the connection generation and removes superseded sealed credentials; local disconnect fences attempts and captures its cleanup set in one store transaction. Graceful receiver-owner shutdown marks pending local attempts interrupted. The sections below add refresh and revocation, the sweep, current-MCP discovery and registration, egress, grants, dispatch, the desktop receiver and the operator routes. Android background/browser callback feasibility still requires isolated device/emulator verification; desktop loopback tests do not establish phone support. The approved design and its compatibility limits are in `.legato/plans/leg-199-mcp-broker/plan.md`.

### MCP connection registry (LEG-203)

`MCPConnectionService` (`internal/service/mcp_connections.go`, migration 119) is this instance's registry of upstream MCP servers: a name (`[a-z0-9][a-z0-9-]{0,62}`), the resource URL, an optional pinned issuer, `auth` (`oauth` or `none`), enabled, the owning `InstanceID` and a revision that changes with every edit and is never reused for a name (`mcp_connection_revisions`). It holds metadata only; tokens, client secrets and verifiers stay in the sealed store under the OAuth attempt. Addresses are checked by the connection's egress policy (see § MCP egress) when saved, and again on every request.

State keeps four layers apart: `enabled` (the operator's switch), `authorization` (`not_required`, `required`, `pending`, `awaiting_confirmation`, `authorized`, `reauth_required`, with `attempt` naming an unfinished attempt so a reloaded page can follow it, also while an authorized connection is being connected again), `connection` (`unknown`, `connected`, `failed`, from `RecordContact` with a fixed code set: unknown codes become `upstream_error`, so no upstream text is shown) and, per caller, `Usable(ctx, name, MCPCaller)`. Usable checks the instance, the switch, authorization and then an `MCPGrantChecker`; with no checker nothing is granted (`not_granted`). Every refusal is a fixed `{code, message}` with a recovery hint.

Fencing: changing the URL, issuer or auth mode invalidates the OAuth authorization and every attempt in the same transaction as the edit (the connection must be authorized again); disabling ends unfinished attempts and keeps the authorization; removal fences everything, then `OAuthFlowService.ForgetAttempts` stops receivers and removes sealed records. Local removal revokes nothing at the provider. With `OAuthFlowOptions.Connections` set, `Begin` refuses a request URL, takes the address and pinned issuer from the registry, and records the attempt only if the connection's revision is unchanged, enabled and `oauth` (`BeginOAuthAttempt` with `ConnectionRevision`).

### MCP egress (LEG-204)

Every request for an MCP connection, OAuth discovery, registration and token exchange included, goes through `internal/engine/egress` with that connection's policy (`MCPAuthorizationTarget.Egress`; `OAuthFlowService` uses it for Begin and for the exchange in Deliver, ignoring `OAuthFlowOptions.HTTPClient` when the registry is set). A connection reaches public addresses only, unless the operator names private prefixes for it (`private_networks`, CIDR, each inside RFC 1918, 100.64/10 or fc00::/7); loopback, link-local and cloud metadata are never reachable, and a private upstream cannot drop its network while its address needs it. An authorization server or endpoint the upstream names elsewhere is held to the same policy, so an upstream cannot steer Legato to an internal address. `MCPConnectionOptions.Egress` adjusts the policy for tests (the loopback fixture); production leaves it nil. Remote Streamable HTTP only: no subprocess or stdio servers, no relay, no proxy. The redirect URI comes from the receiver, never from request Host or forwarded headers. Matching the resource identifier in protected-resource metadata to the configured URL belongs to strict discovery (LEG-205); the pinned issuer is enforced now.

### MCP discovery and client registration (LEG-205)

`OAuthFlowService` needs the registry (`OAuthFlowOptions.Connections`); a request carries no URL. Begin (`oauth_registration.go`) follows MCP 2026-07-28:

- **Discovery** (`oauthclient.Challenge`, `oauthclient.DiscoverStrict`): an unauthenticated `initialize` POST; a 401's `WWW-Authenticate` gives `resource_metadata` and `scope`. Protected-resource metadata comes from that address, else the path-specific, else the root well-known location (RFC 9728), and its `resource` must be the configured URL or its origin. Authorization server metadata comes from the RFC 8414 path-inserted, OIDC path-inserted, then OIDC path-appended location; its issuer must match exactly (and the pinned issuer, if any); `S256` must be advertised. With no metadata at all, discovery stops (`ErrNoServerMetadata`): Legato never guesses `/authorize`, `/token` or `/register`. Legato does not use the Go SDK's `AuthorizationCodeHandler`, whose v1.8.0 falls back to guessed endpoints and tries CIMD before pre-registration.
- **Scope**: the operator's explicit scope, else the challenge's, else the resource's `scopes_supported`, else none (no `scope` parameter). `offline_access` is added when the server lists it and a scope is requested. The attempt records its scope (`oauth_attempts.scope`) and `Status` shows it for confirmation.
- **Client**, in the specification's order: a pre-registered client (`static_client_id`, the bare redirect `http://127.0.0.1:<port>/callback` registered for it, an optional sealed secret `mcp-static-client-<name>`; web mode binds exactly that port and fails if it is taken; an app must use that redirect); then a client ID metadata document (`OAuthFlowOptions.ClientMetadataDocument`, empty in production since Legato publishes none) when the server advertises CIMD and the document names itself and lists the exact redirect; then an earlier dynamic registration for the same issuer, resource and exact redirect (`oauth_client_registrations`, its secret sealed as `oauth-client-<id>`); then a new DCR of the receiver's actual redirect (`application_type: native`). Otherwise `ErrOAuthRegistrationUnsupported`. A web receiver first tries the ports of earlier registrations for the issuer and resource (`oauthclient.ListenLoopbackAt`), so re-authorizing reuses a registration when that port is free; a taken port gets a new port and an exact new registration, never an unregistered address. A token exchange refused with `invalid_client` forgets the registration it used.
- RFC 9207: an advertised `iss` must be present on the response and any `iss` must match exactly (`AuthorizationResponse.Check`).
- Burnlite's is the one shared authorization: the board and the MCP connection at its resource use one (§ One Burnlite connection, LEG-544, which replaced the rule that they never share).

Sources: MCP 2026-07-28 [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery), [Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration); RFC 9728, RFC 8414, RFC 8252 §7.3, RFC 9207.

### Token lifecycle and reconciliation (LEG-206)

`oauth_lifecycle.go`. `OAuthFlowService.AccessToken(ctx, connection)` is the host broker's way to the current access token: never an agent's, and it never starts consent. A token within a minute of expiry is refreshed under a database lease on the connection (`oauth_connections.refresh_holder`, `refresh_lease_until`, 30 s), so one process refreshes while others wait up to 15 s for its result. The rotated refresh token is sealed before the access token is returned, and a refresh that finishes after a disconnect or a newer authorization removes what it wrote and fails. `invalid_grant`, an expired token with no refresh token, or `invalid_client` (which also forgets the registration) mark the active attempt `reauth_required` and drop its tokens; the registry then shows `authorization: reauth_required`. A network failure is `ErrOAuthRefreshUnavailable` and keeps the authorization. Token expiry is rebased on the service clock.

`Disconnect` returns `OAuthDisconnect.Upstream`: `revoked` (RFC 7009 through `oauthclient.Revoke`, refresh token preferred, via the connection's egress policy), `not_supported` (no revocation endpoint: the token may stay valid upstream until it expires), `failed` or `none`. Fencing comes first, revocation second, sealed removal last; the registry's resource change and removal revoke the same way, through the old connection's policy (`MCPConnectionService.EgressPolicy`).

Web attempts record the receiving process (`receiver_owner`) and a lease it renews every 20 s while it listens. `Sweep` (run at start and every 5 minutes by the process that serves the broker, `mcpBrokerRuntime.sweep`) expires overdue attempts, fails exchanges stuck for over 2 minutes (`exchange_interrupted`), interrupts web attempts whose receiver lease lapsed (`receiver_lost`), removes the sealed records of every finished attempt and deletes finished attempts after 7 days, keeping any a connection still points at. A callback for a swept attempt is refused without an exchange.

`Status` carries `Evidence` for confirmation: issuer, resource, requested and granted scope, whether it can refresh and its expiry. `Account` stays empty: Legato does not invent introspection, so the operator confirms the intended account. The credential broker refuses any credential definition naming a sealed MCP OAuth record (`legato://oauth-attempt-*`, `oauth-client-*`, `mcp-static-client-*`), so no agent can read or exec them.

### Tool grants through the credential broker (LEG-207)

`mcp_grants.go`. Each MCP connection is a broker credential `mcp:<name>` with the internal profile `mcp` (not shipped, so no configured credential can use it; `Brokered`: `Value` and `readSecret` refuse, so no agent can read or exec its token). Its rules come from the registry (`rules`, `read_only_tools`; `CredentialBroker.SetMCPRules`), so the broker's own rule selection, approvals (session, window, once; signed when devices are enrolled), limits and meters, look-only refusal and hash-chained audit apply unchanged. No rules means nothing is allowed.

A call's broker resource is `<owner>/<repo>/<tool>` (`-/-/<tool>` for an agent with no repository), and its operation is `mcp.read` for a tool matching the operator's `read_only_tools`, else `mcp.write`. Upstream annotations never decide either. An `MCPRule` is `{tools, repository, access (read|write|""), approve, window, limit}` and becomes the broker rule `{operation, resource: repository/tools, …}`. A look-only (find-out) execution is refused `mcp.write`.

`MCPGrants.Authorize(ctx, connection, MCPCaller{ExecutionID}, tool)` is what every dispatch calls. It validates the tool name (`ErrMCPToolName`), attributes the caller from its execution (its task and that task's code-context repository; a claimed task is passed to the broker, which refuses one that is not the execution's), refuses on the connection's own state (other instance, turned off, not authorized), then asks the broker, which may ask the operator and wait. The audit records `tools/call <tool>`, never arguments. `Visible` is the discovery check: same attribution, a rule that does not deny, nothing asked or spent. `MCPGranted` serves `MCPConnectionService.Usable`. Changing a connection's resource, issuer, auth or client, or removing it, ends every grant for `mcp:<name>` (`store.EndCredentialGrantsFor`). Paired main/worker tokens gain nothing: grants are only for this instance's executions.

### Upstream discovery and dispatch (LEG-208)

`internal/engine/mcpupstream` is a bounded, validating client of one remote MCP server over Streamable HTTP (official Go SDK v1.8.0), knowing nothing of Legato. It advertises no roots, sampling or elicitation (`ClientCapabilities{}`, multi-round-trip disabled), so an upstream cannot ask the operator for a credential through it. It keeps a tool only if its name is valid and its input and output schemas are JSON Schema 2020-12 (another `$schema` is refused), under 64 KiB, and resolve with no remote reference (a nil loader); the others are listed in `Catalog.Rejected`, not weakened. It lists at most 256 tools, cuts descriptions to 2 KiB, and checks arguments (256 KiB, an object, against the input schema) before sending and structured results against the output schema after. Results are capped at 1 MiB, calls at 60 s, and four calls run at once. A 401 means the request was not taken: it gets a new token (`TokenSource.Token(force)`) and sends once more. A session the server ended is reopened and the request repeated only for listing and `CallRead`; `Call` returns `ErrSessionEnded` and never sends a possibly-run call again. `Tool.Hash` covers the whole definition. Standalone SSE is off; `list_changed` delivered on responses marks the catalog stale.

`MCPBroker` (`internal/service/mcp_broker.go`) holds one client per connection and revision, sharing one authorization across every permitted execution (`mcpTokens` over `OAuthFlowService.AccessToken` and `RefreshAccessToken`; agents never see a token). Its HTTP client is the connection's egress policy. `ListTools(caller)` offers, for each connection `Usable` by the caller, the tools `MCPGrants.Visible` allows, under the local name `<connection>__<tool>` (at most 64 characters; connection names have no `_`, so upstream and local names never mix). Each description is prefixed `[<connection>]` as the server's own words. Rejected tools and failed listings are returned as problems. `CallTool(caller, local, args)` authorizes every call through `MCPGrants.Authorize` (so a stale catalog grants nothing), refetches once for an unknown tool, then calls: `CallRead` for an operator-listed read-only tool, `Call` otherwise. A denial is `*MCPDenied` (with the approval when one is pending). Errors are reduced to fixed messages (`safeMCPError`), and every listing and call records the connection's contact code. Catalogs are trusted for 5 minutes or until `list_changed`. Tool hashes are kept in `mcp_tools`: a tool that changed or went away ends the connection's grants (`EndGrants`), so the operator approves again. `Refresh(connection)` lists again now. Returned URLs and content are passed through, never fetched.

Routes `/api/settings/mcp/connections` (GET list, POST add) and `/{name}` (GET, PATCH with `expected_revision`, DELETE). Mutations and `POST /{name}/test` are class `risky` (LEG-248): the Reeve proposes them as change sets, and `/api/settings/mcp/` is in `floorRoutePrefixes`, so no level or rule makes one run without the operator's approval. A stdio add or a change to what one runs then raises its own `mcp_stdio` approval when the set runs, so the operator approves it twice. Authorizing a connection stays `never` (below). Integration tokens, a paired main's included, reach only `/api/integrations/`. Request bodies refuse unknown fields.

### Operator routes and Settings (LEG-211)

`internal/server/mcp_oauth.go` serves the flow under `/api/mcp/`, every route class `never`:

- **Owner**: the server derives each attempt's owner from the operator credential that authenticated the request (a hash of the bearer token, `mcpOAuthOwner`); no body names it, and unknown fields are refused. The web UI and the desktop app use the same operator token, so the app begins and delivers while the page follows the status and confirms. A rotated operator token owns none of the old token's attempts, which expire by themselves.

- **Errors** are Legato's words, never provider or upstream text: `400` input, `409` an attempt over, expired or not this owner's (and a secret store that needs a typed passphrase, `ErrOAuthSecretStoreLocked`), `422` no usable registration, `502` network policy, no metadata, untrusted certificate or unreachable.

- **Caches**: the service worker sends `/api/mcp/`, `/api/settings/mcp/` and `/api/settings/integrations/` to the network only (`NEVER_CACHED` in `web/src/lib/serverPages.ts`); the page keeps no attempt in browser storage.

Inside the desktop app (`window.legatoShell.mcp`) Connect posts `mcpConnect` to the app, which begins in app mode, opens consent in the system browser, delivers, and answers `legato:shell-mcp`; the page then reads the connection's `attempt` and shows its evidence for confirmation. In a browser it says up front that browser-only setup needs Legato on the same computer, opens a tab before beginning (so no popup blocker stops it; a link if one does), points it at the consent page, polls the status, and on expiry says the answer did not arrive and repeats that a remote server needs the app. No pasted-code fallback exists. Android connect is LEG-219.

### Local (stdio) MCP servers (LEG-223)

A connection of `kind: stdio` is a command Legato runs on the host, **outside any sandbox, as the operator's user**, and speaks MCP to over its stdin and stdout. Its tools reach agents through the same broker path as a remote connection's (`mcp.list`, `mcp.call`, `MCPBroker`, the same grants), so a sandboxed agent needs no mounts, runtimes, browsers or ports of the server's. The design choices are recorded as a Note on LEG-223.

- **Stored** in `mcp_connections` (migration 120): `kind` (`http` or `stdio`), `command`, `args_json`, `dir`, `env_json`. A stdio row has no `url`, `issuer` or networks, and `auth` is `none` (`authorization: not_required`). `checkStdio` (`internal/service/mcp_stdio.go`): a command that is absolute or a bare name (a path with `/` must be absolute), at most 64 arguments of 4096 bytes without NUL, `dir` absolute (a leading `~` is the home folder, expanded when saved) and an existing directory, at most 64 variables named `[A-Za-z_][A-Za-z0-9_]*` with values up to 8192 bytes. A value `legato://name` is read from the secret store (`MCPConnectionOptions.Secrets`) when the process starts.
- **Approval.** `MCPConnectionService.Add` of a stdio connection, and `Update` that changes its command, args, dir or env, save nothing: they raise an approval of source `mcp_stdio` (`requestStdio`) and return `*MCPApprovalRequired{ApprovalID, Signed}`, which the routes answer as `202 {status: "needs_approval", approval_id, signed, message}`. The approval is `signed` once any device is enrolled (the Reeve's `risky` default), else a tap. Its details are the proposal (`mcpStdioProposal`: `change` `add` or `edit`, the input or the change with its `expected_revision`) with `command` (the command line, then `NAME=value` lines) and `cwd`, which the tray's generic card shows. Its resolver (`mcpStdioResolver`, registered by `SetApprovals`) applies the proposal once allowed; a connection changed since fails the approval with `ErrMCPConnectionStale`. Turning a stdio connection off or on, removing it and changing its rules apply at once. The routes are class `risky`, so the Reeve can propose one; the operator approves its change set, then this approval. Without `SetApprovals` (no approval service) a stdio connection cannot be added.
- **Processes** (`internal/service/mcp_broker_stdio.go`, `internal/engine/mcpstdio`). One per (connection, execution), made on the session's first call (`MCPBroker.session`). Listing (`mcp.list` at session start, the catalog's 5-minute refresh) starts a process that lists and is stopped at once, so an idle agent keeps nothing running. `MCPBroker.Sweep`, every 3 seconds in the process that serves the broker (`mcpBrokerRuntime.sweep`), stops the servers of executions that are no longer `running` and of connections removed, turned off or at a new revision; `EndExecution` stops one execution's; `Close` all. Stopping (`mcpstdio.Process.Stop`): stdin closed, then SIGTERM to the process group, then SIGKILL to the group and to every descendant seen (Linux: `/proc`, watched every 500 ms and taken again at Stop, matched by start time), each step after a 3-second grace. Descendants are found because Playwright starts Chromium in a session of its own, beyond the group. Either end of the transport stops the process before it is closed: the SDK closes stdout first, and a server whose next write then fails would otherwise exit and orphan its helpers first. A server that dies by itself takes the descendants last seen. On Linux the process has `Pdeathsig` SIGKILL. A crash fails the running call (`ErrSessionEnded`, told to the agent as "stopped before it answered … calling again starts it afresh"); calls are never sent again, read-only tools included, and the next call starts a new process.
- **Environment.** `stdioSpec`: `HOME`, `USER`, `LOGNAME`, `LANG`, `LANGUAGE`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`, `TZ`, `TMPDIR`, the XDG folders and `PATH` from Legato's own environment, then the connection's variables. A bare command is found in that environment's `PATH` only (`mcpstdio.Resolve`); a miss is `mcpstdio.ErrNotFound`, naming the PATH searched. No login-shell lookup: it would depend on rc files.
- **Limits.** `mcpStdioLimits`: results up to 8 MiB (pictures), calls up to 2 minutes (a first call may start a browser). Its clients set `mcpupstream.Options.AcceptDraft07`: servers on the TypeScript SDK declare draft-07 schemas, which are validated as draft-07; remote connections keep to 2020-12, and remote references are refused either way.
- **Errors.** Contact codes `command_not_found` and `process_failed` (`recordStdioContact`). An agent is told a fixed sentence (`stdioAgentError`), never a host path or the server's stderr.
- **stderr** goes to Legato's log, each line cut at 1 KiB, as `mcp stdio <connection> <execution>: <line>` (`list` for a listing, `test` for a Test).
- **Test.** `POST /api/settings/mcp/connections/{name}/test` (class `never`, `MCPBroker.Test`, `server.MCPTester`) reaches a saved connection now: a stdio one is started for the test and stopped, its contact and tool hashes recorded; an HTTP one is listed again. It answers `MCPTestResult{tools, rejected, error, stderr}` (stderr: a stdio server's last 40 lines). Only a saved, so approved, definition is ever run.

## One Burnlite connection (LEG-544)

The Burnlite board integration and the MCP connection to Burnlite used to be two OAuth clients with two token sets for one resource: Burnlite has one protected resource, `<burnlite>/api/llm/mcp` (issuer `<burnlite>`, scopes `read:tasks write:tasks write:projects`), which the board's client (`internal/engine/burnlite`) and agents' tools both speak MCP to. Reconnecting one left the other as it was. Now they are one connection, decided with the Reeve on LEG-544: Burnlite only (no general same-issuer rule: Argus's integration asks only `argus:reply`), the union of scopes (`service.BurnliteScope`), and the tokens kept by the MCP side.

- **Storage.** The tokens are the active authorization of the linked MCP connection, in `oauth_attempts` and the sealed `oauth-attempt-<id>`, like any MCP authorization. `integrations` keeps the board's record of which Burnlite it uses (`url`, `issuer`, `token_endpoint`, `resource`, `client_id`); its `state` column is no longer read for Burnlite. `integration-burnlite-refresh` and `-client-secret` are no longer written, and are removed on connect, disconnect and migration.
- **The link** (`service.BurnliteConnections`, `burnlite_connection.go`): an HTTP OAuth MCP connection whose URL is the integration's `resource`, with the same issuer when it pins one (`burnliteLinks`; the one named `burnlite` first, then an authorized one). With no integration row, an authorized connection whose path is `/api/llm/mcp` (at `burnlite.url`'s origin when that is set) connects the board, and `Current` writes the row. `MCPConnectionState.SharedWith` is `burnlite` on the linked connection.
- **Connecting from the board** (the web callback, `legato integration connect burnlite`) keeps its own flow, so any browser that reaches Legato, and the CLI's loopback and paste, still work. Discovery, registration and the exchange go through `ConnectClient` (the linked connection's egress policy, else the one a new connection would have). `PendingConnection.FinishTokens` returns the tokens and keeps nothing; `BurnliteConnections.Adopt` refuses (`ErrBurnliteInput`) a resource other than `<the address the operator typed>/api/llm/mcp`, so a server cannot name another resource, then makes the MCP connection when there is none (named `burnlite`, else `burnlite-2` …, with no rules) and records the tokens through `OAuthFlowService.Adopt` (sealed first, then `store.AdoptOAuthAuthorization` supersedes the old authorization and unfinished attempts in one transaction, as `Confirm` does; superseded tokens are not revoked, as on reauthorization). `BurnliteLink.Created` says it made the connection.
- **Connecting from Settings › MCP servers** is the usual Begin, Deliver, Confirm, which the board then uses.
- **Tokens for the board** (`BurnliteConnections.Tokens`, `Client`): `OAuthFlowService.AccessToken`/`RefreshAccessToken` on the linked connection; `ErrOAuthNotAuthorized` and `ErrOAuthReauthRequired` are `ErrNotConnected`. The ticket source and `ConnectedBurnlite` take a `service.BurnliteConnection`. `AccessToken` now uses the connection's egress policy whether or not the connection is turned on (`refreshClient`): the switch is about agents, whom the broker refuses through `Usable`.
- **Disconnecting** from either side revokes at Burnlite (RFC 7009, through egress) and forgets the authorization; the MCP connection and its rules stay. From the board, the integration row goes too (state `none`), and a connection made in MCP servers that no board read has recorded yet is found as `Current` finds it; from MCP servers, the board shows `disconnected`.
- **A local Burnlite.** `egress.Policy.Loopback` reaches a loopback literal (`127.0.0.1`, `::1`) over http or https; names, `localhost` and a name resolving to loopback stay refused. `mcp_connections.loopback` (migration 137) sets it, only through `MCPConnectionInput.Loopback`, which no request decodes: the link sets it only when the address the operator typed is a loopback literal (never from the server's metadata), and changing the connection's URL clears it.
- **Attention.** `integration_disconnected` for `burnlite` is raised while the linked connection's current authorization is `reauth_required` (Burnlite refused the token), not after the operator disconnected (`burnliteRefused`).
- **Migration** (`BurnliteConnections.Migrate`, run once per process by `burnliteConnections` and by the CLI before it acts; idempotent). One process at a time: it holds `burnlite_migration_lease` (migration 137, two minutes) and reads everything under it, so a second process starting at once waits and finds nothing to do; the MCP authorization it revokes is fenced by its ID (`RevokeAuthorization`). It acts while `integration-burnlite-refresh` exists, or when an authorized Burnlite MCP connection has no board row. The board's own authorization counts as scope `read:tasks` (it recorded none). It keeps the authorization whose scope covers the other's, else the newer (`connected_at` against the authorization's `updated_at`). Keeping the MCP side, it revokes the board's refresh token (endpoint from discovery again, through egress) and forgets it. Keeping the board's, it revokes the MCP authorization (`OAuthFlowService.RevokeAuthorization`) and adopts the board's refresh token, client and client secret (the first use refreshes). A refused board connection is forgotten. Before the first change it writes `<db>.<UTC>.leg-544.bak` (`store.BackupTo`, `VACUUM INTO`), and it logs what it kept and revoked.

| Protection | Board before | MCP before | Both after |
| --- | --- | --- | --- |
| One refresh at a time across processes | No: a mutex per process; `invalid_grant` read the store again | DB lease (`oauth_connections.refresh_holder`) | The lease |
| Rotated refresh token sealed before use | Yes | Yes | Yes |
| Dead token ends the authorization | `integrations.state = disconnected` | `reauth_required` | `reauth_required` |
| Revocation on disconnect | No | RFC 7009 | RFC 7009 |
| Egress policy on OAuth and calls | No (default client) | Yes | Yes (board connect, refresh, calls) |
| Agents see a token | No | No: the broker calls | No |

## Database

### Persistence boundary and connection policy

Application entry points resolve `config.DBConfig` through `config.ResolveDatabase` and use the shared opener in `cmd/legato/database.go`. An omitted `db.driver` resolves to `sqlite`, preserving existing `db.path` configurations; unsupported drivers fail at startup. `data_dir` is resolved separately and defaults to the SQLite file's parent, so existing auth tokens, certificates, and artifacts do not move.

Production services, CLI commands, TUI code, and the web server use store behavior instead of a raw `*sqlx.DB`. SQLite-specific migrations, reporting SQL, full-text search, generated IDs, and connection setup stay behind the store boundary.

The SQLite DSN enables foreign keys and a 5-second busy timeout on every pooled connection. The pool is capped at four connections. A read-only compatibility preflight runs before WAL mode can be changed. Migration transactions use an immediate SQLite transaction, taking ownership before reading schema state; WAL initialization retries bounded lock contention so racing Legato processes can safely open the same database. `Store.Close` (and `Unmigrated.Close`) closes the pool and then waits, at most 10 seconds (`closeWait`, twice the busy timeout), for connections still in use to be given back, logging when it gives up: `database/sql` closes only idle connections, and a statement on one still checked out would make SQLite create the `-wal` and `-shm` files again after the idle one deleted them. Once `Close` returns they are gone, so a test's `t.TempDir()` cleanup can remove the folder even when a background goroutine outlived the test (LEG-654).

### Migrations and compatibility

Migration SQL remains embedded and SQLite-specific. The backend-neutral `schema_migrations` table becomes authoritative after first open by this version. Existing databases bootstrap it transactionally from `PRAGMA user_version`; each missing migration and its ledger row commit together. The opener validates that ledger versions are contiguous and names match the embedded migrations, rejects schema revisions newer than the binary, and rejects disagreement between the ledger and `user_version`. Supported partial `ADD COLUMN` migrations skip only columns already present and execute every remaining statement before metadata advances. This is the approved new-binary-only compatibility policy.

**Naming a migration.** A ledger row is a position, so a new migration's file name must sort after the newest one on `main` and in the latest release tag: rename a branch's migration to the next free number when it merges. `scripts/migration-order.sh` (CI job `migrations`; tested by `cmd/legato/migration_order_test.go`) fails on a new file that sorts earlier, naming it. v0.21.0 was tagged while `117_agent_docker_host_network.sql` was on a branch, so its databases hold `116_skill_states, 118_oauth_attempts, 119_mcp_connections` at versions 115–117, and v0.22.0 refused them (LEG-249). `knownLedgerReorderings` (`migration_reorder.go`) lists such released orders; `New` repairs a ledger that holds one exactly, in the migration transaction: it runs the missing migrations (an `ADD COLUMN` already present is skipped), renumbers the rows keeping `applied_at`, sets `user_version`, and logs it. Any other mismatch is refused as before. Add an entry only for an order a release really shipped. `Store.SchemaStatus(ctx)` reports the current and supported revisions without exposing the raw connection.

**Opening without migrating, and the backup.** `store.OpenWithoutMigrating(Options)` opens a database as it is: it refuses what `Open` refuses (another driver, a schema newer than the binary, a ledger that disagrees), but runs no migration and leaves the journal mode alone; a missing database is created empty. The `*Unmigrated` it returns has no store behaviour, only `Pending(ctx)` (the migrations this binary would run, by file name, oldest first, read from the ledger's names, so a known reordering's missing migrations count, else from `user_version`), `Backup(ctx)`, `Migrate(ctx)` (runs them, turns on WAL and returns the `*Store`, which owns the connection from then on; `Close` after it does nothing) and `Close`. `Backup` copies the database with SQLite's `VACUUM INTO`, which reads one snapshot, so the copy is consistent and holds commits still in the WAL. It is written beside the database as `<path>.before-<newest pending migration without .sql>` (`store.BackupPath`), for example `legato.db.before-141_job_clone_slot`, mode `0600`, first as `<that>.partial` and renamed when complete, replacing a copy an earlier try left. It writes nothing and returns `""` when nothing is pending, or when no migration has run (a new database). The copy opens at the earlier schema, so the `.prev` binary can run on it. `Open` and `New` still migrate on open. Command entry points open through `openStore`, which runs the upgrade restart when migrations are pending: the other Legato processes on the data folder are asked to exit and waited for (at most 30 s), then `Backup`, then `Migrate`; see [Releases and updates](updates.md) § The upgrade restart. `store.SupportedSchema()` is the newest schema revision the binary knows, and `SchemaStatus.Newer()` says a newer binary migrated the database, on which the review tick does nothing.

Store tests use real temporary SQLite files and cover fresh creation, reopen durability, legacy bootstrap, future/mismatched schema refusal, per-connection PRAGMAs, and racing migration openers. Architecture tests prevent production packages from importing `sqlx`, calling `Store.DB()`, bypassing the shared command opener, or creating sibling dependencies between engine packages.

### Execution activity and reporting

An **execution** is one independently startable and terminable unit of agent work. Interactive agents, workflow `agent.run` attempts, swarm conductors, and swarm workers each receive a Legato-generated `LEGATO_EXECUTION_ID` before spawn. Provider session IDs, tmux names, task IDs, and workflow IDs are metadata and must never select an activity stream.

`executions` durably owns lifecycle (`running` → `succeeded|failed|cancelled|lost`), task/project/workflow/swarm attribution, provider-session links, and start/end timestamps. `execution_activity` stores its `working` and `waiting` spans with at most one open span per execution. Terminalization atomically sets `ended_at` and closes open activity; reporting additionally clips every span to execution end. Parallel execution active time is additive and may exceed workflow/swarm wall-clock time. `ReconcileLostExecutions` marks `lost` a running execution no running agent session backs, checking that in the statements that write; one with no session yet is a spawn in flight for its first 10 minutes and is left alone.

Migration 055 intentionally drops `state_intervals` without importing it because task-keyed intervals cannot be reliably associated with concurrent executions and include known orphan inflation. `reporting_metadata.activity_epoch` records the reset boundary. Tasks, workflows, attempts, sessions, swarms, reviews, plans, and non-duration history are preserved. Product reports treat pre-epoch activity as unavailable, not proven zero.

### Sub-agent time

An execution's agent may run sub-agents (Claude Code's Task/Agent subagents, Chimera's `agent.spawn`). Their time is the execution's, so it is attributed to the execution's task like the agent's own, at any depth. `subagent_activity` (migration 114) holds each sub-agent's `working` and `waiting` spans, keyed by `(execution_id, subagent_id)`, at most one open per sub-agent, with `parent_subagent_id` when the tool says which sub-agent started it (`''` otherwise). `Store.SetSubagentParent` fills it in afterwards for spans recorded before the parent was known (Claude Code names a subagent's parent only in the parent's `Agent` call, which can be reported after the child's `SubagentStart`). `Store.RecordSubagentActivityAt` moves one (state `""` ends it; ending one with no open span does nothing), `EndSubagentsAt` ends every open span but those still running, `OpenSubagents` and `SubagentParents` read them. Terminalization and `ReconcileLostExecutions` close a sub-agent's open span with the execution's, and a running execution refuses spans after it ends (`ErrExecutionTerminal`).

`executions.subagent_telemetry` is set at spawn when the adapter reports sub-agents (`service.SubagentReportingAdapter`: Claude Code with its state plugin, Chimera with the Legato mod). Executions from before migration 114 and those of other tools (Codex; Chimera without the mod) have `0`: their totals are the top-level agent's own, and no backfill is possible, since nothing recorded their sub-agents.

`Store.QueryAgentTime(range)` reads both tables and gives, in all, by attribution task and by execution (`store.AgentTime`):

- `Own`: the top-level agents' own working, waiting and error time, as the other reporting queries count it.
- `Subagents`: the sub-agents' working and waiting time, each sub-agent's own spans counted once. A sub-agent working while its parent is idle or in the background counts; a parent's span is never counted again for its children, nor a nested sub-agent's for its parent.
- `AggregateWorking()`: `Own.Working + Subagents.Working`, agent-time: agents working at once each count (five sub-agents working the same 10 minutes make 50).
- `Elapsed`: the union of every span of the tree (working, waiting, error; top-level and sub-agents), so agents active at once count once (those five make 10). It is wall-clock time with any agent active, not the operator's own time, and it leaves out the top-level agent's idle and background time, as swarm wall-clock does.
- `SubagentCoverage()`: `complete` when every execution with a span in the range reported sub-agents, `partial` when some did, `none` when none did, `""` with no execution.

Spans are clipped to the range and to their execution's end, and an open span of a running execution runs to now, as in the other queries. The day, workspace, directory and swarm breakdowns stay top-level agents' own time; the day breakdown adds the sub-agents' working time and the aggregate beside it.

Execution history is not deleted during normal session cleanup or task deletion. `agent_sessions` remains operational and may be removed only after its linked execution is terminal. Task-triggered workflow executions retain their synthetic task as `execution_task_id` but attribute report totals to `workflow_runs.related_task_id`; repository-only workflow activity remains project/workflow-only.

## Schema

- SQLite file location: `cfg.DB.Path` > `$XDG_DATA_HOME/legato/legato.db` > `~/.local/share/legato/legato.db`
- Core schema includes `tasks`, `column_mappings`, `sync_log`, `agent_sessions`, `executions`, `execution_activity`, `reporting_metadata`, `workspaces`, swarm tables, review tours/passes/findings, plans/revisions/comments/interactions, workflow runs/steps/attempts/artifacts, `task_notes`, and the evidence-backed learning ledger.
- `tasks` table: core fields (id, title, local `description`/`description_md`, provider-owned `remote_description_md`, status, priority, sort_order, workspace_id, archived_at, created_at, updated_at) + nullable provider link (provider, remote_id, remote_meta JSON) + nullable `code_context` TEXT (durable repository/branch/SHA/path/provenance JSON) + nullable `pr_meta` TEXT (refreshable PR number/URL/state/review/check/comment/pin/outcome JSON; since migration 082 a summary of the first of the task's PRs in `task_branches`). `archived_at` is nullable DATETIME — NULL means active, non-NULL means archived (hidden from board but retained in DB). Columns list by `sort_order`, ties (imported tickets start at 0) by `rowid` (`boardOrder` in `task_order.go`); `PlaceTask` puts a card before a neighbour and renumbers the column from 0 without touching `updated_at`. Only the moves (`RecordTaskTransition`) and `PlaceTask` write `sort_order`: `UpdateTask` leaves it alone, so an edit from a copy read before a placement does not undo it
- `workspaces` table: id (INTEGER PRIMARY KEY), name (TEXT UNIQUE), color (TEXT), sort_order (INTEGER)
- Local tasks: provider/remote_id/remote_meta are NULL and render `description_md` unchanged. Synced tasks: provider='jira', remote_id=Jira key, remote provider Markdown in `remote_description_md`, and remote_meta=JSON with remote_status, issue_type, assignee, labels, etc. Their editable `description_md` is composed under `## Legato details` at read time; the combined value is never persisted. A worker's card for a handed-off provider-backed task has provider `<provider>-copy` (`jira-copy`, `burnlite-copy`; no sync source has it), `remote_id` the ticket's key, `remote_description_md` the copy of its text taken at handoff and `remote_meta` `{url}`.
- Task IDs: 8-char lowercase alphanumeric (crypto/rand) for local tasks, provider IDs (e.g. REX-1234) for synced tasks
- `agent_sessions` and `sync_log` reference `task_id` (not ticket_id).
- Migration 114 adds `executions.subagent_telemetry` and `subagent_activity` (see § Sub-agent time).
- Migration 121 adds `agent_sessions.background_shells` (JSON, `store.BackgroundShells`): the background shells an agent's mod reported, running and ended (`id`, `command`, `status` `running`/`exited`/`killed`, `exit_code`, `started_at`, `ended_at`), never their output. Chimera's hook writes it with `SetChimeraHookState`; it is in `GET /api/agents` as `background_shells`. A Claude Code agent's shells live in its bridge instead. See [Chimera native integration](chimera-native.md).
- Migration 112 adds `agent_sessions.chimera_subagents`: bounded, parent-conversation-scoped JSON lifecycle metadata (IDs, purpose, status/reason and millisecond start/end times), not transcripts. `SetChimeraHookState` commits it with activity and active background jobs so native snapshot repair sees completion even when Chimera's idle SSE misses it. See [Chimera native integration](chimera-native.md).
- `workflow_runs.task_id` is the workflow-owned execution task; `related_task_id` is the optional existing task selected through a typed `task` input. The execution task always belongs to the managed **Workflows** workspace. Successful final-step completion atomically moves it to Done and sets `archived_at`; failed and cancelled runs remain active for intervention.
- `workflow_steps`, `workflow_step_attempts`, and `workflow_artifacts` retain ordered state, retries, agent identity, managed paths, media types, sizes, and digests. `(attempt_id, output_key)` is unique so interrupted completion callbacks can safely reuse an unchanged artifact.
- Migration 154 adds `workflow_runs.parent_attempt` and the unique index `idx_workflow_runs_child` on `(parent_run_id, parent_step_path, parent_attempt)` (where `parent_run_id` is set): a `workflow.run` step's child run is unique per attempt. `CreateChildWorkflowRun` writes the child and the step's `child_run_id` in one transaction and returns the existing child when the attempt has one; `ListChildWorkflowRuns`, `SetWorkflowRunOutputs` (a succeeded run's outputs) and `ListWorkflowAttemptsByExecutor` go with it. A partial legacy database without `workflow_runs` skips it. See [Workflows](workflows.md) § Calling a workflow.
- Migration 155 adds the index `idx_workflow_runs_name` on `workflow_runs(workflow_name, created_at DESC)`, for the Workflows page's newest run of each workflow (`LatestWorkflowRuns`) and its runs since a time (`WorkflowRunsSince`). A partial legacy database without `workflow_runs` skips it. See [Workflows](workflows.md) § Tags and the Workflows list.
- Migration 135 replaces `workflow_step_runs` with `workflow_steps`, a run's step tree keyed by `(run_id, path)` with `parent_path`, `step_id`, `pass` and `step_order` (unique per `(run_id, parent_path)`). It adds `advance_due`/`advance_claimed_at` (host-side advance), `loop_state_json`, and the wait record (`wait_signals`, `wait_task_id`, `wait_slot`, `wait_execution_id`, `wait_watermark`, `wait_session_id`, `deadline_at`, `child_run_id`: filled by LEG-485's agent waits and timeouts and LEG-489's child runs). Attempts and artifacts are rebuilt with `path` (FK `(run_id, path)`) beside `step_id`. Existing rows move with `path = step_id`, so a v1 run in flight and its agents carry on; attempts and artifacts with no step row (possible only in legacy databases without foreign keys) are dropped. `workflow_runs` gains `parent_run_id`, `parent_step_path`, `outputs_json` and `schema_version` (default 1). A partial legacy database without all four workflow tables skips it (`store.go`). See [Workflows](workflows.md) § Schema version 2 and the step tree. A loop step's `loop_state_json` (LEG-490, no migration) is its state, a JSON `workflowengine.LoopState`: `started`, an `over:` loop's `items` read once and its `cursor`, the `seen` keys, the `passes` (index, item, key, open, result) and `ended_by`. The loop writes it with a compare-and-set on the text it read (`AdvanceWorkflowLoop`, `EndWorkflowLoop`, `SetWorkflowLoopState`), so two hosts never both move a loop on. A pass's steps are made when it starts, with `parent_path` `<loop>/<pass>` and `pass`; a `next:` loop's query is made first, at step order -1. A loop step's attempts have executor type `loop`.
- `task_notes` stores durable Markdown notes independently of task descriptions (`id`, `task_id`, `body`, `source`, optional remote ID, timestamp). Workflow `task.note` records notes locally for every task, including Jira-backed targets, without publishing Jira comments.
- Migration 049 owns Learn persistence: `learning_evidence` and support/counter links, revisioned `learnings`, reflection requests, replay-safe curation generations, incorporation/verification records, prompt audit manifests, and FTS5 claim/rationale/evidence indexes. Full terminal/JSONL transcripts are not stored. See [Legato Learn](learning.md).
- `state_intervals` table: tracks working/waiting time spans per task_id. After migration 021, `task_id` has no FK and accepts both task IDs (from `tasks`) and swarm sub-task IDs (from `swarm_subtasks`). `Store.DeleteTask` manually cleans up state_intervals for the task and any swarm sub-task children since the FK cascade was removed.
- Migrations: `001_init.sql` through `048_workflow_trigger_definition.sql` cover core tasks, sync, agents, workspaces, swarms, review tours, plans, workflows, attention, Chimera discovery, metadata, code context, and triggers. `049_learning.sql`, `050_learning_proposal_target_revision.sql`, and `051_learning_prompt_activation.sql` own the learning ledger and its revision/activation additions.

## Task metadata and workflow automation

Tasks store local arbitrary JSON metadata in `tasks.metadata`. This is separate from provider-owned `remote_meta`; provider upserts preserve local metadata. Dotted-path updates are transactional so unrelated keys are retained.

Explicit local column moves atomically persist a `task_transitions` snapshot. Matching workflow definitions create `workflow_trigger_requests` with a definition digest and full definition snapshot. `(transition_id, workflow_name, definition_digest)` is unique, and `workflow_runs.trigger_request_id` is unique when present, preventing replay from launching duplicate runs. Requests remain durable in `pending`, `waiting_input`, `waiting_confirmation`, `starting`, `started`, `skipped`, or `failed` state. `starting` is an atomic confirmation claim that prevents duplicate workflow launches.

Migrations 044-046 add task metadata, transition/request persistence, and the workflow-run trigger link. Migration 047 adds `code_context`, backfills repository identity from legacy `pr_meta`, and pins existing numbered PR links. Migration 048 repairs early migration-045 databases by adding the missing workflow-trigger definition snapshot column. Migration 058 extends the trigger status constraint for explicit confirmation.

Migration 152 adds `workflow_step_effects`: what a step instance made outside Legato, such as a `ticket.create` step's ticket and a `ticket.comment` step's comment (LEG-640). It is keyed by `(run_id, path, effect)`, since a retry is a new attempt of the same path, and cascades with its run. `state` is `pending` (an attempt began and did not learn the outcome) or `done`. `target` is the project or ticket, `summary` the title a pending create looks for, and `key`, `remote_id` and `url` what was made. The times are RFC 3339 text. See [Workflows](workflows.md).

### Agent UI items

Migration 063 adds `agent_ui_items` and `agent_ui_item_revisions`: what agents asked Legato to show through `legato mcp serve`. See [Agent tools](agent-mcp.md).

The files themselves are not in the database: they are under `<data_dir>/agent-ui-images/<task-id>/`, kept and removed by `AgentUIService`. See [Agent tools](agent-mcp.md) § Image files.

### Credentials

Migration 070 adds `secrets` (Legato's own store: values sealed under a master key kept outside the database), `credential_grants` (what an execution may do with a credential, until an expiry, a number of uses or its end) and `credential_audit` (append-only and hash-chained; the time is TEXT because it is part of the hash). See [Credentials](credentials.md).

Migration 118 adds the LEG-199 OAuth transaction foundation, not yet wired into Settings or agent tools: `oauth_connections` keeps a connection generation, active attempt and refresh lease (`refresh_holder`, `refresh_lease_until`); `oauth_attempts` keeps hashed operator/state/receiver bindings, the requested scope, the web receiver's owning process and lease, initiating instance, expiry and exchange/confirmation state. Exchange claims and activation are conditional database transitions shared across processes. Activation requires confirmation and supersedes competing attempts; disconnect advances the generation before credentials are removed. Verifiers, client secrets and tokens belong in the existing sealed `secrets` store, not these transaction rows.

Migration 119 adds `mcp_connections` (LEG-203's registry of upstream MCP servers: name, url, issuer, auth, enabled, instance_id, revision, last contact/error code; no credentials) `mcp_tools` (each connection's last tool definition hashes, so a changed tool ends its grants across processes) and `mcp_connection_revisions`, the per-name revision counter that outlives removal so a revision is never reused. It also holds a connection's pre-registered client (`static_client_id`, `static_redirect_uri`, `static_secret_set`; the secret is sealed) and `oauth_client_registrations` (dynamic registrations, unique by issuer, resource and exact redirect; a confidential client's secret is sealed under its ID). `UpdateMCPConnection` (where changing the pre-registered client also invalidates the authorization) and `DeleteMCPConnection` fence OAuth attempts in their own transaction; `BeginOAuthAttempt` with `ConnectionRevision` requires that revision, enabled and `oauth`.

Migration 120 adds a connection's `kind` (`http`, the default, or `stdio`) and a local server's `command`, `args_json` (a JSON list), `dir` and `env_json` (a JSON object) to `mcp_connections` (LEG-223). `UpdateMCPConnection` treats a change to any of them as a change of resource: the connection's tool hashes are forgotten. See [Integrations](integrations.md) § Local (stdio) MCP servers.

Migration 071 adds `credential_placeholders` (the SHA-256 of each placeholder key the `http-proxy` channel gave an execution, with its credential; a placeholder resolves only while its execution runs) and `credential_meter_totals` (each amount a channel measured, by credential and meter, for the limits of rules; the time is TEXT like the audit log's).

### Agent slots

Migrations 090 to 093 kept a worker's review passes until the loop record replaced them (§ Loop record: migration 148 converted these tables and 149 dropped them; the functions named here read and write the record) (see [Integrations](integrations.md) § Review passes): `handoff_reviews` (one loop per card: settings, phase, pass, mismatches, reason, `delivered_pass`, the comment poll's `polled_at`, `last_new_at` and `skipped_comments`, and from 093 the check poll's `checks_polled_at`, `checks_heads` and `checks_pending`), `handoff_review_passes`, `handoff_review_prs` (each pass's pinned pull requests; from 127 the `event` of its review: `APPROVE`, `COMMENT`, or `kept` for an earlier approval that stands; from 138 `local_branch`, the branch of a run's reviewer clone it was put on, and `head_repo`, the repository of its head branch), `handoff_review_findings`, `handoff_review_items` (the author's feedback: findings, comments and checks, with answers, versions, `posted`, `closed` and `delivered`; findings and items are keyed by `(task_id, id)` since 144, so each is its loop's; from 145 `answer_marker`, set anew with each answer, which names the answer on GitHub) and `handoff_review_poll_pages` (each polled page's ETag and body). `DeleteHandoffReview` forgets all of a card's. Each change to a pass and its loop is one transaction (LEG-567): `StartHandoffReviewPass` (the pass, its pinned pull requests and the loop that now names it), `UpdateHandoffReviewPassWithLoop` (a pass unable and its loop stuck), `SubmitHandoffReviewPass` (the pass's findings, its rulings and its state), `FinishHandoffReviewPass` (the items a posted pass raises, the pass and its loop), `DiscardHandoffReviewPass` (the pass set aside, its findings and rulings undone, and the loop's count stepped back), `EndHandoffReview` and `HoldHandoffReviewForRetry` (a failed workflow step's loop kept for Retry; see [Workflows](workflows.md)). `TestAPassAndItsLoopAreWrittenTogetherOrNotAtAll` aborts each loop write (on `review_loops` now) with a trigger after the pass's write and finds neither.

Migration 089 makes the agent slot a store key. `agent_sessions.slot` (default `main`; existing rows are `main`) is the task's slot the session runs in. `task_native_sessions` is rebuilt keyed by `(task_id, slot, agent_kind)`, with `chimera` among its kinds: Chimera's selector moves into it from `tasks.chimera_session_id`, which is dropped (a Chimera record has no directory or owner, so `cwd`, `agent_session_id` and `execution_id` default to empty). `RecordTaskNativeSession` keeps its signature and saves into the slot of the session saving it, whose ownership is checked against the newest session of that slot only.

Every query that addresses a task's agent without a slot means the main slot: `GetAgentSessionByTaskID`, `UpdateAgentSessionStatus`, `UpdateAgentActivity`, `DeleteDeadAgentSessions`, `LatestAgentSessionForTask`, `GetTaskNativeSession`, `ListTaskNativeSessions`, `TaskChimeraSessionID` and `SetTaskChimeraSessionID`. Their `…InSlot` forms name a slot. Inside a session, `GetRunningAgentSession(task, execution)` finds the caller's own session in whichever slot (the main slot's with no execution), and `UpdateAgentActivityForSession` writes to it. `ListTaskAgentSessions` lists a task's running sessions, the main slot's first. `ListRunningExecutionPeers` returns each peer's slot and `read_only`. Executions keep `task_id`, so a slot's active time counts toward its task. A database built in part (a migration test's) runs only the statements whose tables and columns it has. See `internal/service/agent_slot.go` and `GLOSSARY.md` § Agents on a task.

### Loop record

Migration 146 adds the loop record (LEG-578, spec LEG-559 § Loop record schema and claims): the review loop engine's own record of each review loop, which replaced `handoff_review*` and the `legato.review_loop` task metadata. Migration 148 converts the old rows into it (§ The conversion below) and migration 149 drops them (§ Dropping the old tables). The review engine (its tick, passes, posts, feedback and polls), the `github.pr.review_passes` step, the handoff caller and every reader of the loop record (related agents, the agent graph's `review_loop` links, the Attention producers, Done gating and the review block a main reads) read and write only the record, through the engine's view (§ The engine's view below). The review tours table `review_passes` is never used for loops. `internal/engine/store/review_loops.go` owns it.

- `review_loops`: one row per loop, ID `rl-` and 12 hex characters (`NewReviewLoopID`). The owner (`owner_kind` `run` with `run_id`, `step_path`, `attempt_id`; or `handoff` with `handoff_id` and its `main_instance_id`), the handoff binding's `handoff_columns` (JSON), `host_task` (the run's task, which holds the reviewer slot and the clone; cascades on delete), `repo`, the subject (`subject_pr`, `scope`), `agent_author`, `author_task`, `linked_task`, `state` (`open`, `closed`), `phase`, `outcome`, `reason`; the settings (`passes_off`, a handoff whose main turned its review passes off; `max_passes`, `max_reentries`, `ready`, `steward`, `reviewer`, `reviewer_model`, `reviewer_tier`, `skill`, `skill_managed`); the counters (`pass`, `window_start`, `reentries`, `passes_since_approval`, `pass_deaths`, `not_converging`, `mismatches`, `delivered_pass`, `last_wake` and `last_wake_at`); `held`, `idle_deadline`, `confirmed_at`, `clean_pass`, `confirm_clean`; today's nudge, seen-head, `replies` (JSON) and poll columns; `marker_key`, `clone_id`, `clone_dir`, `queued_at`, and `rev`, the compare-and-swap counter. A partial unique index allows one open agent-authored loop per `author_task`, another one open loop per workflow run.
- `review_loop_prs`: the layers in stack order (`position`): branch, base, title, URL, head repository, `state` (`open`, `closed`, `merged`), `draft`, `mergeable`, `approval_dismissed` (migration 157: a person dismissed legato-reviews' approval at `clean_head` with no push since; the steward's watch writes it with `state`, `draft` and `mergeable` (`SetReviewLoopPRStatus`), so every process on the data folder reads the same Attention and run page), the GitHub author and `author_association`, `author_task`, `pinned_head` (the last pinned), `clean_head` (confirmed clean), the latest review's ID and URL, `claimed_at`, and `local_branch` (the reviewer clone's branch of the layer when it is not `branch`).
- `review_loop_claims`: primary key `(repo COLLATE NOCASE, pr)` to `loop_id`, held from open to close.
- `review_loop_passes`: `(loop_id, pass)`, `pass_window`, `step_path` (Retry re-attaches by it), `state` (`reviewing`, `submitted`, `posting`, `posted`, `discarded`, `unable`), verdict, summary, reason, execution, checkout, `pins` (JSON: each pull request's head, title, body, branch, local branch, head repository, review ID and URL, and `event`), `submission_digest`, `posting_started_at`, `attempts` (post tries whose outcome was unknown), `attempt` (how many times the pass's number was pinned before, LEG-560). A partial unique index allows one pass in flight (`reviewing`, `submitted`, `posting`) per loop.
- `review_loop_findings`, `review_loop_items` and `review_loop_poll_pages` are keyed by loop: `(loop_id, id)`, and `(loop_id, pr, list, page)`. Findings carry `critical` beside today's columns; items take the kinds `blocking`, `nit`, `comment`, `check`, `mergeability` and `merged`, and an `answer_marker`.

Operations. `OpenReviewLoop` writes the loop, its layers and their claims in one transaction, idempotent by `(run_id, step_path)`; a held pull request, an author with an open agent-authored loop and a run with an open loop are refused with a `*ReviewLoopConflictError` naming the other loop (`ErrReviewLoopActive`, `ErrAuthorLoopActive`, `ErrRunLoopActive`). `UpdateReviewLoop(id, rev, change)` is a transition: one transaction that refuses a stale `rev` (`ErrConflict`) or a closed loop (`ErrReviewLoopClosed`) before `change` runs, and writes nothing if `change` fails; within it, `ReviewLoopTx` adds and claims a layer (`AddPR`, refused naming the holder without writing), saves layers, passes, findings and items, and `StartPass` takes one of `max_concurrent` slots, counting the in-flight passes of open loops in the same transaction (`ErrReviewSlotsFull`; `takeReviewSlot`, which the engine's `StartHandoffReviewPass` runs too). `CloseReviewLoop` releases the claims, marks the loop closed with its outcome and discards a pass in flight, in one transaction; closing a closed loop changes nothing. `CheckReviewLoopOwner` is the re-check before a GitHub write (`ErrNotFound`, `ErrReviewLoopClosed`, `ErrReviewLoopNotOwned`). `ActiveReviewLoop(repo, pr)` reads the claim. Item answers, delivery, posting marks and poll pages are written outside a transition, as today's are. SQLite transactions here are immediate (`_txlock=immediate`), so a read-check-write inside one is serialized across processes.

#### The conversion

Migration 148 (`148_review_loop_conversion.sql`, pure SQL) copies every `handoff_reviews` row, with its passes, pinned pull requests, findings, items and poll pages, onto the loop record. The old tables and the metadata stay, unchanged, until migration 149 drops them; a database a backup was taken of before it (LEG-577) can go back. It reads only `handoff_review*`, `handoffs`, `tasks.metadata`, `workflow_runs` and `workflow_steps`, so a database from before 148 runs it and then 148.

- **One loop per old row**, with a new `rl-` ID, `rev` 1, `host_task` and `marker_key` the old task ID (so the markers, `<task>/pass-N/pr-M`, answer markers and pin refs already on GitHub still match). The engine's view carries it to the marker builders (`HandoffReview.MarkerKey`, `HandoffReviewPass.MarkerKey`). To find a converted loop from its task or run: `host_task` = the task, or `run_id` and `step_path` (`ReviewLoopForStep`).
- **The owner** is the run the task's `legato.review_loop` metadata names (`run_id`, `step_id` as `step_path`, `attempt_id`, the attempt that opened it, which may be an earlier attempt than a waiting Retry's), else the task's handoff (the open one, else the newest), whose card is the author (`agent_author`, `author_task` and `linked_task` the card). The metadata's `repo`, `pr` (`subject_pr`), `scope`, `linked_task`, `author_task`, `seen_head`/`seen_at`, `replies`, `confirm_clean`, `clone_id` and `dir` (`clone_dir`) land on the loop; the old `settings` JSON lands as `passes_off` (`enabled: false`), `max_passes` (0: the instance's), `reviewer` (`agent`), `reviewer_model`, `reviewer_tier`, `skill`, `skill_managed`; every other `handoff_reviews` column keeps its name. `phase` and `reason` are copied as they were (`ended`, `clean`, `waiting_for_author`, …). `created_at` is when the loop opened: its run's or handoff's creation, else its first pass.
- **Closed loops stay as history**: one in phase `ended`, a run's whose run is gone or `succeeded`, `cancelled` or `stopped` or whose step `succeeded`, `skipped` or was `cancelled`, a handoff's whose handoff is closed or gone. `outcome` is the old `reason` for `ended` (`closed`, `cancelled`, `stuck`); `approved` only for a loop that was confirmed (invariant 9): a run's, `clean`, its metadata's `confirm_clean` false, and closed by its step's success (its step `succeeded`, or no step row and the run `succeeded`), which also gets `confirmed_at` (its `closed_at`), `clean_pass` and `window_start` (its pass); else `cancelled` for a run `cancelled` or `stopped` or a step `cancelled` (a run cancelled after its clean pass posted, before Confirm read GitHub's heads, is not approved), else `ended`. The older Legato never confirmed a handoff's heads, so a handoff's clean loop converts `ended`. A failed run's loop stays open for Retry (D1). Every other loop is open; an open `clean` loop converts unconfirmed with `confirm_clean` set, so the engine's Confirm reads GitHub's heads before anything reports it approved.
- **Layers** (`review_loop_prs`): a run's from its metadata's `stack` (or its one `pr`), with each `local_branch`; a handoff's are the pull requests its latest pass pinned (none before its first pass: its first pass claims them). Each layer takes its latest pin's branch, base, title, URL, head repository, author and head (`pinned_head`; `clean_head` too for a loop that converts approved), and the latest posted review's ID and URL.
- **Claims**: among open loops, the newest on a pull request (`created_at`, the repository's case ignored) holds it. An older open loop on it converts as `stuck`, open, its `reason` naming the pull request and the loop that holds it; it keeps claims no newer loop wanted. Two open loops of one run, or two open agent-authored loops of one author, which the record's indexes forbid, leave the newer open and close the older as `stuck` naming it.
- **Passes** keep their states, with `pins` built from `handoff_review_prs` (each pin also names its `repo`), `post_attempts` as `attempts`, `attempt`, `posting_started_at`. A pass in flight (`reviewing`, `submitted`) is set aside (`discarded`, with a reason) unless it is the newest in flight of an open loop that lost no claim, so the record's one-in-flight index holds and no stuck or closed loop keeps a reviewer slot.
- **Findings, items and poll pages** are copied by loop. Answers keep `posted` and `answer_marker`: an answer posted before the upgrade is never posted again, and an unposted one is looked for by its marker before it is posted (an answer that somehow has no marker gets one). An item kind the record does not know becomes `comment`.

A legacy database built in part, without the tables the conversion reads, gets the new columns and converts nothing (`prepareMigration`).

#### Dropping the old tables

Migration 149 (`149_review_loop_old_tables.sql`, LEG-606) drops `handoff_reviews`, `handoff_review_passes`, `handoff_review_prs`, `handoff_review_findings`, `handoff_review_items` and `handoff_review_poll_pages`, and removes `legato.review_loop` from every task's metadata (a `legato` object left empty goes too, and metadata left empty is `NULL`). Nothing reads either since the engine moved onto the record. A legacy database built in part without `tasks` only loses the tables. Replayed on a database that has the record and no `handoff_reviews` (a ledger rebuilt from before 090), the migrations that made or changed the old tables (`oldReviewTableMigrations` in `store.go`) leave out their statements on them, so the tables stay gone. Only migration tests that build a store at an earlier migration (`newStoreAtMigration`, `NewBefore`) still write or read the old tables.

#### The engine's view

The review engine is keyed by task, as it was before the record: `internal/engine/store/handoff_reviews.go` keeps its API (`HandoffReview`, `GetHandoffReview`, `SaveHandoffReview`, `StartHandoffReviewPass`, `SubmitHandoffReviewPass`, `FinishHandoffReviewPass`, items, findings, poll pages and the rest) and implements it on the record, never on `handoff_review*`.

- **A task's loop** is the loop it hosts (`host_task`): its open one, else its newest (`CurrentReviewLoop`). `HandoffReview.LoopID` names it. Its settings JSON is read from and written to the settings columns (`passes_off` is `enabled: false`; none set reads as `""`, the engine's defaults); a pass's pinned pull requests are its `pins` (`ListHandoffReviewPRs`, `SetHandoffReviewPRPosted`, which also sets the layer's review ID and URL); pinning a pass sets each held layer's `pinned_head`.
- **Writes of the loop** are compare-and-swap transitions on its `rev`, the loop found in the same transaction (`reviewTransition`, `UpdateHostedReviewLoop`; a lost race is tried again on the loop as it then stands). A pass and its loop are one transition (`StartHandoffReviewPass`, which also takes the pass's reviewer slot in it: one of `max_concurrent`, counted from the in-flight passes (`reviewing`, `submitted`, `posting`) of open loops, so concurrent starts never exceed it; every slot taken is `ErrReviewSlotsFull` and writes nothing. `ReviewPassesInFlight` is the same count, read outside a transaction; `UpdateHandoffReviewPassWithLoop`, `FinishHandoffReviewPass`, `DiscardHandoffReviewPass`, `HoldHandoffReviewForRetry`, `EndHandoffReview`). A closed loop refuses them (`ErrReviewLoopClosed`; `EndHandoffReview` and `HoldHandoffReviewForRetry` change nothing). Writes of a loop's passes, findings and items alone leave the loop row as it is.
- **A run's loop** is opened by its step's attempt with `OpenReviewLoop` (the service's `openReviewRun`): owner `run`, its layers (each with the reviewer clone's `local_branch`) claimed, `marker_key` the loop's own ID (`OpenReviewLoop`'s default), so a later step's loop on the same run task never shares its markers: the second would find the first's review on GitHub by its marker and take it for its own. Pin refs keep the task ID (`refs/legato/review/<task>/<pass>/<pr>`): they are in the reviewer's clone, read only by the loop's own later passes. What the run caller kept in `legato.review_loop` is on the loop (`readReviewRun`, `saveReviewRun`). `CloseHostedReviewLoop` closes it when the step ends (approved, closed, stuck, or cancelled), releasing its claims; a failed step's loop stays open for Retry, until the run is cancelled (`CancelWorkflowRun` takes a `failed` run too) and the holder's tick closes it. The holder's tick also closes the open loop of a run that ended where the run caller never heard of it (a Cancel in a process without the engine). `ListRunReviewLoopsAuthoredBy` finds the run loops an agent authors (`reviewLoopTask`).
- **A handoff card's loop** is opened by the handoff's review-loop run's binding through the engine's `Open` (`store.HandoffRunReviewLoopOpen`: owner `run`, with `handoff_id`, `main_instance_id` and `handoff_columns`; LEG-600). A record owned by the card's handoff itself (`store.HandoffReviewLoopOpen`) is opened only by the first write for a card that hosts none (`newHostedReviewLoop`, in the write's transaction): the record that keeps a main's "review passes off" for its handoff, which nothing moves. A loop the handoff owned before LEG-600 (or that migration 148 converted) is adopted by a review-loop run (`AdoptHandoffReviewLoop`: in one compare-and-swap transaction the owner becomes the run's `open` step and the binding's columns are written; the claims, passes, findings, items and `marker_key` stay; LEG-601). Either is owned by the card's handoff (the open one, else the newest; idempotent per handoff, so another handoff of the same card gets a loop of its own once the earlier one's is closed), `author_task` and `linked_task` the card, `agent_author` 1 (as a converted handoff loop has, so one agent-authored loop per author holds alike on a new and an upgraded database: an agent-authored run by the card is refused while the handoff's loop is open), `marker_key` its own ID, with no layers at first: each pass makes the pull requests it pins layers and claims them in its transaction (`holdReviewLoopLayer`; another loop's claim is a `*ReviewLoopConflictError`, which makes the loop stuck). A handoff loop that is approved (phase `clean`, confirmed: `confirm_clean` cleared, `confirmed_at` set and `clean_pass` its pass), `skipped` or `ended` holds no claims (`writeReviewLoop` releases them, `handoffLoopLetsGo`; a later pass claims them again). A clean pass Confirm has yet to confirm keeps them, so `ActiveReviewLoop` still finds the loop that `heldLoopOn` counts as active. When the card's agent already authors a run's open loop, the handoff's loop is opened with `agent_author` 0 (`ReviewLoopOpen.YieldAuthor`), so the handoff reviews as it did before the record. The handoff caller's sweep in each tick of the engine (`sweepLoops`) closes the open record a handoff owns once the handoff has closed or is gone (`CloseReviewLoop`, outcome `ended`, phase kept), freeing its claims, and cancels the run of a run-owned one, whose end closes it. See [Integrations](integrations.md) § Review passes › Opening and closing a loop.
- **Confirming a clean pass** (LEG-582): the view carries `confirm_clean` (written with the phase: every write of `clean` sets it) and reads `confirmed_at`, `clean_pass` and whether the loop is closed. `ConfirmReviewLoop(ctx, loopID, pass, heads, at)` is the engine's Confirm's one transition: the loop open, `clean` and at `pass` (else `ErrReviewLoopClosed`, `ErrReviewLoopNotClean`), it sets `confirmed_at`, `clean_pass` and `window_start` to the pass, clears `confirm_clean`, and sets each confirmed layer's `clean_head`. The run caller no longer writes `confirm_clean` (`saveReviewRun`). See [Integrations](integrations.md) § Review passes › The engine's operations.
- **The write check** (`CheckHandoffReviewWrite`, `CheckReviewLoopWrite`) is one read-only transaction: the loop open and not `ended`, the pass (when not 0) `submitted` or `posting`, the owner the loop's (`ReviewLoopOwner`, as `CheckReviewLoopOwner` checks it; a run owner names its attempt, a handoff owner its main instance) and still live (its attempt waiting in a running run, or its handoff open here and not returning).
- `NewBefore(path, migration)` opens a database at the schema before a migration, for tests of an upgrade; the harness's `WorkerOptions.Database` starts a worker on one (`TestARunLoopConvertedMidReviewFinishesOnTheLoopRecord`). `TestAHandoffLoopAndARunLoopMidReviewFinishOnTheLoopRecordAfterTheUpgrade` (`internal/handofftest/review_upgrade_test.go`) takes a worker with a handoff's loop after pass 1 back to the schema before 148 (`asOlderLegato`: every shared table's rows, the handoff's loop written into `handoff_review*` through the view's types, and a run's loop seeded on top), restarts it, and finishes both loops with each pass posted once.

### Agent stages

Migration 130 adds `agent_stages`, one row for each agent place: keyed `(task_id, slot, place_execution_id)`, where `place_execution_id` is a workflow agent's execution and empty for every other place. ### Session history

Migration 131 adds the session history: every provider conversation an agent reported, with each execution it was live in. `task_native_sessions` stays what a slot resumes by default; these rows outlive it, the agent session and the task (`GLOSSARY.md` § Session history).

- `agent_conversations`: one row per conversation, unique on `(agent_kind, storage_dir, provider_session_id)`. `task_id` and `slot` have no foreign key, so deleting a task leaves its conversations. `task_title` is the newest title seen when the conversation was recorded; `ephemeral` and `reeve` are the task's at that time; `cwd`, and `repo`/`branch` of the live job clone at that path. `source` is `recorded` (an agent reported it) or `recovered` (found by folder and time). `first_message` and `last_message` (with `last_message_at`) are the conversation's first operator message and newest assistant message, clipped (below); `transcript_path`, `transcript_state` (`present`, `missing`, `unknown`) and `transcript_checked_at` are where the conversation's transcript was found and when (`RecordTranscriptCheck`, which also fills `first_message` and `last_message` when they are empty, and the FTS row). `SessionHistoryService.checkTranscript` looks again when an entry is listed or shown and the last look is over an hour old, never for a running one (its tool may not have written it yet); a Chimera entry stays `unknown`. A `missing` transcript makes an entry not restorable, offering a fresh start. `GET /api/sessions/{id}` adds `transcript_path` and `preview` (the newest 10 messages, cleaned) when it is present. The readers are `internal/engine/transcript` (see [Claude Code native integration](claude-code-native.md) and [Codex native integration](codex-native.md)). `first_seen_at` and `last_seen_at`, which is moved on every record and when a run ends.
- `agent_conversation_runs`: `(conversation_id, execution_id)` primary key, cascading from the conversation; `started_at` (when the conversation was first reported in that execution), `ended_at`, and `end_reason`, NULL while the run is live: `exited` (its pane went while Legato ran), `stopped` (the operator, or the task's delete or archive), `lost` (`ReconcileLostExecutions`, or an execution ended `lost` with no reason given), `interrupted` (the startup sweep), `dismissed` (an interrupted run whose agent was dismissed), `replaced` (the execution went on in another conversation of the same tool: `/clear`, `/resume`, `/background`).
- `agent_conversations_fts`: FTS5 over `task_title`, `task_id`, `cwd`, `repo`, `branch`, `first_message`, `last_message`, with `conversation_id` unindexed. It is written in Go in the transaction of its row (`writeConversationFTS`), as `learnings_fts` is.

`RecordTaskNativeSession` and `SetChimeraResumeInSlot` record the conversation and its run in their own transaction (`recordConversation`): the entry upserted, any other conversation of the same tool still live in that execution ended `replaced`, and the run opened, or opened again when the execution comes back to a conversation it left. A legacy Chimera selector's run is the slot's live execution, when there is one. `TerminalizeExecution` ends an execution's live runs for its status (`cancelled` is `stopped`, `lost` is `lost`, else `exited`); `TerminalizeExecutionEndingRuns` takes the reason, which the agent service passes through the context of `EndExecution` (`withRunEndReason`: `exited` for a gone pane, `interrupted` from the sweep). `DismissConversationRuns` turns an execution's `interrupted` runs into `dismissed`. `ListTaskConversations`, `ListConversationRuns` and `MatchAgentConversations` (an FTS5 expression, best first) read them.

**Text.** `service.ConversationTextCapture` (`internal/service/conversation_text.go`) reads a native agent's conversation when a turn ends: on `EventAgentActivityChanged` to anything but `working`, at most once per 5 seconds per task (later turn ends inside the wait share its read), in whichever process serves the broker (`captureConversationText`, `cmd/legato/session_history_runtime.go`, in the TUI and `legato serve`). It reads the same endpoint as `ConversationTail`, whose `FirstUser` is the first user turn that is the operator's (`IsOperatorText`: no `[legato …]` tag), else the first user turn, and takes the newest assistant entry of the last 40. Both are cleaned (`cleanConversationText`: escape sequences and control characters out, 2,000 characters at most). `RecordConversationText(execution, first, last, at)` writes them to the conversations live in that execution with their FTS rows: `first_message` is set once, except that a tagged one gives way to the first untagged one seen; an empty value changes nothing. An agent with no endpoint (legacy hooks, `native_off`) records nothing. No read is tried when a run ends, since the agent's endpoint is gone by then; the last turn end has already read the last message.

`SweepAgentConversations(before)` removes the conversations last seen before a time, with their runs and FTS rows, except those with a live or `interrupted` run; `agents.history.keep` decides the time ([Configuration](config.md)).

Migration 132 adds `agent_conversation_runs.sandboxed`: whether the run's agent ran in Legato's sandbox, copied from its agent session when the run opens (NULL when not known), since that session's row is deleted on the slot's next spawn. `ListAgentConversations(ConversationFilter)` lists `AgentConversationRow`s (the conversation with `run_count`, `live`, `last_end_reason`, `task_exists`, `task_archived`, and the task's own title while it exists) filtered by tool, task, repository, last-seen range and state (`running`: a live run; `interrupted`: its latest run was; `ended`), by an FTS5 `Match` ranked by bm25, else the most recently seen first, with `Limit` and `Offset`. `GetAgentConversation` reads one. `ForgetAgentConversation` removes one with its runs and FTS row, `ErrConflict` for one running or interrupted.

Migration 133 adds `agent_conversations.workspace_id`: the task's workspace when the conversation was last recorded (filled from `tasks` for the rows already there), so a conversation restored into a new task lands in its workspace even once its task is gone. `MoveAgentConversation(id, task, slot)` gives a conversation to another task's slot (with its FTS row), as that restore does before the new task's agent starts, and back when the start fails.

**Recovery.** Migration 134 adds `agent_conversation_scans` (`execution_id`, `scanned_at`): the runs recovery has looked at. `SessionHistoryService.Recover` (`internal/service/session_recovery.go`) takes up to 200 ended `interactive` and `swarm_conductor` executions of Claude Code or Codex with a folder, no run in the history and no scan (`ListUnrecordedExecutions`, those started within `agents.history.keep`, else 180 days), and for each scans its tool's transcripts (`transcript.Reader.Scan`) in the default storage folder and every `storage_dir` the history has seen (`ConversationStorageDirs`) for those whose folder is the run's and whose first line is from a minute before it began to its end. `RecordRecoveredConversation` keeps each as `source = recovered` (the task the execution was for, slot `main`, the task's title, else the execution's `task_title`; `transcript_state = present`) with a run on that execution ended as it ended, and gives an already recovered one the run too (two agents in one folder at once both get both); a conversation already recorded, by any storage folder, is left alone. Then the execution is marked scanned (`MarkExecutionScanned`), so it is read once. A pass is bounded to 30 seconds. `StartRecovery` runs one off the start, and again after each `EventAgentDied`, in whichever process serves the broker (`recoverSessionHistory`, `cmd/legato/session_history_runtime.go`). A recovered conversation restores as any other.

The migration backfills one conversation for each `task_native_sessions` row, its execution as its run, ended as that execution ended (`interrupted` when its agent session is). A database built in part (a migration test's) skips the backfill.

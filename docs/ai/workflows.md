## Workflows: internals

The user guide, with the YAML schema, executors, templates, triggers and CLI, is [Workflows](../../site/src/content/docs/using/workflows.md) (on the site at `/legato/using/workflows/`). This file keeps what an agent working on Legato's code needs beyond it. Parsing and discovery are in `internal/engine/workflow/`; runs, executors and triggers in `WorkflowService` (`internal/service/`); see [Packages](packages.md). The web pages are in [Web UI](web-ui.md) § Workflows; the CLI in [CLI](cli.md).

### Runs and tasks

- A run creates one local execution task in the reserved **Workflows** workspace (`ViewAll` excludes it; `ViewWorkspace(id)` opts in). A succeeded run moves it to **Done** and archives it at once.
- A `task` input's selected task is stored on the run as `related_task_id`. Agent sessions use the execution task, so an existing task's active agent session is not replaced, except for an `agent.run` step with `with.task`, whose agent is that task's own (below). `GET /api/tasks/{id}/activity` lists related runs and their managed artifacts.
- Deterministic steps execute synchronously until an agent step starts; the run then advances when that agent completes or fails its step through the CLI callback (§ Agent completion).

### The run-ended hook

One subscription hears every run end, whatever its terminal status: `succeeded`, `failed`, `cancelled` or `stopped` (spec LEG-559 B3; LEG-581, built for LEG-489's parent reconcile, which reuses it: § Calling a workflow; `workflow_run_ended.go`). `WorkflowRunTerminal` says which statuses are ends; only a `failed` run runs again (Retry).

- **Subscribing.** `WorkflowService.OnRunEnded(listener)` takes a `WorkflowRunEndedListener`: `RunEnded(ctx, WorkflowRunEnd)` (run, status, error, task, and `ParentRunID`/`ParentStepPath` for a child run; `Gone` for a run that no longer exists, with no status) and `RunsHeld(ctx)`, the runs the listener still waits on.
- **At once.** `changed(ctx, run, step, kind)` (`workflow_events.go`) is the one place the service writes a run's state from. After a kind that can end a run (`step_completed`, `step_failed`, `step_skipped`, `run_cancelled`, `run_stopped`) it reads the run, and when it has ended tells every listener (`tellIfEnded`). This covers every end the service makes: the last step completing (in `advance`, `Complete` or `CompleteWaiting`), `Fail`, `FailWaiting`, a step whose executor errors, `Cancel` and `Stop`. A run whose last step an agent completed has not ended for the hook (nor for `keepRunOutputs`) until a host has filled that step's outputs (`outputsUnfilled`: a step `succeeded`, advance due, with wait signals and no `signal` output yet); `processAdvance` keeps the outputs and tells the listeners once `fillRecordedOutputs` has, so neither the run's outputs nor a parent's `workflow.run` step read the step before.
- **The sweep.** `SweepEndedRuns` asks each listener for `RunsHeld` and tells it of each one that has ended or is gone. `StartAdvanceLoop` runs it at its start (runs that ended while no host ran, or while Legato was down), on every `EventWorkflowChanged` except its own `advanced` (an end another process made, which reaches serve and the TUI by IPC, or the agent service's direct `store.FailWorkflowStep` when an agent exits or never binds), and every `advanceReconcileInterval`. Listeners live in the process that subscribed, so an end in a process without them (the CLI, a TUI without the review engine) is told by a host's sweep.
- **At least once.** A run a listener still holds is told again at each sweep (a failed run's review loop stays held until Retry, Cancel or End), so `RunEnded` must be idempotent and cheap to repeat.
- **Stop.** `WorkflowService.Stop(ctx, run, reason)` ends a running run as `stopped` (`WorkflowRunStopped`), as `Cancel` ends one `cancelled`: each step under way is cancelled through its executor, then `store.StopWorkflowRun` (one transaction with `CancelWorkflowRun`'s shape, `endWorkflowRun`) cancels its unfinished steps and attempts. It is the run end a gate's Stop makes, and Stop on a step paused after a failure (§ Expressions, if:, on_failure and the gate); the web UI's run page and Attention offer it there, and nothing offers it on a run otherwise.
- **The review run caller** is a listener (`ReviewRunCaller.SetWorkflows` subscribes it): a run that ends `succeeded`, `cancelled` or `stopped`, or is gone, closes the open loops it owns; a `failed` run keeps its loop open and claimed (D1). See [Integrations](integrations.md) § Review passes › Opening and closing a loop.

### Schema version 2 and the step tree

Spec LEG-482; LEG-483 is its first slice. `Parse` accepts `schema_version` 1 and 2 (`SchemaVersion`, `SchemaVersion2`). `Step.Start` (`StartAutomatic`, `StartManual`, and `StartAgentEnded`, internal: only a v1 `trigger: agent_ended` reads as it) is the one model of how a step starts. A v1 file says `trigger:` (`normalizeStart` reads it into `Start` and clears `Trigger`). A v2 file says `start:`, and each version refuses the other's key. The `start` refusal only applies to a file just decoded (`Definition.fromFile`), so validating a parsed definition again is harmless. `Definition.MarshalYAML` writes each version's own key. `Step.UnmarshalJSON` reads a run's stored definition: one kept before this change says `trigger`, which reads as `start`, so `definition_changed` and `waitsForAgentToEnd` see old runs correctly. JSON writes `start` only. The web UI reads `start ?? trigger` from step rows' `definition_json` (`stepStart`, `runNeedsYou.ts`, `WorkflowRunPage.tsx`). Graph version 2 names it `start` too (§ Workflow graph). `readableOutputs` makes a step's catalog outputs readable by later steps without declaring them (both versions). Struct fields tagged `legato:"v2"` are in version 2's JSON Schema only, and `legato:"v1"` (`Step.Trigger`) in version 1's (§ JSON Schema). `LatestSchemaVersion` (2) is the version Legato writes: the bundled templates, a new workflow, drafts and `Upgrade` (§ Upgrading to version 2).

Runs keep their steps in `workflow_steps` (migration 135), keyed by `(run_id, path)`. `workflowengine.StepPath`/`SplitStepPath` define the path: a top-level step's ID, or `<scope path>/<id>` for a loop pass's step (`each/2/build`, LEG-490). Each row has `parent_path`, `step_id`, `pass` (NULL outside loops) and `step_order`, unique per scope. `store.WorkflowStep` (was `WorkflowStepRun`) keeps the JSON names the web UI reads (`step_id`, `resolved_inputs_json` from column `resolved_json`) and adds `path`, `parent_path` and `pass`. A run creates its top-level instances at start (`stepInstances`); `CreateWorkflowSteps` adds a nested scope's when the run reaches it (idempotent). `GetWorkflowRun` lists steps by scope, the run's own first. The runs list's step summaries are top-level only. Attempts and artifacts carry `path` (FK to the step) besides `step_id`. Every service method that takes a step ID takes its path: `current_step_id`, `ResolvedWorkflowStep.StepID`, `LEGATO_WORKFLOW_STEP_ID`, `Details` keys and attention source keys are paths. `workflow_runs` gains `parent_run_id`, `parent_step_path`, `outputs_json` and `schema_version` (the definition's); migration 154 adds `parent_attempt` (LEG-489, § Calling a workflow). `child_run_id` names a `workflow.run` step's child. `loop_state_json` is a loop's state (LEG-490, § Loops).
- A step whose executor returns `WorkflowStepWaiting` (`"waiting"`, `workflow_waiting.go`) waits on that executor's own service. The step and its attempt are `waiting` (the run stays `running`; a run that is `waiting` is one at a manual gate) and carry no agent session, so `endGoneSession` does not fail them and a restart leaves them as they are. The service finishes the step with `WorkflowService.CompleteWaiting` (its outputs as a deterministic executor returns them, then the steps after it run) or `FailWaiting`, and finds its steps again after a restart with `WaitingAttempts(executorType)`. `Cancel` calls the executor's `Cancel` for a waiting attempt, as for a running one. Such a step's service may act on an outside service: the one exception to schema v1's rule against outside publishers is `github.pr.review_passes` (LEG-253), whose loop posts to GitHub; see [Integrations](integrations.md) § Review loops on any pull request. Its outputs are `outcome`, `passes`, `findings`, `reviews` (each `{pass, pr, url, event, approved}`, with `approval_withheld` and `withheld_reason` on a clean pass's outside-author `COMMENT`), `approval_withheld` (an `approved` loop that commented on an outsider's pull request instead of approving it), `summary_path` and `linked_task`. Its `Start` only writes the step, in any process; the review engine's tick in the process that serves the broker opens the loop or fails the step (spec LEG-559 D9), so a process without the engine that advances a run to it, as the TUI's `StartAdvanceLoop` may for a `serve`-started run, leaves it waiting for the holder.
- **Retry of a failed `github.pr.review_passes` step resumes its loop** (LEG-567, spec LEG-559 D1). `WorkflowService.Fail` calls an executor's `FailStep` in place of `Cancel` when it is a `WorkflowStepFailer`; the review step's (`ReviewRunCaller.FailStep`) keeps the loop: the reviewer stops, `store.HoldHandoffReviewForRetry` discards a pass in flight (reviewing or submitted) and steps the pass count back over it in one transaction, a loop that held or waited for a reviewer is `ready`, and every other phase, pass, finding, ruling and item stays; the clone is removed. Retry starts a new attempt, which waits to open as any start does. When the holder's tick opens it, `open` finds the loop an earlier attempt of the same run and step path opened (`earlierLoop`: the open run loop the task hosts names the run and step, and another attempt) and adopts it (`adopt`) instead of beginning at pass 0: it refuses as `open` does a pull request another loop now holds, an author already authoring one, or a pull request no longer open; holds the loop as above (also when the failure did not go through the executor, as `FailWaiting`'s does not; a loop a cancel ended goes back to `waiting_for_author` after a pass that asked for changes, else `ready`); makes a fresh clone; and last writes the record with the new attempt ID, so a crash before it leaves the step waiting to open and the next tick adopts again. The next pass takes the number after the last that counted: a pass set aside is pinned again under its own number (`InsertHandoffReviewPass`), never as a second pass 1. A failed run keeps its loop and the loop's claims, so the operator gives it up with Cancel: `store.CancelWorkflowRun` cancels a `failed` run as it does one not ended (the failed step keeps its error), `ReviewRunCaller.runEnded` then sees `cancelled`, and the holder's tick closes the loop (outcome `cancelled`), releasing its claims. The run page offers **Cancel run** on a failed run too.
- Embedded examples (`internal/engine/workflow/examples/*.workflow.yaml`, `workflow.Examples`, `ExampleNamed`) are definitions Legato ships for people to add; `TestEveryEmbeddedExampleValidates` parses each. Every one but `review-pr-passes` is schema version 2 and matches its schema (`TestTheBundledExamplesAreVersion2`): `review-pr-passes` stays version 1 for LEG-599 to withdraw, so no release ships a v2 copy built on the deprecated inline review step. An optional input a step references as a field's whole value is left out of `with` when not given; within longer text it fails the step unless the expression gives a fallback with `??`.
- `WorkflowService.Show` fills `WorkflowRunView.Details` (by step ID) from each step's latest attempt whose executor is a `WorkflowStepDetailer`; the review step's is `ReviewRunDetails` (phase, pass, a summary line, blocking open, reason, every review posted). A run's loop publishes `EventWorkflowChanged` with kind `review_loop` (`service.ReviewLoopChangedKind`), which `Server.StartWorkflowEvents` forwards as `workflow_changed` like every other workflow change, so an open run page follows the loop. The review-pass runtime (`reviewPassWake`) never ticks for a `review_loop` change, and ticks once `reviewPassRunGap` (2 s) after any other run change, however many come in that time.
- `NormalizeInputs` takes an empty value for an `integer` or `boolean` input as not given (its default, or required), as a form's blank field sends it.
- `task.note` takes `task` as a task input or a task ID as text; `optional: true` (a boolean, checked at validation) makes an empty task a skip (`note_id` empty, `skipped: true`) instead of a failure.
- `task.move` calls the sync service's `PushMove` in a configured provider runtime, which may queue the mapped remote transition even for a same-column no-op, so a previously failed push can recover. Success confirms local persistence and queueing, not remote completion.
- `agent.run` takes an optional `with.engram` (text, templated like the step's other fields; anything else fails validation, and a template that resolves to anything but text fails the step): the agent starts as that engram (`AgentSpawnOptions.Engram` with `EngramRequired`). An engram `engram identity list` does not list fails the step before anything starts; any other boot failure starts the agent without it, as an interactive spawn does (the warning goes to the log and Attention). A workflow never reads or writes engram bindings: its spawn does not touch `last_used_at`. Finishing a workflow agent (`FinishWorkflowAgent`) ends its engram session (`EndEngramSession`). See [Engram sessions](engram.md).
- `agent.run`, `agent.dispatch` and `agent.message` take exactly one of `with.prompt` and `with.macro` (the catalog's `ExactlyOne` constraint; both, neither or an empty macro fail validation). The executors resolve a macro when the step starts through `SetMacros` (`service.MacroService`, wired in `cmd/legato/workflow_runtime.go`; `workflow_macro.go`): an unknown one fails the step (`macro "x": no macro of that name`). `agent.run` uses the macro's text as the assignment; `agent.dispatch`, `agent.message` and `agent.run` with `on: <task>` or `task` send `MacroService.Message` (the task header, then the text). A step's own `agent`/`tier` win; with neither, the macro's apply.
- `agent.run`'s `with.name` (LEG-613) names that agent only: `WorkflowAgentRunner` passes it as `AgentSpawnOptions.Label`, kept on the execution (`executions.label`, migration 139), and `ListAgents` shows it as the agent's title. It no longer renames the run's task, which keeps the run's title. Without `run_title`, `WorkflowService.start` names a run with a `task` input `<title> · <card key>` (`cardKey`: the ticket's `remote_id`, else the task ID). An agent on a run's own task (a step's agent, the reviewer slot) carries `AgentSession.RunCard` (`{task_id, key, title}` of the run's `related_task_id`, joined in `agentSessionSelect`), served as `run_card` by `/api/agents` and shown as "for <key>" in the web rail; the workflows Attention producer puts "For <key>: <title>" in each item's `Detail` (`runCardDetail`, from `WorkflowRun.RelatedTaskKey`, which `WorkflowService.ListRuns` fills).
- `agent.run` with `with.task` (LEG-540; `stepAgentTask`, `workflow_agent.go`) spawns on that task instead of the run's: `LEGATO_TASK_ID`, the tmux session `legato-<task>`, slot main and the execution's attribution are the task's, and the execution stays `workflow_agent` (so Restart still refuses it). With `repo`, the clone is a card's (`legato/<task>`, `FreshBranch` in `agent.go`). A macro goes through `MacroService.Message` as `agent.dispatch`'s does. The executor returns `WorkflowExecutionResult.TaskID`, which `store.MarkWorkflowStepWaiting` writes over the attempt's `task_id`, so `Cancel`, `Prompt`, stall attention (`enrichWorkflowAttention`) and the server's activity mapping (`ActiveAgentAttemptsByTask`) find the card's agent. `WorkflowAgentRunner.TaskHasAgent` refuses a task with an agent already running. Stage places: `executionPlace(kind, attribution, task)` (`agent_stage.go`) keeps a workflow agent's stage at its execution's place only when it works on the run's own task (attribution differs from its task); a task's own agent keeps it at the card's place. Its execution is attributed to and run for its task, so it owns the card's conversation (`store.OwnsTaskConversation`, LEG-539) and its bridge saves a resume identity. The catalog refuses `task` with `working_dir`, `scratch` or `name` (`Excludes`, checked); before this change `task` on `agent.run` was an unknown key, ignored with a warning.
- `agent.run` with `task` and `slot` (LEG-618; `stepAgentSlot`) spawns in that named slot of the card (`AgentSpawnOptions.Slot`): tmux `legato-<task>_<slot>`, beside the main slot's agent. The engine checks the slot at load. `slot` is a `Literal`, checked field with `Field.Pattern` (`SlotNamePattern`) and `Field.Reserved` (`ReservedSlots`: `reviewer`), and a `Requires` constraint (`slot` needs `task`; draft-07 `dependencies` in the schema). `TestTheEngineChecksSlotsByTheAgentServicesRules` keeps the engine's copy of the rules equal to `agent_slot.go`'s. `stepAgentSlot` checks the resolved value again. `WorkflowAgentRunner.SpawnWorkflowAgent` returns the slot's session (`GetAgentSessionInSlot`), so the attempt records the slot's agent, never the main one's. `SlotHasAgent` refuses a slot that has an agent. The attempt's `task_id` is still the card. `Cancel` and `Prompt` therefore address the attempt's own agent through `AttemptAgentID`, the stall attention through `attemptAgentSession`: both use the attempt's recorded session, and fall back to the main slot only when the attempt's tmux session is not a named slot's. `FinishWorkflowAgent` was already slot-safe (session ID and tmux name) and now puts `Slot` on `EventAgentCompleted`. `StartAgentEndedLoop` still ignores a named slot's end. With `repo`, the clone request carries `Slot` and `FreshBranch` `legato/<task>-<slot>`. `RepositoryService.JobClone` always makes a named slot a new clone (a `CloneID` is refused), records `job_clones.slot`, and skips `recordCodeContext`. `LiveJobCloneForTask` joins only `slot = 'main'` clones. A review-pass run's reviewer clone is made with `Slot: SlotReviewer` too. Its reviewer still runs on the run's task; the card's reviewer slot is a follow-up.
- `agent.compact` (LEG-536; `workflow_agent_compact.go`) compacts a task's agent and waits on its own service until the agent reports the compaction's end, asking again while the agent is in its turn; see [Compacting an agent](compaction.md) § The agent.compact step.
- Where an agent lives (LEG-607, spec LEG-482 §5.1; `internal/engine/workflow/agent_place.go`, `internal/service/workflow_agent_place.go`). `agent.run`'s `with.on` is `run` (the default, `workflowengine.AgentOnRun`: an agent of the workflow, as before) or a task, or a task ID (`AgentOnTask`). `on: <task>` is a plain agent in that task's main slot: `startOnTask` spawns it through `SpawnWorkflowAgent` with no `ExecutionKind`, `WorkflowRunID` or `WorkflowAttemptID`, so it is started, sandboxed and staged as an operator's spawn is (its stage place is the card's), and it outlives the run. With `repo`, `ref`, `branch`, `engram`, `agent` and `tier` as for any `agent.run`; the catalog refuses `task`, `slot`, `working_dir`, `scratch` and `name` with it (`checkAgentStep`, at load), and `keep`/`keep_agent`, since it keeps running unless `stop: true`; `reuse` and `stop` are refused without it. A running agent in the slot fails the step (`reuse: true messages it instead`) unless `reuse: true`, which sends it the work: a prompt with the contract appended, tagged `[legato workflow]` (`WorkflowMessageTag`), or a macro untagged (the operator's words) and then the contract on its own, tagged. Either way the step waits on that session (`waiting_agent`, `WorkflowExecutionResult.TaskID`). The contract (`workflowContract`) names the step in the commands (`legato workflow step complete --run <run> --step <path> --attempt <attempt>`, and the same for `fail`), since a task's agent outlives the step and its environment names none, and says the agent keeps running (or, with `stop: true`, that Legato stops it). `keepsAgent`/`stepKeepsAgent` read `keep` (the v2 name), `keep_agent`, or `on: <task>` without `stop`. A completed `on: <task>` step with `stop: true` is finished through `FinishWorkflowAgent`, which stops a plain agent with `KillAgent` (`plainTaskAgent`: no run and not a `workflow_agent` execution) rather than removing it as a workflow's. `AgentRunExecutor.Cancel` leaves a plain agent alone (`AttemptHasTaskAgent`, which reads the step's recorded `with.on`, not the attempt's session, so it holds after the operator has replaced that agent): a cancel never stops the card's agent, reused, restarted or not. `wait_for`, the stage watermark, timeouts, the filled outputs and rebinding by place are LEG-485's: see § Agent waits, timeouts and clones. An `on: <task>` agent that ends before its step's signal fails the step, unless the step waits for `ended`.
- `agent.message` (LEG-607; `AgentMessageExecutor`) sends a prompt, tagged `[legato workflow]`, or a macro, untagged, to a running agent, and, without a `wait_for` (§ Agent waits), succeeds at once with the filled outputs (`task`, `session_id` among them). It takes exactly one of `task` (that task's main slot) and `agent: {from: <step>}`; no running agent fails the step (`task X has no agent running`, `the agent of step X has ended`). `agent.stop` takes the same pair (`task` is no longer required; `ExactlyOne` of `task` and `agent`, task first so the builder offers it first) and succeeds when the agent has ended already. `{from: <step>}` (`workflowengine.AgentFrom`: a map with the one key `from`, a step ID, never an expression) must name an earlier `agent.run`, `agent.message` or `agent.dispatch` step (`checkAgentFrom` in `problems()`, at load). - `agent.dispatch` is read as `agent.run` (LEG-607): `AgentDispatchExecutor` wraps the `AgentRunExecutor` and calls `startOnTask` with its `task` as `on`, `reuse: true` and no wait, so it starts the task's agent (as before, `created: true`, the work as the assignment with no contract) or messages the running one, now tagged `[legato workflow]` (a prompt) or untagged (a macro). Its `repo` is still only the pull request a macro names (`stepPR`): `startOnTask` reads `repo`, `ref`, `branch` and `engram` for a clone only when it waits (`agent.run`), so a new agent starts in `working_dir`, or where agents start by default, never in a job clone (address-feedback gives both). Its outputs are unchanged (`agent_session_id`, `created`, `working_dir`). - `github.pr.wait` (LEG-540; `workflow_pr_wait.go`, `PRWaitExecutor`) reads the pull request with `PRStateReader` (`GitHubPRStates`: `github.Client.FetchPRWaitState`, one GET for the PR and, while it is open, two for its head's CI; no reviews) when it starts: done, it succeeds at once; open, it returns `WorkflowStepWaiting`. `WorkflowService.CheckPRWaits` reads each waiting attempt's PR (its step's resolved `with`) and calls `CompleteWaiting` or, for a PR closed without merging under `until: merged` (`errPRClosedUnmerged`), `FailWaiting`; a read that fails is logged and tried at the next check. A read that fails in `Start` fails the step (the operator's Retry step reads again), so a wrong repository or number is seen at once. `StartPRWaitLoop` (serve and the TUI, beside `StartAdvanceLoop`) checks at start, every `prWaitInterval` (2 minutes, `cmd/legato/workflow_runtime.go`) and on `EventPRStatusUpdated`, at most every 30 seconds. The runtime gives it `lazyPRStates`, which makes the GitHub client at the first read, so a CLI command that runs no wait never runs `gh auth token`; without a credential the read fails the step. A checked `Enum` field (`until`) now refuses a literal outside its values at load (`Field.accepts`).
- **A waiting merge needs the operator** (LEG-614; `workflow_merge_wait.go`). `GitHubPRStates` reads with `github.Client.FetchPRWaitState`: the PR, and for an open one its head's CI (`fetchCheckStatus`, two more GETs; a CI read that fails is the read's error, so nothing is taken for "no CI": in a later check the step stays waiting for the next one, and in `Start` it fails the step, as any read there does). `PRState` carries `HeadBranch`, `BaseBranch`, `Conflicts` (`mergeable_state: dirty`, else `!mergeable`; nil while GitHub works it out) and `CheckStatus`. `PRWaitExecutor` keeps the last state per waiting attempt in memory (`remember`, `last`, `forget`; an unknown `Conflicts` keeps the last answer), filled in `Start` and `checkPRWaits`; each host process reads GitHub for itself at start, so nothing is kept across a restart. `checkPRWaits` returns the runs whose conflict or CI changed or whose wait it ended (`CompleteWaiting` and `FailWaiting` publish nothing themselves), and `StartPRWaitLoop` publishes `EventWorkflowChanged` (`Kind: PRWaitChangedKind`, `pr_wait`) for each, which the `workflows` Attention producer reconciles on. `addMergeWaits` (from `enrichWorkflowAttention`, so `ListRuns`, `AttentionCount` and `Show` all see it) gives each waiting `github.pr.wait` attempt a `MergeWait` in `view.Details[path]` (repo, number, url, state, branches, conflicts, CI, the card `task_id` from `with.task` (`stepAgentTask`) else `run.related_task_id`, its title, the card's agent `""`/`running`/`waiting`, `notify`) and, unless `with.notify: false`, `NeedsAttention` with `MergeWait.Reason()`. It fills the run view's `resume_task_id`, `resume_agent_state` and `can_resume_agent` (running or waiting run, a card, its agent not `waiting`, no attempt `waiting_agent`, a resumer wired). The catalog adds `task` (`KindTaskOrID`) and `notify` (literal boolean, default true) to `github.pr.wait`.
- **Resume agent** (LEG-614). `WorkflowService.ResumeAgent(runID, macro)` (`SetAgentResumer(MacroService, AgentService)`, wired in `buildWorkflowService`) refuses a run that has ended, a step's agent at work (`waiting_agent`) or a run with no card (`ErrWorkflowStateConflict`), and a card agent waiting on the operator (`ErrResumeAgentWaiting`). Nothing moves the card or touches its ticket. `MacroService.Start` now checks the folder it would start or resume in (`folderExists`, `os.Stat`); one that is gone becomes a new job clone of the PR's repository (else the code context's) on `Branch` (else the code context's branch) with `PushedBranch`, a new conversation (`SessionPolicy: new`, no resume: Claude Code and Codex keep a conversation with its folder) and a task note; with no repository it is `ErrMacroFolderGone`. - `burnlite.task.close` (LEG-540; `workflow_burnlite_close.go`) reads the task from the store: `provider` must be `burnlite` (not a handoff's `burnlite-copy`) with a `remote_id`, else it fails, or with `optional: true` succeeds with `skipped`. It closes through `BurnliteTaskCloser` (`ConnectedBurnlite`: the connected integration's address and `OAuthTokens`, `burnlite.Client.CloseTask`, the `close_task` tool). `service.BurnliteScope` is now `read:tasks write:tasks`; a connection made with `read:tasks` gets `insufficient_scope` (`burnlite.ErrInsufficientScope`), and the step says to connect again. The summary is folded to one line and cut at 200 characters, as Burnlite takes it. Nothing pulls the card at once: the next sync moves it.
- `ticket.create` and `ticket.comment` (LEG-640; `workflow_ticket.go`, `ticket_writer.go`) write through a `TicketWriter` per provider, kept apart from `TicketSource`: `JiraTicketWriter` (`cfg.Jira`'s `base_url`, `email`, `api_token`, read when `ticketWriters` in `cmd/legato/workflow_runtime.go` builds the executors, so a change applies after a restart, as for sync) and `BurnliteTicketWriter` (`openBurnlite` on the shared connection, holder `legato`, Burnlite's relative URLs made absolute). `Configured` names every empty Jira setting, or says Legato is not connected to Burnlite. An empty `provider` is the one writer whose `Configured` is nil; none or both fail the step. `readTicketDraft` and `checkTicketDraft` check the fields before any call: `project` and `summary` (whitespace folded, at most 255 characters) are required; `type` (Jira, `Bug` when empty), `priority` and `fields` are refused with Burnlite, `kind`, `size`, `uncertainty` and `milestone` with Jira; a Work task needs `size` and `uncertainty`, and a Meta task takes neither; Jira labels hold no whitespace, and `fields` may not name `project`, `issuetype`, `summary`, `description`, `labels` or `priority`. Each step keeps what it made in `workflow_step_effects` by run, step path and effect (`store.BeginWorkflowStepEffect`, `FinishWorkflowStepEffect`, `DropWorkflowStepEffect`), since a retry is a new attempt: a `done` record is returned (`created: false`) and nothing is called. A write is begun as `pending`. A refusal (`ticketRefused`: Jira's `*jira.APIError` 4xx, a Burnlite tool error or `ErrUnauthorized`) made nothing, so the record is dropped. Anything else (a lost connection, a timeout, Jira's 5xx) keeps it pending, and the step says the ticket may have been created. On retry, a pending create is looked for (`FindCreated`: Jira's `project = … AND creator = currentUser() AND created >= -Nm`, Burnlite's `ListTasksSince` a minute before the attempt began, which filters on the last change, so each Task of the exact summary is read with `GetTask` and kept only when its `createdAt` is that late, and a Burnlite that gives no `createdAt` fails the step): one match is adopted, none creates, and several fail the step naming their keys and saying a retry will not tell them apart (no step can be skipped, so the operator cancels the run). A pending comment is not looked for: the step drops the record and asks the operator to check the ticket, so the retry after that comments. `burnlite.ErrInsufficientScope` gets the "connect Legato to Burnlite again" text of `burnlite.task.close`.
- `WorkflowService.SetAgentKinds` gives the service the configured adapters: an `agent.run` step whose `agent` is known from the inputs alone and names no configured adapter is refused when the run starts, and no run is created.

### Expressions, if:, on_failure and the gate

LEG-486, spec LEG-482 §1, §3, §6. Mostly `internal/engine/workflow/expr.go`, `definition.go`, `trigger.go` and `internal/service/workflow_control.go`.

- **The tokenizer.** `ParseExpression` reads the inside of a `${{ }}`: operands joined by `??`, the first a path, the others a path or a literal (`'text'`, `"text"`, `null`, `true`, `false`, a whole number). A path is names joined by `.`, and `[n]` (`[-1]` is the last item); a name is a run of anything but space, quotes, `.`, brackets, braces and `?`. `findExpressions` finds each `${{ }}` in a text, skipping `}}` inside a quoted literal (a quote with no close is not one, so the parse says so). `ParsePath` reads a bare path (a condition's `field`). `web/src/lib/workflowExpressionParse.ts` is the same parser for the editor; `testdata/expressions.json` is the table both run (`TestTheSharedExpressionTable`, `workflowExpressions.test.ts`); its cases may say `whole` (the field's whole value) and use location `if`.
- **What may be read** (`pathType`, which also says the declared type): as before, plus `[n]` and `.field` into a `json` input, a `json` output (declared or in the catalog) and `metadata`; anything else after a step output is still only `.path`. A step with `on_failure: continue` can be read for `status`, `error` and `error_code` (`FailureOutputs`). `readableOutputs` now gives types. The `if` expression context (`ExpressionContexts`) is the inputs, the workflow task and earlier steps.
- **`??`** is the next operand when one is missing or null; the empty string counts. In a field's whole value both sides must have the same declared type when the file loads (`typesMatch`: `json` and `null` match anything); within longer text they are rendered as text and need not.
- **Missing values** (`resolveScope`, `errMissing`, exported as `ErrMissing`): an input not given, a skipped step's outputs, a field or item that is not there, a reach into the wrong kind of value. A field whose whole value is missing is left out of `with` (`ResolveStep`; in a list it is null); within longer text a missing value fails the step, saying to give a fallback with `??`. `advance` records any error resolving a step's `if:` or `with` as a failed attempt with that error, as an executor's error, so the step's `on_failure` applies (a run is never left running at a step with no attempt). Null renders as nothing in text.
- **Trigger input mappings** (`resolveMappedInputs`, `workflow_trigger.go`) resolve through the same scope: `ResolveFromRoots(value, roots)` is `resolveScope` with `roots`, where a path's first name is a root (a column trigger's `event` (`{task: <id>}`) and `task`; an event trigger's request context: `event`, `schedule`) and `.field`/`[n]` reach into it. A whole value keeps its type (a non-string is stored as JSON, as before); within text it is interpolated. A missing or null whole value, a missing value within text and an expression that does not parse all leave the input out, so its default or the request's `waiting_input` follows. The load-time check of trigger inputs (`validateTriggerInputs`) checks only that each key is a declared input.
- **`Condition`** gains `gt`, `lt` (a number or text, checked at load) and `empty`; `evaluate(lookup)` is shared by trigger conditions and `if:`. Numbers compare by value (`ValuesEqual`, `compareValues`: `3` equals `3.0` and `json.Number`), text as text; missing makes `gt`, `lt`, `equals` and `in` false, `not_equals` and `empty` true, `exists` false. A trigger's fields stay `ConditionFields` and `task.metadata.<key>`; an `if:`'s field is any path the step could read (`validateControl`).
- **`if:`** (v2 only, `legato:"v2"`, so not in the published v1 schema yet). `WorkflowService.advance` checks it first (`Definition.StepRuns`, `stepRuns`), before a manual wait. False: `store.SkipWorkflowStep` marks the step `skipped` with outputs `{}` and moves the run on (`moveRunPast`, which also ends it succeeded at the last step), publishing `step_skipped` (an end kind for the run-ended hook). `loadExecution` gives later steps the outputs of steps that succeeded or failed (a failed step before the current one was continued); skipped ones are missing. `stepOutputsUsed` counts an `if:`'s fields, so the graph draws their data edges.
- **`on_failure`** (v2 only): `fail` (the default), `continue`, `pause`. It lives in the step's `definition_json`, so the store applies it wherever a step fails: `store.FailWorkflowStepWith(run, path, attempt, StepFailure{Message, Code, Link, InProcess})`, which `FailWorkflowStep` calls (the agent service's direct fails included). Every failed step's `outputs_json` is the failure: `status: failed`, `error`, `error_code` and, when set, `error_link` (`store.FailureOutputs`); `GetWorkflowRun` puts the code and link on `WorkflowStep.ErrorCode`/`ErrorLink` for failed and paused steps. No migration.
  - `fail`: as before, the run fails.
  - `continue`: the step is `failed`, the run moves to the next step of its scope (`nextStepPath`) or ends succeeded. `advance` goes on itself (`InProcess`); any other caller leaves the step `advance_due`, and `processAdvance` (finish its agent unless kept, then `startNextStep`) moves the run: at once in a host (`failRecorded` after `Fail`/`FailWaitingError`), else on the next `EventWorkflowChanged` (the advance loop now runs `AdvanceDue` on every change but its own `advanced`) or reconcile.
  - `pause`: the step is `paused` (`store.WorkflowStepPaused`), the run `waiting`. `enrichWorkflowAttention` makes the run need the operator with `pausedReason` (the error and the link). `StepAction` on a paused step takes `retry` (`Retry`: `ResetWorkflowStepForRetry` now takes a paused step of a waiting run), `skip` (`SkipStep`: outputs missing, the next step runs) and `stop` (`Stop`). `endWorkflowRun` cancels paused steps too.
- **Error codes.** An executor returns `*service.WorkflowStepError{Code, Link, Message, Err}` for a typed failure (`stepFailure` reads it with `errors.As`); a service failing a waiting step uses `FailWaitingError(ctx, run, step, attempt, err)`. LEG-489's `workflow.run` and LEG-585's review steps (`review_loop_active`, `author_loop_active` with the other loop's run as the link) use it.
- **The gate** (`gate`, group `Control`, `GateStepType`): `title`, `body` or `body_path` (one of the run's own file outputs, the managed copy in the data folder, matched against the run's artifacts when the gate starts and when it is shown, so never a path in an agent's checkout that could be made a link to a file its sandbox hides; at most 64 KiB read; `Excludes`), `options` (a list of different names, checked at load; `DefaultGateOptions` Continue, Stop). Every `WorkflowService` registers `gateExecutor` itself. It waits on its service (`WorkflowStepWaiting`); `Details` is `GateDetails{title, body, options, choice}` from the step's resolved `with`; `Attention` gives the title and one action per option, `choose:<option>` (`GateChoiceAction`); `Act` completes the step with output `choice`, or for `Stop` (any case) calls `Stop`, ending the run `stopped`. The `workflows` Attention producer makes a gate's item `workflow_gate` (rail group `workflows`; title the question, one action per option, Stop confirmed) and a paused step's `workflow_failed` (high; Retry, Skip, Stop); a failed step only makes an item when it is the step its failed run stopped at (`current_step_id`), since a continued one does not need the operator; `ResetWorkflowStepForRetry` refuses any other failed step, so Retry never rewinds a run into steps it went on to.
- **API.** `POST /api/workflow-runs/{run_id}/steps/{step_id}/action` with `{action, text}` is `StepAction` (`workflowStepActor`): a gate's `choose:<option>`, or `retry`, `skip`, `stop` on a paused step; 409 when the step does not take it now. The route is class `change`, but an action that ends the run (`stop`, or a gate's `choose:Stop` in any case) is `risky`, as `/cancel` is, both here (`ClassifyCall` reads the body) and as the Attention action `POST /api/attention/{id}/actions/{action_id}` (`ClassifyRequest` reads the action ID); `stopsAWorkflowRun` in `internal/server/route_classes.go`. The run page's Now panel shows a gate (`GateNow`) and a paused step (`PausedNow`, with the link), and says **Stopped** for a stopped run.

### Agent waits, timeouts and clones

LEG-485, spec LEG-482 §5.2–§5.6 (part 2 of the agent primitives; part 1 is LEG-607). Engine: `internal/engine/workflow/agent_wait.go`; service: `workflow_agent_wait.go`, `workflow_agent_clone.go`; store: `internal/engine/store/workflow_wait.go`.

- **The model.** `Step.WaitFor` (`wait_for`) and `Step.Timeout` (`timeout`) are tagged `legato:"v2"`: a version 1 file refuses them (`checkWait`), and they stay out of the v1 schema. `EffectiveWaitFor` is the one rule for defaults: declared outputs → `complete`; `agent.run` → `complete`, or `ended` with `on:` a task; `agent.message` → `none`; `agent.stop` → `none` (stop now); other types nil. Load checks: agent steps only, known signals (`idle` refused as a later slice), no repeats, `none` alone, `agent.stop` only `ended` or `none`, declared outputs need `complete`, `none` on an `on: run` agent needs `keep`. `Step.TimeoutDuration` is Go's `time.ParseDuration`, positive.
- **Filled outputs.** `agent.run` and `agent.message` list `agentFilledOutputs` in the catalog (so later steps read them without declaring them; `DeclaredOutputs` executors may now list outputs, which are Legato's): `signal`, `stage`, `stage_reason`, `last_message`, `session_id`, `task`, `working_dir`, `clone_id`, `branch`, `top_branch`, `stack`, `prs`. `WorkflowService.agentOutputs` fills them: the stage from the wait's place, the last message from `AgentOutputSources.LastMessage` (the agent service's `ConversationTail`, capped at 4 KiB), the branch from `gitrepo.Head` of the working folder, and for a job clone (`JobCloneByPath`) `AgentOutputSources.Stacks.Record` (`TaskStackService`), the recorded stack, `top_branch` (`topOfStack`), then `PRs.AddTaskBranches` of the stack's branches and the HEAD branch, `DiscoverAndRefreshPRs` (the PRs of branches with none found, and those found before fetched again, so an earlier step's draft PR the agent has since marked ready is not read as a draft) and `TaskPullRequests` filtered to the clone's repository and those branches. A GitHub error there, finding or refetching, fails the step (`outputs_unavailable`), at a host-detected signal (`resolveAgentWait`) and at `complete` (below). Declared values win over filled ones. Wired by `agentOutputSources` in `cmd/legato/workflow_runtime.go`.
- **The wait record.** `advance` computes `ResolvedWorkflowStep.WaitFor`; for a step that waits (`beginsWait`: any agent step, `agent.stop` only with `ended`) `beginAgentWait` calls `store.BeginWorkflowWait` before the executor sends anything: in one transaction it reads the place's newest `agent_stage_events.id` (the watermark) and, when an agent is already running there and the step waits for `finished`, resets the place to Implementing with source `workflow` (migration 153), and writes `wait_signals`, `wait_task_id`, `wait_slot`, `wait_execution_id`, `wait_watermark` on the step while it is `running`. The place is known before the prompt for an agent on a task (`TaskPlace(task, main)`), a `task:`/`slot` agent and a message's target (`SessionPlace`); a new `on: run` agent's place is a new execution's, so its watermark is 0. After `Start`, `BindWorkflowWait` ties the wait to the session (place and `wait_session_id`, and the attempt's `agent_session_id` and `working_dir`, the session's execution's folder) before `MarkWorkflowStepWaiting` (whose empty `working_dir` is the session's), so no host sees it waiting on nothing and the outputs find the agent's job clone after it ends, when its session is deleted; then `checkAgentWaitAt` looks for a signal at once (`none` ends the step there).
- **Signals from the tables.** `CheckAgentWaits` lists `waiting_agent` steps with a wait record (`ListWorkflowAgentWaits`) and, for each (`checkAgentWait`): `none` ends it; `waitedAgent` finds the live agent (the attempt's session, which a resume of a workflow's own agent moves, else the wait's, else the place's running one; an `interrupted` session or slot is not ended) and rebinds the wait when the place has another session (a resume); `finished` is an event of the recorded or rebound place above the watermark with stage `finished` (`WorkStageEventAbove`); `ended` is no live agent and none interrupted. An agent that ended when the step does not wait for `ended` fails the step for a plain agent (`on:` a task, a message or stop's target: "the agent ended before the step completed"); a workflow's own agent keeps the old rule (needs attention). `resolveAgentWait` fills the outputs, records the step with `RecordWorkflowStepCompletion` (its CAS on the attempt lets one host through) and, outside `recordOnly`, `advanceRecorded`. `StartAdvanceLoop` runs `CheckAgentWaits` and `SweepTimeouts` at start, on `EventAgentStageChanged` and `EventAgentDied` (`SubscribeInvalidations`, coalesced) and on each 30-second tick. Waits are never taken from bus events alone.
- **`WorkStageService.Report` always writes** an event, even when the stage and note repeat: a second Finished from the same agent ends a second step.
- **Complete from the pane.** `Complete` still only records (§5.4); the host's `processAdvance` first calls `fillRecordedOutputs`, which fills the step's outputs with `signal: complete` (`MergeWorkflowStepOutputs`) while the agent is still there. When `agentOutputs` errs (a GitHub error), the step fails as at a host-detected signal, error code `WorkflowErrorOutputsUnavailable` (`outputs_unavailable`, `outputsUnavailable`, also `resolveAgentWait`'s): `failUnfilled` calls `store.FailRecordedWorkflowStep`, which turns the recorded step (`succeeded`, advance due, its run at the next step, still pending, or after a loop pass's last step at its loop, still running) back into a failure with CAS on each row, so of two hosts one does it, then stops the agent as `Fail` does (`FailStep` or `Cancel`). Its `on_failure`: `fail` puts the run back at the step, failed, `pause` puts it back waiting, and either ends the advance there (Retry runs the step again); `continue` leaves the run at the next step and the step due, and `processAdvance` goes on as for a continued failure. A loop pass's step with no `on_failure` of its own follows the loop's, as `FailWorkflowStepWith` does: `pause` by default, else the pass ends (`FailurePassEnded`), the run goes to its loop with the step due, and the loop's next tick applies its policy. The exceptions are the last step of a run (its record ended the run) and a conflict where the step is still `succeeded` (the run left the next step, such as by a cancel): nothing reads its outputs, so `prs` is left out (logged). A conflict where the step is no longer `succeeded` (another host failed it) ends this advance. `TaskStackService.Record` errors are only logged: it reads the clone's files and returns only database write errors (a stack it cannot read is recorded with its problem), and the HEAD branch is looked up anyway. `processAdvance` does not `Finish` a step whose `signal` is `ended`.
- **`agent.message`** now returns `waiting_agent` on its target's session; the service ends it on its signal (`none` at once), so it fills the same outputs. When it waits, its message ends with `messageContract`, which names the step's own `--run/--step/--attempt` (the agent's environment names another step), its declared outputs and its signals; after a macro the contract goes in a second, tagged message. `workflowContract` and `messageContract` share `awaitedSignals`.
- **`agent.stop` with `wait_for: [ended]`** (`AgentStopExecutor.waitForEnd`) waits on the agent's session (or succeeds at once when none runs) and ends on `ended`; nothing is stopped. On the agents graph it is `AgentRoleAwaited`; a waiting `agent.message` on a plain agent is `AgentRoleAgent`.
- **The agent service.** `endGoneSessionFor` leaves alone an attempt whose step waits for `ended` (the host ends it) or whose wait it cannot read (logged; the host reads the tables again), and, when interrupted, one with a wait record on a plain agent or a message/stop (it rebinds when resumed); a workflow's own interrupted agent is still suspended. `enrichWorkflowAttention` does not flag an idle agent whose step waits only for `ended`.
- **Timeouts.** `advance` sets `deadline_at` (`SetWorkflowStepDeadline`, fixed-width UTC text) from `timeout` when an attempt starts, so Retry gets a new one. `SweepTimeouts(now)` lists steps under way past their deadline, claims each by moving the deadline it read to two minutes later (`ClaimWorkflowStepTimeout`, a CAS; `timeoutClaimStale`), so a host that stops, or whose `Cancel` fails, before the failure is recorded leaves the step to a later sweep, and `timeoutStep` fails it through `Fail` ("timed out after …", error code `WorkflowErrorTimeout`): `Cancel` stops an `on: run` agent and leaves a task's own. Manual gates (`waiting_manual`) are not timed. The failure goes through `failRecorded`, so the step's `on_failure` applies; a `workflow.run` step's child is cancelled after that failure is written, so the child's end settles nothing (LEG-489).
- **Explicit clones.** `ResolvedWorkflowStep.SchemaVersion`; from version 2, `stepCloneOptions` sets `AgentSpawnOptions.OwnClone` (`JobCloneRequest.Own`) for a step with `repo` and no clone, or `Clone` for `with.clone` (`resolveStepClone`: `{from: <step>}` reads that step's `clone_id` output, an expression gives an ID; `JobCloneByID`), and makes `branch` `WorkflowBranch(task, name)`: `legato/<task>-<name>`. `grantBranch` then grants it to the session through `BranchGranter` (`CredentialBroker.GrantBranches`, wired after the approvals runtime by `grantWorkflowBranches` in `cmd/legato/workflow_runtime.go`; a failed grant is logged). Version 1 steps keep finding the task's clone and their branch names. `clone` is checked at load (`cloneForm`, `checkCloneFrom`).

### Calling a workflow: outputs and workflow.run

LEG-489, spec LEG-482 §1 (Calling a workflow), §4. `internal/engine/workflow/run_outputs.go`, `call.go`, `call_check.go`; `internal/service/workflow_call.go`; migration 154.

- **Outputs.** `Definition.Outputs` (`outputs:`, v2 only, `legato:"v2"`) maps names to `WorkflowOutput{Type, Value, Description}`: `type` is `string`, `integer`, `boolean` or `json`; `value` is checked at load like a `with` value against the inputs and every step's readable outputs (`outputProblems`). `Definition.ResolveOutputs(inputs, task, steps)` returns the resolved outputs and a warning for each left out: missing, an error, or a value not of its type (`valueOfType`). It is a thin wrapper of `resolveOutputMap(declared, scope)`, which LEG-490's loop pass results can reuse in a pass's scope. The service computes them when a run ends succeeded: `changed` calls `keepRunOutputs` before the run-ended hook's listeners hear of the end (for a run an agent's completion ended, `processAdvance` does, once the step's outputs are filled: § The run-ended hook), and `store.SetWorkflowRunOutputs` keeps them in `workflow_runs.outputs_json` (only on a succeeded run). `Show` puts the outputs and `WorkflowRunView.OutputWarnings` on the view (`addRunOutputs`, computed again: a run's steps do not change once it has succeeded); the run page's Produced panel lists them under **Run outputs** and the warnings under **Outputs not resolved**. A run's outputs read its own steps (a loop's through the loop step's outputs), never a pass's.
- **The step.** `workflow.run` (catalog group `Control`, `WorkflowRunStepType`): `workflow` (required) and `inputs` (a map). `checkWorkflowRunStep` refuses a `workflow` that is not a literal name or a whole `${{ workflow.inputs.<x> }}` of an input with `choices` (`CalledWorkflows` lists the names either way), and `inputs` that is not a map. Its outputs are open: `readableOutputs` gives it `anyOutput` (`*`, type `json`), so `pathType` lets later steps read any name; a name the step declares under `outputs:` gets that type. The catalog's are `status` and `run_id`. Every `WorkflowService` registers `workflowRunExecutor` itself (as the gate), and `SetDefinitions` gives it the workflows found (`workflowDiscoveryProvider`, in `buildWorkflowService`).
- **Typed inputs.** `Definition.NormalizeValues(map[string]any)` is `NormalizeInputs` for values a step passes: unknown names refused, defaults filled, each checked against its type and `choices` (`typedValue`). A task is its ID (a resolved task context passes its `id`); a repository is a preset's name or the object a run resolved (`repo` and `primary_dir` required), which `createRun` keeps as it is. `start` is now `NormalizeInputs` then `createRun` (inputs resolved, task and run recorded, nothing started) then `advance`.
- **The child.** `startChild` (the executor's `Start`) finds what the step resumes first: a child its row names (`workflow_steps.child_run_id`) that runs, waits or succeeded is kept; a failed one has its failed step reset (`ResetWorkflowStepForRetry`: Retry resumes the same child); a cancelled or stopped one is replaced. Otherwise it checks the call (`workflow_not_found`; `callChain`, the workflow names from this run up: `workflow_recursion` when the name is in it, `workflow_too_deep` past `MaxCallDepth` (5) ancestors; `workflow_inputs`) and `createRun`s the child with `ParentRunID`, `ParentStepPath` and `ParentAttempt`. `store.CreateChildWorkflowRun` writes the child and the step's `child_run_id` in one transaction, unique on `(parent_run_id, parent_step_path, parent_attempt)` (index `idx_workflow_runs_child`): a second create for the attempt returns the first child, and `createRun` removes the task it made. The step then waits on its service (`WorkflowStepWaiting`).
- **Starting it after the wait.** `advance` tells an executor that is a `workflowStepWaiter` once its step is marked waiting: `Waiting` (`driveChild`) advances a child that is `running` at a `pending` current step (`resumeRun`; a new child, or one reset for Retry), then settles the step if the child has ended. So the child's end always finds its parent's step waiting.
- **Settling.** `childRuns` is a run-ended hook listener every service subscribes: `RunEnded` with a `ParentRunID` calls `settleChild`, which acts only on a `waiting` `workflow.run` attempt at that path whose row still names that child. `succeeded`: `CompleteWaiting` with the child's outputs (`runOutputs`) plus `status: succeeded` and `run_id`. Anything else: `FailWaitingError` with `childFailure`, a `WorkflowStepError` with `Status` (`failed`, `cancelled` or `stopped`; `store.StepFailure.Status`), the child's failed step's `error_code` and `error_link`, `Outputs: {run_id}`, and the message `workflow <name> failed: <error>`; the step's `on_failure` decides. A child that is gone fails it with `workflow_run_gone`. `RunsHeld` is the children of waiting `workflow.run` attempts, so the sweep settles a child that ended in another process or while Legato was down. A `recordOnly` service (the CLI in an agent's pane) never settles or drives: a host does.
- **Cancel and Stop.** `WorkflowService.end` writes the run's end, then `cancelChildren` cancels each child that has not ended (and theirs, through `Cancel`). The executor's `Cancel` does nothing, so the order holds: by the time a child's cancellation reaches `settleChild`, the parent's step is cancelled and is passed over; the parent's `on_failure` never runs. A child cancelled or stopped on its own fails the step as above. `Fail` by hand keeps the child, for Retry.
- **The reconcile.** `ReconcileChildRuns(ctx, olderThan)` runs with the sweep in `StartAdvanceLoop` (at its start, on each change and each tick; `olderThan` is `advanceClaimStale`). An attempt still `running` past it (a crash after the child was made, before the step was marked waiting) runs `startChild` again (it finds the child), is marked waiting and its child driven; each waiting attempt is driven (a child made but never started is started; an ended one settled). Before those, it cancels each child that has not ended (or has failed) whose parent ended `cancelled` or `stopped` (`store.ListUncancelledChildrenOfEndedWorkflowRuns`, `cancelChild`): a parent's end is written before `cancelChildren` runs, so a cancellation that failed, or a crash between the two, is retried here; the parent's step is already cancelled, so its `on_failure` still never runs. Advancing a child twice is harmless: `StartWorkflowStepAttempt` is a compare-and-set.
- **Diagnostics.** `CallDiagnostics(data, definition, others)` checks the call graph across the workflows found: a call that leads back (`callChainBack`) or nests past 5 (`callDepth`) is an error; a workflow not found, an input the child does not declare or requires and is not given (`callInputDiagnostics`), and an output read the child does not declare (`callOutputDiagnostics`, from `stepOutputsUsed` of the later steps and the workflow's outputs) are warnings. The server adds them for a definition that `Calls()` to the editor's check (`checked`) and the workflows list (`definitionWithGraph`).
- **Run page.** A run with `parent_run_id` says "called by <run> at <path>"; a `workflow.run` step's row and panel link its `child_run_id`; while it waits, the Now panel links **Open child run** with `WorkflowCallDetails` (`run_id`, `workflow`, `title`, `status`, the executor's `Details`).

### Loops

LEG-490, spec LEG-482 §1 (Loops), §9.8, and Ship's additions (LEG-559 X1). Engine: `internal/engine/workflow/loop.go`; service: `internal/service/workflow_loop.go`; store: `AdvanceWorkflowLoop`, `EndWorkflowLoop`, `SetWorkflowLoopState`, `ListWorkflowRunsAtLoops` in `internal/engine/store/workflow.go`. No migration: the state is `workflow_steps.loop_state_json` (migration 135).

- **The model.** `Step.Loop` (`Loop`: `Over`, `Next` (`LoopQuery{Type, With}`), `Repeat`, `Key`, `Max`, `Until`, `OnFailure`) and `Step.Steps`, both `legato:"v2"`. A loop step has no `type` or `with`; its `outputs:` are the pass result's, each with `Output.Value` (`legato:"v2"`; any other step refuses `value`). `Limit()` is `max` (`DefaultLoopMax` 20, at most `MaxLoopMax` 100); `Failure()` is `on_failure` (`pause` by default). v2 refuses `/` in step IDs (paths use it).
- **Checks** (`stepScope.check`, `checkLoop`): `problems()` checks each `steps:` list as a scope, a loop's body recursively. IDs are unique per list; a body may reuse an enclosing ID, and its own is the nearest. The readable outputs map is copied into a body with the steps before the loop, so references point backward only and a step after the loop cannot read a pass's steps. Exactly one of over/next/repeat; `key` required with `next`, refused with `repeat`; `max` 0–100; no `wait_for`/`timeout` on a loop; a `next:` loop's body may not have a step `next`. `over` is a list or a whole `${{ }}` of a `json` value (`checkOver`). The loop context's types ride in the readable-outputs map under keys no ID can have (`" loop"`, `" pass"`): `pathType` sends `loop.*` to `loopPathType`. `loop.index` integer, `loop.item` and `loop.results` json, `loop.previous.<name>`/`loop.last.<name>` the pass output's type (`status`, `error` string; an undeclared name refused). Where: a body's with/if/outputs and `key` read index, item, previous, results; `next.with` the same without item; `until` also `last`. Pass outputs are checked against the body's steps (all of them) and refuse `status`/`error`. `readableOutputs` of a loop step is `LoopOutputs` (`results`, `last`, `count`, `succeeded`, `failed`, `ended_by`), plus the failure outputs with `on_failure: continue`. `ExpressionContexts` has `pass` (with's roots plus `loopRoots`); the web uses it for a body location.
- **Paths and scopes.** A pass's scope is `<loop path>/<pass>` (`PassPath`), its steps `each/2/build`; a `next:` query is `each/2/next` (`NextStepID`, step order -1, made before the body; `StepAt` synthesises it from the loop). `Definition.StepAt`, `Scopes(path)` (`ScopeLevel`: path, steps, how many come before, loop, pass; outermost first), `PassScopes`, `NextPath` (the next step in the scope; after a pass's last step or its query, the loop's path; after the run's last, ""), `PassSteps`, `Nearest`. `ResolveStepAt`/`StepRunsAt` take a `Scope{Inputs, Task, Steps, Loop}` (`ResolveStep`/`StepRuns` wrap them for the run's own steps).
- **The advance** (`WorkflowService.advance(ctx, run, selected, force)`) follows `current_step_id` (`loadExecution` returns a `runAt`: the run, the step at the path, its row, `prior` from `scopeOutputs` and the loop context, and `next`). `scopeOutputs` walks the scopes outermost first and sets each earlier step's outputs (succeeded, or failed and so continued) or deletes the ID (skipped, not reached): the nearest step of an ID wins, and a skipped one hides an enclosing one. Each turn: a pending step runs (`runStep`: if:, manual wait, attempt, executor, as before, with `CompleteWorkflowStep(…, next)`), a loop step that is pending starts (`startLoop`: an attempt of executor `loop`, `Started`, the over list read now), a loop that is `running` and that the run is at ticks (`loopTick`); anything else stops. `start`, `TriggerStep`, `Retry`, `SkipStep`, `CompleteWaiting`, `resumeRun` and `startNextStep` (now: advance when the record moved the run on) all call it.
- **The tick** (`loopTick`), on the state (`LoopState`: `Started`, `Items`/`Cursor`, `Seen`, `Passes` (`LoopPass`: index, item, key, `Body`, `Open`, `Result`), `EndedBy`): an open `next:` pass whose query succeeded picks its item (`pickNext`: the first of `items` whose key is unseen, made into the body's rows; none: the pass is dropped, `ended_by: next_empty`; `items` not a list: the pass fails). An open pass the run came back from ends: `passOutcome` (failed when a step failed without its own `continue`, the query included; skipped when every body step was), `PassResult` (pass outputs resolved in `passScope` for a succeeded pass, `status` and `error` always, over `PassResultLimit` 16 KiB a failed pass with no outputs). A failed pass under `fail` (or an oversized result under `pause`) sets `ended_by: failure` and fails the loop step through `FailWorkflowStepWith` with `LoopState.Outputs()` (its own `on_failure` applies), the state written over the one read in the failure's transaction (`StepFailure.LoopState`), so a crash leaves neither. Then `until` (`UntilContext`: `loop.last`), then `max`, then `over`'s next unseen item (an item whose `key` was seen is passed over), else the next pass: `AdvanceWorkflowLoop` writes the state over the one read (CAS on `loop_state_json`), makes the pass's rows (`stepInstances` with the pass) and moves the run from the loop to the pass's first step, in one transaction; `EndWorkflowLoop` writes the state and completes the loop step with its outputs and `next`. A conflict is another host's move (`conflictIsNotMoved`). Change kind `loop_pass` (`WorkflowChangeLoopPass`).
- **Per-pass on_failure** lives in the store, so it holds wherever a pass's step fails (an agent's exit too): `FailWorkflowStepWith` reads, for a step in a pass whose own `on_failure` is empty or `fail`, the loop's (`loopFailurePolicy`, from the loop row's `definition_json`): `pause` pauses the step (run `waiting`, Retry/Skip/Stop as LEG-486's); `continue` and `fail` return `FailurePassEnded`: the step is failed and the run moves to the loop (`advance_due` unless `InProcess`; `failRecorded` advances it in a host). A step's own `continue` goes on in its pass; `nextStepPath` leads from a pass's last step (or its query, order -1) to the loop.
- **Retry.** A pass's paused step retries in place (the run is at it). `Retry` refuses a pass's step the run is not at: a loop that failed is retried as the loop, which keeps its passes (`Started`) and goes on with the next pass. The `workflows` Attention producer and the web's needs-you rows skip a pass's failed step when the run failed: the loop is the item.
- **Restarts.** Everything is in the tables. A pass's agent step recorded from a pane is advanced by a host as any (`advance_due` → `startNextStep` → the tick). `ReconcileLoops` (at the advance loop's start and each reconcile) advances each run left at a running loop (`ListWorkflowRunsAtLoops`: the run's current step's attempt is a running `loop`), which a host that died between a pass's end and the tick leaves, or between `startLoop`'s attempt and its state: a tick on a state not `Started` starts the loop (`loopStarted`: the over list read then) instead of ending it with no passes; the CAS makes a race with a live host harmless.
- **Elsewhere.** `createRun` checks executors through loop bodies and `next:` queries (`checkExecutors`). `MarshalYAML` writes bodies' `start` as the file's version does. Graph version 2 (LEG-484) draws a loop as a node of type `loop` whose body's steps are nodes inside it (§ Workflow graph). The web run page lists a loop's passes under it (`runStepTree`, `web/src/lib/workflowRunTree.ts`), keys steps, attempts, artifacts and details by path (`stepPathOf`), counts the run's own steps on its bar, and takes the Now step from `current_step_id`; `runNeedsYou` draws a pass's rows in its loop's node.
- **Acceptance** (`internal/engine/workflow/loop_test.go`, `internal/service/workflow_loop_test.go`): LEG-480's B, C and D and LEG-559's `review-loop` sketch, with the steps not built yet (LEG-488's tickets, LEG-487's deliver, LEG-585's review steps) named by catalog types (`task.context`, `task.note`, `github.pr.wait`) whose executors the tests fake.

### Review loop steps

The review loop steps (spec LEG-559 § The five steps; LEG-585 `github.pr.review.open` and `github.pr.review.close`) are catalog steps over the review engine's operations on one loop record (`internal/engine/workflow/review_loop.go` for the contracts and file checks, `internal/service/review_loop_steps.go` for the executors). Every workflow service registers them (`ReviewLoopSteps.Executors`, `reviewLoopSteps` in `cmd/legato/workflow_runtime.go`); `attachReviewRuns` attaches the run caller (`ReviewLoopStepsOf`). Each is a service waiting step: `Start` checks the inputs in any process and waits; the review engine's tick in the broker holder does the work and ends it (D9), so a process without the engine never fails one.

- **Open.** `parseReviewOpen` reads the inputs and refuses with a code (`WorkflowStepError`, so `error_code` beside `error`): `handoff_input_refused` for any `handoff` key (only the handoff service will set it, slice 5), `invalid_subject` (not exactly one of `pr_number` and `prs` resolving to something; more than 20; duplicates; `scope` with `prs` or unknown), `steward_needs_agent_author`, `invalid_settings` (a negative count), `max_reentries_raised` (above `review_passes.max_reentries`), then `review_passes_off`, and `review_loop_active` for a pull request a loop (or a step waiting to open) holds. The tick's `OpenWaiting` then runs `openSteps`: the loop the step opened already (`store.ReviewLoopForStep`, idempotent by run and step path), else `ReviewRunCaller.open` with the parsed input (the inline step's open, shared: `openInline` reads the inline step's inputs into the same `reviewOpenInput`), which adds `reviewer_app_missing`, `pr_not_open`, `no_author`, `reviewer_not_advertised`, `skill_not_advertised` and `author_loop_active`. A list subject keeps `subject_pr` 0 and reviews exactly the listed pull requests (`readReviewRun` puts the clone at the top one); a `pr_number` finds its stack. The record carries `max_reentries` (the instance's when 0), `ready` and `steward`. Outputs: `loop_id`, `linked_task`, `prs` (number, url, branch, base, author_task), `warnings` (`sameToolWarning`: the reviewer runs the tool the author's agent last ran).
- **Ownership.** A loop an open step opened belongs to its run, not to a waiting step: `store.ReviewLoopOpenedByStep` (its owning attempt is a `github.pr.review.open` attempt) makes `CheckReviewLoopWrite` allow writes while the run is `running` or `waiting` (the inline step's loop still needs its attempt waiting), `ReviewRunCaller.Loops` moves it on (`stepLoops`) only while its run runs (a failed run's loop waits for Retry), `closeEnded` closes it only when its run ends, and the operator's actions on it need only its run to run (`stepWaits`). An approved step loop stays open and confirmed for the run's next steps (`finishStepLoop`); a loop whose pull requests closed, or that the operator ended while stuck, closes with that outcome. `OpenReviewLoopClones` spares its clones while it is open.
- **Pass, wait, confirm** (LEG-586; `reviewObserver`, one type each so `Type` names it). Each takes `loop` (`ownedStepLoop`: refused unless open and its run's), waits, and is tied to no session: the holder's tick moves the loop on as for the inline step, then `SettleSteps` reads the record (`settleObservers`). `github.pr.review.pass` completes once a pass later than any an earlier pass step of the run reported (`consumedPass`, from the run's succeeded pass steps' `pass` output for the same `loop_id`) is posted, with `verdict` (`clean`, `changes`), `state` `posted` and `pass`; a loop the operator ended while stuck gives `state` `stuck`, one whose pull requests closed `closed`. `github.pr.review.wait` takes `mode: author` (the only mode yet; `watch` is the steward's, LEG-590) and completes `ready` once the author's round is done (`Wait`), `closed`, or `stuck` after End. `github.pr.review.confirm` completes `approved` once `Confirm` (the tick's `confirmLoop`) confirmed the run's last clean pass at GitHub's heads (`confirmed_at`, `pass`), `moved` when the loop went on to a new pass instead (a head moved, or a counted check sent it back to its author), or `closed`/`stuck`. While the loop is stuck each waits, and `Attention` and `Act` give the inline step's: Run another pass, Message the author (agent author) and End, by loop ID (`ActOnLoop`); End closes the loop with outcome `stuck` (`finishStepLoop`). Retry of a failed observer finds the same loop where it stands. A reviewer that dies runs its pass once more and a second death is stuck, and Another pass raises only the current window (see [Integrations](integrations.md) § Limits).
- **Close.** `Start` refuses a loop that is not found (`loop_not_found`) or not its run's (`loop_not_owned`, `ownedStepLoop`); a closed loop is no refusal. The tick settles waiting close steps after moving the loops, outside the engine's lock (`ReviewPassService.settleSteps`, `ReviewRunCaller.SettleSteps`): `Close` with the outcome the record gives (`stepOutcome`: `approved` when `confirmed`, `stuck` while stuck, else `ended`), then the outputs (`closeOutputs`): `outcome`, `passes` (posted passes only), `clean_pass`, `confirmed_at`, `findings` `{total, blocking, nits, open}`, `prs[]` `{number, url, state (GitHub's, else the record's), draft, author_task, approved (an APPROVE at the clean pass), head_sha (clean head, else last pinned), review_url}`, `approval_withheld`, `summary_path` (`<summary dir>/<run>/review-loop-<loop>.md`, every pass), `linked_task`, `loop_id`.
- **File checks.** `checkReviewLoopStep` refuses `handoff`, `steward: true` without `agent_author` (unless it is an expression), both subjects written as values, neither, `scope` with literal `prs`, and a literal `prs` that is not a list of at most 20 numbers; the catalog's `pr_number`/`prs` constraints are unchecked so a workflow such as `review-loop` can pass both on from its inputs. `ReviewLoopDiagnostics(data, d, maxReentries)` marks a literal `max_reentries` above the instance's; the server adds it to the editor's and the definitions' diagnostics (`Server.SetReviewMaxReentries`).
- **Tests.** `internal/handofftest/review_loop_pass_steps_test.go` (T1: a repeat loop of pass, confirm and wait to approval; a reviewer killed once and twice; a stuck loop's actions and End; Another pass and the window), `internal/handofftest/review_loop_steps_test.go` (T1: outputs, `loop_not_owned`, `invalid_subject`, codes and the other loop's ID, the settings on the record); `internal/engine/workflow/review_loop_test.go` (T4); `TestALoopAnOpenStepHandedOnIsOwnedWhileItsRunRuns` (store).

### Agent completion

Host-side advance (spec LEG-482 §5.4; `workflow_advance.go`). `legato workflow step complete` runs inside the agent's own pane, so its service is record-only (`SetRecordOnly`, set by `workflowServiceFactory` for every CLI command). `Complete` collects the outputs, then `store.RecordWorkflowStepCompletion` marks the step and its attempt succeeded and moves the run's `current_step_id` to the next step, which stays `pending`. It also sets the step's `advance_due`, all in one CAS. A host (serve and the TUI start `StartAdvanceLoop`) then claims the advance (`ClaimWorkflowAdvances`: `advance_claimed_at`, taken again after `advanceClaimStale`, 2 minutes, from a process that died). It calls the executor's `Finish` unless the step keeps its agent (`keepsAgent`: `keep`, `keep_agent`, or `on: <task>` without `stop`), then starts the next step if the run is still at it and it is still pending (`startNextStep`), then clears the advance (`FinishWorkflowAdvance`). A failed `Finish` leaves the advance due for a later try. A recovered advance (its claimer died after starting the next step) runs `Finish` again, so `FinishWorkflowAgent` returns at once when the attempt's own session row is gone: the agents of one task share the tmux name `legato-<task>`, and killing it again would stop the next step's agent. The advance loop wakes on the IPC message in serve too (`Server.NotifyWorkflowChangedKind` keeps the kind). The loop advances at once on start, on each `completed_step` `EventWorkflowChanged` (the CLI broadcasts it over IPC, as does `legato learn reflection submit`), and every 30 seconds. A host's own `Complete` (the server's reflection route, tests) advances inline through the same claim. This order fixes LEG-452: the next `agent.run` never meets the last agent still running on the run task. When the step is recorded but the next step cannot start, a host's `Complete` returns a `*StepRecordedError` (matched by `ErrWorkflowStepRecorded`) that says the step was completed and why the next one failed, so a caller does not retry a completion that already took; the run is failed at the next step as before. Learn's borrowed-agent interview completes through `legato learn reflection submit`, which persists the typed reflection before completing its exact waiting attempt ([Legato Learn](learning.md)).

Where an agent step's result must go (LEG-532). `buildWorkflowAssignment` (`workflow_agent.go`) lists the declared outputs, sorted, and says the conversation is not kept: Legato removes the agent once the step completes, unless `keep_agent` is set. With no outputs, it says nothing the agent writes is kept and not to report a result as delivered in chat. `workflowengine.Check` warns of an `agent.run` step with no outputs and no `keep_agent` (`outputlessAgentSteps`), but only for a file that otherwise loads. A `keep_agent` that is an expression gets no warning. `WorkflowService.Show` fills `output_warning` on each succeeded `agent.run`/`agent.dispatch` step whose recorded outputs are empty (none, or only empty values) and which kept no artifact. It also fills a quiet `output_warning` on the run (`workflow_output_warning.go`). `ListRuns` fills the run's from one query (`store.ListSucceededAgentStepsWithoutArtifacts`). The web run page shows the step's warning in **Now** (**No output** when nothing was produced) and in the step, and the runs list adds it after how long the run took.

Scratch folders (LEG-530; `workflow_scratch.go`). An `agent.run` step with `with.scratch: true` (a literal boolean; the catalog refuses it with `working_dir` or `repo`) works in `<data_dir>/workflow-scratch/<attempt>`. `AgentRunExecutor.SetScratchRoot` gives it, wired in `cmd/legato/workflow_runtime.go`, with `store.WorkflowAttemptInUse` (the attempt runs, or the agent it kept does). `Start` sweeps kept folders over a week old that nothing uses, then makes the attempt's folder. `Finish` (a completion that does not keep its agent) removes it after `FinishWorkflowAgent`, and only a direct child of the root with a plain name. A failed or cancelled attempt never finishes, so its folder stays for a look. The completion contract tells the agent that the folder goes. The sandbox shows the agent its own folder only (`workflowScratchDir` in `sandbox_plan.go`).

### Suspended steps: an agent Legato stopped with

A shutdown or crash is not a failure of a step (LEG-625; `internal/service/agent_interrupted_workflow.go`, `workflow_suspend.go`, `internal/engine/store/workflow_suspend.go`). The status `suspended` (`store.WorkflowSuspended`) is set on an `agent.run` attempt, its step and its run together. Statuses are free text, so it needed no migration; the store's `FailWorkflowStep` and `CancelWorkflowRun` take it.

- **When.** Only the startup sweep (`SweepInterruptedAgents`) suspends: a main-slot session whose tmux session is gone becomes `interrupted`, and `endGoneSessionFor` suspends each `agent.run` attempt waiting on it (`SuspendWorkflowStep`, error `Legato stopped while the agent was working`; the attempt keeps no end time). Before that, the sweep works out the resume (`planInterruptedResume`). If the agent could not be resumed (no conversation, folder gone, a tool that cannot resume), the session is ended `dead` and the step fails with `…, and it cannot be resumed: <why>`, so the failed step is the one Attention item. An `agent.interview` attempt on an interrupted agent still fails, as does any attempt of a named slot's agent (the sweep ends those `dead`; making the interrupted list slot-aware is a follow-up). An agent that exits while Legato runs fails its step as before.
- **A Legato restart marks nothing.** `legato restart`, an update and stopping `legato serve` or the TUI all leave tmux running, so the agents go on working, and one that finishes meanwhile records its completion from its pane (`RecordWorkflowStepCompletion`, which needs the attempt `waiting_agent`); the next host advances it. Only a lost tmux session suspends a step, so nothing is marked at a clean stop.
- **Attention.** A suspended step has no item of its own: the run is not `running`, so `ListRuns` does not enrich it, and the workflow producer skips it. The interrupted agents' item (`interrupted_agents`) is the one item; it lists the agent with `InterruptedAgent.Workflow` (run, step, run title).
- **Resume.** The agent service's `ResumeInterruptedAgent` (Resume, Resume all, `POST /api/agents/{task_id}/resume`) no longer refuses a workflow's agent: `restartOwner` is split, and only `swarmOwner` refuses here (Reload still refuses both). `interruptedAttemptOf` finds the attempt the resume continues; `workflowResumeOptions` starts the agent as the workflow's again (`ExecutionWorkflowAgent`, the run, the attribution task, slot and label, so it is sandboxed as before), with its saved conversation (`SessionPolicy: "resume"`) in the same working folder or job clone (`Repo` is not passed, so no new clone), and the attempt's env (`LEGATO_TASK_ID`, `LEGATO_WORKFLOW_RUN_ID`, `LEGATO_WORKFLOW_STEP_ID`, `LEGATO_WORKFLOW_ATTEMPT_ID`, and `LEGATO_WORKFLOW_BINARY` when the agent service knows its binary). Its first message is `WorkflowResumedNote` (`[legato interrupted]`, the step is still open). `ResumeWorkflowStep` then points the same attempt at the new session (`agent_session_id`, `tmux_session`) and sets it, its step and its run back to `waiting_agent`/`running`, so `legato workflow step complete` completes it and `FinishWorkflowAgent` stops the right agent (or keeps it, with `keep_agent`). The new execution names no attempt: `idx_executions_workflow_attempt` allows one execution per attempt, and the agent graph falls back to the run's current step. A kept agent (`keep_agent`, no open attempt) resumes as the workflow's agent too, with no attempt env.
- **Cannot resume after the sweep.** If the resume's plan fails (the folder or conversation went since), the step fails with the reason and the interrupted agent is ended. Retry is offered as for any failed step.
- **Dismiss, Retry, Cancel.** Dismissing the agent fails the step (`its agent was dismissed after Legato stopped`). `Retry` on a suspended step fails the attempt (`retried by the operator`, `StepFailure.Retired`: as `on_failure: fail` would, whatever the step says, so a `continue` never moves the run past the step it retries), dismisses the agent, then retries as usual with a fresh agent. `Cancel` dismisses the interrupted agents of the run's suspended steps.
- **The run page.** `WorkflowService.ResumeStep` (`POST /api/workflow-runs/{run_id}/steps/{step_id}/resume`, `SetInterruptedAgents`) resumes the agent of the step's resumable attempt. `Show` marks an attempt `resumable` when an interrupted agent that can be resumed lists it.
- **Runs an earlier Legato failed.** A failed attempt whose error is `agent exited before step completion`, executor `agent.run`, latest of its step, at the failed run's current step, and whose agent session is still `interrupted`, is offered Resume too (`legacyInterruptedAttempt`); the resume first reopens it as suspended (`ReopenWorkflowStepSuspended`). Nothing is migrated. A run whose interrupted session was replaced (by a hand-started agent on the card) is not offered it.
- **Steps that wait on a service or the operator** (`waiting`: `github.pr.wait`, `github.pr.review_passes`; `waiting_manual` gates) have no agent session, so the sweep leaves them as they were (`TestStepsWaitingOnAServiceOrTheOperatorSurviveTheStartupSweep`). A review loop's reviewer is a named slot: the sweep ends it `dead`, and its review pass handles that.

Managed artifact collection is replay-safe: rerunning an interrupted completion callback reuses an existing `(attempt, output)` artifact only when its source path and SHA-256 digest still match; changed content is rejected. Accepted files are copied atomically into managed storage so worktree cleanup does not destroy them.

### Workflow files

`internal/engine/workflow/files.go` and `internal/server/workflow_files.go`. `Folders(legacy, global, repositories, project)` lists the folders in increasing precedence, with IDs `legacy`, `global`, `repo:<preset name>` and `project`. A folder named twice is kept once, at its later place. `DiscoverFolders` reads them, and `DiscoveryResult.Shadows` names, for each workflow, the files that a later file of the same name replaced. Every discovery uses it: the server (`discoverWorkflowsIn`, presets from `s.repositories`), `workflowDiscoveryProvider(cfg, db)` for triggers, the task launcher and the Reeve (the configuration's and the web UI's presets), `legato workflow list`, `run` and `validate <name>`, `doctor` and the setup checklist. `FileFor(definition, folders)` gives `{path, folder, editable, reason}`. A built-in has no file. A file in no folder, or one that is not a regular file whose links resolve inside its folder, is read-only, so the API never writes through a link to somewhere else. The legacy folder's files are editable, but nothing is created there.

Writes go through `CreateFile` and `ReplaceFile`. `CreateFile` writes a temp file in the folder, then `os.Link`s it to `<name>.workflow.yaml`, so it never overwrites (`ErrWorkflowNameTaken`); `AddTemplate` and `SaveDraft` use it too. `ReplaceFile` compares `FileDigest` (`sha256:<hex>` of the bytes) with the digest the client read (`ErrStaleFile` otherwise), then writes a temp file and renames it over the original, keeping its mode. `RemoveFile` checks the digest the same way. The bytes are written as sent, comments and all.

Routes. Refusals are `{error, code}` with:

- `not_found` (404)
- `not_editable` (403)
- `invalid` (422, with `diagnostics`)
- `rename` (422)
- `name_taken` (409)
- `stale` (409, with the file's current `yaml` and `digest`)
- `confirm_triggers` (409, with `triggers`)
- `folder` (400)
- `not_builtin` (400)

The routes:

- `GET /api/workflows/{name}/file`: `{name, yaml, path, folder, digest, editable, reason}`. A built-in's `yaml` is its definition marshalled, and its `digest` is empty.
- `PUT /api/workflows/{name}/file {yaml, digest, confirm_triggers}`: validation (`Check`) comes first. The `name` can't change (LEG-460), and the save has to confirm triggers. Answers `{name, path, folder, digest, diagnostics}` (the warnings).
- `DELETE /api/workflows/{name}/file {digest}`: when no file of that name remains (a file it shadowed would keep the name alive), this Legato's trigger switches for the name go too (`WorkflowTriggerCoordinator.ForgetTriggers`). Runs are kept.
- `POST /api/workflow-files {yaml, folder, confirm_triggers}`: `folder` is a `writableFolders` ID, `global` by default. A name that any workflow has, a built-in's included, is `name_taken` (LEG-460), and the name must pass `ValidName`.
- `POST /api/workflow-files/check {yaml}`: `{definition, graph, diagnostics, schedule}`, writing nothing. `schedule` (with a schedule trigger) is `{description, timezone, next}`: its next three due times by `ScheduleTrigger.Next` in this machine's zone (`schedulePreview`).
- `POST /api/workflows/{name}/copy {folder}`: a built-in marshalled to a file of its name, with a comment at the top. The file then replaces the built-in (LEG-458).

Every write broadcasts `workflow_changed`. The trigger rule (LEG-459): a create or save is refused with `confirm_triggers` when the new definition has a trigger that would start runs here and the old one did not (`newlyActiveTriggers`: this Legato's switch if it has one, else the file's `enabled`). The client then repeats the request with `confirm_triggers: true`. A trigger that is paused here by a switch never asks. `GET /api/workflows` adds `folder`, `editable`, `read_only_reason`, `shadows` and `warnings` (the file's `Check` warnings) to each definition, plus `folders`, the folders a workflow can be created in. A run keeps its own `definition_json`, so a save changes no run that has started; its page says `definition_changed`.

`GET /api/workflow-runs` returns each run with `related_task_title` (also on `GET /api/workflow-runs/{id}`) and `steps`, a summary of its steps in order (`step_id`, `title`, `status`, `trigger`), which the web UI's runs list draws its step bar and sentence from (the handler sets `WorkflowRunFilter.WithSteps`; the service's own scans of runs, such as the attention count, leave it off). It takes optional `status`, `workflow_name`, `limit` (1–100) and `input.<name>=<value>` parameters. Multiple input filters are ANDed and compare normalized scalar JSON values, so numeric and boolean inputs can be given as query text. Results are newest first. Input names that cannot be represented safely as a direct JSON object key, repeated singleton or input values, empty input values and out-of-range limits return `400` rather than silently broadening the query.

### Workflow graph

`workflowengine.BuildGraph(*Definition) *Graph` (`internal/engine/workflow/graph.go`) builds the **workflow graph** of a parsed definition: a pure function, so it never disagrees with what validation accepted. The model is JSON, versioned with `GraphVersion` (2 since LEG-484), and general: nothing in it assumes one chain. Version 2 changed three things: a step says how it starts as `start` (was `trigger`) and carries its `path`; a loop's body is drawn; and `if:` is drawn as branches (below). Every graph is built from a definition when it is served, a run's from its own `definition_json`, so a version 1 file or run gets a version 2 graph too.

- **Nodes**, each `{id, kind}` with a stable ID: `trigger:manual` (kind `trigger`, `trigger: {kind: "manual", summary: "Run by hand", enabled: true}`), the start node every workflow has; `trigger:<kind>` for each kind the definition's `on:` declares (`workflowengine.TriggerKinds`: `task.entered_column`, `schedule`, `pr.changes_requested`, `chat.message`, `chat.mention`, `chat.button`, in that order), with `summary` ("Card enters Triage", `ScheduleTrigger.Describe`, "Changes requested on a PR", "Message in C123 on slack", "Mention of discord", "Button fix:… in C1 on slack", with " (fallback)" after a fallback chat trigger), `enabled` as the file says, `confirm`, `max_runs_per_day` (`TriggerCommon.Limit`, so 3 when absent) and `definition` (the trigger as declared); and `step:<step path>` (kind `step`) with `step: {id, path, title, type, start, key, definition}`, where `path` is the step's path without a pass (its ID, or in a loop's body the loop's path, a slash and its ID: `each/build`; a run's step instance `each/2/build` is drawn in that node), `start` is `automatic`, `manual` or (a version 1 file's) `agent_ended`, `gate` is `manual` or `agent_ended` for a **gate** (a step that does not start by itself; empty otherwise), `definition` is the step as declared, and `key` is `{field, value}`, the one value chosen per executor type (`stepKey`): `macro`, else the prompt's first line, for `agent.run`, `agent.dispatch`, `agent.message` and `agent.interview`; `instructions` for `agent.compact`; `column` for `task.move`; `pr` (`repo#pr_number`) for `github.pr.review_passes`, `github.pr.prepare` and `github.pr.wait`; `repo` for `repo.ensure`; `path` for `file.remove` and `worktree.remove`; `body` or `body_path` for `task.note`; the sorted keys of `values` for `task.metadata.set`; `text`, else `channel`, for `chat.message.send`; `emoji`, else `message_id`, for `chat.reaction.add` and `chat.reaction.remove`; `thread_id`, else `channel`, for `chat.thread.read`; empty otherwise. Values are as written, expressions included.
- **Groups**: a `github.pr.review_passes` step keeps its node (`step:<id>`, so order and data edges and run state attach to it) with `step.group: "review_loop"`, and gains two nodes of kind `inner` with `parent` set to it: `step:<id>/pass` (`inner: {role: "pass", title: "Review pass"}`) and `step:<id>/fixes` (`role: "fixes"`, "Author fixes"), joined by two `loop` edges, pass → fixes and fixes → pass. The loop itself runs in `ReviewPassService`.
- **Loops** (`GroupLoop`): a loop step's node has `step.type: "loop"`, `step.group: "loop"` and `step.loop` (`GraphLoop`: `form` `over`, `next` or `repeat`, `max` (its `Limit()`), `summary` in words, and `until` in words). Each body step is a step node of its own whose `parent` is the loop's node, nested loops included; a `next:` loop's query is a node `step:<loop>/next` (ID `next`, the query's type) at the start of the pass. `loop` edges lead from the loop to its pass's first node and from its pass's last back to the loop.
- **Edges**, each `{id, kind, source, target}`, ID `<kind>:<source>><target>`: `start` (each trigger node → first step), `order` (step → next step in its scope), `loop` (above), `branch` and `data`. A step with `if:` is led into by `branch` edges in place of start or order edges, with `condition`, its `if:` in words (`conditionText`: `steps.a.outputs.choice equals Continue`, `all` joined by `and`, `any` by `or`, `not (…)`, `exists`, `is empty`, `in a, b`, `>`, `<`), and its predecessors have a `branch` edge with `skip: true` past it to the next step of its scope (the loop, after a body's last). `data` leads from a step to a later step whose `with`, output `path`, `if:`, or (for a loop) over, query, key and until read its outputs as `steps.<id>.outputs.<key>`, the source found as the engine finds it (the nearest step of that ID: the step's own scope, then each enclosing one); a loop's pass `outputs:` values make `data` edges from its body's steps to the loop. One edge per pair of nodes, with `outputs`, the keys used, sorted, after every other edge.

`GET /api/workflow-runs/{id}` adds `graph` (built from the run's own `definition_json`, never the current file; `runWithGraph` in `internal/server/workflows.go`), `definition_changed` (a discovered definition of the run's name differs from that copy; both are compared with `Source` cleared, through `workflowengine.Digest`, so a moved file is not a change), `definition_missing` (none is discovered) and `trigger_kind` (`WorkflowRunView.TriggerKind`, which `WorkflowService.Show` reads from the run's trigger request; empty for a run started by hand). `GET /api/workflows` adds `graph` to each definition (`definitionWithGraph` in `internal/server/workflows.go`). The graph is never part of a definition's own JSON, which runs store and digest. A file that fails to parse stays in `errors`, with no graph.

### Live updates and stalls

Workflow agents on the agents graph (LEG-612). `AgentGraphService` (`agent_graph_workflow.go`) gives `GET /api/agents/graph` each running agent's `workflows` (`AgentWorkflowPlace`: `run_id`, top-level `step_id`, `role`) and `runs` (`AgentGraphRun`, in the runs list's shape: title, status, current top-level step, `needs_attention` from `WorkflowService.ListRuns` when `AgentGraphOptions.Runs` is set, the top-level step summaries, and `pass` while a review loop runs). Only runs `running` or `waiting` count, read with `ListRuns` and `store.ListWorkflowAttemptsForRuns` once per graph read. Roles: `agent` (the execution's `workflow_run_id`, its step from `workflow_attempt_id`, which `store.AgentSession` now carries; or, for a task's own agent with no run (`on: <task>`), a `waiting_agent` `agent.run` attempt on its session), `interview` (a `waiting_agent` `agent.interview` attempt on the agent's session), `reviewer` and `author` (a waiting `github.pr.review_passes` attempt: its task's `reviewer` slot, and `author_task`, else `linked_task`, while its loop has not ended), and `awaited` (a waiting run whose current step starts on `agent_ended`: the run task's main agent). One place per agent and run, the one on the run's current step when there are several; an agent's places list the run that needs the operator first, then the newest. A bare `agent.dispatch` target is not placed. `WorkflowService.Show` fills each attempt's `agent_id` from its `agent_session_id` (`AgentSlotKey` of the session's task and slot): an `agent.interview` attempt keeps the run's `task_id`, so the run page links to `agent_id` first. The web UI's side is in [Web UI](web-ui.md) § Ensemble.

Run views update through targeted `workflow_changed` events (LEG-616). `WorkflowService` publishes `EventWorkflowChanged` after each write of a run's state (`workflow_events.go`, `SetEventBus`), with the run, the step path and a kind: `run_started`, `run_cancelled`, `run_stopped`, `step_started`, `step_waiting` (an agent, a service or a manual gate), `step_triggered`, `step_completed`, `step_failed`, `step_retried`. None is `completed_step`, which only a step recorded from an agent's pane sends, and which the advance loop acts on. So a run that a trigger, a schedule, a pull request's merge or the advance loop moves on shows at once. `Server.StartWorkflowEvents`, started in both runtimes, sends every `EventWorkflowChanged` on the bus to the web UI as `workflow_changed` with its `kind`, and `EventWorkflowTriggerChanged` as kind `trigger`; `NotifyWorkflowChangedKind` publishes on the bus and lets it send, so each change is one message. A workflow file created, saved, copied or deleted and a trigger switched or reset are kind `definitions`. The TUI's workflow service also tells other processes by IPC (`SetChangeListener`, `workflowChangeBroadcaster`, a message carrying its `pid`, which the TUI ignores when it comes back), so a `legato serve` on the same database shows the TUI's run changes. When an agent activity transition belongs to an active `agent.run` attempt, the server resolves its task to the persisted run and step and emits that targeted event; unrelated `agents_changed` events do not reload workflow runs or definitions. An unfinished `agent.run` step needs attention while its agent is waiting or idle. A detected exit (including a pane back at a shell) fails every waiting attempt tied to that exact session (owned `agent.run` and borrowed `agent.interview`) with `agent exited before step completion`, rather than leaving it at `waiting_agent`; Retry step can start it again. An agent whose adapter binds natively (Claude Code, Codex, Chimera) but whose endpoint is not bound within `nativeBindTimeout` (30 s) fails the attempts waiting on its session with `the agent never connected to Legato: …` and drops its launch messages (`agentService.failUnboundWorkflowSteps`, called from `deliverLaunchMessages`); other agents keep their launch messages as before (LEG-531). Such an agent's bridge must not save a resume identity the store refuses, since the refusal ends the bridge (and the Chimera link before it binds): the bridges ask `store.OwnsTaskConversation`, the same ownership rule `RecordTaskNativeSession` applies, before saving any (LEG-539). A workflow agent of a run with no related card is attributed to no task and saves none; nor does one attributed to its related card. The Workflows navigation item takes its red count from the navigation summary (`/api/navigation-summary`); run rows explain the stall, and the run page offers **Prompt to continue** for a live stalled agent. Legato does not prompt automatically, to avoid duplicate or unsafe agent work. The Runs tab loads only the runs; the Workflows tab loads the definitions and the runs (for each workflow's last run). On a phone, run rows stack, steps stay one to a line, wide values scroll inside their box, and actions are touch-sized.

The card context menu's Workflows flyout on the web board scrolls independently and flips around viewport edges; cards also expose an action button for keyboard, touch and assistive-technology access.

### Diagnostics

`workflow.Check(source, data)` (`diagnostics.go`) is `Parse` for an editor: it returns the definition only when there is no error, and `[]Diagnostic` (`severity`, `message`, `path`, `line`, `column`, `end_line`, `end_column`; 1-based, end exclusive) with every problem it can find. A YAML syntax or decoding error stops it, with the line yaml.v3 reports (a syntax error's is where its context starts) and, for an unknown key, the key's path and column (`keyOnLine`). Otherwise `Definition.problems()` lists the validation problems in the order `Validate` checks them, at most one per step (`validateStep`), so `Validate` and `Parse` still return the first, word for word. Each is a `*PathError` (`ErrorPath(err)`), whose path is built with `within` as the error is wrapped (`steps[1]` + `with.column`; triggers give `on.schedule.cron`, `on.task.entered_column.inputs.x`); `diagnosticAt` walks the `yaml.Node` tree to it and spans a one-line scalar value, else the key, else as far as the file goes. Maps (inputs, `with`, outputs, trigger inputs) are checked in key order, so the first problem no longer depends on map order. `legato workflow validate <file>` prints them as `file:line:col: message` and exits 2 (`--json`: `workflow_invalid` with `details.diagnostics`), without opening the database.

### JSON Schema

`workflow.JSONSchemaFor(version)` (`schema.go`) is the draft-07 schema of a file of schema version 1 or 2, the same bytes every time; `JSONSchema()` is version 1's, which stays published unchanged. Each has its own `$id` (`SchemaID`, `SchemaID2`, `SchemaIDFor`) and `x-legato.schema_version`. A struct field tagged `legato:"v2"` is reflected in version 2's only, `legato:"v1"` (`Step.Trigger`) in version 1's only, and `fieldSchemasV2` holds the entries version 2 says otherwise (`Step.type` is not required: a loop has none). Version 2's `step` adds `start` (`automatic` or `manual`), `if`, `on_failure`, `wait_for` (items from the signals), `timeout` (a Go duration pattern), `loop` (`Loop`: `oneOf` over/next/repeat, `max` 0–100, `next` needs `key`) and `steps` (recursive), and to its `allOf` `anyOf` type or loop, `not` loop with type or with, and `dependencies` loop ↔ steps; `loop_query` takes its `type` enum and `with` cases from the catalog as `step` does, so a step type added to the catalog needs no schema edit; `Output.value` and `Definition.outputs` (`workflow_output`) are version 2's. `schemaReflector` makes the object schemas from the `yaml` tags of `Definition`, `Input`, `Step`, `Output`, `Triggers`, each trigger kind and `Condition` (recursive, by `$ref`), all `additionalProperties: false` as `KnownFields` is. `fieldSchemas` gives each field's description, enum, pattern, default and required: every reflected field must have an entry (it panics otherwise), so a new struct field needs one. A step's `with` comes from the catalog: `step.allOf` holds one `if type == X then with: $ref with.X` for each executor (and `required: [with]` when the type has a required field or a checked group, `needsWith`, as the engine requires); `with.X` lists its fields (`fieldSchema`: integers, booleans and enums also take a `${{ }}` string unless `Literal`; `task` is a whole-reference pattern only where the engine checks it at load, `Checked`), its required fields, its checked constraints (`ExactlyOne` → `oneOf`, `AtLeastOne` → `anyOf`, `Excludes` → `not`), and `additionalProperties: false`. An unknown `with` key is a warning, not an error (LEG-461): the editor reports `additionalProperties` under `with` as a warning, and `Check` returns a `SeverityWarning` diagnostic (`unknownWithKeys`) with the definition. A later release will make it an error.

The `x-legato` extensions: at the root, `schema_version`, `step_groups`, `executors` (type, title, description, summary, group, in catalog order), `expressions` (`ExpressionContexts()`, `expressions.go`: what `${{ }}` may read at `run_title`, `with`, `output_path` and each `trigger.<kind>`'s inputs, as patterns such as `steps.<earlier step>.outputs.<output>`) and `task_fields` and `repository_fields` (`TaskFields`, `RepositoryFields`, which `validateReferences` uses too). On each `with.X` there are `type`, `outputs`, `declared_outputs`, `run_constraints` (the unchecked constraints) and `summary`. On each field there are `kind`, `expressions`, `context`, `required_at_run`, `essential`, `label` and `order` (each only when set). On the properties that take expressions, `context` names their entry in `expressions`.

The copies at `web/src/generated/workflow.schema.json` and `site/public/schemas/workflow-v1.schema.json` (published at `SchemaID`), and `web/src/generated/workflow-v2.schema.json` and `site/public/schemas/workflow-v2.schema.json` (at `SchemaID2`), are generated: `go test ./internal/engine/workflow -run TestTheGeneratedSchemaIsCurrent -update` rewrites them, and the test fails when one is stale. `TestEveryValidV2TestDefinitionMatchesTheV2Schema` validates every whole v2 file in this package's tests (any string literal that starts `schema_version: 2`) against version 2's, and `TestTheV2SchemaRefusesInvalidFiles` holds a sample it refuses. `TestEveryExampleAndBuiltInMatchesTheSchema`, `TestEveryValidTestDefinitionMatchesTheSchema` (every string literal this package's tests pass to `Parse` that it accepts, read from the source, with the lenient copy when `Check` warns) and the service's `TestBuiltInWorkflowsMatchTheSchema` validate with `google/jsonschema-go`. `TestTheSchemaRefusesInvalidFiles` holds a sample of files the schema refuses. `GET /api/workflow-schema` (`internal/server/workflow_schema.go`) serves version 2's, or with `?version=1` version 1's (another version is `400`), with `ETag`, `Cache-Control: private, max-age=300` and `X-Legato-Workflow-Schema-Version`.

### Upgrading to version 2

LEG-484, spec LEG-482 §8. `workflow.Upgrade(source, data)` (`upgrade.go`) upgrades a version 1 file that loads (else `Parse`'s error) and returns `UpgradeResult{YAML, Changed, Notes}`; a version 2 file comes back unchanged. It rewrites the text in place, as the web builder's document model does (LEG-470): each change is a byte-range edit found from `yaml.Node` positions (`sourceText`: offsets from lines and character columns, a one-line scalar's end, a block's end by indentation), applied last first, so every byte it does not change, comments included, stays. It sets `schema_version: 2`; renames a step's `trigger:` to `start:` (an empty one is removed, with its comma in a flow mapping); renames `agent.run`'s `keep_agent:` to `keep:`; and rewrites a step that started when the agent ended (`trigger: agent_ended`): the nearest earlier `agent.run` that is the run's own agent (no `on:` task, no `task`) is the source, which gets `wait_for: [complete]` when it keeps its agent; an `agent.stop` whose `with` is only `task: ${{ workflow.task }}` becomes `wait_for: [ended]` with `agent: {from: <source>}` (or keeps `task` with no source); any other such step gets an `agent.stop` inserted before it (`<id>-agent-ended`, made unique) that waits for the agent to end. `wait_for` goes on the line after the step's `type`.

**Step rewrites.** `stepRewrites` maps a step type to a `StepRewrite`, which gets an `UpgradeStep` (`ID`, `Type`, `With`, `Line`) and may `Replace` the step with version 2 steps (YAML written at the left margin, indented as the step was; the upgrade's own edits inside it are dropped), and say where each of its outputs went: `MapOutput(name, path)` rewrites every later `steps.<id>.outputs.<name>` in the file to `path`, and `Unmapped(name, reason)` flags each one as a warning note at that reference's line and columns in the upgraded text (`flag`, shifted past the edits before it). The map is empty: LEG-599 adds the inline review step's rewrite (`github.pr.review_passes`) there. `TestAStepRewriteFlagsAReferenceItCannotMap` drives a fake one. When the upgraded file does not load, `Check`'s errors are added to `Notes`.

Callers: `legato workflow upgrade <file> [--stdout] [--json]` (`cmd/legato/workflow_upgrade.go`, see [CLI](cli.md)); `POST /api/workflow-files/upgrade {yaml}` (`workflowFileUpgradeHandler`, read class, writing nothing) answers `{yaml, changed, notes}`, or `422` `invalid` with `diagnostics` for a file that does not load, for the web editor's **Upgrade to v2** (see [Web UI](web-ui.md)); and `PausedDraft` (`draft.go`), which upgrades a version 1 draft before it pauses its triggers and refuses one the upgrade left notes on, so `draft_workflow` and `POST /api/workflow-drafts` save version 2. The built-in workflows (`legato-job`, the Learn ones) stay version 1 in Go: a copy of one is a version 1 file, which the editor offers to upgrade.

Expression contexts: `ExpressionContexts()` is what the web editor completes and checks `${{ }}` from (`web/src/lib/workflowExpressions.ts`). A change to the rules in `validateReferences` (or a new context) must change `expressions.go` too. `testdata/expressions.json` holds the verdicts both sides must give (`TestTheSharedExpressionTable` here, `workflowExpressions.test.ts` in the web UI), so add a row when a rule changes.

### Extension model

**The executor catalog** (`internal/engine/workflow/catalog.go`, `Catalog()`, `LookupExecutor`) is where a step type declares its contract, and the one place a new executor is added before anything else: its `with` fields (`Field`: name, `FieldKind` such as `text`, `task`, `task_or_id`, `repository`, `path`, `column`, `macro`, `agent`, `tier`, `json`; `Required` (the file does not load without it), `RequiredAtRun` (the executor fails without it), `Default`, `Enum`, `Literal` (no `${{ }}`), `Checked` with `Invalid` (the value's kind is checked at load, with that message), and for the editor's inspector `Essential` (shown first; the rest go under More options), `Label` (plain words, such as "What it should do"; `Field.at` places a shared field with its own order and label) and `Order` (from 1)), its `Group` (where the step picker lists it: one of `StepGroups`, Agents, Code, Board, Learn or Cleanup; `TestOfferedStepTypesAreInAPickerGroup`), its `Summary` (the fields a step row is summed up by, the first with a value: `macro` then `prompt` for `agent.run`, `column` for `task.move`), its `Constraints` (`ExactlyOne`, `AtLeastOne`, `Excludes`; a `Checked` one is enforced at load), its `Outputs`, and `DeclaredOutputs` (an agent completes the step with the outputs the step declares, as for `agent.run`). Every step type is offered; the Learn ones (`agent.interview`, `learning.packet.prepare`, `learning.proposals.submit`, group Learn) were `Internal` and hidden from the builder until LEG-603, which removed the flag. `TestOfferedStepTypesSayWhatTheInspectorAndTheirRowShow` fails when an offered step type has no essential field, no summary, or a field without a label or a distinct order (LEG-502). `Definition.Validate` takes its list of step types from the catalog, and `validateStepContract` checks checked constraints, then checked fields, then required fields. Only what was checked before the catalog is `Checked` or `Required`, so every file that loaded still loads; unknown `with` keys are still accepted (LEG-461). `TestEveryWorkflowExecutorHasACatalogEntry` (`internal/service`) finds each executor's `Type()` in the package's source and fails when one has no catalog entry, or an entry no executor. The JSON Schema and the web builder are made from the catalog (LEG-457).

Workflow persistence and UI are executor-neutral. A future deterministic executor declares its contract in the catalog, implements the service executor contract and renders type-specific details without replacing runs, steps, attempts, outputs or artifacts. DAGs, parallel execution, schedules, shell plugins, approval gates and native external publishers (but for `github.pr.review_passes`) are not part of schema version 1.

## Triggers on a worker's handed-off cards

A card a main handed off to this Legato is the main's (LEG-243). `WorkflowTriggerCoordinator.process` checks `store.OpenHandoffForTask` before anything else and marks the trigger request `skipped` with the reason ("the card was handed off from <main>, whose workflows run when it returns; set handed_off: true on the trigger to run on such cards") unless the trigger sets `handed_off: true` (`TaskEnteredColumnTrigger.HandedOff`, schema v1). The `learn` template's trigger is skipped the same way (it does not set `handed_off`), so a worker's curator does not curate a main's task into the worker's ledger. The main's own triggers run when the task returns into another column (a `handoff` transition; see [Integrations](integrations.md) § Handing off a task). Review passes are not workflows and are unaffected. The Workflows page says "cards handed off from a main included" on a trigger that opts in; trigger requests themselves, skipped ones included, are not listed by any route yet.

## Steps on a task that is away

A task away on a worker is read-only on the main (`RefuseAway`). `task.move` was already refused through `moveCard`; `task.metadata.set` now asks `RefuseAway` too and fails the step with its words (LEG-239). `task.note` still adds the note on the main, where it is when the task returns, and adds `away_on` and `warning` to its outputs: the note is not forwarded, so the worker's agent works without it. Forwarding it to the worker as a main note was the alternative; it would need a handoff route of its own and an agent told mid-turn, and the operator can message the agent instead.

## Pausing triggers

Every trigger kind has `enabled` (`*bool`; absent is on). `Triggers.List` gives each declared trigger's kind (`TriggerTaskEnteredColumn`, …) and `EnabledByDefault`; a new trigger kind adds itself there. ## Loop stop and trigger requests for every kind

Migrations 123 and 124 make `workflow_trigger_requests` hold every trigger kind: `transition_id` may be NULL (123 edits the table text through `writable_schema`, so `store.go`'s `triggerSchemaEdits` bumps `schema_version` after it, as for 058), status `held` is added, and 124 adds `trigger_kind` (default `task.entered_column`), `item` (what the loop stop counts by: the task, `owner/repo#n`, the due time), `event_key` (unique per `(workflow_name, trigger_kind, event_key)`, NULL for a column move) and `event_json` (`{task_id, context}`). Reads go through `triggerRequestColumns`, which gives a missing transition or key as `""`. `InsertWorkflowTriggerEvent` (`ErrTriggerEventSeen` when another Legato on the database made it first), `CountStartedTriggerRuns`, `LatestTriggerEvent`.

Every trigger kind says `confirm`, `enabled`, `max_runs_per_day` and `inputs` (`Triggers.Common`; `TriggerCommon.Limit`, `DefaultMaxRunsPerDay` 3). Before a request starts a run, `WorkflowTriggerCoordinator.loopStop` counts the requests of that workflow and trigger for the item that reached `starting`/`started` in the 24 hours before the coordinator's clock (`SetClock`; a request's `created_at` is set from it); at the limit the request is `held` with "stopped to prevent a loop: …". `RunAnyway` starts a held request past the limit; `PauseTrigger` sets the trigger's switch to paused here and skips the request. Attention: `workflow_trigger_loop_stop` (high urgency, actions `run_anyway` and `pause_trigger`), navigating to the task, or to the Workflows tab (`workflows`) when the event names none.

`Fire(TriggerEvent)` is the path for every kind but column moves: a paused trigger or an event already seen makes nothing; otherwise the request is inserted and `processEvent` resolves the trigger's `inputs` against the event's context (`${{ schedule.time }}`, `${{ event.repo }}`, … through `resolveMappedInputs`, which the column trigger shares), then the loop stop, confirmation and the run. `Reconcile`, `SupplyInputs` and `Confirm` take event requests through the same path.

## Schedule trigger

`on.schedule` (`workflowengine.ScheduleTrigger`, `schedule.go`): `every` (`daily`, `weekdays`, `weekly`) with `at` (`HH:MM`) and, for weekly, `on` (a weekday); or `cron` (five fields, `*`, n, `a-b`, lists, `/step`, month and weekday names, weekday 7 = Sunday; day-of-month and weekday ORed when both are restricted, as cron does). `every` forms compile to a cron spec (`spec`). `timezone` (an IANA zone, checked with `time.LoadLocation`; `time/tzdata` is embedded), `catch_up` (`once`, default, or `skip`; used by missed runs), and the common `enabled`, `confirm`, `max_runs_per_day`, `inputs`. `Next(after, loc)` and `Prev(before, loc)` are pure: they walk wall-clock dates in the zone, and `wallInstant` turns a wall minute into an instant: one that does not exist (clocks forward) is the next minute that does, one that repeats (clocks back) its first coming, so each fires once. `DueBetween(from, to, loc, limit)`. `Describe` is the page's words.

`WorkflowTriggerCoordinator.TickSchedules` (every process that runs triggers: `StartEventLoop` starts `scheduleLoop`, a tick just after each minute) fires each schedule's latest due time when it is at most `scheduleTickWindow` (5 minutes) old, through `Fire` with key and item = the due time in UTC RFC 3339: the unique `(workflow_name, trigger_kind, event_key)` index makes it one request whichever process ticks first; there is no leader. The event context is `schedule.time` and `schedule.previous_time` (the schedule's due time before it), RFC 3339 in the schedule's zone. `SetHostZone` (tests) replaces `time.Local`. `TriggerStates` adds `schedule` (`description`, `timezone`, the next three due times, and `last`: the newest due time's status and run, `LatestTriggerEvent`), which the Workflows tab shows beside the trigger's switch (`ScheduleTimes`).

### Missed runs

`CatchUpSchedules` runs in `StartEventLoop` before the first tick: for each enabled schedule with a due time recorded (`LatestTriggerItem`, the greatest `item`; a schedule's item is its due time in UTC RFC 3339, which sorts as time does), the due times after it and before the tick window are each recorded as a `missed` request (status added to migration 124's check; `recordMissed`, error "Legato was not running at … (catch_up: …)"), once: the event key makes a restart record nothing new. With `catch_up: once` and anything newly recorded, one late run is fired with key `late:<newest missed>`, item the newest missed, `schedule.time` the newest missed, `schedule.previous_time` the due time recorded before them, and `schedule.late: true`. A schedule never recorded has nothing to catch up. `ScheduleState` adds `missed` (newest ten, `ListTriggerEvents`) and `catch_up`, shown on the Workflows tab. A due time whose run cannot start is a `failed` request, which the trigger Attention producer already shows.

## chat.message and chat.mention

`on.chat.message` and `on.chat.mention` (LEG-624; `workflowengine.ChatTrigger` in `chat_triggers.go`, declared as the distinct types `ChatMessageTrigger` and `ChatMentionTrigger` so the schema has a definition per kind; `Triggers.Chat(kind)` gives either as a `*ChatTrigger`). Fields: `bot` (required, a bot's name matching `^[a-z][a-z0-9_-]*$`; Legato's bots are `slack` and `discord`), `channel` and `user` (the platform's IDs), `text` (`{contains}`, ignoring case, or `{regex}`, Go RE2 at most 512 characters, at most one; and `not_contains`/`not_regex`, the same tests negated, alone or beside one (LEG-637); every test given must hold and at least one is required), `include_bots` (messages other bots post; off by default), `fallback` (below), `loop_item` (`channel`, the default, or `thread`), and the common `enabled`, `confirm`, `max_runs_per_day`, `inputs`. `ChatTrigger.Matches(ChatEventFields)` is the filter, pure. It ignores `fallback`: a fallback's filters apply as any trigger's.

The chat bots' supervisor (`service.ChatBots`, see [Integrations](integrations.md) § Chat bots) hands each message to `WorkflowTriggerCoordinator.ChatEvent` directly, not through the event bus, which drops when full. `ChatEvent` fires `chat.message` for every message that matches, and `chat.mention` too when the message mentions the bot or is sent to it directly (a DM), so a workflow declaring both gets two requests for a mention, each counted by its own kind. The bot's own messages never reach it (the adapters drop them). Key `<platform>:<bot>:<channel>:<message id>` (a Slack ts is unique only within its channel; a Slack redelivery is the same key); item `<bot>:<channel>`, or `<bot>:<channel>/<thread id>` with `loop_item: thread` (`ChatTrigger.ItemFor`), never empty. Inputs read `${{ event.bot }}`, `event.platform`, `event.channel`, `event.user`, `event.text` (the sender's own text, then `"\n\n"`, then `ChatEvent.ForwardedText`, the messages it forwards quoted (LEG-634); the `text` filter matches all of it uncut, and the request keeps it cut to `MaxChatEventText`, 8 KiB, in `event_json` by `keptChatText`: the forwarded part first, ending `\n> …`, and only when the own text alone is too long is that cut and the forwarded part dropped), `event.forwarded` and `event.forwarded_url` (on every chat event, `false` and `""` for a message that forwards nothing, so a mapping never misses), `event.message_id` and `event.thread_id` (the forwarding message's, not the original's): what `chat.message.send`'s `thread_id` takes to reply to the message (Slack: the thread's ts, or the message's own; Discord: the thread channel's ID when in a thread, else the message's ID, sent as a reply).

**Fallbacks (LEG-637).** `ChatEvent` works in two passes. `matchingChatTriggers` collects every trigger whose filters pass and that is on here (`triggerEnabled`: a paused trigger never matches), split into normal and fallback; then it fires the normal ones, then the fallbacks. With no normal match, each fallback fires with `fallback: "no other enabled chat trigger on <bot> matched"` beside `event` in its event record (`event_json`'s `context`). Otherwise each fallback gets a request recorded `skipped` (`TriggerEvent.Skip`: `Fire` inserts it under the usual key, so a redelivery stays a no-op, and starts nothing), its `error` `fallback: matched by <workflow> (<kind>), …`, sorted, the first five then `and N more`. Scope is the bot across both kinds, the fallback's own workflow included; a normal match counts whatever its request then does (held, waiting, failed); fallbacks never stop each other, so several may fire. `skipped` requests are not counted by the loop stop nor shown in Attention. `workflowengine.ChatFallbackDiagnostics(data, d, others, enabled)` warns at `on.<kind>.fallback` when an enabled normal trigger on the bot has no `channel`, `user` or `text` (a `chat.message` one covers both kinds, a `chat.mention` one only mention fallbacks; one without `include_bots` does not cover a fallback with it); `others` named as `d` are passed over. The server runs it in `checked` and the list's `definitionWithGraph` with this Legato's switches (`Server.triggerActive`); `legato workflow validate` runs it over the discovered folders with each file's `enabled`.

**`chat_help` and `event.commands` (LEG-637).** `Definition.ChatHelp` (`chat_help: true`) lists a workflow in `${{ event.commands }}`, which `ChatEvent` sets on every event it fires (`chatCommands`): one line per `chat_help` workflow with an enabled, non-fallback chat trigger on the message's bot, sorted by title, `• <title> — <first line of description>` (the description cut to 200 characters by `cutRunes`; the title alone without one), joined by `\n`, at most 4 KiB, `maxDiscordCommandsBytes` (1,500) on Discord, its last line `… and N more` counted in the bound (`boundedLines`); `""` when none. Plain text, so Slack mrkdwn and Discord markdown show it alike. `Check` warns at `chat_help` (`unlistedChatHelp`) when the workflow has no chat trigger.

`chat.message.send` (`service.ChatSendExecutor`, group **Chat**): `bot` (field kind `chat_bot`, checked against the name pattern at load), `channel` (`required_at_run`: empty is the bot's `default_channel`), `text`, `thread_id` (any message's ID in the channel: a Slack ts becomes `thread_ts`, so the reply goes in that message's thread, and a reply's ts is untested there, so the docs say to give the parent; a Discord message ID becomes `message_reference`), `buttons` (field kind `chat_buttons`, LEG-636, LEG-641: a list of 1 to 25 (`MaxChatButtonEntries`) `{label, value, style, if}`, at most 5 without `if`, checked at load by `checkChatButtons` in `chat_button.go`: only those keys, label and value text, a literal label at most 75 characters and a literal value at most 100, literal values unique among buttons without `if`, `style` `primary` or `danger` or absent; `checkChatButtonConditions` (from `validateStep`) decodes each `if` as a `Condition` (`decodeCondition`, unknown keys refused) whose fields `pathType` reads as a step's `if:` fields are read. At run `ResolveStep` resolves a `chat_buttons` field with `resolveScope.chatButtons`: each button's `if` is evaluated with `resolveScope.field` (as `StepRuns` does), a false one drops the button, and the rest are resolved without their `if`; every button dropped leaves `[]`, which sends the message without buttons. A list given whole by `${{ }}` resolves as it is, any `if` in it ignored. `chatSendButtons` in `workflow_chat_send.go` checks the resolved buttons with `checkChatButtons` (at most 5; label 75; value 100, unique; style), failing the step as `with buttons: button N: …` before sending. `stepOutputsUsed` draws a button `if`'s fields as data edges (`chatButtonConditions`).) The `bot` and `channel` fields are the catalog's `chatBot` and `chatChannel`, which every chat step shares. On Discord the text's `:names:` in `chatEmoji` become the emoji, outside code spans and blocks and custom emoji markup (`<:name:id>`, `<a:name:id>`; `expandEmojiShortcodes`); Slack renders shortcodes itself, so its text is sent as written. The schema gives `chat_buttons` the item shape (`if` a `$ref` to `condition`, `maxItems` 25); the web editor draws it as rows (`ChatButtonsField` in `StepsEditor.tsx`), keeps a row's `if` when the row is edited, notes the rows that have one, and offers **Add a button** while fewer than 5 rows have none. Outputs `message_id`, `channel`, `thread_id` (what replies in the same thread). It fails at once, never waiting for a connection, when the bot is unknown, switched off or refused by its platform (`auth_failed`); a bot still connecting or backing off can send, since sending is an HTTP call. Each send is bounded by `ChatBots.SendTimeout` (15 s). Errors name the bot's state and never a token.

## chat.button

`on.chat.button` (LEG-636; `workflowengine.ChatButtonTrigger` in `chat_button.go`) starts a run on a click on a button a bot posted. Fields: `bot` (required), `channel`, `user` (who may click), `value` (a `ChatTextMatch` on the clicked button's value, named `value` in its errors), and the common `enabled`, `confirm`, `max_runs_per_day`, `inputs`; no `text`, `include_bots` or `loop_item`. `Match(ChatClickFields)` gives `ClickUnmatched` (bot, channel or value differ), `ClickRefused` (only the user differs) or `ClickMatched`; `Groups` is the value regex's named groups; `ItemFor` is `<bot>:<channel>/<message id>`, so the loop stop counts runs per message with buttons. `Check` warns (`chatButtonsWithoutUser`) when `user` is empty: anyone in the channel could start the workflow. `ChatBotDiagnostics` checks its `bot`.

The supervisor hands a click (a `ChatEvent` whose `Click` is set) to `startChatBots`'s handler, which calls `WorkflowTriggerCoordinator.ChatButton` (`workflow_chat_button.go`), not `ChatEvent` (which ignores clicks). `ChatButton` skips a trigger that is paused before calling `Fire`, since `Fire` returns `nil, nil` for both a paused trigger and a key seen before; key `<platform>:<bot>:click:<interaction id>` (Slack's `trigger_id`, else `action_ts`; Discord's interaction ID). Inputs read `${{ event.bot }}`, `event.platform`, `event.channel`, `event.user` (who clicked), `event.value`, `event.label`, `event.match.<name>` (`{}` without a regex), `event.message_id` (the message with the buttons), `event.message_text` (LEG-641: `ChatClick.MessageText`, Slack's `message.text` (the fallback text `PostMessage` sends beside the blocks) or Discord's `message.content`, cut with `cutUTF8` to `MaxChatEventText`, 8 KiB), `event.thread_id` (as for messages: Slack the message's thread or its own ts; Discord the thread channel, else the message's ID). Its `ChatClickOutcome` is `accepted` (with `Started` when a run started at once), `duplicate`, `refused` or `unmatched`, in that order of precedence across workflows; an accepted click's `Line` is `<label> — chosen by <@user>`, with ` · waiting in Legato` when no run started. The handler then calls `ChatBots.SettleClick(ctx, e, Line)` for an accepted click only; a refused click gets no reply (the operator's choice), and nothing is sent for the others. A click is no message, so it never fires a fallback or stops one (`ChatEvent` returns before `matchingChatTriggers`), and `chat.button` triggers are neither "other chat triggers" to a fallback nor listed in `${{ event.commands }}` (`chatCommands` reads only `chat.message` and `chat.mention`).

`chat.reaction.add` and `chat.reaction.remove` (LEG-633; `service.ChatReactionAddExecutor` and `ChatReactionRemoveExecutor`, two types so each `Type()` is one constant for the catalog parity scan, both calling `startChatReaction`): `bot`, `channel` (as send's), `message_id` and `emoji`, all essential, `message_id` and `emoji` required; nothing defaults the emoji. Output `ok: true`. `ChatBots.React` shares `Send`'s bot lookup and refusals (`ready`), its `default_channel` fallback and `SendTimeout`, and scrubs errors the same way. The emoji resolves per platform in `chat_emoji.go`, from one table of about 30 common emoji (`chatEmoji`, Slack's name first): Slack takes a name, colons trimmed, as it is (so its custom emoji and skin tones work), and an emoji Legato knows by its name; Discord takes a known name as its emoji, any non-ASCII value as itself, and `name:id` as a custom emoji, and refuses an unknown ASCII name. A reaction already there (Slack `already_reacted`; Discord answers 204 again) or already gone (Slack `no_reaction`) is success. Slack `missing_scope` fails naming the `needed` scope (else `reactions:write`) and saying to reinstall the app; Discord 50013 names Add Reactions and Read Message History, 50001 View Channel, 10008 the message, 10014 the emoji.

`chat.thread.read` (`service.ChatThreadReadExecutor`, `workflow_chat_thread.go`, group **Chat**, LEG-635): `bot` and `channel` as `chat.message.send`'s, `thread_id` (required: `event.thread_id`), `limit` (integer, default 50, 1–200, the parent included; out of range fails the step), `include_bots` (literal boolean, default false). It reads through `ChatBots.ReadThread` (see [Integrations](integrations.md) § Chat bots) and renders `chatTranscript`: a block per message, `<author name, else <@id>> · 2006-01-02 15:04 UTC`, a newline, then `keptChatText(text, forwarded)` (each message cut as `event.text` is, 8 KiB); blocks joined by a blank line. Over `MaxChatThreadTranscript` (16 KiB) the oldest non-parent blocks go until it fits, and a `[… N earlier replies left out]` line follows the parent, N counting the limit's drops too (bots left out by choice are not counted). Outputs `transcript`, `messages` (json: `id`, `author_id`, `author_name`, `at` RFC 3339 or empty, `text` as in the transcript, `forwarded`, `forwarded_url`, `parent`, `from_bot`) and `count`, both describing exactly the messages in `transcript`. It is never part of a trigger: a workflow reads the thread only with this step. `ChatBotDiagnostics` checks its `bot` as it checks a send's.

Whether a bot is set up is this Legato's, not the file's: `workflowengine.ChatBotDiagnostics` (run by the server's workflow check, file and list paths; the triggers' `bot` and every `chat.*` step's) is an error for a name no Legato has and a warning for a bot not set up or switched off here, since repository workflows are shared by Legatos that differ. A step's bot given by `${{ }}` is checked when it runs.

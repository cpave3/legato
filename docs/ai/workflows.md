## Workflows: internals

The user guide, with the YAML schema, executors, templates, triggers and CLI, is [Workflows](../../site/src/content/docs/using/workflows.md) (on the site at `/legato/using/workflows/`). This file keeps what an agent working on Legato's code needs beyond it. Parsing and discovery are in `internal/engine/workflow/`; runs, executors and triggers in `WorkflowService` (`internal/service/`); see [Packages](packages.md). The web pages are in [Web UI](web-ui.md) § Workflows; the CLI in [CLI](cli.md).

### Runs and tasks

- A run creates one local execution task in the reserved **Workflows** workspace (`ViewAll` excludes it; `ViewWorkspace(id)` opts in). A succeeded run moves it to **Done** and archives it at once.
- A `task` input's selected task is stored on the run as `related_task_id`. Agent sessions use the execution task, so an existing task's active agent session is not replaced, except for an `agent.run` step with `with.task`, whose agent is that task's own (below). `GET /api/tasks/{id}/activity` lists related runs and their managed artifacts.
- Deterministic steps execute synchronously until an agent step starts; the run then advances when that agent completes or fails its step through the CLI callback (§ Agent completion).

### Schema version 2 and the step tree

Spec LEG-482; LEG-483 is its first slice. `Parse` accepts `schema_version` 1 and 2 (`SchemaVersion`, `SchemaVersion2`). `Step.Start` (`StartAutomatic`, `StartManual`, and `StartAgentEnded`, internal: only a v1 `trigger: agent_ended` reads as it) is the one model of how a step starts. A v1 file says `trigger:` (`normalizeStart` reads it into `Start` and clears `Trigger`). A v2 file says `start:`, and each version refuses the other's key. The `start` refusal only applies to a file just decoded (`Definition.fromFile`), so validating a parsed definition again is harmless. `Definition.MarshalYAML` writes each version's own key. `Step.UnmarshalJSON` reads a run's stored definition: one kept before this change says `trigger`, which reads as `start`, so `definition_changed` and `waitsForAgentToEnd` see old runs correctly. JSON writes `start` only. The web UI reads `start ?? trigger` from step rows' `definition_json` (`stepStart`, `runNeedsYou.ts`, `WorkflowRunPage.tsx`). The graph keeps its `trigger` field until graph v2 (LEG-484). `readableOutputs` makes a step's catalog outputs readable by later steps without declaring them (both versions). Struct fields tagged `legato:"v2"` (`Step.Start`) are left out of the published v1 JSON Schema until v2 has its own (LEG-484); the schema literal test skips v2 test files.

Runs keep their steps in `workflow_steps` (migration 135), keyed by `(run_id, path)`. `workflowengine.StepPath`/`SplitStepPath` define the path: a top-level step's ID, or `<scope path>/<id>` for a loop pass's step (`each/2/build`, LEG-490). Each row has `parent_path`, `step_id`, `pass` (NULL outside loops) and `step_order`, unique per scope. `store.WorkflowStep` (was `WorkflowStepRun`) keeps the JSON names the web UI reads (`step_id`, `resolved_inputs_json` from column `resolved_json`) and adds `path`, `parent_path` and `pass`. A run creates its top-level instances at start (`stepInstances`); `CreateWorkflowSteps` adds a nested scope's when the run reaches it (idempotent). `GetWorkflowRun` lists steps by scope, the run's own first. The runs list's step summaries are top-level only. Attempts and artifacts carry `path` (FK to the step) besides `step_id`. Every service method that takes a step ID takes its path: `current_step_id`, `ResolvedWorkflowStep.StepID`, `LEGATO_WORKFLOW_STEP_ID`, `Details` keys and attention source keys are paths. `workflow_runs` gains `parent_run_id`, `parent_step_path` (LEG-489), `outputs_json` (LEG-489) and `schema_version` (the definition's). The wait-record columns (`wait_*`, `deadline_at`, `child_run_id`) and `loop_state_json` exist and stay empty until their slices.
- A step whose executor returns `WorkflowStepWaiting` (`"waiting"`, `workflow_waiting.go`) waits on that executor's own service. The step and its attempt are `waiting` (the run stays `running`; a run that is `waiting` is one at a manual gate) and carry no agent session, so `endGoneSession` does not fail them and a restart leaves them as they are. The service finishes the step with `WorkflowService.CompleteWaiting` (its outputs as a deterministic executor returns them, then the steps after it run) or `FailWaiting`, and finds its steps again after a restart with `WaitingAttempts(executorType)`. `Cancel` calls the executor's `Cancel` for a waiting attempt, as for a running one. Such a step's service may act on an outside service: the one exception to schema v1's rule against outside publishers is `github.pr.review_passes` (LEG-253), whose loop posts to GitHub; see [Integrations](integrations.md) § Review loops on any pull request. Its outputs are `outcome`, `passes`, `findings`, `reviews` (each `{pass, pr, url, event, approved}`, with `approval_withheld` and `withheld_reason` on a clean pass's outside-author `COMMENT`), `approval_withheld` (an `approved` loop that commented on an outsider's pull request instead of approving it), `summary_path` and `linked_task`. Its `Start` only writes the step, in any process; the review engine's tick in the process that serves the broker opens the loop or fails the step (spec LEG-559 D9), so a process without the engine that advances a run to it, as the TUI's `StartAdvanceLoop` may for a `serve`-started run, leaves it waiting for the holder.
- **Retry of a failed `github.pr.review_passes` step resumes its loop** (LEG-567, spec LEG-559 D1). `WorkflowService.Fail` calls an executor's `FailStep` in place of `Cancel` when it is a `WorkflowStepFailer`; the review step's (`ReviewRunCaller.FailStep`) keeps the loop: the reviewer stops, `store.HoldHandoffReviewForRetry` discards a pass in flight (reviewing or submitted) and steps the pass count back over it in one transaction, a loop that held or waited for a reviewer is `ready`, and every other phase, pass, finding, ruling and item stays; the clone is removed. Retry starts a new attempt, which waits to open as any start does. When the holder's tick opens it, `open` finds the loop an earlier attempt of the same run and step path opened (`earlierLoop`: the task's `legato.review_loop` record names the run and step, another attempt) and adopts it (`adopt`) instead of beginning at pass 0: it refuses as `open` does a pull request another loop now holds, an author already authoring one, or a pull request no longer open; holds the loop as above (also when the failure did not go through the executor, as `FailWaiting`'s does not; a loop a cancel ended goes back to `waiting_for_author` after a pass that asked for changes, else `ready`); makes a fresh clone; and last writes the record with the new attempt ID, so a crash before it leaves the step waiting to open and the next tick adopts again. The next pass takes the number after the last that counted: a pass set aside is pinned again under its own number (`InsertHandoffReviewPass`), never as a second pass 1.
- Embedded examples (`internal/engine/workflow/examples/*.workflow.yaml`, `workflow.Examples`, `ExampleNamed`) are definitions Legato ships for people to add; `TestEveryEmbeddedExampleValidates` parses each. `review-pr-passes` is the first. An optional input a step references needs a `default`, or resolving it fails as unavailable.
- `WorkflowService.Show` fills `WorkflowRunView.Details` (by step ID) from each step's latest attempt whose executor is a `WorkflowStepDetailer`; the review step's is `ReviewRunDetails` (phase, pass, a summary line, blocking open, reason, every review posted). A run's loop publishes `EventWorkflowChanged` with kind `review_loop` (`service.ReviewLoopChangedKind`), which `Server.StartWorkflowEvents` forwards as `workflow_changed` like every other workflow change, so an open run page follows the loop. The review-pass runtime (`reviewPassWake`) never ticks for a `review_loop` change, and ticks once `reviewPassRunGap` (2 s) after any other run change, however many come in that time.
- `NormalizeInputs` takes an empty value for an `integer` or `boolean` input as not given (its default, or required), as a form's blank field sends it.
- `task.note` takes `task` as a task input or a task ID as text; `optional: true` (a boolean, checked at validation) makes an empty task a skip (`note_id` empty, `skipped: true`) instead of a failure.
- `task.move` calls the sync service's `PushMove` in a configured provider runtime, which may queue the mapped remote transition even for a same-column no-op, so a previously failed push can recover. Success confirms local persistence and queueing, not remote completion.
- `agent.run` takes an optional `with.engram` (text, templated like the step's other fields; anything else fails validation, and a template that resolves to anything but text fails the step): the agent starts as that engram (`AgentSpawnOptions.Engram` with `EngramRequired`). An engram `engram identity list` does not list fails the step before anything starts; any other boot failure starts the agent without it, as an interactive spawn does (the warning goes to the log and Attention). A workflow never reads or writes engram bindings: its spawn does not touch `last_used_at`. Finishing a workflow agent (`FinishWorkflowAgent`) ends its engram session (`EndEngramSession`). See [Engram sessions](engram.md).
- `agent.run` and `agent.dispatch` take exactly one of `with.prompt` and `with.macro` (the catalog's `ExactlyOne` constraint; both, neither or an empty macro fail validation). The executors resolve a macro when the step starts through `SetMacros` (`service.MacroService`, wired in `cmd/legato/workflow_runtime.go`; `workflow_macro.go`): an unknown one fails the step (`macro "x": no macro of that name`). `agent.run` uses the macro's text as the assignment; `agent.dispatch` sends `MacroService.Message` (the task header, then the text). A step's own `agent`/`tier` win; with neither, the macro's apply.
- `agent.run`'s `with.name` (LEG-613) names that agent only: `WorkflowAgentRunner` passes it as `AgentSpawnOptions.Label`, kept on the execution (`executions.label`, migration 139), and `ListAgents` shows it as the agent's title. It no longer renames the run's task, which keeps the run's title. Without `run_title`, `WorkflowService.start` names a run with a `task` input `<title> · <card key>` (`cardKey`: the ticket's `remote_id`, else the task ID). An agent on a run's own task (a step's agent, the reviewer slot) carries `AgentSession.RunCard` (`{task_id, key, title}` of the run's `related_task_id`, joined in `agentSessionSelect`), served as `run_card` by `/api/agents` and shown as "for <key>" in the web rail; the workflows Attention producer puts "For <key>: <title>" in each item's `Detail` (`runCardDetail`, from `WorkflowRun.RelatedTaskKey`, which `WorkflowService.ListRuns` fills).
- `agent.run` with `with.task` (LEG-540; `stepAgentTask`, `workflow_agent.go`) spawns on that task instead of the run's: `LEGATO_TASK_ID`, the tmux session `legato-<task>`, slot main and the execution's attribution are the task's, and the execution stays `workflow_agent` (so Restart still refuses it). With `repo`, the clone is a card's (`legato/<task>`, `FreshBranch` in `agent.go`). A macro goes through `MacroService.Message` as `agent.dispatch`'s does. The executor returns `WorkflowExecutionResult.TaskID`, which `store.MarkWorkflowStepWaiting` writes over the attempt's `task_id`, so `Cancel`, `Prompt`, stall attention (`enrichWorkflowAttention`) and the server's activity mapping (`ActiveAgentAttemptsByTask`) find the card's agent. `WorkflowAgentRunner.TaskHasAgent` refuses a task with an agent already running. Stage places: `executionPlace(kind, attribution, task)` (`agent_stage.go`) keeps a workflow agent's stage at its execution's place only when it works on the run's own task (attribution differs from its task); a task's own agent keeps it at the card's place. Its execution is attributed to and run for its task, so it owns the card's conversation (`store.OwnsTaskConversation`, LEG-539) and its bridge saves a resume identity. The catalog refuses `task` with `working_dir`, `scratch` or `name` (`Excludes`, checked); before this change `task` on `agent.run` was an unknown key, ignored with a warning.
- `agent.run` with `task` and `slot` (LEG-618; `stepAgentSlot`) spawns in that named slot of the card (`AgentSpawnOptions.Slot`): tmux `legato-<task>_<slot>`, beside the main slot's agent. The engine checks the slot at load. `slot` is a `Literal`, checked field with `Field.Pattern` (`SlotNamePattern`) and `Field.Reserved` (`ReservedSlots`: `reviewer`), and a `Requires` constraint (`slot` needs `task`; draft-07 `dependencies` in the schema). `TestTheEngineChecksSlotsByTheAgentServicesRules` keeps the engine's copy of the rules equal to `agent_slot.go`'s. `stepAgentSlot` checks the resolved value again. `WorkflowAgentRunner.SpawnWorkflowAgent` returns the slot's session (`GetAgentSessionInSlot`), so the attempt records the slot's agent, never the main one's. `SlotHasAgent` refuses a slot that has an agent. The attempt's `task_id` is still the card. `Cancel` and `Prompt` therefore address the attempt's own agent through `AttemptAgentID`, the stall attention through `attemptAgentSession`: both use the attempt's recorded session, and fall back to the main slot only when the attempt's tmux session is not a named slot's. `FinishWorkflowAgent` was already slot-safe (session ID and tmux name) and now puts `Slot` on `EventAgentCompleted`. `StartAgentEndedLoop` still ignores a named slot's end. With `repo`, the clone request carries `Slot` and `FreshBranch` `legato/<task>-<slot>`. `RepositoryService.JobClone` always makes a named slot a new clone (a `CloneID` is refused), records `job_clones.slot`, and skips `recordCodeContext`. `LiveJobCloneForTask` joins only `slot = 'main'` clones. A review-pass run's reviewer clone is made with `Slot: SlotReviewer` too. Its reviewer still runs on the run's task; the card's reviewer slot is a follow-up.
- `agent.compact` (LEG-536; `workflow_agent_compact.go`) compacts a task's agent and waits on its own service until the agent reports the compaction's end, asking again while the agent is in its turn; see [Compacting an agent](compaction.md) § The agent.compact step.
- `github.pr.wait` (LEG-540; `workflow_pr_wait.go`, `PRWaitExecutor`) reads the pull request with `PRStateReader` (`GitHubPRStates`: `github.Client.FetchPRWaitState`, one GET for the PR and, while it is open, two for its head's CI; no reviews) when it starts: done, it succeeds at once; open, it returns `WorkflowStepWaiting`. `WorkflowService.CheckPRWaits` reads each waiting attempt's PR (its step's resolved `with`) and calls `CompleteWaiting` or, for a PR closed without merging under `until: merged` (`errPRClosedUnmerged`), `FailWaiting`; a read that fails is logged and tried at the next check. A read that fails in `Start` fails the step (the operator's Retry step reads again), so a wrong repository or number is seen at once. `StartPRWaitLoop` (serve and the TUI, beside `StartAdvanceLoop`) checks at start, every `prWaitInterval` (2 minutes, `cmd/legato/workflow_runtime.go`) and on `EventPRStatusUpdated`, at most every 30 seconds. The runtime gives it `lazyPRStates`, which makes the GitHub client at the first read, so a CLI command that runs no wait never runs `gh auth token`; without a credential the read fails the step. A checked `Enum` field (`until`) now refuses a literal outside its values at load (`Field.accepts`).
- **A waiting merge needs the operator** (LEG-614; `workflow_merge_wait.go`). `GitHubPRStates` reads with `github.Client.FetchPRWaitState`: the PR, and for an open one its head's CI (`fetchCheckStatus`, two more GETs; a CI read that fails is the read's error, so nothing is taken for "no CI": in a later check the step stays waiting for the next one, and in `Start` it fails the step, as any read there does). `PRState` carries `HeadBranch`, `BaseBranch`, `Conflicts` (`mergeable_state: dirty`, else `!mergeable`; nil while GitHub works it out) and `CheckStatus`. `PRWaitExecutor` keeps the last state per waiting attempt in memory (`remember`, `last`, `forget`; an unknown `Conflicts` keeps the last answer), filled in `Start` and `checkPRWaits`; each host process reads GitHub for itself at start, so nothing is kept across a restart. `checkPRWaits` returns the runs whose conflict or CI changed or whose wait it ended (`CompleteWaiting` and `FailWaiting` publish nothing themselves), and `StartPRWaitLoop` publishes `EventWorkflowChanged` (`Kind: PRWaitChangedKind`, `pr_wait`) for each, which the `workflows` Attention producer reconciles on. `addMergeWaits` (from `enrichWorkflowAttention`, so `ListRuns`, `AttentionCount` and `Show` all see it) gives each waiting `github.pr.wait` attempt a `MergeWait` in `view.Details[path]` (repo, number, url, state, branches, conflicts, CI, the card `task_id` from `with.task` (`stepAgentTask`) else `run.related_task_id`, its title, the card's agent `""`/`running`/`waiting`, `notify`) and, unless `with.notify: false`, `NeedsAttention` with `MergeWait.Reason()`. It fills the run view's `resume_task_id`, `resume_agent_state` and `can_resume_agent` (running or waiting run, a card, its agent not `waiting`, no attempt `waiting_agent`, a resumer wired). The catalog adds `task` (`KindTaskOrID`) and `notify` (literal boolean, default true) to `github.pr.wait`.
- **Resume agent** (LEG-614). `WorkflowService.ResumeAgent(runID, macro)` (`SetAgentResumer(MacroService, AgentService)`, wired in `buildWorkflowService`) refuses a run that has ended, a step's agent at work (`waiting_agent`) or a run with no card (`ErrWorkflowStateConflict`), and a card agent waiting on the operator (`ErrResumeAgentWaiting`). It calls `MacroService.Start` with the card, the waiting merge's PR and its head branch (`MacroStart.Branch`): a running agent gets the macro queued; else the card's main agent starts with it. An agent it started while a `github.pr.wait` waits is recorded on that attempt (`store.RecordWorkflowAttemptAgent`: `agent_session_id`, `tmux_session`, `agent_kind`, only while the attempt is `waiting`). When the PR merges or closes, `stopResumedAgent` kills the card's agent only when that very session (IDs are AUTOINCREMENT, never reused) is still its running main session, so an agent the operator started since is left alone. Nothing moves the card or touches its ticket. `MacroService.Start` now checks the folder it would start or resume in (`folderExists`, `os.Stat`); one that is gone becomes a new job clone of the PR's repository (else the code context's) on `Branch` (else the code context's branch) with `PushedBranch`, a new conversation (`SessionPolicy: new`, no resume: Claude Code and Codex keep a conversation with its folder) and a task note; with no repository it is `ErrMacroFolderGone`. Served at `POST /api/workflow-runs/{id}/resume-agent` `{"macro"}` (`workflowResumeAgentHandler`, through the optional `WorkflowAgentResumer` interface): 200 with `MacroStartResult`, 400 without a macro, 404 for an unknown run or macro, 409 for the refusals and `ErrMacroFolderGone`, 503 when the service cannot resume.
- `burnlite.task.close` (LEG-540; `workflow_burnlite_close.go`) reads the task from the store: `provider` must be `burnlite` (not a handoff's `burnlite-copy`) with a `remote_id`, else it fails, or with `optional: true` succeeds with `skipped`. It closes through `BurnliteTaskCloser` (`ConnectedBurnlite`: the connected integration's address and `OAuthTokens`, `burnlite.Client.CloseTask`, the `close_task` tool). `service.BurnliteScope` is now `read:tasks write:tasks`; a connection made with `read:tasks` gets `insufficient_scope` (`burnlite.ErrInsufficientScope`), and the step says to connect again. The summary is folded to one line and cut at 200 characters, as Burnlite takes it. Nothing pulls the card at once: the next sync moves it.
- `WorkflowService.SetAgentKinds` gives the service the configured adapters: an `agent.run` step whose `agent` is known from the inputs alone and names no configured adapter is refused when the run starts, and no run is created.

### Agent completion

Host-side advance (spec LEG-482 §5.4; `workflow_advance.go`). `legato workflow step complete` runs inside the agent's own pane, so its service is record-only (`SetRecordOnly`, set by `workflowServiceFactory` for every CLI command). `Complete` collects the outputs, then `store.RecordWorkflowStepCompletion` marks the step and its attempt succeeded and moves the run's `current_step_id` to the next step, which stays `pending`. It also sets the step's `advance_due`, all in one CAS. A host (serve and the TUI start `StartAdvanceLoop`) then claims the advance (`ClaimWorkflowAdvances`: `advance_claimed_at`, taken again after `advanceClaimStale`, 2 minutes, from a process that died). It calls the executor's `Finish` unless the step's resolved `with` has `keep_agent`, then starts the next step if the run is still at it and it is still pending (`startNextStep`), then clears the advance (`FinishWorkflowAdvance`). A failed `Finish` leaves the advance due for a later try. A recovered advance (its claimer died after starting the next step) runs `Finish` again, so `FinishWorkflowAgent` returns at once when the attempt's own session row is gone: the agents of one task share the tmux name `legato-<task>`, and killing it again would stop the next step's agent. The advance loop wakes on the IPC message in serve too (`Server.NotifyWorkflowChangedKind` keeps the kind). The loop advances at once on start, on each `completed_step` `EventWorkflowChanged` (the CLI broadcasts it over IPC, as does `legato learn reflection submit`), and every 30 seconds. A host's own `Complete` (the server's reflection route, tests) advances inline through the same claim. This order fixes LEG-452: the next `agent.run` never meets the last agent still running on the run task. When the step is recorded but the next step cannot start, a host's `Complete` returns a `*StepRecordedError` (matched by `ErrWorkflowStepRecorded`) that says the step was completed and why the next one failed, so a caller does not retry a completion that already took; the run is failed at the next step as before. Learn's borrowed-agent interview completes through `legato learn reflection submit`, which persists the typed reflection before completing its exact waiting attempt ([Legato Learn](learning.md)).

Where an agent step's result must go (LEG-532). `buildWorkflowAssignment` (`workflow_agent.go`) lists the declared outputs, sorted, and says the conversation is not kept: Legato removes the agent once the step completes, unless `keep_agent` is set. With no outputs, it says nothing the agent writes is kept and not to report a result as delivered in chat. `workflowengine.Check` warns of an `agent.run` step with no outputs and no `keep_agent` (`outputlessAgentSteps`), but only for a file that otherwise loads. A `keep_agent` that is an expression gets no warning. `WorkflowService.Show` fills `output_warning` on each succeeded `agent.run`/`agent.dispatch` step whose recorded outputs are empty (none, or only empty values) and which kept no artifact. It also fills a quiet `output_warning` on the run (`workflow_output_warning.go`). `ListRuns` fills the run's from one query (`store.ListSucceededAgentStepsWithoutArtifacts`). The web run page shows the step's warning in **Now** (**No output** when nothing was produced) and in the step, and the runs list adds it after how long the run took.

Scratch folders (LEG-530; `workflow_scratch.go`). An `agent.run` step with `with.scratch: true` (a literal boolean; the catalog refuses it with `working_dir` or `repo`) works in `<data_dir>/workflow-scratch/<attempt>`. `AgentRunExecutor.SetScratchRoot` gives it, wired in `cmd/legato/workflow_runtime.go`, with `store.WorkflowAttemptInUse` (the attempt runs, or the agent it kept does). `Start` sweeps kept folders over a week old that nothing uses, then makes the attempt's folder. `Finish` (a completion that does not keep its agent) removes it after `FinishWorkflowAgent`, and only a direct child of the root with a plain name. A failed or cancelled attempt never finishes, so its folder stays for a look. The completion contract tells the agent that the folder goes. The sandbox shows the agent its own folder only (`workflowScratchDir` in `sandbox_plan.go`).

### Suspended steps: an agent Legato stopped with

A shutdown or crash is not a failure of a step (LEG-625; `internal/service/agent_interrupted_workflow.go`, `workflow_suspend.go`, `internal/engine/store/workflow_suspend.go`). The status `suspended` (`store.WorkflowSuspended`) is set on an `agent.run` attempt, its step and its run together. Statuses are free text, so it needed no migration; the store's `FailWorkflowStep` and `CancelWorkflowRun` take it.

- **When.** Only the startup sweep (`SweepInterruptedAgents`) suspends: a main-slot session whose tmux session is gone becomes `interrupted`, and `endGoneSessionFor` suspends each `agent.run` attempt waiting on it (`SuspendWorkflowStep`, error `Legato stopped while the agent was working`; the attempt keeps no end time). Before that, the sweep works out the resume (`planInterruptedResume`). If the agent could not be resumed (no conversation, folder gone, a tool that cannot resume), the session is ended `dead` and the step fails with `…, and it cannot be resumed: <why>`, so the failed step is the one Attention item. An `agent.interview` attempt on an interrupted agent still fails, as does any attempt of a named slot's agent (the sweep ends those `dead`; making the interrupted list slot-aware is a follow-up). An agent that exits while Legato runs fails its step as before.
- **A Legato restart marks nothing.** `legato restart`, an update and stopping `legato serve` or the TUI all leave tmux running, so the agents go on working, and one that finishes meanwhile records its completion from its pane (`RecordWorkflowStepCompletion`, which needs the attempt `waiting_agent`); the next host advances it. Only a lost tmux session suspends a step, so nothing is marked at a clean stop.
- **Attention.** A suspended step has no item of its own: the run is not `running`, so `ListRuns` does not enrich it, and the workflow producer skips it. The interrupted agents' item (`interrupted_agents`) is the one item; it lists the agent with `InterruptedAgent.Workflow` (run, step, run title).
- **Resume.** The agent service's `ResumeInterruptedAgent` (Resume, Resume all, `POST /api/agents/{task_id}/resume`) no longer refuses a workflow's agent: `restartOwner` is split, and only `swarmOwner` refuses here (Reload still refuses both). `interruptedAttemptOf` finds the attempt the resume continues; `workflowResumeOptions` starts the agent as the workflow's again (`ExecutionWorkflowAgent`, the run, the attribution task, slot and label, so it is sandboxed as before), with its saved conversation (`SessionPolicy: "resume"`) in the same working folder or job clone (`Repo` is not passed, so no new clone), and the attempt's env (`LEGATO_TASK_ID`, `LEGATO_WORKFLOW_RUN_ID`, `LEGATO_WORKFLOW_STEP_ID`, `LEGATO_WORKFLOW_ATTEMPT_ID`, and `LEGATO_WORKFLOW_BINARY` when the agent service knows its binary). Its first message is `WorkflowResumedNote` (`[legato interrupted]`, the step is still open). `ResumeWorkflowStep` then points the same attempt at the new session (`agent_session_id`, `tmux_session`) and sets it, its step and its run back to `waiting_agent`/`running`, so `legato workflow step complete` completes it and `FinishWorkflowAgent` stops the right agent (or keeps it, with `keep_agent`). The new execution names no attempt: `idx_executions_workflow_attempt` allows one execution per attempt, and the agent graph falls back to the run's current step. A kept agent (`keep_agent`, no open attempt) resumes as the workflow's agent too, with no attempt env.
- **Cannot resume after the sweep.** If the resume's plan fails (the folder or conversation went since), the step fails with the reason and the interrupted agent is ended. Retry is offered as for any failed step.
- **Dismiss, Retry, Cancel.** Dismissing the agent fails the step (`its agent was dismissed after Legato stopped`). `Retry` on a suspended step fails the attempt (`retried by the operator`), dismisses the agent, then retries as usual with a fresh agent. `Cancel` dismisses the interrupted agents of the run's suspended steps.
- **The run page.** `WorkflowService.ResumeStep` (`POST /api/workflow-runs/{run_id}/steps/{step_id}/resume`, `SetInterruptedAgents`) resumes the agent of the step's resumable attempt. `Show` marks an attempt `resumable` when an interrupted agent that can be resumed lists it.
- **Runs an earlier Legato failed.** A failed attempt whose error is `agent exited before step completion`, executor `agent.run`, latest of its step, at the failed run's current step, and whose agent session is still `interrupted`, is offered Resume too (`legacyInterruptedAttempt`); the resume first reopens it as suspended (`ReopenWorkflowStepSuspended`). Nothing is migrated. A run whose interrupted session was replaced (by a hand-started agent on the card) is not offered it.
- **Steps that wait on a service or the operator** (`waiting`: `github.pr.wait`, `github.pr.review_passes`; `waiting_manual` gates) have no agent session, so the sweep leaves them as they were (`TestStepsWaitingOnAServiceOrTheOperatorSurviveTheStartupSweep`). A review loop's reviewer is a named slot: the sweep ends it `dead`, and its review pass handles that.

Managed artifact collection is replay-safe: rerunning an interrupted completion callback reuses an existing `(attempt, output)` artifact only when its source path and SHA-256 digest still match; changed content is rejected. Accepted files are copied atomically into managed storage so worktree cleanup does not destroy them.

### Workflow files

`internal/engine/workflow/files.go` and `internal/server/workflow_files.go`. `Folders(legacy, global, repositories, project)` lists the folders in increasing precedence, with IDs `legacy`, `global`, `repo:<preset name>` and `project`. A folder named twice is kept once, at its later place. `DiscoverFolders` reads them, and `DiscoveryResult.Shadows` names, for each workflow, the files that a later file of the same name replaced. Every discovery uses it: the server (`discoverWorkflowsIn`, presets from `s.repositories`), `workflowDiscoveryProvider(cfg, db)` for triggers, the task launcher and the Reeve (the configuration's and the web UI's presets), `legato workflow list`, `run` and `validate <name>`, `doctor` and the setup checklist. `FileFor(definition, folders)` gives `{path, folder, editable, reason}`. A built-in has no file. A file in no folder, or one that is not a regular file whose links resolve inside its folder, is read-only, so the API never writes through a link to somewhere else. The legacy folder's files are editable, but nothing is created there.

Writes go through `CreateFile` and `ReplaceFile`. `CreateFile` writes a temp file in the folder, then `os.Link`s it to `<name>.workflow.yaml`, so it never overwrites (`ErrWorkflowNameTaken`); `AddTemplate` and `SaveDraft` use it too. `ReplaceFile` compares `FileDigest` (`sha256:<hex>` of the bytes) with the digest the client read (`ErrStaleFile` otherwise), then writes a temp file and renames it over the original, keeping its mode. `RemoveFile` checks the digest the same way. The bytes are written as sent, comments and all.

Routes. Refusals are `{error, code}` with:

- `not_found` (404)
- `not_editable` (403)
- `invalid` (422, with `diagnostics`)
- `rename` (422)
- `name_taken` (409)
- `stale` (409, with the file's current `yaml` and `digest`)
- `confirm_triggers` (409, with `triggers`)
- `folder` (400)
- `not_builtin` (400)

The routes:

- `GET /api/workflows/{name}/file`: `{name, yaml, path, folder, digest, editable, reason}`. A built-in's `yaml` is its definition marshalled, and its `digest` is empty.
- `PUT /api/workflows/{name}/file {yaml, digest, confirm_triggers}`: validation (`Check`) comes first. The `name` can't change (LEG-460), and the save has to confirm triggers. Answers `{name, path, folder, digest, diagnostics}` (the warnings).
- `DELETE /api/workflows/{name}/file {digest}`: when no file of that name remains (a file it shadowed would keep the name alive), this Legato's trigger switches for the name go too (`WorkflowTriggerCoordinator.ForgetTriggers`). Runs are kept.
- `POST /api/workflow-files {yaml, folder, confirm_triggers}`: `folder` is a `writableFolders` ID, `global` by default. A name that any workflow has, a built-in's included, is `name_taken` (LEG-460), and the name must pass `ValidName`.
- `POST /api/workflow-files/check {yaml}`: `{definition, graph, diagnostics, schedule}`, writing nothing. `schedule` (with a schedule trigger) is `{description, timezone, next}`: its next three due times by `ScheduleTrigger.Next` in this machine's zone (`schedulePreview`).
- `POST /api/workflows/{name}/copy {folder}`: a built-in marshalled to a file of its name, with a comment at the top. The file then replaces the built-in (LEG-458).

Every write broadcasts `workflow_changed`. The trigger rule (LEG-459): a create or save is refused with `confirm_triggers` when the new definition has a trigger that would start runs here and the old one did not (`newlyActiveTriggers`: this Legato's switch if it has one, else the file's `enabled`). The client then repeats the request with `confirm_triggers: true`. A trigger that is paused here by a switch never asks. `GET /api/workflows` adds `folder`, `editable`, `read_only_reason`, `shadows` and `warnings` (the file's `Check` warnings) to each definition, plus `folders`, the folders a workflow can be created in. A run keeps its own `definition_json`, so a save changes no run that has started; its page says `definition_changed`.

`GET /api/workflow-runs` returns each run with `related_task_title` (also on `GET /api/workflow-runs/{id}`) and `steps`, a summary of its steps in order (`step_id`, `title`, `status`, `trigger`), which the web UI's runs list draws its step bar and sentence from (the handler sets `WorkflowRunFilter.WithSteps`; the service's own scans of runs, such as the attention count, leave it off). It takes optional `status`, `workflow_name`, `limit` (1–100) and `input.<name>=<value>` parameters. Multiple input filters are ANDed and compare normalized scalar JSON values, so numeric and boolean inputs can be given as query text. Results are newest first. Input names that cannot be represented safely as a direct JSON object key, repeated singleton or input values, empty input values and out-of-range limits return `400` rather than silently broadening the query.

### Workflow graph

`workflowengine.BuildGraph(*Definition) *Graph` (`internal/engine/workflow/graph.go`) builds the **workflow graph** of a parsed definition: a pure function, so it never disagrees with what validation accepted. The model is JSON, versioned with `GraphVersion` (1), and general: nothing in it assumes one chain, so branches or parallel steps would only add edges.

- **Nodes**, each `{id, kind}` with a stable ID: `trigger:manual` (kind `trigger`, `trigger: {kind: "manual", summary: "Run by hand", enabled: true}`), the start node every workflow has; `trigger:<kind>` for each kind the definition's `on:` declares (`workflowengine.TriggerKinds`: `task.entered_column`, `schedule`, `pr.changes_requested`, `chat.message`, `chat.mention`, in that order), with `summary` ("Card enters Triage", `ScheduleTrigger.Describe`, "Changes requested on a PR", "Message in C123 on slack", "Mention of discord"), `enabled` as the file says, `confirm`, `max_runs_per_day` (`TriggerCommon.Limit`, so 3 when absent) and `definition` (the trigger as declared); and `step:<step id>` (kind `step`) with `step: {id, title, type, trigger, key, definition}`, where `trigger` is `automatic`, `manual` or `agent_ended`, `gate` is `manual` or `agent_ended` for a **gate** (a step that does not start by itself; empty otherwise), `definition` is the step as declared, and `key` is `{field, value}`, the one value chosen per executor type (`stepKey`): `macro`, else the prompt's first line, for `agent.run`, `agent.dispatch` and `agent.interview`; `instructions` for `agent.compact`; `column` for `task.move`; `pr` (`repo#pr_number`) for `github.pr.review_passes`, `github.pr.prepare` and `github.pr.wait`; `repo` for `repo.ensure`; `path` for `file.remove` and `worktree.remove`; `body` or `body_path` for `task.note`; the sorted keys of `values` for `task.metadata.set`; `text`, else `channel`, for `chat.message.send`; `emoji`, else `message_id`, for `chat.reaction.add` and `chat.reaction.remove`; empty otherwise. Values are as written, expressions included.
- **Groups**: a `github.pr.review_passes` step keeps its node (`step:<id>`, so order and data edges and run state attach to it) with `step.group: "review_loop"`, and gains two nodes of kind `inner` with `parent` set to it: `step:<id>/pass` (`inner: {role: "pass", title: "Review pass"}`) and `step:<id>/fixes` (`role: "fixes"`, "Author fixes"), joined by two `loop` edges, pass → fixes and fixes → pass. The loop itself runs in `ReviewPassService`.
- **Edges**, each `{id, kind, source, target}`, ID `<kind>:<source>><target>`: `start` (each trigger node → first step), `order` (step → next step) and `data` (from a step to a later step whose `with` or output `path` references its outputs as `steps.<id>.outputs.<key>`, read with the same expression pattern as validation, so they may skip steps; one edge per pair of steps, with `outputs`, the keys used, sorted).

`GET /api/workflow-runs/{id}` adds `graph` (built from the run's own `definition_json`, never the current file; `runWithGraph` in `internal/server/workflows.go`), `definition_changed` (a discovered definition of the run's name differs from that copy; both are compared with `Source` cleared, through `workflowengine.Digest`, so a moved file is not a change), `definition_missing` (none is discovered) and `trigger_kind` (`WorkflowRunView.TriggerKind`, which `WorkflowService.Show` reads from the run's trigger request; empty for a run started by hand). `GET /api/workflows` adds `graph` to each definition (`definitionWithGraph` in `internal/server/workflows.go`). The graph is never part of a definition's own JSON, which runs store and digest. A file that fails to parse stays in `errors`, with no graph.

### Live updates and stalls

Workflow agents on the agents graph (LEG-612). `AgentGraphService` (`agent_graph_workflow.go`) gives `GET /api/agents/graph` each running agent's `workflows` (`AgentWorkflowPlace`: `run_id`, top-level `step_id`, `role`) and `runs` (`AgentGraphRun`, in the runs list's shape: title, status, current top-level step, `needs_attention` from `WorkflowService.ListRuns` when `AgentGraphOptions.Runs` is set, the top-level step summaries, and `pass` while a review loop runs). Only runs `running` or `waiting` count, read with `ListRuns` and `store.ListWorkflowAttemptsForRuns` once per graph read. Roles: `agent` (the execution's `workflow_run_id`, its step from `workflow_attempt_id`, which `store.AgentSession` now carries), `interview` (a `waiting_agent` `agent.interview` attempt on the agent's session), `reviewer` and `author` (a waiting `github.pr.review_passes` attempt: its task's `reviewer` slot, and `author_task`, else `linked_task`, while its loop has not ended), and `awaited` (a waiting run whose current step starts on `agent_ended`: the run task's main agent). One place per agent and run, the one on the run's current step when there are several; an agent's places list the run that needs the operator first, then the newest. A bare `agent.dispatch` target is not placed. `WorkflowService.Show` fills each attempt's `agent_id` from its `agent_session_id` (`AgentSlotKey` of the session's task and slot): an `agent.interview` attempt keeps the run's `task_id`, so the run page links to `agent_id` first. The web UI's side is in [Web UI](web-ui.md) § Ensemble.

Run views update through targeted `workflow_changed` events (LEG-616). `WorkflowService` publishes `EventWorkflowChanged` after each write of a run's state (`workflow_events.go`, `SetEventBus`), with the run, the step path and a kind: `run_started`, `run_cancelled`, `step_started`, `step_waiting` (an agent, a service or a manual gate), `step_triggered`, `step_completed`, `step_failed`, `step_retried`. None is `completed_step`, which only a step recorded from an agent's pane sends, and which the advance loop acts on. So a run that a trigger, a schedule, a pull request's merge or the advance loop moves on shows at once. `Server.StartWorkflowEvents`, started in both runtimes, sends every `EventWorkflowChanged` on the bus to the web UI as `workflow_changed` with its `kind`, and `EventWorkflowTriggerChanged` as kind `trigger`; `NotifyWorkflowChangedKind` publishes on the bus and lets it send, so each change is one message. A workflow file created, saved, copied or deleted and a trigger switched or reset are kind `definitions`. The TUI's workflow service also tells other processes by IPC (`SetChangeListener`, `workflowChangeBroadcaster`, a message carrying its `pid`, which the TUI ignores when it comes back), so a `legato serve` on the same database shows the TUI's run changes. When an agent activity transition belongs to an active `agent.run` attempt, the server resolves its task to the persisted run and step and emits that targeted event; unrelated `agents_changed` events do not reload workflow runs or definitions. An unfinished `agent.run` step needs attention while its agent is waiting or idle. A detected exit (including a pane back at a shell) fails every waiting attempt tied to that exact session (owned `agent.run` and borrowed `agent.interview`) with `agent exited before step completion`, rather than leaving it at `waiting_agent`; Retry step can start it again. An agent whose adapter binds natively (Claude Code, Codex, Chimera) but whose endpoint is not bound within `nativeBindTimeout` (30 s) fails the attempts waiting on its session with `the agent never connected to Legato: …` and drops its launch messages (`agentService.failUnboundWorkflowSteps`, called from `deliverLaunchMessages`); other agents keep their launch messages as before (LEG-531). Such an agent's bridge must not save a resume identity the store refuses, since the refusal ends the bridge (and the Chimera link before it binds): the bridges ask `store.OwnsTaskConversation`, the same ownership rule `RecordTaskNativeSession` applies, before saving any (LEG-539). A workflow agent of a run with no related card is attributed to no task and saves none; nor does one attributed to its related card. The Workflows navigation item takes its red count from the navigation summary (`/api/navigation-summary`); run rows explain the stall, and the run page offers **Prompt to continue** for a live stalled agent. Legato does not prompt automatically, to avoid duplicate or unsafe agent work. The Runs tab loads only the runs; the Workflows tab loads the definitions and the runs (for each workflow's last run). On a phone, run rows stack, steps stay one to a line, wide values scroll inside their box, and actions are touch-sized.

The card context menu's Workflows flyout on the web board scrolls independently and flips around viewport edges; cards also expose an action button for keyboard, touch and assistive-technology access.

### Diagnostics

`workflow.Check(source, data)` (`diagnostics.go`) is `Parse` for an editor: it returns the definition only when there is no error, and `[]Diagnostic` (`severity`, `message`, `path`, `line`, `column`, `end_line`, `end_column`; 1-based, end exclusive) with every problem it can find. A YAML syntax or decoding error stops it, with the line yaml.v3 reports (a syntax error's is where its context starts) and, for an unknown key, the key's path and column (`keyOnLine`). Otherwise `Definition.problems()` lists the validation problems in the order `Validate` checks them, at most one per step (`validateStep`), so `Validate` and `Parse` still return the first, word for word. Each is a `*PathError` (`ErrorPath(err)`), whose path is built with `within` as the error is wrapped (`steps[1]` + `with.column`; triggers give `on.schedule.cron`, `on.task.entered_column.inputs.x`); `diagnosticAt` walks the `yaml.Node` tree to it and spans a one-line scalar value, else the key, else as far as the file goes. Maps (inputs, `with`, outputs, trigger inputs) are checked in key order, so the first problem no longer depends on map order. `legato workflow validate <file>` prints them as `file:line:col: message` and exits 2 (`--json`: `workflow_invalid` with `details.diagnostics`), without opening the database.

### JSON Schema

`workflow.JSONSchema()` (`schema.go`) is the draft-07 schema of a v1 file, the same bytes every time. `schemaReflector` makes the object schemas from the `yaml` tags of `Definition`, `Input`, `Step`, `Output`, `Triggers`, each trigger kind and `Condition` (recursive, by `$ref`), all `additionalProperties: false` as `KnownFields` is. `fieldSchemas` gives each field's description, enum, pattern, default and required: every reflected field must have an entry (it panics otherwise), so a new struct field needs one. A step's `with` comes from the catalog: `step.allOf` holds one `if type == X then with: $ref with.X` for each executor (and `required: [with]` when the type has a required field or a checked group, `needsWith`, as the engine requires); `with.X` lists its fields (`fieldSchema`: integers, booleans and enums also take a `${{ }}` string unless `Literal`; `task` is a whole-reference pattern only where the engine checks it at load, `Checked`), its required fields, its checked constraints (`ExactlyOne` → `oneOf`, `AtLeastOne` → `anyOf`, `Excludes` → `not`), and `additionalProperties: false`. An unknown `with` key is a warning, not an error (LEG-461): the editor reports `additionalProperties` under `with` as a warning, and `Check` returns a `SeverityWarning` diagnostic (`unknownWithKeys`) with the definition. A later release will make it an error.

The `x-legato` extensions: at the root, `schema_version`, `step_groups`, `executors` (type, title, description, summary, group, in catalog order), `expressions` (`ExpressionContexts()`, `expressions.go`: what `${{ }}` may read at `run_title`, `with`, `output_path` and each `trigger.<kind>`'s inputs, as patterns such as `steps.<earlier step>.outputs.<output>`) and `task_fields` and `repository_fields` (`TaskFields`, `RepositoryFields`, which `validateReferences` uses too). On each `with.X` there are `type`, `outputs`, `declared_outputs`, `run_constraints` (the unchecked constraints) and `summary`. On each field there are `kind`, `expressions`, `context`, `required_at_run`, `essential`, `label` and `order` (each only when set). On the properties that take expressions, `context` names their entry in `expressions`.

The copies at `web/src/generated/workflow.schema.json` and `site/public/schemas/workflow-v1.schema.json` (published at `SchemaID`) are generated: `go test ./internal/engine/workflow -run TestTheGeneratedSchemaIsCurrent -update` rewrites both, and the test fails when either is stale. `TestEveryExampleAndBuiltInMatchesTheSchema`, `TestEveryValidTestDefinitionMatchesTheSchema` (every string literal this package's tests pass to `Parse` that it accepts, read from the source, with the lenient copy when `Check` warns) and the service's `TestBuiltInWorkflowsMatchTheSchema` validate with `google/jsonschema-go`. `TestTheSchemaRefusesInvalidFiles` holds a sample of files the schema refuses. `GET /api/workflow-schema` (`internal/server/workflow_schema.go`) serves it with `ETag`, `Cache-Control: private, max-age=300` and `X-Legato-Workflow-Schema-Version`.

Expression contexts: `ExpressionContexts()` is what the web editor completes and checks `${{ }}` from (`web/src/lib/workflowExpressions.ts`). A change to the rules in `validateReferences` (or a new context) must change `expressions.go` too. `testdata/expressions.json` holds the verdicts both sides must give (`TestTheSharedExpressionTable` here, `workflowExpressions.test.ts` in the web UI), so add a row when a rule changes.

### Extension model

**The executor catalog** (`internal/engine/workflow/catalog.go`, `Catalog()`, `LookupExecutor`) is where a step type declares its contract, and the one place a new executor is added before anything else: its `with` fields (`Field`: name, `FieldKind` such as `text`, `task`, `task_or_id`, `repository`, `path`, `column`, `macro`, `agent`, `tier`, `json`; `Required` (the file does not load without it), `RequiredAtRun` (the executor fails without it), `Default`, `Enum`, `Literal` (no `${{ }}`), `Checked` with `Invalid` (the value's kind is checked at load, with that message), and for the editor's inspector `Essential` (shown first; the rest go under More options), `Label` (plain words, such as "What it should do"; `Field.at` places a shared field with its own order and label) and `Order` (from 1)), its `Group` (where the step picker lists it: one of `StepGroups`, Agents, Code, Board, Learn or Cleanup; `TestOfferedStepTypesAreInAPickerGroup`), its `Summary` (the fields a step row is summed up by, the first with a value: `macro` then `prompt` for `agent.run`, `column` for `task.move`), its `Constraints` (`ExactlyOne`, `AtLeastOne`, `Excludes`; a `Checked` one is enforced at load), its `Outputs`, and `DeclaredOutputs` (an agent completes the step with the outputs the step declares, as for `agent.run`). Every step type is offered; the Learn ones (`agent.interview`, `learning.packet.prepare`, `learning.proposals.submit`, group Learn) were `Internal` and hidden from the builder until LEG-603, which removed the flag. `TestOfferedStepTypesSayWhatTheInspectorAndTheirRowShow` fails when an offered step type has no essential field, no summary, or a field without a label or a distinct order (LEG-502). `Definition.Validate` takes its list of step types from the catalog, and `validateStepContract` checks checked constraints, then checked fields, then required fields. Only what was checked before the catalog is `Checked` or `Required`, so every file that loaded still loads; unknown `with` keys are still accepted (LEG-461). `TestEveryWorkflowExecutorHasACatalogEntry` (`internal/service`) finds each executor's `Type()` in the package's source and fails when one has no catalog entry, or an entry no executor. The JSON Schema and the web builder are made from the catalog (LEG-457).

Workflow persistence and UI are executor-neutral. A future deterministic executor declares its contract in the catalog, implements the service executor contract and renders type-specific details without replacing runs, steps, attempts, outputs or artifacts. DAGs, parallel execution, schedules, shell plugins, approval gates and native external publishers (but for `github.pr.review_passes`) are not part of schema version 1.

## Triggers on a worker's handed-off cards

A card a main handed off to this Legato is the main's (LEG-243). `WorkflowTriggerCoordinator.process` checks `store.OpenHandoffForTask` before anything else and marks the trigger request `skipped` with the reason ("the card was handed off from <main>, whose workflows run when it returns; set handed_off: true on the trigger to run on such cards") unless the trigger sets `handed_off: true` (`TaskEnteredColumnTrigger.HandedOff`, schema v1). The `learn` template's trigger is skipped the same way (it does not set `handed_off`), so a worker's curator does not curate a main's task into the worker's ledger. The main's own triggers run when the task returns into another column (a `handoff` transition; see [Integrations](integrations.md) § Handing off a task). Review passes are not workflows and are unaffected. The Workflows page says "cards handed off from a main included" on a trigger that opts in; trigger requests themselves, skipped ones included, are not listed by any route yet.

## Steps on a task that is away

A task away on a worker is read-only on the main (`RefuseAway`). `task.move` was already refused through `moveCard`; `task.metadata.set` now asks `RefuseAway` too and fails the step with its words (LEG-239). `task.note` still adds the note on the main, where it is when the task returns, and adds `away_on` and `warning` to its outputs: the note is not forwarded, so the worker's agent works without it. Forwarding it to the worker as a main note was the alternative; it would need a handoff route of its own and an agent told mid-turn, and the operator can message the agent instead.

## Pausing triggers

Every trigger kind has `enabled` (`*bool`; absent is on). `Triggers.List` gives each declared trigger's kind (`TriggerTaskEnteredColumn`, …) and `EnabledByDefault`; a new trigger kind adds itself there. Migration 122 adds `workflow_trigger_switches` (`workflow_name`, `trigger`, `enabled`, `updated_at`), this Legato's switch, which beats the file both ways and never rewrites it (store: `WorkflowTriggerSwitches`, `WorkflowTriggerSwitchFor`, `SetWorkflowTriggerSwitch`, `DeleteWorkflowTriggerSwitch`). `WorkflowTriggerCoordinator.triggerEnabled` is checked before a request is made (`CaptureTransition`), so a paused trigger makes no request at all; requests made before the pause are left as they are. `TriggerStates` (by workflow: `trigger`, `file_enabled`, `enabled`, `overridden`), `SetTriggerEnabled`, `ResetTrigger` (`ErrNoSuchTrigger` for an undeclared workflow or kind; `workflow_trigger_switch.go`). API: `GET /api/workflows` adds `trigger_states`; `PUT /api/workflows/{name}/triggers/{trigger}` `{enabled}` and `DELETE` (back to the file) answer `404` for an undeclared trigger and broadcast `workflow_changed`. Web: the Workflows tab's `TriggerSwitch` (`role="switch"`, labelled by `triggerLabel`, "on here"/"paused here").

## Loop stop and trigger requests for every kind

Migrations 123 and 124 make `workflow_trigger_requests` hold every trigger kind: `transition_id` may be NULL (123 edits the table text through `writable_schema`, so `store.go`'s `triggerSchemaEdits` bumps `schema_version` after it, as for 058), status `held` is added, and 124 adds `trigger_kind` (default `task.entered_column`), `item` (what the loop stop counts by: the task, `owner/repo#n`, the due time), `event_key` (unique per `(workflow_name, trigger_kind, event_key)`, NULL for a column move) and `event_json` (`{task_id, context}`). Reads go through `triggerRequestColumns`, which gives a missing transition or key as `""`. `InsertWorkflowTriggerEvent` (`ErrTriggerEventSeen` when another Legato on the database made it first), `CountStartedTriggerRuns`, `LatestTriggerEvent`.

Every trigger kind says `confirm`, `enabled`, `max_runs_per_day` and `inputs` (`Triggers.Common`; `TriggerCommon.Limit`, `DefaultMaxRunsPerDay` 3). Before a request starts a run, `WorkflowTriggerCoordinator.loopStop` counts the requests of that workflow and trigger for the item that reached `starting`/`started` in the 24 hours before the coordinator's clock (`SetClock`; a request's `created_at` is set from it); at the limit the request is `held` with "stopped to prevent a loop: …". `RunAnyway` starts a held request past the limit; `PauseTrigger` sets the trigger's switch to paused here and skips the request. Attention: `workflow_trigger_loop_stop` (high urgency, actions `run_anyway` and `pause_trigger`), navigating to the task, or to the Workflows tab (`workflows`) when the event names none.

`Fire(TriggerEvent)` is the path for every kind but column moves: a paused trigger or an event already seen makes nothing; otherwise the request is inserted and `processEvent` resolves the trigger's `inputs` against the event's context (`${{ schedule.time }}`, `${{ event.repo }}`, … through `resolveMappedInputs`, which the column trigger shares), then the loop stop, confirmation and the run. `Reconcile`, `SupplyInputs` and `Confirm` take event requests through the same path.

## Schedule trigger

`on.schedule` (`workflowengine.ScheduleTrigger`, `schedule.go`): `every` (`daily`, `weekdays`, `weekly`) with `at` (`HH:MM`) and, for weekly, `on` (a weekday); or `cron` (five fields, `*`, n, `a-b`, lists, `/step`, month and weekday names, weekday 7 = Sunday; day-of-month and weekday ORed when both are restricted, as cron does). `every` forms compile to a cron spec (`spec`). `timezone` (an IANA zone, checked with `time.LoadLocation`; `time/tzdata` is embedded), `catch_up` (`once`, default, or `skip`; used by missed runs), and the common `enabled`, `confirm`, `max_runs_per_day`, `inputs`. `Next(after, loc)` and `Prev(before, loc)` are pure: they walk wall-clock dates in the zone, and `wallInstant` turns a wall minute into an instant: one that does not exist (clocks forward) is the next minute that does, one that repeats (clocks back) its first coming, so each fires once. `DueBetween(from, to, loc, limit)`. `Describe` is the page's words.

`WorkflowTriggerCoordinator.TickSchedules` (every process that runs triggers: `StartEventLoop` starts `scheduleLoop`, a tick just after each minute) fires each schedule's latest due time when it is at most `scheduleTickWindow` (5 minutes) old, through `Fire` with key and item = the due time in UTC RFC 3339: the unique `(workflow_name, trigger_kind, event_key)` index makes it one request whichever process ticks first; there is no leader. The event context is `schedule.time` and `schedule.previous_time` (the schedule's due time before it), RFC 3339 in the schedule's zone. `SetHostZone` (tests) replaces `time.Local`. `TriggerStates` adds `schedule` (`description`, `timezone`, the next three due times, and `last`: the newest due time's status and run, `LatestTriggerEvent`), which the Workflows tab shows beside the trigger's switch (`ScheduleTimes`).

### Missed runs

`CatchUpSchedules` runs in `StartEventLoop` before the first tick: for each enabled schedule with a due time recorded (`LatestTriggerItem`, the greatest `item`; a schedule's item is its due time in UTC RFC 3339, which sorts as time does), the due times after it and before the tick window are each recorded as a `missed` request (status added to migration 124's check; `recordMissed`, error "Legato was not running at … (catch_up: …)"), once: the event key makes a restart record nothing new. With `catch_up: once` and anything newly recorded, one late run is fired with key `late:<newest missed>`, item the newest missed, `schedule.time` the newest missed, `schedule.previous_time` the due time recorded before them, and `schedule.late: true`. A schedule never recorded has nothing to catch up. `ScheduleState` adds `missed` (newest ten, `ListTriggerEvents`) and `catch_up`, shown on the Workflows tab. A due time whose run cannot start is a `failed` request, which the trigger Attention producer already shows.

## pr.changes_requested

`on.pr.changes_requested` (`workflowengine.PRTrigger`: `enabled`, `confirm`, `max_runs_per_day`, `inputs`; give `{}` for none, since an empty key is no trigger). `StartEventLoop` subscribes to `EventPRChangesRequested` and calls `ChangesRequested`, which fires every such workflow through `Fire`: key `owner/repo#n/review/<id>` (one request per review), item the task (the loop stop counts by it), task the task. Inputs read `${{ event.task }}`, `${{ event.repo }}`, `${{ event.pr_number }}`, `${{ event.pr_url }}`, `${{ event.reviewer }}`, `${{ event.review_id }}`. Where the reviews come from: [PR tracking](pr-tracking.md) § Reviews and pr.changes_requested.

## chat.message and chat.mention

`on.chat.message` and `on.chat.mention` (LEG-624; `workflowengine.ChatTrigger` in `chat_triggers.go`, declared as the distinct types `ChatMessageTrigger` and `ChatMentionTrigger` so the schema has a definition per kind; `Triggers.Chat(kind)` gives either as a `*ChatTrigger`). Fields: `bot` (required, a bot's name matching `^[a-z][a-z0-9_-]*$`; Legato's bots are `slack` and `discord`), `channel` and `user` (the platform's IDs), `text` (`{contains}`, ignoring case, or `{regex}`, Go RE2 at most 512 characters; exactly one), `include_bots` (messages other bots post; off by default), `loop_item` (`channel`, the default, or `thread`), and the common `enabled`, `confirm`, `max_runs_per_day`, `inputs`. `ChatTrigger.Matches(ChatEventFields)` is the filter, pure.

The chat bots' supervisor (`service.ChatBots`, see [Integrations](integrations.md) § Chat bots) hands each message to `WorkflowTriggerCoordinator.ChatEvent` directly, not through the event bus, which drops when full. `ChatEvent` fires `chat.message` for every message that matches, and `chat.mention` too when the message mentions the bot or is sent to it directly (a DM), so a workflow declaring both gets two requests for a mention, each counted by its own kind. The bot's own messages never reach it (the adapters drop them). Key `<platform>:<bot>:<channel>:<message id>` (a Slack ts is unique only within its channel; a Slack redelivery is the same key); item `<bot>:<channel>`, or `<bot>:<channel>/<thread id>` with `loop_item: thread` (`ChatTrigger.ItemFor`), never empty. Inputs read `${{ event.bot }}`, `event.platform`, `event.channel`, `event.user`, `event.text` (the sender's own text, then `"\n\n"`, then `ChatEvent.ForwardedText`, the messages it forwards quoted (LEG-634); the `text` filter matches all of it uncut, and the request keeps it cut to `MaxChatEventText`, 8 KiB, in `event_json` by `keptChatText`: the forwarded part first, ending `\n> …`, and only when the own text alone is too long is that cut and the forwarded part dropped), `event.forwarded` and `event.forwarded_url` (on every chat event, `false` and `""` for a message that forwards nothing, so a mapping never misses), `event.message_id` and `event.thread_id` (the forwarding message's, not the original's): what `chat.message.send`'s `thread_id` takes to reply to the message (Slack: the thread's ts, or the message's own; Discord: the thread channel's ID when in a thread, else the message's ID, sent as a reply).

`chat.message.send` (`service.ChatSendExecutor`, group **Chat**): `bot` (field kind `chat_bot`, checked against the name pattern at load), `channel` (`required_at_run`: empty is the bot's `default_channel`), `text`, `thread_id` (any message's ID in the channel: a Slack ts becomes `thread_ts`, so the reply goes in that message's thread, and a reply's ts is untested there, so the docs say to give the parent; a Discord message ID becomes `message_reference`). The `bot` and `channel` fields are the catalog's `chatBot` and `chatChannel`, which every chat step shares. On Discord the text's `:names:` in `chatEmoji` become the emoji, outside code spans and blocks (`expandEmojiShortcodes`); Slack renders shortcodes itself, so its text is sent as written. Outputs `message_id`, `channel`, `thread_id` (what replies in the same thread). It fails at once, never waiting for a connection, when the bot is unknown, switched off or refused by its platform (`auth_failed`); a bot still connecting or backing off can send, since sending is an HTTP call. Each send is bounded by `ChatBots.SendTimeout` (15 s). Errors name the bot's state and never a token.

`chat.reaction.add` and `chat.reaction.remove` (LEG-633; `service.ChatReactionAddExecutor` and `ChatReactionRemoveExecutor`, two types so each `Type()` is one constant for the catalog parity scan, both calling `startChatReaction`): `bot`, `channel` (as send's), `message_id` and `emoji`, all essential, `message_id` and `emoji` required; nothing defaults the emoji. Output `ok: true`. `ChatBots.React` shares `Send`'s bot lookup and refusals (`ready`), its `default_channel` fallback and `SendTimeout`, and scrubs errors the same way. The emoji resolves per platform in `chat_emoji.go`, from one table of about 30 common emoji (`chatEmoji`, Slack's name first): Slack takes a name, colons trimmed, as it is (so its custom emoji and skin tones work), and an emoji Legato knows by its name; Discord takes a known name as its emoji, any non-ASCII value as itself, and `name:id` as a custom emoji, and refuses an unknown ASCII name. A reaction already there (Slack `already_reacted`; Discord answers 204 again) or already gone (Slack `no_reaction`) is success. Slack `missing_scope` fails naming the `needed` scope (else `reactions:write`) and saying to reinstall the app; Discord 50013 names Add Reactions and Read Message History, 50001 View Channel, 10008 the message, 10014 the emoji.

Whether a bot is set up is this Legato's, not the file's: `workflowengine.ChatBotDiagnostics` (run by the server's workflow check, file and list paths; the triggers' `bot` and every `chat.*` step's) is an error for a name no Legato has and a warning for a bot not set up or switched off here, since repository workflows are shared by Legatos that differ. A step's bot given by `${{ }}` is checked when it runs.

## Workflows: internals

The user guide, with the YAML schema, executors, templates, triggers and CLI, is [Workflows](../../site/src/content/docs/using/workflows.md) (on the site at `/legato/using/workflows/`). This file keeps what an agent working on Legato's code needs beyond it. Parsing and discovery are in `internal/engine/workflow/`; runs, executors and triggers in `WorkflowService` (`internal/service/`); see [Packages](packages.md). The web pages are in [Web UI](web-ui.md) § Workflows; the CLI in [CLI](cli.md).

### Runs and tasks

- A run creates one local execution task in the reserved **Workflows** workspace (`ViewAll` excludes it; `ViewWorkspace(id)` opts in). A succeeded run moves it to **Done** and archives it at once.
- A `task` input's selected task is stored on the run as `related_task_id`. Agent sessions use the execution task, so an existing task's active agent session is not replaced. `GET /api/tasks/{id}/activity` lists related runs and their managed artifacts.
- Deterministic steps execute synchronously until an agent step starts; the run then advances when that agent completes or fails its step through the CLI callback.
- A step whose executor returns `WorkflowStepWaiting` (`"waiting"`, `workflow_waiting.go`) waits on that executor's own service. The step and its attempt are `waiting` (the run stays `running`; a run that is `waiting` is one at a manual gate) and carry no agent session, so `endGoneSession` does not fail them and a restart leaves them as they are. The service finishes the step with `WorkflowService.CompleteWaiting` (its outputs as a deterministic executor returns them, then the steps after it run) or `FailWaiting`, and finds its steps again after a restart with `WaitingAttempts(executorType)`. `Cancel` calls the executor's `Cancel` for a waiting attempt, as for a running one. Such a step's service may act on an outside service: the one exception to schema v1's rule against outside publishers is `github.pr.review_passes` (LEG-253), whose loop posts to GitHub; see [Integrations](integrations.md) § Review loops on any pull request.
- Embedded examples (`internal/engine/workflow/examples/*.workflow.yaml`, `workflow.Examples`, `ExampleNamed`) are definitions Legato ships for people to add; `TestEveryEmbeddedExampleValidates` parses each. `review-pr-passes` is the first. An optional input a step references needs a `default`, or resolving it fails as unavailable.
- `WorkflowService.Show` fills `WorkflowRunView.Details` (by step ID) from each step's latest attempt whose executor is a `WorkflowStepDetailer`; the review step's is `ReviewRunDetails` (phase, pass, a summary line, blocking open, reason, every review posted). A run's loop publishes `EventWorkflowChanged` with kind `review_loop` (`service.ReviewLoopChangedKind`), which `Server.StartReviewRunEvents` forwards as `workflow_changed`, so an open run page follows the loop.
- `NormalizeInputs` takes an empty value for an `integer` or `boolean` input as not given (its default, or required), as a form's blank field sends it.
- `task.note` takes `task` as a task input or a task ID as text; `optional: true` (a boolean, checked at validation) makes an empty task a skip (`note_id` empty, `skipped: true`) instead of a failure.
- `task.move` calls the sync service's `PushMove` in a configured provider runtime, which may queue the mapped remote transition even for a same-column no-op, so a previously failed push can recover. Success confirms local persistence and queueing, not remote completion.
- `agent.run` takes an optional `with.engram` (text, templated like the step's other fields; anything else fails validation, and a template that resolves to anything but text fails the step): the agent starts as that engram (`AgentSpawnOptions.Engram` with `EngramRequired`). An engram `engram identity list` does not list fails the step before anything starts; any other boot failure starts the agent without it, as an interactive spawn does (the warning goes to the log and Attention). A workflow never reads or writes engram bindings: its spawn does not touch `last_used_at`. Finishing a workflow agent (`FinishWorkflowAgent`) ends its engram session (`EndEngramSession`). See [Engram sessions](engram.md).
- `agent.run` and `agent.dispatch` take exactly one of `with.prompt` and `with.macro` (the catalog's `ExactlyOne` constraint; both, neither or an empty macro fail validation). The executors resolve a macro when the step starts through `SetMacros` (`service.MacroService`, wired in `cmd/legato/workflow_runtime.go`; `workflow_macro.go`): an unknown one fails the step (`macro "x": no macro of that name`). `agent.run` uses the macro's text as the assignment; `agent.dispatch` sends `MacroService.Message` (the task header, then the text). A step's own `agent`/`tier` win; with neither, the macro's apply.
- `WorkflowService.SetAgentKinds` gives the service the configured adapters: an `agent.run` step whose `agent` is known from the inputs alone and names no configured adapter is refused when the run starts, and no run is created.

### Agent completion

Completion is persisted and downstream steps are advanced before Legato removes the completed agent session, because the callback (`legato workflow step complete`) may be running inside that session. When the step is recorded but the next step cannot start, `Complete` returns a `*StepRecordedError` (matched by `ErrWorkflowStepRecorded`) that says the step was completed and why the next one failed, so a caller does not retry a completion that already took; the run is failed at the next step as before. Learn's borrowed-agent interview completes through `legato learn reflection submit`, which persists the typed reflection before completing its exact waiting attempt ([Legato Learn](learning.md)).

Managed artifact collection is replay-safe: rerunning an interrupted completion callback reuses an existing `(attempt, output)` artifact only when its source path and SHA-256 digest still match; changed content is rejected. Accepted files are copied atomically into managed storage so worktree cleanup does not destroy them.

### Workflow files

`internal/engine/workflow/files.go` and `internal/server/workflow_files.go`. `Folders(legacy, global, repositories, project)` lists the folders in increasing precedence, with IDs `legacy`, `global`, `repo:<preset name>` and `project`. A folder named twice is kept once, at its later place. `DiscoverFolders` reads them, and `DiscoveryResult.Shadows` names, for each workflow, the files that a later file of the same name replaced. Every discovery uses it: the server (`discoverWorkflowsIn`, presets from `s.repositories`), `workflowDiscoveryProvider(cfg, db)` for triggers, the task launcher and the Reeve (the configuration's and the web UI's presets), `legato workflow list`, `run` and `validate <name>`, `doctor` and the setup checklist. `FileFor(definition, folders)` gives `{path, folder, editable, reason}`. A built-in has no file. A file in no folder, or one that is not a regular file whose links resolve inside its folder, is read-only, so the API never writes through a link to somewhere else. The legacy folder's files are editable, but nothing is created there.

Writes go through `CreateFile` and `ReplaceFile`. `CreateFile` writes a temp file in the folder, then `os.Link`s it to `<name>.workflow.yaml`, so it never overwrites (`ErrWorkflowNameTaken`); `AddTemplate` and `SaveDraft` use it too. `ReplaceFile` compares `FileDigest` (`sha256:<hex>` of the bytes) with the digest the client read (`ErrStaleFile` otherwise), then writes a temp file and renames it over the original, keeping its mode. `RemoveFile` checks the digest the same way. The bytes are written as sent, comments and all.

Routes. Refusals are `{error, code}` with:

- `not_found` (404)
- `not_editable` (403)
- `invalid` (422, with `diagnostics`)
- `rename` (422)
- `name_taken` (409)
- `stale` (409, with the file's current `yaml` and `digest`)
- `confirm_triggers` (409, with `triggers`)
- `folder` (400)
- `not_builtin` (400)

The routes:

- `GET /api/workflows/{name}/file`: `{name, yaml, path, folder, digest, editable, reason}`. A built-in's `yaml` is its definition marshalled, and its `digest` is empty.
- `PUT /api/workflows/{name}/file {yaml, digest, confirm_triggers}`: validation (`Check`) comes first. The `name` can't change (LEG-460), and the save has to confirm triggers. Answers `{name, path, folder, digest, diagnostics}` (the warnings).
- `DELETE /api/workflows/{name}/file {digest}`: when no file of that name remains (a file it shadowed would keep the name alive), this Legato's trigger switches for the name go too (`WorkflowTriggerCoordinator.ForgetTriggers`). Runs are kept.
- `POST /api/workflow-files {yaml, folder, confirm_triggers}`: `folder` is a `writableFolders` ID, `global` by default. A name that any workflow has, a built-in's included, is `name_taken` (LEG-460), and the name must pass `ValidName`.
- `POST /api/workflow-files/check {yaml}`: `{definition, graph, diagnostics}`, writing nothing.
- `POST /api/workflows/{name}/copy {folder}`: a built-in marshalled to a file of its name, with a comment at the top. The file then replaces the built-in (LEG-458).

Every write broadcasts `workflow_changed`. The trigger rule (LEG-459): a create or save is refused with `confirm_triggers` when the new definition has a trigger that would start runs here and the old one did not (`newlyActiveTriggers`: this Legato's switch if it has one, else the file's `enabled`). The client then repeats the request with `confirm_triggers: true`. A trigger that is paused here by a switch never asks. `GET /api/workflows` adds `folder`, `editable`, `read_only_reason`, `shadows` and `warnings` (the file's `Check` warnings) to each definition, plus `folders`, the folders a workflow can be created in. A run keeps its own `definition_json`, so a save changes no run that has started; its page says `definition_changed`.

`GET /api/workflow-runs` returns each run with `related_task_title` (also on `GET /api/workflow-runs/{id}`) and `steps`, a summary of its steps in order (`step_id`, `title`, `status`, `trigger`), which the web UI's runs list draws its step bar and sentence from (the handler sets `WorkflowRunFilter.WithSteps`; the service's own scans of runs, such as the attention count, leave it off). It takes optional `status`, `workflow_name`, `limit` (1–100) and `input.<name>=<value>` parameters. Multiple input filters are ANDed and compare normalized scalar JSON values, so numeric and boolean inputs can be given as query text. Results are newest first. Input names that cannot be represented safely as a direct JSON object key, repeated singleton or input values, empty input values and out-of-range limits return `400` rather than silently broadening the query.

### Workflow graph

`workflowengine.BuildGraph(*Definition) *Graph` (`internal/engine/workflow/graph.go`) builds the **workflow graph** of a parsed definition: a pure function, so it never disagrees with what validation accepted. The model is JSON, versioned with `GraphVersion` (1), and general: nothing in it assumes one chain, so branches or parallel steps would only add edges.

- **Nodes**, each `{id, kind}` with a stable ID: `trigger:manual` (kind `trigger`, `trigger: {kind: "manual", summary: "Run by hand", enabled: true}`), the start node every workflow has; `trigger:<kind>` for each kind the definition's `on:` declares (`task.entered_column`, `schedule`, `pr.changes_requested`, in that order), with `summary` ("Card enters Triage", `ScheduleTrigger.Describe`, "Changes requested on a PR"), `enabled` as the file says, `confirm`, `max_runs_per_day` (`TriggerCommon.Limit`, so 3 when absent) and `definition` (the trigger as declared); and `step:<step id>` (kind `step`) with `step: {id, title, type, trigger, key, definition}`, where `trigger` is `automatic`, `manual` or `agent_ended`, `gate` is `manual` or `agent_ended` for a **gate** (a step that does not start by itself; empty otherwise), `definition` is the step as declared, and `key` is `{field, value}`, the one value chosen per executor type (`stepKey`): `macro`, else the prompt's first line, for `agent.run`, `agent.dispatch` and `agent.interview`; `column` for `task.move`; `pr` (`repo#pr_number`) for `github.pr.review_passes` and `github.pr.prepare`; `repo` for `repo.ensure`; `path` for `file.remove` and `worktree.remove`; `body` or `body_path` for `task.note`; the sorted keys of `values` for `task.metadata.set`; empty otherwise. Values are as written, expressions included.
- **Groups**: a `github.pr.review_passes` step keeps its node (`step:<id>`, so order and data edges and run state attach to it) with `step.group: "review_loop"`, and gains two nodes of kind `inner` with `parent` set to it: `step:<id>/pass` (`inner: {role: "pass", title: "Review pass"}`) and `step:<id>/fixes` (`role: "fixes"`, "Author fixes"), joined by two `loop` edges, pass → fixes and fixes → pass. The loop itself runs in `ReviewPassService`.
- **Edges**, each `{id, kind, source, target}`, ID `<kind>:<source>><target>`: `start` (each trigger node → first step), `order` (step → next step) and `data` (from a step to a later step whose `with` or output `path` references its outputs as `steps.<id>.outputs.<key>`, read with the same expression pattern as validation, so they may skip steps; one edge per pair of steps, with `outputs`, the keys used, sorted).

`GET /api/workflow-runs/{id}` adds `graph` (built from the run's own `definition_json`, never the current file; `runWithGraph` in `internal/server/workflows.go`), `definition_changed` (a discovered definition of the run's name differs from that copy; both are compared with `Source` cleared, through `workflowengine.Digest`, so a moved file is not a change), `definition_missing` (none is discovered) and `trigger_kind` (`WorkflowRunView.TriggerKind`, which `WorkflowService.Show` reads from the run's trigger request; empty for a run started by hand). `GET /api/workflows` adds `graph` to each definition (`definitionWithGraph` in `internal/server/workflows.go`). The graph is never part of a definition's own JSON, which runs store and digest. A file that fails to parse stays in `errors`, with no graph.

### Live updates and stalls

Run views update through targeted `workflow_changed` events. When an agent activity transition belongs to an active `agent.run` attempt, the server resolves its task to the persisted run and step and emits that targeted event; unrelated `agents_changed` events do not reload workflow runs or definitions. An unfinished `agent.run` step needs attention while its agent is waiting or idle. A detected exit (including a pane back at a shell) fails every waiting attempt tied to that exact session (owned `agent.run` and borrowed `agent.interview`) with `agent exited before step completion`, rather than leaving it at `waiting_agent`; Retry step can start it again. The Workflows navigation item takes its red count from the navigation summary (`/api/navigation-summary`); run rows explain the stall, and the run page offers **Prompt to continue** for a live stalled agent. Legato does not prompt automatically, to avoid duplicate or unsafe agent work. The Runs tab loads only the runs; the Workflows tab loads the definitions and the runs (for each workflow's last run). On a phone, run rows stack, steps stay one to a line, wide values scroll inside their box, and actions are touch-sized.

The card context menu's Workflows flyout on the web board scrolls independently and flips around viewport edges; cards also expose an action button for keyboard, touch and assistive-technology access.

### Diagnostics

`workflow.Check(source, data)` (`diagnostics.go`) is `Parse` for an editor: it returns the definition only when there is no error, and `[]Diagnostic` (`severity`, `message`, `path`, `line`, `column`, `end_line`, `end_column`; 1-based, end exclusive) with every problem it can find. A YAML syntax or decoding error stops it, with the line yaml.v3 reports (a syntax error's is where its context starts) and, for an unknown key, the key's path and column (`keyOnLine`). Otherwise `Definition.problems()` lists the validation problems in the order `Validate` checks them, at most one per step (`validateStep`), so `Validate` and `Parse` still return the first, word for word. Each is a `*PathError` (`ErrorPath(err)`), whose path is built with `within` as the error is wrapped (`steps[1]` + `with.column`; triggers give `on.schedule.cron`, `on.task.entered_column.inputs.x`); `diagnosticAt` walks the `yaml.Node` tree to it and spans a one-line scalar value, else the key, else as far as the file goes. Maps (inputs, `with`, outputs, trigger inputs) are checked in key order, so the first problem no longer depends on map order. `legato workflow validate <file>` prints them as `file:line:col: message` and exits 2 (`--json`: `workflow_invalid` with `details.diagnostics`), without opening the database.

### JSON Schema

`workflow.JSONSchema()` (`schema.go`) is the draft-07 schema of a v1 file, the same bytes every time. `schemaReflector` makes the object schemas from the `yaml` tags of `Definition`, `Input`, `Step`, `Output`, `Triggers`, each trigger kind and `Condition` (recursive, by `$ref`), all `additionalProperties: false` as `KnownFields` is. `fieldSchemas` gives each field's description, enum, pattern, default and required: every reflected field must have an entry (it panics otherwise), so a new struct field needs one. A step's `with` comes from the catalog: `step.allOf` holds one `if type == X then with: $ref with.X` for each executor (and `required: [with]` when the type has a required field or a checked group, `needsWith`, as the engine requires); `with.X` lists its fields (`fieldSchema`: integers, booleans and enums also take a `${{ }}` string unless `Literal`; `task` is a whole-reference pattern only where the engine checks it at load, `Checked`), its required fields, its checked constraints (`ExactlyOne` → `oneOf`, `AtLeastOne` → `anyOf`, `Excludes` → `not`), and `additionalProperties: false`. An unknown `with` key is a warning, not an error (LEG-461): the editor reports `additionalProperties` under `with` as a warning, and `Check` returns a `SeverityWarning` diagnostic (`unknownWithKeys`) with the definition. A later release will make it an error.

The `x-legato` extensions: at the root, `schema_version`, `executors` (type, title, description, internal, in catalog order), `internal`, `expressions` (`ExpressionContexts()`, `expressions.go`: what `${{ }}` may read at `run_title`, `with`, `output_path` and each `trigger.<kind>`'s inputs, as patterns such as `steps.<earlier step>.outputs.<output>`) and `task_fields` and `repository_fields` (`TaskFields`, `RepositoryFields`, which `validateReferences` uses too). On each `with.X` there are `type`, `internal`, `outputs`, `declared_outputs` and `run_constraints` (the unchecked constraints). On each field there are `kind`, `expressions`, `context` and `required_at_run`. On the properties that take expressions, `context` names their entry in `expressions`.

The copies at `web/src/generated/workflow.schema.json` and `site/public/schemas/workflow-v1.schema.json` (published at `SchemaID`) are generated: `go test ./internal/engine/workflow -run TestTheGeneratedSchemaIsCurrent -update` rewrites both, and the test fails when either is stale. `TestEveryExampleAndBuiltInMatchesTheSchema`, `TestEveryValidTestDefinitionMatchesTheSchema` (every string literal this package's tests pass to `Parse` that it accepts, read from the source, with the lenient copy when `Check` warns) and the service's `TestBuiltInWorkflowsMatchTheSchema` validate with `google/jsonschema-go`. `TestTheSchemaRefusesInvalidFiles` holds a sample of files the schema refuses. `GET /api/workflow-schema` (`internal/server/workflow_schema.go`) serves it with `ETag`, `Cache-Control: private, max-age=300` and `X-Legato-Workflow-Schema-Version`.

### Extension model

**The executor catalog** (`internal/engine/workflow/catalog.go`, `Catalog()`, `LookupExecutor`) is where a step type declares its contract, and the one place a new executor is added before anything else: its `with` fields (`Field`: name, `FieldKind` such as `text`, `task`, `task_or_id`, `repository`, `path`, `column`, `macro`, `agent`, `tier`, `json`; `Required` (the file does not load without it), `RequiredAtRun` (the executor fails without it), `Default`, `Enum`, `Literal` (no `${{ }}`), `Checked` with `Invalid` (the value's kind is checked at load, with that message)), its `Constraints` (`ExactlyOne`, `AtLeastOne`, `Excludes`; a `Checked` one is enforced at load), its `Outputs`, `DeclaredOutputs` (an agent completes the step with the outputs the step declares, as for `agent.run`) and `Internal` (the learning executors, which the builder does not offer). `Definition.Validate` takes its list of step types from the catalog, and `validateStepContract` checks checked constraints, then checked fields, then required fields. Only what was checked before the catalog is `Checked` or `Required`, so every file that loaded still loads; unknown `with` keys are still accepted (LEG-461). `TestEveryWorkflowExecutorHasACatalogEntry` (`internal/service`) finds each executor's `Type()` in the package's source and fails when one has no catalog entry, or an entry no executor. The JSON Schema and the web builder are made from the catalog (LEG-457).

Workflow persistence and UI are executor-neutral. A future deterministic executor declares its contract in the catalog, implements the service executor contract and renders type-specific details without replacing runs, steps, attempts, outputs or artifacts. DAGs, parallel execution, schedules, shell plugins, approval gates and native external publishers (but for `github.pr.review_passes`) are not part of schema version 1.

## Triggers on a worker's handed-off cards

A card a main handed off to this Legato is the main's (LEG-243). `WorkflowTriggerCoordinator.process` checks `store.OpenHandoffForTask` before anything else and marks the trigger request `skipped` with the reason ("the card was handed off from <main>, whose workflows run when it returns; set handed_off: true on the trigger to run on such cards") unless the trigger sets `handed_off: true` (`TaskEnteredColumnTrigger.HandedOff`, schema v1). The built-in learning triggers are skipped the same way, so a worker's curator does not curate a main's task into the worker's ledger. The main's own triggers run when the task returns into another column (a `handoff` transition; see [Integrations](integrations.md) § Handing off a task). Review passes are not workflows and are unaffected. The Workflows page says "cards handed off from a main included" on a trigger that opts in; trigger requests themselves, skipped ones included, are not listed by any route yet.

## Steps on a task that is away

A task away on a worker is read-only on the main (`RefuseAway`). `task.move` was already refused through `moveCard`; `task.metadata.set` now asks `RefuseAway` too and fails the step with its words (LEG-239). `task.note` still adds the note on the main, where it is when the task returns, and adds `away_on` and `warning` to its outputs: the note is not forwarded, so the worker's agent works without it. Forwarding it to the worker as a main note was the alternative; it would need a handoff route of its own and an agent told mid-turn, and the operator can message the agent instead.

## Pausing triggers

Every trigger kind has `enabled` (`*bool`; absent is on). `Triggers.List` gives each declared trigger's kind (`TriggerTaskEnteredColumn`, …) and `EnabledByDefault`; a new trigger kind adds itself there. Migration 122 adds `workflow_trigger_switches` (`workflow_name`, `trigger`, `enabled`, `updated_at`), this Legato's switch, which beats the file both ways and never rewrites it (store: `WorkflowTriggerSwitches`, `WorkflowTriggerSwitchFor`, `SetWorkflowTriggerSwitch`, `DeleteWorkflowTriggerSwitch`). `WorkflowTriggerCoordinator.triggerEnabled` is checked before a request is made (`CaptureTransition`), so a paused trigger makes no request at all; requests made before the pause are left as they are. `TriggerStates` (by workflow: `trigger`, `file_enabled`, `enabled`, `overridden`), `SetTriggerEnabled`, `ResetTrigger` (`ErrNoSuchTrigger` for an undeclared workflow or kind; `workflow_trigger_switch.go`). API: `GET /api/workflows` adds `trigger_states`; `PUT /api/workflows/{name}/triggers/{trigger}` `{enabled}` and `DELETE` (back to the file) answer `404` for an undeclared trigger and broadcast `workflow_changed`. Web: the Workflows tab's `TriggerSwitch` (`role="switch"`, labelled by `triggerLabel`, "on here"/"paused here").

## Loop stop and trigger requests for every kind

Migrations 123 and 124 make `workflow_trigger_requests` hold every trigger kind: `transition_id` may be NULL (123 edits the table text through `writable_schema`, so `store.go`'s `triggerSchemaEdits` bumps `schema_version` after it, as for 058), status `held` is added, and 124 adds `trigger_kind` (default `task.entered_column`), `item` (what the loop stop counts by: the task, `owner/repo#n`, the due time), `event_key` (unique per `(workflow_name, trigger_kind, event_key)`, NULL for a column move) and `event_json` (`{task_id, context}`). Reads go through `triggerRequestColumns`, which gives a missing transition or key as `""`. `InsertWorkflowTriggerEvent` (`ErrTriggerEventSeen` when another Legato on the database made it first), `CountStartedTriggerRuns`, `LatestTriggerEvent`.

Every trigger kind says `confirm`, `enabled`, `max_runs_per_day` and `inputs` (`Triggers.Common`; `TriggerCommon.Limit`, `DefaultMaxRunsPerDay` 3). Before a request starts a run, `WorkflowTriggerCoordinator.loopStop` counts the requests of that workflow and trigger for the item that reached `starting`/`started` in the 24 hours before the coordinator's clock (`SetClock`; a request's `created_at` is set from it); at the limit the request is `held` with "stopped to prevent a loop: …". `RunAnyway` starts a held request past the limit; `PauseTrigger` sets the trigger's switch to paused here and skips the request. Attention: `workflow_trigger_loop_stop` (high urgency, actions `run_anyway` and `pause_trigger`), navigating to the task, or to the Workflows tab (`workflows`) when the event names none.

`Fire(TriggerEvent)` is the path for every kind but column moves: a paused trigger or an event already seen makes nothing; otherwise the request is inserted and `processEvent` resolves the trigger's `inputs` against the event's context (`${{ schedule.time }}`, `${{ event.repo }}`, … through `resolveMappedInputs`, which the column trigger shares), then the loop stop, confirmation and the run. `Reconcile`, `SupplyInputs` and `Confirm` take event requests through the same path.

## Schedule trigger

`on.schedule` (`workflowengine.ScheduleTrigger`, `schedule.go`): `every` (`daily`, `weekdays`, `weekly`) with `at` (`HH:MM`) and, for weekly, `on` (a weekday); or `cron` (five fields, `*`, n, `a-b`, lists, `/step`, month and weekday names, weekday 7 = Sunday; day-of-month and weekday ORed when both are restricted, as cron does). `every` forms compile to a cron spec (`spec`). `timezone` (an IANA zone, checked with `time.LoadLocation`; `time/tzdata` is embedded), `catch_up` (`once`, default, or `skip`; used by missed runs), and the common `enabled`, `confirm`, `max_runs_per_day`, `inputs`. `Next(after, loc)` and `Prev(before, loc)` are pure: they walk wall-clock dates in the zone, and `wallInstant` turns a wall minute into an instant: one that does not exist (clocks forward) is the next minute that does, one that repeats (clocks back) its first coming, so each fires once. `DueBetween(from, to, loc, limit)`. `Describe` is the page's words.

`WorkflowTriggerCoordinator.TickSchedules` (every process that runs triggers: `StartEventLoop` starts `scheduleLoop`, a tick just after each minute) fires each schedule's latest due time when it is at most `scheduleTickWindow` (5 minutes) old, through `Fire` with key and item = the due time in UTC RFC 3339: the unique `(workflow_name, trigger_kind, event_key)` index makes it one request whichever process ticks first; there is no leader. The event context is `schedule.time` and `schedule.previous_time` (the schedule's due time before it), RFC 3339 in the schedule's zone. `SetHostZone` (tests) replaces `time.Local`. `TriggerStates` adds `schedule` (`description`, `timezone`, the next three due times, and `last`: the newest due time's status and run, `LatestTriggerEvent`), which the Workflows tab shows beside the trigger's switch (`ScheduleTimes`).

### Missed runs

`CatchUpSchedules` runs in `StartEventLoop` before the first tick: for each enabled schedule with a due time recorded (`LatestTriggerItem`, the greatest `item`; a schedule's item is its due time in UTC RFC 3339, which sorts as time does), the due times after it and before the tick window are each recorded as a `missed` request (status added to migration 124's check; `recordMissed`, error "Legato was not running at … (catch_up: …)"), once: the event key makes a restart record nothing new. With `catch_up: once` and anything newly recorded, one late run is fired with key `late:<newest missed>`, item the newest missed, `schedule.time` the newest missed, `schedule.previous_time` the due time recorded before them, and `schedule.late: true`. A schedule never recorded has nothing to catch up. `ScheduleState` adds `missed` (newest ten, `ListTriggerEvents`) and `catch_up`, shown on the Workflows tab. A due time whose run cannot start is a `failed` request, which the trigger Attention producer already shows.

## pr.changes_requested

`on.pr.changes_requested` (`workflowengine.PRTrigger`: `enabled`, `confirm`, `max_runs_per_day`, `inputs`; give `{}` for none, since an empty key is no trigger). `StartEventLoop` subscribes to `EventPRChangesRequested` and calls `ChangesRequested`, which fires every such workflow through `Fire`: key `owner/repo#n/review/<id>` (one request per review), item the task (the loop stop counts by it), task the task. Inputs read `${{ event.task }}`, `${{ event.repo }}`, `${{ event.pr_number }}`, `${{ event.pr_url }}`, `${{ event.reviewer }}`, `${{ event.review_id }}`. Where the reviews come from: [PR tracking](pr-tracking.md) § Reviews and pr.changes_requested.

## Provider Architecture

Several ticket providers sync at once. The sync service (`internal/service/sync.go`, `NewTicketSync`) holds one `service.TicketSource` per provider (`internal/service/ticket_source.go`), and a task belongs to the source whose `Name` is its `provider`. A source owns what is its own: `Pull` (the tracked tasks' tickets, and `Missing` for the keys the provider no longer has), `Search` by text, `Get` by key, `Column` (where a status goes on the board), `Enabled` (configured and connected; a source that is not is skipped quietly), `Interval` and `MovesCards`. The service owns what they share: updating tasks, stale marks, the conflict window, local-only columns, attachments, events.

- **Jira** is `NewJiraSource` over `service.TicketProvider` (`internal/service/provider.go`; `JiraProviderAdapter` in `provider_jira.go` bridges `jira.Provider`). It builds JQL for pulls and searches and places statuses through the column mappings. ADF-to-Markdown conversion is internal to the Jira provider. Jira is the one provider that takes card moves.
- `cmd/legato/ticket_sync_runtime.go` (`newTicketSync`) builds the sources the configuration names, for the TUI, `legato serve` and workflow commands; nil when there are none.
- A source that fails leaves the others syncing: `SyncResult.Sources` has each one's outcome by name, and `Sync` returns an error only with them.
- Remote update times are kept with sub-second precision (`RFC3339Nano`), so a ticket changed within a second is not applied again each cycle.

### Sync Algorithm

### Jira image attachments

Tracked Jira tickets cache `image/*` attachments during import and every sync. Existing tickets are backfilled on the first sync after enabling this behavior, even when the Jira issue timestamp has not changed. Missing temporary files are restored on later syncs, removed Jira attachments are deleted locally, and archiving a task removes its attachment directory.

The cache lives under `$XDG_RUNTIME_DIR/legato/jira-attachments` when available, otherwise under the user's system temporary directory. Absolute paths appear in `legato task show` output and swarm briefs so agents can inspect images locally. Configure `jira.attachment_max_size_bytes` to limit each image; the default is 25 MiB. Non-image attachments are not downloaded.


- **Pull**: periodic fetch via provider → **update existing tracked tasks only** (new tickets must be imported manually via `i` overlay or `ImportRemoteTask`). Provider Markdown refreshes `remote_description_md` while preserving editable Legato `description_md`; status-to-column mapping and stale detection use remote_meta. Archived tasks skipped. Untracked remote tickets are silently ignored — pull never auto-imports
- **Push**: local SQLite update first (non-blocking), then async remote transition, for Jira's tasks only: other providers' cards move locally; failure logs to `sync_log` and preserves local column
- **Conflict resolution**: local wins within 5-minute window of `local_move_at` (stored in remote_meta); after window, remote state accepted on next pull
- **Scheduler**: ticks at the shortest source interval (Jira's default 60s) and pulls each source when its own interval has passed; a manual sync pulls them all. Publishes SyncStarted/SyncCompleted/SyncFailed events
- **SearchRemote**: asks every enabled source (min 2-char query) and labels each result with its `Provider`; results from the sources that answered, an error only when none did. Jira's search is JQL `summary ~ "query" OR key = "query"` scoped to `projectKeys`, `ORDER BY updated DESC`
- **ImportRemoteTask**: `ImportRemoteTask(ctx, provider, ticketID, ImportRemoteTaskOptions{WorkspaceID, Column})` fetches one ticket from the named source (`""`: the only enabled one, else an error naming them) and creates a local task with that provider and optional workspace. `Column` (matched ignoring case) is the task's `Status` when it is created, before `EventCardsRefreshed`; `""` is `source.Column`, else Backlog. A column the board lacks is `ErrUnknownColumn` (naming the columns) and creates nothing. Import never writes to the provider (no move is pushed), and sync is unchanged: the picked column holds until the ticket changes remotely, when the card follows the status mapping by the usual rules (`MovesCards`, local-only columns, the conflict window). A task of the same key from the same provider is returned as it is, whatever the options; one from another provider, or a local task, is `ErrTicketKeyTaken`, since the key is the task ID. The returned card carries the task's column, provider and workspace (ID and name). `POST /api/remote/import` takes `provider` and an optional `column` in the same way (`400` for an unknown column), answers with those fields, and `/api/remote/search` results carry `provider`
- **Handed-off tasks**: a provider-backed task (Jira, Burnlite, any source) handed to a worker keeps its link and its sync on the main, away and after; only its Legato details come back. The main sends the key, text and URL every source stores the same way (`remote_id`, `remote_description_md`, `remote_meta.url`). The worker's card is a copy under the provider `<provider>-copy` (`jira-copy`, `burnlite-copy`; `service.HandoffCopyProvider`), which no source has, so the worker never pulls it or pushes its moves. See [Integrations](integrations.md) § Handing off a task, Provider-backed tasks
- **Provider sync** (`POST /api/board/sync`, `r` in the TUI): `ProviderSyncResult` is each provider's outcome by name (`jira`, `burnlite`, `github`), `jira` and `github` always present

## Burnlite

Burnlite (an issue tracker and estimator) is a read-only ticket provider: `NewBurnliteSource` in `internal/service/provider_burnlite.go`, over `internal/engine/burnlite`. It takes part only while the integration `burnlite` is connected (`legato integration connect burnlite`, or Settings › Integrations; see [Integrations](integrations.md)), reading the address from that connection and its tokens from `OAuthTokens` (scope `read:tasks`). `cmd/legato` registers it always, so connecting while Legato runs is enough. When Burnlite refuses the refresh token the integration becomes `disconnected`, the source is skipped, and Attention raises `integration_disconnected` for `burnlite`.

- **State and column.** A task is `Closed` or `Not planned` when closed, else `Claimed` when someone holds its claim, else `Blocked` with an open blocker, else `Ready` (Burnlite's frontier). That is its `remote_status`, and `burnlite.columns` (`ready`, `blocked`, `claimed`, `closed`) places the card. Not the column mappings, which are Jira's.
- **Fields.** The key is the task ID and `remote_id`; the name is the title; `remote_description_md` is the Description, then `## Plan`, then `## Checklist` as `- [x]` items. `remote_meta`: `issue_type` (`Work`, `Meta`), `assignee` (the claim holder), `labels`, `epic_key`/`epic_name` (the milestone), `url` (`<burnlite>/EST-42`), and `size`, `uncertainty`, `blocked_by` (open blockers' keys) and `resolution` (a closed task's summary). Priority is empty.
- **Milestones.** A milestone's key is from the same series as its project's task keys, and `get_task` refuses it as `not_found`, so `Get` (import, and a search by key) tries `get_milestone` then. The card's title is the milestone's name; `remote_description_md` is its Description, then `## Tasks`: a line for each of its tasks in Burnlite's order, `- [x] [EST-43](<burnlite>/EST-43) Name (State)` (checked when closed, `Claimed by <holder>` for a claim). `issue_type` is `Milestone`; its state is `Ready`, `Closed` or `Not planned`. Burnlite gives a milestone no `updatedAt`, and a task leaving one changes no timestamp the milestone still lists, so `Pull` reads each tracked milestone (by `issue_type`) with `get_milestone` every time and dates it now only when its title, text, state, labels or URL differ from what Legato holds (`pullMilestone`). One that is gone is stale.
- **Pull.** One `list_tasks` (state `any`) for each project with tracked tasks; `get_task` only for a task whose `updatedAt` is newer than the `remote_updated_at` Legato holds. A task the list no longer has, or the tasks of a project that is gone, are stale. A Burnlite whose rows have no `updatedAt` fails the sync with a message to update it.
- **Search.** Burnlite has no text search: the open tasks of `burnlite.projects` (else the projects saved in the web UI, `BurnliteProjects`/`SaveBurnliteProjects` in `instance_values` `burnlite.projects`; else every project) whose name contains the text, and a task named by its key in any state. At most 50.
- **Card moves** stay local: Burnlite is never written. With `burnlite.status_sync_enabled` (default `true`) a task's change of state moves its card, within the same conflict window and local-only columns as Jira.
- **Errors.** Search and import with no provider connected, or not the one named, are `ErrNoTicketProvider` (`/api/remote/*` answer `503`); a key another provider owns is `ErrTicketKeyTaken` (`409`); an import into a column the board lacks is `ErrUnknownColumn` (`400`).

# Sandbox

With `agents.sandbox.enabled`, Legato starts each agent tool inside a sandbox: bubblewrap on Linux, Seatbelt on macOS (see Backends and macOS). The agent sees its work, its tool's own state, the person's toolchains, and Legato's sockets for it; it does not see the person's credentials, Legato's database or configuration, or sockets that give the host away. Its agent-side processes (hooks, `legato mcp serve`, the native bridges, the `legato` commands it runs) reach the host Legato through the broker instead (see [CLI](cli.md) § The host broker). The design is in `openspec/changes/sandboxed-cloud-agents` (phases 2 and 3).

The sandbox keeps secrets from agents. It does not filter the network, and it does not hide the agent tool's own model login, which the tool needs.

## Backends

`agents.sandbox.backend` is `bwrap` on Linux and `seatbelt` on macOS (`sandboxBackend`, `cmd/legato/sandbox_runtime.go`). `BuildSandboxPlan` makes one plan for either, from the host's `HostLayout` (`LayoutFor`) and the backend's `Capabilities`: bwrap has them all; Seatbelt (`sandbox-exec` with a profile, `internal/engine/sandbox/seatbelt.go`) only allows and denies, so for it the plan shows every path where it is. `TMPDIR` and `HOME` name the execution's scratch `tmp` and `home`, the home holds links to what the plan shows of the real one (`Plan.Links`, `homeLinks`), the `gh` and `az` wrappers run the real command where it is (they are first on `PATH` instead of covering it), and `Plan.Sockets` names the Unix sockets an agent may connect to. On macOS the line typed into the pane is `<legato> sandbox exec <runtime>/legato/sandbox/<execution>/seatbelt.json --`: the launcher (`ExecLaunchSpec`, before anything else in `main`) applies the spec's environment and working directory and becomes `/usr/bin/sandbox-exec -f seatbelt.sb -D… -DTTY=<the pane's terminal>`. The facts the profile relies on were measured on macOS 15.8 and 26.7 by `cmd/validate/seatbelt-probe` (LEG-168; the `seatbelt-probe` workflow runs it). The sections below describe bwrap unless they say otherwise; macOS has its own section.

`TestBwrapArgumentsOfKnownPlansDoNotChange` keeps the bwrap arguments of four plans in `internal/service/testdata/bwrap` (`-update-bwrap` rewrites them); `TestTheSeatbeltProfileOfAKnownPlanDoesNotChange` keeps a profile in `internal/engine/sandbox/testdata/seatbelt` (`-update-seatbelt`).

## How a spawn is wrapped

- `SpawnAgent` decides before any tmux session exists: a sandbox that cannot be built (no `bwrap`, a forbidden path) fails the spawn and never leaves an unsandboxed agent.
- The pane runs the person's shell, on the host, with the session's environment. The launch command typed into it is prefixed with `bwrap --args 3 3<<runtime>/legato/sandbox/<execution>/bwrap.args --`, so `$(cat $LEGATO_ROLE_PROMPT_FILE)` is still expanded by the host shell. A shell agent gets the same prefix before `${SHELL:-/bin/bash}`.
- The sandbox's options are in that file (NUL-separated, mode `0600`), not on the typed line: a terminal cuts a typed line at 4096 bytes before the shell reads it, and a sandbox's mounts easily pass that. bwrap closes the file before it starts the agent.
- **The pane's terminal.** The agent keeps the pane's terminal (its size changes reach it, `/dev/tty` opens), so bwrap runs without `--new-session`. Instead, `argsFileCommand` writes `seccomp.bpf` beside `bwrap.args` and the line passes it as `--seccomp 4 4<…/seccomp.bpf`: `sandbox.TerminalFilter` (`internal/engine/sandbox/seccomp.go`) refuses the ioctls `TIOCSTI` and `TIOCLINUX` with `EPERM` and allows every other call, comparing the request's low 32 bits as the kernel truncates it, for amd64 (with i386 and x32 calls) and arm64 (with 32-bit ARM). Without it, an agent on a kernel that allows `TIOCSTI` (before 6.2, or `dev.tty.legacy_tiocsti=1`) could push a command into the pane's input, which the host shell reads after the agent exits. `TestInsideTheSandboxNothingCanBeTypedIntoThePane` runs the real bwrap in a pseudo-terminal and expects `EPERM`, the sandbox's refusal, not the kernel's `EIO`.
- The adapter is told its tool runs in the sandbox (`LEGATO_SANDBOXED=1` in the environment it builds the launch command from, not in the pane's). Chimera then drops its own `--sandbox` and `--sandbox-*` flags: its sandbox is a Docker container, and the Docker or Podman socket would undo Legato's.
- `bwrap` runs with the host's network and user, fresh PID, IPC, UTS and cgroup namespaces, and `--die-with-parent`: everything inside ends with the pane.
- `agent_sessions.sandboxed` (migration 075) records which sessions run inside.

Built by `service.BuildSandboxPlan` from the host's real paths (links resolved first: on a host whose `/home` is a link to `var/home`, every path is checked and mounted where it really is).

Independent of `default_mounts`; never a mise shim (`SandboxEngram`; see [Engram sessions](engram.md)) |
| With an `azure` credential: Legato's `az` wrapper (`<runtime>/legato/sandbox/<execution>/az`) over every real `az` on the host's `PATH` (links resolved), and the real `az` at `…/az-real` (`LEGATO_AZ_REAL`); `AZURE_CONFIG_DIR` is unset | read-only (`sandboxAz`, `SandboxWrapper`; see [Credentials](credentials.md) § Azure) |

A chain of links that passes through a forbidden path is left out, and the link stays broken.

Never seen: Legato's configuration file and data folder, `~/.config/legato` (the 1Password token file), `~/.ssh`, `~/.config/gh`, `~/.gitconfig`, git credential stores, `~/.netrc`, `~/.1password`, `~/.config/op`, `~/.docker`, `~/.aws`, `~/.azure`, `~/.kube`, `~/.gnupg`, password stores and keyrings, `~/.npmrc`, `~/.pypirc`, `~/.yarnrc`, `~/.yarnrc.yml`, Gradle's `gradle.properties`, Maven's `settings.xml`, Composer's `auth.json`, the Docker and Podman sockets, and the person's runtime folder (`/run/user/<uid>`: the session bus, every Legato's IPC socket). A mount that is inside one of these is refused; one that holds one has it covered with an empty file or folder. bwrap mounts in order, a later mount covering an earlier one, so the plan's mounts and covers are ordered by the depth of their path inside (`mountDepth`, the build order kept between equals): each lands after everything that holds it. A cover is then on top of every mount that holds what it hides, also one put back inside another cover (the repository cache in the data folder, under a mounted home), and before the mounts inside it that the sandbox may see (a job clone, `claude-mod`, `repos`), which it would otherwise cover in turn.

The environment loses the variables secrets come from (`OP_SERVICE_ACCOUNT_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN` unless it is Legato's stand-in, the session bus, `TMUX`, `DOCKER_HOST` unless it is the execution's own socket (Docker, below), cloud and registry tokens, …) and `SSH_AUTH_SOCK` unless it is the execution's own socket. It gains `LEGATO_SANDBOXED=1`, `TMPDIR=/tmp`, and the person's git name and address (read from `git config --global` at start), since `~/.gitconfig` is not there.

## The checkout's git folder

The person's own git, outside the sandbox, runs what an agent leaves in its checkout's git folder. The hooks folder (`gitHooksDir`: the common `.git`'s for a worktree, else `<work>/.git/hooks`) is mounted read-only over the writable checkout, in both backends (on macOS its folders cannot be renamed either, as for any read-only path inside writable work). `.git/config` stays writable, since agents set upstreams and remotes; instead `SandboxGitConfig` (`internal/service/sandbox_git_config.go`, `SandboxSettings.GitConfig`, data in `<data_dir>/sandbox-git-config`) notes at spawn the entries of `<common .git>/config` that run a command (`gitConfigRunsCommand`: `core.fsmonitor` naming a program, `core.hooksPath`, `core.sshCommand`, `core.editor`, `core.pager`, an alias with `!`, `filter.*` drivers, `diff.*.textconv`, `credential.*.helper`, `gpg.program`, `include.path`, `includeIf.*.path`, …; read by `git config --file --no-includes --list -z`, with no global or system configuration), in the execution's runtime folder, and compares when the execution ends (`EndExecution`). Each one added or changed is kept as a finding and shown as an Attention item on the agent's task until it is gone (`sandbox_git_config`, **Remove them**). A finding is only made for an execution that ends through `EndExecution`, and only while the sandbox is on. A hook the repository itself tracks (`core.hooksPath` set to `.husky`, a tracked hook script) is the repository's content, which the agent may change like any other file.

## SSH and git

bwrap is not setuid on most systems, so it always makes a user namespace, and there every file root owns shows as owned by `nobody`. ssh refuses a system configuration file that belongs to neither root nor the person (`Bad owner or permissions on /etc/ssh/ssh_config.d/…`), so without help ssh does not start at all.

- **The configuration.** Before each sandboxed spawn, `writeSandboxSSHConfig` (`internal/service/sandbox_ssh.go`) copies `/etc/ssh/ssh_config` and every file it includes, following `Include` lines (relative to `/etc/ssh`, globs expanded, links followed, `~` skipped, 16 deep) as ssh would. The copies are the person's, mode `0600`, and each is mounted over the real path of its original (on Fedora: `ssh_config.d/50-redhat.conf`, the systemd proxy file, `/usr/share/crypto-policies/…/openssh.txt`).
- **Known hosts.** The copy of `ssh_config` starts with `UserKnownHostsFile <that folder>/known_hosts`, and `credential_channels.ssh_agent.known_hosts` is mounted there read-only: the file Legato's SSH agent names hosts by. It holds host keys, not secrets. A host it does not list cannot be verified, and the agent's `ssh` stops there.
- **Keys.** None: `~/.ssh` stays hidden. A login is signed by Legato's SSH agent socket for the execution, when an `ssh` credential covers the host (see [Credentials](credentials.md) § SSH agent); otherwise ssh starts and finds no key.
- **Git fetches from GitHub.** With a `github` credential, a sandboxed session also sends fetches from `git@github.com:` and `ssh://git@github.com/` to `https://github.com/` (`sandboxGitFetches`, added after the session's `GIT_CONFIG_*`), where Legato's credential helper gives read tokens; pushes from those forms already go to the proxy through `pushInsteadOf`. So a clone whose `origin` is an ssh URL fetches and pushes with no ssh key. The repository must be in the credential's `settings.repositories`. The proxy's `/git/` route serves pushes only and answers fetches `403`.

## Docker

The Docker and Podman sockets are among the forbidden paths, and `DOCKER_HOST` is a secret variable: a rootful daemon's socket is root on the host, and any container could bind `~/.ssh`. Porting to Podman does not help (rootless Podman cannot run inside bwrap: `NoNewPrivs` stops `newuidmap`, there is no `/dev/net/tun` and no cgroup tree), and running `./dev` on the host for an agent runs code the agent can edit. With `agents.sandbox.docker.enabled` each sandboxed execution gets a socket of its own that passes to the real daemon only what keeps within its sandbox. Agents outside the sandbox, and the person's shells, are untouched: no proxy, the host's `DOCKER_HOST` and socket as before.

- **Spawn** (`agent_sandbox.go`, `sandbox_docker.go`). `SandboxSettings.Docker` (`*SandboxDocker`, built by `sandboxDocker` in `cmd/legato/sandbox_docker_runtime.go`; nil when off or when the daemon address cannot be read) sets `SandboxPlanInput.DockerSocket` to `<runtime>/legato/sandbox/<execution>/docker/docker.sock`. `BuildSandboxPlan` mounts that socket's folder read-only (the folder, so a socket made again by another process is seen), sets `DOCKER_HOST=unix://<socket>`, keeps `DOCKER_HOST` out of `Unsetenv` and unsets `DOCKER_CONTEXT`, `DOCKER_TLS_VERIFY`, `DOCKER_CERT_PATH` and `DOCKER_CONFIG`. After the plan is built, `SandboxDocker.WriteView` writes `<runtime>/legato/sandbox/<execution>/docker-view.json` (`0600`, outside every mount): the plan as `dockerproxy.View` (`dockerViewOf`: the home bind first, then each mount in bwrap's order; an overlay's lower path read-only; an optional bind whose path is missing left out). Every sandboxed spawn goes through `sandboxPrefix`, so manual, swarm, workflow and reviewer agents and the Reeve all get it.
- **Serving** (`cmd/legato/sandbox_docker_runtime.go`). `startDockerHost`, from `startApprovals` (both runtimes), takes `<data_dir>/docker-proxy.lock` (per Legato: each serves its own executions) and every 2 seconds, and on `EventAgentStarted`, serves a socket (`0600`) for each running execution that has a view, and closes the server (live connections too) of each that ended. A process that takes the lock over makes the sockets again. Agents of a command that spawns and exits (a workflow or swarm command) are served by the host Legato, as with the credential channels; with none running they get no Docker until one starts.
- **Policy** (`internal/engine/dockerproxy`, which knows nothing of Legato). Deny by default; a refusal is `403` (`404` for something not the agent's) with `{"message": "legato: <reason>"}`, which the CLI prints, logged with the execution.
  - Routes: `_ping`, `version`, `info`, `system/df`, `events`, containers, `exec`, `commit`, images (pull, build, tag, inspect, history, save, load, search; push refused), `build` and `build/cancel` (`build/prune` refused: the cache is shared), `session` and `grpc` (BuildKit), networks, volumes, `distribution/*/json`. Swarm, services, secrets, configs, plugins, nodes, tasks and everything else are refused. Paths with `.`/`..` segments or escaped characters are refused; a `/v1.xx` prefix is kept.
  - Ownership: containers, networks and volumes get `legato.execution=<id>` on create (`Labels`), and so do built and committed images (`labels` on `/build`, `Labels` on `/commit`). Lists, `events` and prunes get `label=legato.execution=<id>` added to `filters`. A route that names a container, exec instance, network or volume inspects it upstream first and goes on only for the execution's own; a container is then named by its full ID, so a name or prefix cannot come to mean another. `DELETE /images/<ref>` only for images carrying the label. A named volume a container would make is made first, labelled (`checkVolumeRef`); one that exists and is not the agent's is refused. Networks: only `bridge`/`none`/`default` or the agent's own, by `NetworkMode`, `EndpointsConfig` or `connect`; `Links`, `VolumesFrom`, `container:` modes only to the agent's own containers.
  - Bodies are read as `object`s (`object.go`): the daemon's decoder matches field names ignoring case and takes the last of several, so every field is first renamed to the exact name it matches in an allowlist, a field matching none is refused (a field added to the API later is refused until listed), and one given twice is refused. Without this, `"privileged": true`, or a HostConfig field at the top level (the old `ContainerConfigWrapper` read those), would pass a check of `Privileged`.
  - Mounts (`View.Resolve`): a bind source must be absolute; it is mapped to the host path through the view (the mount that shows it, links the sandbox makes followed; a cover refuses it), resolved with `filepath.EvalSymlinks` on the host, and the resolved path must itself be shown by the mount that shows it there: a link in the worktree to `~/.ssh`, or in `/tmp` to anywhere, is refused. The daemon is sent the resolved path, read-only (`:ro`, `ReadOnly`, `o=…,ro`) when the sandbox shows it read-only. A missing source is refused (the daemon would make it as root). This applies to `Binds`, `Mounts` of type `bind` (propagation other than private refused; `ReadOnlyNonRecursive` refused when read-only is forced), volume driver options (`POST /volumes/create` `DriverOpts`, `Mounts[].VolumeOptions.DriverConfig`: only `local`, a `tmpfs`, or `o=bind` of a path the view allows) and `VolumesFrom`. `:z`/`:Z` relabel the host path, so only on paths the agent may write.
  - Containers: refused `Privileged`, `Devices`, `DeviceCgroupRules`, `DeviceRequests`, `CapAdd` outside `cap_add`, `host` (or `container:` someone else's) for `NetworkMode`, `PidMode`, `IpcMode`, `UTSMode`, `UsernsMode`, `CgroupnsMode`, a `Cgroup` or `CgroupParent`, `SecurityOpt` other than `no-new-privileges`, `Sysctls` outside `kernel.shm*`, `kernel.msg*`, `kernel.sem`, `fs.mqueue.*`, `net.*`, `MaskedPaths`/`ReadonlyPaths` (`systempaths=unconfined` unmasks `/proc`, and a writable `/proc/sys/kernel/core_pattern` is a known escape), `Annotations`, runtimes other than runc, crun, runsc, a volume driver other than local. `exec` with `Privileged` is refused; `update` takes resource fields only. With `publish: loopback`, published ports bind `127.0.0.1` and `PublishAllPorts` is refused.
  - Builds: `networkmode` other than default/bridge/none is refused; `remote` must be `client-session` or an http(s)/git address. A BuildKit build over `/session` and `/grpc` carries its options inside gRPC, which the proxy does not read: its entitlements (`security.insecure`, `network.host`) are the daemon's to refuse. dockerd refuses `security.insecure` unless its configuration allows it; `network.host` gives a build step the host network, which the sandbox shares anyway.
  - Streams: `httputil.ReverseProxy` with `FlushInterval: -1` passes `101` upgrades (attach, `exec start`, BuildKit's `h2c`) and streamed bodies (`logs -f`, `events`, pulls) through.
- **Cleanup.** `agentService.EndExecution` (every way an execution ends) asks `SandboxDocker.HasProxy` before the scratch goes, then removes in the background what the execution made (`dockerproxy.Cleaner.Clean`: containers with `force` and `v`, then networks, then volumes; images stay). `ReconcileSessions` ends with `SandboxDocker.Sweep`: every `legato.execution` value on the daemon whose execution this database knows and is not running is cleaned; one it does not know (another Legato's) is left. A sweep failure is logged once until it changes (a daemon that is not running). A reload ends the execution, so its containers go with it.
- **Residual risks.** Between the check and the daemon's mount, an agent could replace a folder on the resolved path with a link (the source is resolved, but the daemon resolves it again when it mounts); a rootless daemon limits what that would give. The daemon is reached through Legato's own access to it.

Not done: registry logins (`~/.docker` stays hidden; public images pull), Chimera's own Docker sandbox inside Legato's (its `--sandbox` flags are still dropped), `ssh://` and TLS daemon addresses.

## Scratch

`<scratch>` is `agents.sandbox.scratch_dir`, `<data_dir>/sandbox` by default (`SandboxScratch`, `sandbox_scratch.go`). Before, `/tmp` was in `<runtime>/legato/sandbox/` and the home a `--tmpfs`: both in RAM (`/run/user/<uid>` is a tmpfs shared by every sandbox, and without swap its pages cannot be evicted), and nothing removed `/tmp` when an agent ended. A build cache in `/tmp` took the memory the compiler needed, and twenty ended executions filled the space (LEG-78).

- **Layout.** `<scratch>/<execution>/tmp`, `home`, and `overlay/<n>/{upper,work}` for each throwaway mount (`--overlay-src <path> --overlay <upper> <work> <path>`; `--tmp-overlay`, a tmpfs, only without a scratch folder). Made `0700` at spawn, as agents can write tokens there and on disk they outlive a reboot. The runtime folder keeps the small files of a spawn: `bwrap.args`, `seccomp.bpf`, the ssh copies, `gh-real`.
- **Private to its execution.** The scratch folder is one of the forbidden paths (`forbidden`): a mount into it, or a working directory inside it, is refused, and a mount that holds it (a custom `scratch_dir` under `/opt`, or under a folder given as a resource) has it covered. A mount at or inside it (a default mount the scratch folder is, such as `~/.cache/go-build` or `/opt`) is left out of the plan, apart from this execution's own runtime folder. These rules (`inOthersScratch`) come before the data folder's exemptions (`allowedInside`: the repository cache, `claude-mod`, the job clone), so a scratch folder inside one of those is no less private; the configuration refuses one there anyway, since hiding it would break what agents need. A sandbox sees its own folders only where they are bound, at `/tmp` and the home. `sandboxPrefix` makes the folder before the plan is built, since a cover is only made for a path that exists, so the first spawn is covered too. bwrap makes the mount points of the binds inside the home (`.local/bin`, `.claude.json`, …) as empty entries in `<scratch>/<execution>/home`.
- **Removed when the execution ends.** The pane is stopped first (`KillAgent` and `FinishWorkflowAgent` return tmux's error, which is never "no such session", and change nothing): until then the session is still `running`, so a sweep meanwhile keeps the scratch. Then `agentService.EndExecution` records the end and removes both of the execution's folders (scratch and `<runtime>/legato/sandbox/<execution>`): a kill (also a reviewer's, `KillAgentInSlot`), a pane found dead by `ReconcileSessions` or at respawn, a failed spawn, and a finished workflow agent (`WorkflowAgentRunner.FinishWorkflowAgent`). Folders an agent made unwritable (Go's module cache) are made writable first.
- **Swept.** `ReconcileSessions` ends with `SandboxScratch.Sweep`: every folder of either root whose execution this database knows and is not `running` is removed. A running execution's folder, and one this database does not know (another Legato's: the runtime folder is shared by every Legato of the user), are left alone. An execution whose agent session is still `running` counts as running whatever its own status (`StoreExecutionStatus`). A spawn records its execution, makes its scratch, starts its pane and only then links its session; `store.ReconcileLostExecutions` (just before the sweep) leaves an unlinked running execution alone for 10 minutes (`unlinkedExecutionGrace`), and checks its whole condition in the statements that write, so a session linked meanwhile is never marked lost. Folders are listed before statuses are read. `SandboxScratch` is passed to every agent service (`AgentServiceOptions.SandboxScratch`), so the sweep also runs while the sandbox is off.
- **Host paths.** A forwarded command's `/tmp/...` argument is mapped to `<scratch>/<execution>/tmp` (`cliRunOp`).
- **No size limit.** Nothing caps or warns about how much one execution writes; a runaway agent can fill the disk the scratch folder is on.

## What sandboxes share

Each sandbox has its own namespaces, `/tmp`, ssh copies and mounts; nothing is kept from one to the next. What two sandboxes see in common is what both are given from the host: the person's toolchains and caches, the system, and each tool's own state. All Claude Code agents share `~/.claude` read-write (their login, and every project's transcripts), as all Codex agents share `~/.codex`. The sandbox keeps secrets from agents; it does not keep agents of one tool from each other's state.

## Commands an agent runs

In the sandbox, `legato task|plan|review|swarm|learn …`, `credential request|get|list`, `agent peers|message|broadcast`, `workflow step|show` and a few read-only listings are forwarded through the broker (`cli.run`, `cmd/legato/cli_forward.go`): the host runs its own binary with the caller's task and execution from the token (never from the agent), the agent's working directory, its stdin when the command reads `-`, and paths under the sandbox's `/tmp` mapped to the session's host folder. `credential exec` fetches the value that way and runs its command inside. Host-only commands (`device`, `secret`, `audit`, `hooks`, `auth`, `serve`, …) are not forwarded, and `openStore` refuses in the sandbox.

## Job clones

A job clone (`<data_dir>/jobs/<execution>/<name>`, see [Workflows](../../site/src/content/docs/using/workflows.md) § The agent job workflow) is in Legato's data folder, which the sandbox never sees. An agent may still work in one when its task works in that clone (`job_clone_tasks`: the task it was made for, or one that joined it for the next branch of a stack; `SandboxPlanInput.JobDir`): it is mounted as the working directory, and nothing else of the data folder is. That holds when the agent is started again in it (a reload, a resume), however its path is spelled: `taskJobClone` finds the clone with the data folder and the working directory resolved (a resume's working directory, read back from the pane, is `/var/home/...` on a host whose `/home` is a link, while the clone's record says `/home/...`), and the sweep's `inUse` compares a running execution's working directory with a clone the same way. A task that never joined it is refused it. Joining is the spawn's (`clone_id`), which checks nothing in the clone runs: Legato reads and writes the clone's `.git` files itself through `os.Root` (`gitrepo.Head`, `StartBranch`) and never runs git in it. The clone's objects come from the repository cache, mounted read-only at its host path so the clone's `objects/info/alternates` resolves inside. A clone the spawn has just made is set up in the sandbox too, before the agent tool starts (`legato clone setup` behind the same prefix), and the files it links to in the repository's `primary_dir` are mounted read-only; see [Configuration](config.md) § Setting up a fresh clone.

## Leaving it

- **One agent outside.** The spawn dialogs offer **Run without sandbox** (web, unticked each time) and `ctrl+u` (TUI); the API takes `sandbox: false` on `POST /api/agents/spawn` and `POST /api/tasks/{id}/agent`. Such an agent is marked `unsandboxed` (`/api/agents`), and the TUI's agents view marks it: an icon beside its ID in the list, the word over its terminal and on its tile. Swarm and workflow agents, and the Reeve, are always sandboxed: a `reeve` task's spawn is refused with `Unsandboxed` or with the sandbox off, and its sandbox switch is refused too (see [The Reeve](reeve.md)). The Reeve's engram store, `<Reeve folder>/engram`, is inside its read-write folder and is mounted read-write again as its engram store, with the engram binary read-only first on `PATH`, as for any engram session. **Reload agent** keeps the choice. `U` in the TUI's agents view reloads a running agent on the other side of the sandbox, resuming its conversation: out when it ran in it, back in when it ran outside. The web UI's **Reload without sandbox** / **Reload in sandbox** (More actions and the sidebar's right-click menu) does the same through `POST /api/agents/{id}/restart` with `switch_sandbox`. The agent is told by a `[legato sandbox]` message that the sandbox was added or removed (`restartNote` in `internal/service/agent_restart.go`).
- **Folders added later.** A sandbox's mounts are fixed when it starts. Adding a resource to a running sandboxed agent is refused (`409`) unless the request asks to reload (`{names, reload: true}`): the agent is then restarted with its resources and the new ones, resuming its conversation. The web Resources button explains this and asks first.

## Known limits

- A global hook of the person's agent tool that runs something outside the mounts (a Flatpak's data folder, as GitKraken's `gk` hooks for Claude Code are) fails inside, on every tool call; the tool reports it as a hook error. Mount the folder with `agents.sandbox.mounts`, or remove the hook.
- An SSH socket or a socket file reopened by a new channel host while an agent runs is not seen by that agent until it is reloaded.
- Not built yet: repository tools and pushes from the sandbox through the proxy (phase 4). Running Legato on a server of its own, with or without the sandbox: [Agents on a server of their own](../../site/src/content/docs/running/agent-server.md). Progress is kept in `openspec/changes/sandboxed-cloud-agents/tasks.md` § Status.

## macOS

Seatbelt (`internal/engine/sandbox/seatbelt.go`) renders the same plan as a deny-by-default profile. The profile, in order: processes (fork; exec, signal, `process-info` and task ports only within the sandbox), the system facts programs read (`sysctl-read` by name, Codex's list plus what zsh, git and Go need on macOS 15 and 26), devices and the terminal (the pane's tty, named by the launcher's `TTY` parameter, `/dev/tty`, ptys the sandbox opens), every path's metadata, a short list of Mach services (opendirectoryd, logging, notifications, trustd, configd, cfprefsd, FSEvents, …), the network as on Linux (TCP and UDP unfiltered, `mDNSResponder`'s socket for DNS), the agent's own home, the plan's mounts in its order (a read-only mount denies writes after its allow; a cover denies everything after the mounts that hold it), the plan's Unix sockets, `file-write-unlink` denied on every folder inside writable work that holds a read-only or hidden path (renaming one would put what it holds at a path no rule names), and last the fixed denials: securityd (the Keychain), the pasteboard, LaunchServices and Apple Events, launchd jobs, `kern.procargs*`, `system-fcntl` 80 and 110, setuid writes, `osascript`, `open`, `launchctl`, `security`, `pbcopy`, `pbpaste`, `screencapture`, `crontab`, `at`, `sudo`, `su`, `login`, and `TIOCSTI`. Every denial is tagged `legato:<execution>`.

What differs from bwrap, and how the plan answers it (`Capabilities` empty):

| bwrap | Seatbelt |
| --- | --- |
| An empty home | `HOME` is `<scratch>/<execution>/home`, with links to the plan's home mounts (`homeLinks`); programs that find the home by `getpwuid` (`ssh`) are refused the person's |
| `/tmp` is the execution's | `TMPDIR` is the scratch `tmp`; `/private/tmp` is forbidden (`DarwinLayout`) |
| A hidden path is absent | It is denied: name and size visible through `stat` on paths no cover holds, content never |
| `gh` and `az` wrappers over every real one | Wrappers first on `PATH` (the session's and its shells' startup files; `az` linked into the execution's `bin`); the wrapper is routing, not secrecy: `~/.config/gh` and the Keychain are closed |
| ssh copies over `/etc/ssh` | No user namespace, so no ownership problem; `GIT_SSH_COMMAND="ssh -F <copy>"` names Legato's `known_hosts` for git |
| A reviewer's overlay | An APFS clone in the scratch folder (see A throwaway checkout) |
| A PID namespace, `--die-with-parent` | No signals, task ports or arguments of outside processes; `EndSandboxProcesses` ends what still names the execution when it ends (`ps -E` on the host) |
| An IPC namespace | POSIX semaphores and shared memory are shared by name |
| A new `/dev` | The pane's tty and the sandbox's own ptys; `TIOCSTI` denied |

Agent tools: Claude Code and Codex cannot start their own sandbox inside one (`sandbox_apply: Operation not permitted`), so the launch environment names the backend (`LEGATO_SANDBOX_BACKEND`) and inside Seatbelt Claude Code starts with `--settings '{"sandbox":{"enabled":false}}'` and Codex with `sandbox_mode="danger-full-access"`. Claude Code's login is in the Keychain: `agents.sandbox.claude_code_token` (a `claude setup-token` token) is given as `CLAUDE_CODE_OAUTH_TOKEN` inside the sandbox (`sandboxToolLogin`), and without it or another login it can reach, the spawn is refused; so is Codex's when its login is in the Keychain. Chimera's state folders include `~/Library/Application Support/chimera`.

Residual risks against bwrap: every allowed Mach service is a channel to an unsandboxed daemon, and a bug in one is an escape; process names and PIDs are visible; a process that detaches and clears its environment survives its execution (still sandboxed, its broker token refused); hidden paths' names are visible; `ps` cannot run (setuid); `sandbox-exec` is deprecated by Apple, and if it goes `Seatbelt.Available` fails and no sandboxed agent starts. Unchanged from Linux: the network is open, tool state is read-write, caches can be poisoned, forwarded commands read the host paths an agent names.

Tested: `cmd/validate/seatbelt-probe` measured what the profile relies on (LEG-168, notes on LEG-160). The `sandbox-macos` workflow runs on macos-15 and macos-26 for every pull request and any push that changes the sandbox: the Seatbelt package, the plan tests with the Mac layout, and the walls (`sandbox_walls_test.go`, which runs on bwrap too, and `sandbox_walls_darwin_test.go`). Not on the runners: real agent tools, Docker (no daemon), and a person's Keychain; those are the MacBook checklist:

1. Use a scratch instance (see [Claude Code native integration](claude-code-native.md) § Trying it without touching real state) with `agents.sandbox.enabled: true` and `agents.sandbox.claude_code_token` set.
2. Start sandboxed Claude Code, Codex and Chimera agents on a worktree. Each is logged in.
3. In each, these fail: `cat ~/.ssh/id_*`, `cat` the scratch config, `ls ~/Library/Keychains`, `security find-generic-password -s gh:github.com -w`, `printf 'protocol=https\nhost=github.com\n\n' | git credential-osxkeychain get`, `pbpaste`, `open -a Calculator`, `osascript -e 'tell app "Terminal" to do script "id"'`, `tmux -S /private/tmp/tmux-$(id -u)/default ls`, `ls /tmp/legato-$(id -u)`, `kill -0 <Legato's PID>`.
4. In each, these work: edit a file, `go test ./...`, `pnpm install`, `git commit -S`, `git push` through the proxy, `gh pr view`, `ssh -T git@github.com`, `legato task note`, the MCP tools, the native panel.
5. Start the Reeve and message it from another instance.
6. With `agents.sandbox.docker.enabled`, `docker run --rm -v "$PWD:/w" alpine ls /w` works and `docker run -v ~/.ssh:/x alpine true` is refused.
7. A reviewer agent builds in its copy; the author's checkout is unchanged.
8. Leave an unattended agent overnight; in the morning read `log show --last 12h --predicate 'eventMessage CONTAINS "legato:"'` and report denials that stopped normal work; no process of an ended agent is left.

## A throwaway checkout

A reviewer builds and runs tests in the author's checkout without changing it. `AgentSpawnOptions.ThrowawayCheckout`, with `ReadOnlyCheckout`, mounts the working directory and its git folder as `sandbox.Overlay`: bwrap's `--overlay-src <path> --overlay <upper> <work> <path>`, a read-only lower layer under an upper one in the execution's scratch folder on disk (see Scratch). What the agent writes there (build output, test files, an edit) is seen inside and removed with the scratch when the execution ends; the host checkout is never written. Forbidden paths inside the checkout stay hidden, as in any mount (`binds`). The execution is still read-only, so the credential broker's refusals (pushes, pull request and issue writes) are unchanged.

On macOS Seatbelt has no overlays: `SandboxSettings.CopyCheckout` (`sandbox.CloneTree`, `clonefile(2)`) copies the checkout copy-on-write into `<scratch>/<execution>/checkout/<name>` (`copyCheckout`), the agent works there (`SandboxPlanInput.CheckoutCopyOf`: the copy read-write, the author's checkout and a git folder outside the copy, a worktree's main `.git`, read-only), and the copy goes with the scratch. A copy that cannot be made (another volume, not APFS) leaves the plain read-only checkout. `CheckoutOverlayAvailable` says yes for either. `TestWallsOnAMacAThrowawayCheckoutIsACopyThatGoesWithTheExecution` runs it on macOS CI.

Overlays need bubblewrap 0.10.0 or later. `sandbox.Bwrap.SupportsOverlay` reads `bwrap --help` for `--tmp-overlay`; the agent service asks it through `CheckoutOverlayProber.CheckoutOverlayAvailable`, and without it mounts a throwaway checkout plain read-only. A caller asks first, so a reviewer's brief can say that builds and tests that write to the tree will fail. `TestWritesIntoAThrowawayCheckoutNeverReachTheHost` runs the real bwrap: the overlay where it has one, the read-only fallback where it does not.

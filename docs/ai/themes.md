# Client themes

## Source and scope

[`DESIGN.md`](../../DESIGN.md) records the approved visual intent and component guidance (The Control Room). Its frontmatter binds existing roles; it does not supersede the canonical palette/derivation contract below. `.impeccable/design.json` supplies documentation previews, not runtime components.

`themes/palettes.json` is the canonical semantic/syntax source for `dracula`, `ocular-light`, `ocular-dark`, `ocular-light-vivid`, `ocular-dark-vivid`; `legato` preserves each client's existing default. `themes/README.md` records the research source hash/date, naming, rendering contract and Dracula attribution/license. Runtime never reads the research resource. Ocular is not a proven fatigue intervention.

The two **Vivid** choices are additive accent variants, not replacements for the unchanged research candidates. They keep the original neutral bases and material recipes. Dark Vivid strengthens accent chroma/brightness; Light Vivid deepens the accents. Their shared state washes and readable UI inks derive normally. Their per-entry provenance is distinct from the original research source hash. No screen-specific styles or live/default preferences change.

Web and desktop import the source through `themes/render.ts`; Android packages the same JSON as a build asset. Canonical research values remain unchanged. A terminal-safe view falls back to foreground for faint secondary/comment text and to focus for an insufficient control boundary. Separately, `materials` derives recessed rail, panel, raised, divider and status-wash roles from shared sRGB recipes; the reading canvas stays exact. `material_ink_contract` blends original UI ink toward foreground in 5% steps until it passes 4.5:1 across canvas, selection and all material surfaces (except divider). This preserves a readable secondary hierarchy in Dracula instead of flattening metadata to white. Web/desktop use offset contact/ambient shadow tokens, native Android uses Material3 surface levels/elevation. Decorative separators are distinct from required 3:1 control borders. The sandbox/download theme variables and Mermaid fills/ink consume these same material roles, including shared shadow tokens. No page owns an alternate palette; Legato defaults, terminal ANSI, IDs and saved choices are unchanged.

### Application identity roles

Each named palette has a required `ui` record containing role references `accent`, `identity`, `voice_start` and named `surfaces` blend recipes. `themeMaterial()` combines those recipes with the polarity materials before the UI-ink contract, then exposes `accent`, `identity`, `voiceStart` and `notice` (the notice-tint ink) separately from canonical/readable `tokens`. All four Ocular themes choose keyword purple for actions, identity and voice-start, with success green and blue links unchanged. `identitySurface` is the purple message/identity wash; `noticeSurface` is the teal informational-message wash. Dracula's explicit mappings reproduce its previous values, not Ocular's design.

Web/desktop expose the UI accent as `--theme-accent` and `--theme-focus`, identity as `--theme-identity`, and voice-start as `--theme-voice-start`; web also exposes notice ink as `--theme-notice`. Canonical `tokens.focus` stays unchanged for independent terminal use. `--color-lw-accent-soft` uses the identity wash, not text selection. The generated legacy-utility adapter maps purple-family washes to identity and teal-family ink/washes to notice; other state families remain distinct. No new screen-specific selector/palette is needed for agent-message interiors.

The shared voice ring uses the identity material inside the seal and interpolates speaking ticks from voice-start to success; its mode labels, animation geometry, timings and reduced-motion preference are preserved. Desktop signing identity uses the shared identity ink with the old link fallback; actual links stay links. Android reads the same metadata and derives materials/inks before mapping native primary/identity roles. Focus uses the shared UI accent without changing the compound composer's rounded inset indicator. These changes do not rewrite source-token colours, neutral planes, Dracula/default output, terminal ANSI or saved terminal overrides.

`web/src/lib/appTheme.ts` owns browser identity/state/change: `appTheme()`, `setAppTheme(id)`, `applyAppTheme()`, `subscribeTheme()`. `legato:app-theme` persists the explicit local app ID; `legato:theme-mode` stores `local` or `server`, separately from `legato:effective-app-theme`. Missing/unknown IDs fall back to `legato` without rewriting unrelated preferences. The public DOM signal is `legato:theme-changed`. Application starts apply the preference before React mounts; local changes apply immediately, and storage events synchronize other tabs. A rejected storage/native save reaches the picker as an alert.

## Server preference and client ownership

App appearance remains client-owned. **Follow server** opts a browser/PWA or native app into the active server's preferred theme; choosing a named theme exits this mode. Existing installs are not opted in. The saved local choice remains the fallback for no preference, an older server, an unsupported ID or no active server. A failed connection keeps only that connection's cached preference; switching to an offline server uses its own cache or the local fallback, never another server's theme. Authoritative no-preference metadata stops using the old preference. Explicit terminal overrides and `web.tint` are independent. The existing `theme` config entry is not this preference.

`service.ThemePreferenceService` validates the six stable IDs (or empty for no preference), commits a compare-and-set through the store, then publishes `EventServerThemeChanged`. Migration 113 keeps one current row, not a history ledger. Authenticated `GET /api/settings/theme` returns `{id, revision}`; `PUT` takes `{id, expected_revision}` and returns the saved snapshot (409 on conflict, 400 on invalid ID, read/save failures surfaced). Public `GET /api/meta` includes nonsecret `theme_preference: {id, revision}`; `id: ""` means no preference. A read failure is not a cleared preference. WebSocket `server_theme_changed` and reconnect trigger metadata refresh; cross-process IPC carries content-free invalidations. Metadata describes the server, not any client's current appearance.

## Surfaces

- **Web/PWA:** Settings › Appearance › App theme. `main.tsx` applies semantic CSS variables; `theme.css` covers selection, caret, focus, controls and scrollbars. Existing Tailwind neutral scales are mapped by role. `scripts/theme-utilities.mjs` maps legacy chromatic ink/washes/boundaries to the same roles; after adding or removing a palette class (such as `text-red-600`) anywhere in `web/src`, run `node scripts/theme-utilities.mjs` and commit `web/src/theme-utilities.css`: `pnpm run build` starts with `--check`, so a stale file fails CI's `web` job and the release (LEG-494). It reads `web/src` in name order and sorts the classes it finds, so its output depends only on the sources, never on the filesystem. Hardcoded application colours use semantic variables with original-value fallbacks so Legato's palette is preserved. User/server tint colours, media, QR codes and externally authored pages are not globally recoloured.
- **Terminals:** Settings › Terminal theme retains Legato, Night, Solarized Dark and Classic, adds all five named palettes and Follow app. `legato:terminal-theme` is unchanged. Existing saved overrides are preserved; missing/unknown/`app` follows the app. Both `LiveTerminal` and `TerminalPanel` update xterm's `options.theme` in place, not by rebuilding the terminal, reconnecting, resetting scrollback or resending input. ANSI normal/bright, cursor and active/inactive selection come from the canonical roles. Original Ocular keeps ANSI ink unchanged when selected; Vivid also preserves it when all selected ANSI pairs pass (otherwise it uses foreground selection ink); Dracula uses foreground selection ink because some original hues fail contrast on its selection colour. Explicit truecolour/RGB, OSC palette overrides and backgrounds emitted by remote applications can override xterm's palette; Legato does not rewrite terminal bytes or reconfigure those tools.
- **Native conversation, diffs, cards and artifacts:** role-based foreground/surface colours, unchanged added/removed markers, selected ranges and labelled statuses. Sandboxed HTML has an isolated theme document, rebuilt when the app theme changes; downloads capture the selected theme. Mermaid and Wiremark use the same polarity/roles and redraw on change. An author's explicit colours can still override supplied artifact variables; a separately authored review briefing owns its own theme.
- **Desktop:** native persisted `app_theme`, shell picker, key-bound page requests, save-before-delivery, all retained/new server views and reload paths. See [Desktop](desktop.md). Remote pages gain no Tauri command capability. System-native dialogs, certificate trust prompts and OS controls remain platform-owned.
- **Android:** native persisted choice, Compose role mappings and system bars, native picker and WebView delivery. See `mobile/README.md`. The WebView's origin-restricted bridge and top-frame key remain required. The on-screen keyboard, camera and system fingerprint/file-picker dialogs remain OS-owned.
- **Terminal TUI / other tools:** no change to the standalone Bubble Tea palette, external editors, tmux applications or the Even G2 display. These are not native desktop/mobile wrapper surfaces.

## Native page contract

A capable app advertises `window.legatoShell.theme = 2`. The web picker posts `{legatoShell:"theme", type:"theme", key, id}` through `ReactNativeWebView.postMessage`; `id` is one of the six app IDs or `server` for Follow server. It waits for `legato:shell-theme` with `{id, error?}` and shows refusal/timeout. Native saves mode/local choice before delivery, resolves metadata through its own server connection, and seeds retained/new/reloaded top-frame pages with `legato:theme-mode`, local `legato:app-theme`, effective `legato:effective-app-theme`, then `legato:theme-changed`. Existing origin/top-frame/key guards remain required; no remote Tauri permission is added. A `theme: 1` shell keeps named choices only: the page must not offer web-only Follow server inside it. Terminal preferences remain independent.

## MQTT / Home Assistant

`integrations.mqtt.theme_control` is an independent, default-off, risky restart setting. Cameron approved **broker-grant** authority: enabling it grants server-theme mutation to every publisher allowed by the broker on the exact `<base>/theme/set` topic. There is no sender identity or application token. Aggregate-only configurations keep their existing ACLs and subscriptions. Automatic discovery supplies a nonoptimistic select; no manual token-bearing select is needed. See [Integrations](integrations.md#home-assistant-mqtt) for the command, replay and ACL contract.

## Verification

The regression entry points are the Settings page picker, mounted terminal picker, native shell picker/storage/delivery, artifact builders and actual rendered components. `scripts/verify-themes.mjs` drives an isolated Chromium against an explicitly supplied scratch instance, takes desktop/390px/320px captures, checks picker/reload behaviour and can verify real component contrast via `web/src/test/theme-preview.html`. The fixture imports production components; it creates no review tour, agent or command authority. See the final verification record in `themes/VERIFICATION.md` for exact results and native execution limits. Research prototype tests are not counted as application tests.

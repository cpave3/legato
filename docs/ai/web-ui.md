## Web UI

Remote web interface for monitoring and interacting with agent sessions from any device (mobile, tablet, second screen). Built with React 19 + Vite + xterm.js + TailwindCSS. Compiled to `internal/server/static/dist/` and embedded in the Go binary via `embed.FS`. Installable as a PWA with offline support.

**Workflows**: `/workflows` lists legacy-global (`~/.legato/workflows`), XDG-global, and project definitions plus run history, generates typed input forms, offers editable repository/path presets from `workflows.repositories` config, and launches runs. Definitions and runs are separate lazy tabs: only the visible tab requests its snapshot. Board cards expose a viewport-clamped context menu on right-click and through an accessible action button; it reuses Open/Move/Delete behavior and opens eligible workflows in a separately scrollable, edge-flipping flyout, binding the selected card read-only in the shared run dialog. `/workflows/runs/:runId` shows responsive ordered step progress, executor-specific PR/agent details, attempts, errors, typed outputs, Markdown/file artifacts, retry/cancel controls, and live-agent links. Targeted `workflow_changed` WebSocket messages refresh run lists and the matching detail; run/agent events never rediscover definition files. Mobile views stack step cards, contain wide JSON/code, use touch-sized controls, and preserve a backlink when opening an agent terminal.

**Learning**: `/learning` lists and filters the local learning ledger and performs FTS claim/rationale search. `/learning/:learningId` shows status/scope/revision, linked evidence provenance, incorporation history, and revision-aware edit/accept/reject controls. Incorporation creation/submission/verification and prompt-manifest browsing currently remain CLI/API surfaces. Learning candidates, verification work, and stale records remain in Learning and do not increment Attention. See [Legato Learn](learning.md).

**Reports**: `/reports` is a responsive operational dashboard backed by the existing `service.ReportService`. It defaults to the current week and supports server-local Day/Week/Month navigation, neutral immediately-prior-period comparisons, exact range boundaries, accessible active/waiting activity bars, and sortable Tasks/Workspaces/Projects/Swarms/Executions breakdowns. Reports show the activity epoch, suppress duration comparisons that predate it, and distinguish additive agent active time from elapsed execution/swarm wall-clock time. Initial loads use a page skeleton; navigation retains the prior report while busy; failed requests are retryable; completely empty periods use a dedicated no-activity state. The desktop sidebar links directly to Reports, while mobile exposes it in the More sheet. Copy Markdown requests the same server-side exporter used by the TUI.

**Report API**: Authenticated `GET /api/report?period=<day|week|month>&offset=<0..-120>&format=<json|markdown>` selects ranges through `internal/engine/analytics`; browser timestamps are not accepted. JSON returns the selected complete report plus the immediately previous period summary. Its explicit snake_case DTO uses numeric `*_seconds` durations, named period kinds, RFC3339 boundaries, nullable workspace IDs, non-null arrays, `activity_epoch`/availability flags, and execution kind/status/task/workflow/wall-clock fields. `working_seconds` is retained as the wire name but means additive agent active seconds. `format=markdown` returns `text/markdown; charset=utf-8`, generates only the selected report, and delegates formatting to `service.ExportReportMarkdown`. Both standalone `legato serve` and TUI auto-start web servers wire the report service.

**Task activity**: Board task detail uses `GET /api/tasks/{id}/activity` to show tabs for notes, review tours, plans, and related workflow runs with downloadable managed artifacts. Reviews, plans, and runs link into their existing detail pages. **Open agent** calls `POST /api/tasks/{id}/agent`: live task agents are selected without spawning, while absent agents are launched against the existing task with the chosen adapter and working directory. Task detail exposes `has_chimera_session` without exposing the provider session ID. When Chimera is the selected or configured default adapter and durable history exists, the task dialog offers **Resume previous session** (default) or **Start new session** and sends `chimera_session_policy: "resume" | "new"`. The stored hook ID is only evidence that history exists; every task-bound Chimera launch uses the Legato task ID as the canonical create/resume selector. A stale explicit choice returns `409 Conflict` and remains visible in the dialog. Callers that omit the policy retain backward-compatible behavior: persisted Chimera sessions auto-resume, while first-time launches start normally. Chimera policies on non-Chimera launches and unsupported values return `400 Bad Request`. Ephemeral-agent launch does not show this task-session choice.

**Starting**: `legato serve [--port 3080]` for standalone, or `web.enabled: true` in config to auto-start alongside TUI. Auto-start probes the port first — skips if another instance already has it. `Server.Serve(ln)` accepts pre-bound listener to avoid close-rebind race. Server shuts down when TUI exits via a bounded `webSrv.Stop()` context.

**Development hot reload**: `task run:hot` launches the stable `./legato --hot-reload` binary for the TUI and its optional in-process web server; `task server:hot` launches `./legato --hot-reload serve` and honors `LEGATO_SERVER_PORT`. The Unix foreground supervisor watches the resolved executable rather than source or `dist`, inherits args/env/CWD/stdio/terminal, and uses a private child marker to prevent recursion. A stable replacement triggers SIGTERM, complete old-child shutdown, then one new child; children never overlap. Missing/partial replacements leave the current child running. Once a stable build starts shutdown, the TUI gets a bounded graceful quit followed by Bubble Tea's terminal-restoring hard stop; the supervisor then force-stops and reaps any process that exceeds its wider deadline before starting the replacement. An immediately failing replacement leaves the supervisor waiting for a later build. `task build` reloads Go against the already embedded bundle; `task build:full` first emits and embeds a fresh web build identity. Hot mode resets transient TUI state and allows a brief web disconnect; it is not a daemon or zero-downtime deployment mechanism. A hot-reload child running from a checkout exposes `hot_reload_enabled` in authenticated `/api/settings` and accepts authenticated `POST /api/hot-reload/build`; Settings uses that capability to show a mobile-friendly **Rebuild and hot reload** action. The endpoint starts `task build:full` asynchronously from the executable's checkout directory, rejects concurrent builds, and redirects output to `.legato/run/hot-reload-build.log` so it cannot corrupt the TUI. Normal/non-checkout processes do not install the trigger and return no capability. `server:restart` remains a separate detached standalone-server helper.

**TLS**: Disabled by default for simple local-network development. Set `web.tls.enabled: true` for auto-generated HTTPS, or set both `web.tls.cert` and `web.tls.key` to enable HTTPS with explicit files. `Server.SetTLS(certFile, keyFile)` configures TLS before `Start()`/`Serve()`. `Serve()` calls `http.Server.ServeTLS` when TLS is set, plain `Serve` otherwise. HTTP/2 is disabled via an empty `TLSNextProto` map because WebSocket upgrades require HTTP/1.1. The web client auto-detects `ws:` versus `wss:`. Auto-generated certificates live at `~/.local/share/legato/certs/`; the server certificate is regenerated when it expires or no longer includes the configured hostname or current local IP addresses, while retaining the CA.

**Authentication**: Bearer token auth on all API/WebSocket requests. Token auto-generated on first server start at `<dataDir>/auth-token` (32 bytes, hex-encoded). `Server.SetAuthToken(token)` configures auth middleware. REST uses `Authorization: Bearer <token>` header, WebSocket uses `?token=` query param. Exempt: `GET /health` (monitoring), `OPTIONS` (CORS preflight), static assets (SPA shell). Web UI checks auth on load — shows `TokenPrompt` modal on 401. Token stored per-server in localStorage (`legato:token:<url>`). Stored token invalidation triggers page reload to re-prompt. `web/src/lib/auth.ts` provides `getToken`/`setToken`/`clearToken`/`authHeaders` helpers.

**CORS**: `Access-Control-Allow-Origin: *` on all responses via `corsMiddleware` in `server.go`. Enables cross-origin access from PWA served by another legato instance. `Access-Control-Allow-Headers` includes `Authorization` for token auth.

**QR pairing**: `legato pair` CLI renders terminal QR code encoding `legato://pair?url=<serverUrl>&token=<token>`. PWA Settings page has "Scan QR Code" button using `html5-qrcode` library — opens device camera, decodes QR, stores server URL + token in one step. Falls back to manual token paste on camera denial. `QRScanner` component in `web/src/components/QRScanner.tsx`.

**PWA**: Installable progressive web app via `vite-plugin-pwa` (Workbox). Service worker auto-updates (`registerType: 'autoUpdate'`), `skipWaiting: true` + `clientsClaim: true` for immediate activation on update. Each production Vite build generates one UUID, compiles it into the browser, and emits `dist/build-id` for Go embedding. Public no-cache `GET /frontend-meta` returns the serving binary's embedded ID independently of Go's local `dev` version. Initial WebSocket connection and every reconnect compare the IDs: a mismatch updates registered workers, waits briefly for controller change, and reloads once. Session storage bounds automatic attempts; a repeated mismatch displays a manual **Reload update** action rather than looping. Same-build network reconnects never reload. Precaches app shell (HTML/CSS/JS/icons), runtime caches API routes with NetworkFirst strategy. Manifest at `/manifest.webmanifest` (auto-injected by plugin). Icons: `web/public/pwa-192x192.png` and `pwa-512x512.png` (pre-generated from `favicon.svg`). PWA requires HTTPS on non-localhost — hence TLS auto-generation.

**Offline dialog**: `OfflineDialog` (`web/src/components/OfflineDialog.tsx`) is mounted inside the authenticated `Layout` and appears when the WebSocket remains disconnected for two seconds, avoiding a flash on slow initial connections. It keeps the current page rendered behind a centered modal, offers Retry, server switching, Settings/QR actions, and a TLS hint for remote servers. Users can dismiss it with the close control or Escape to inspect cached UI; desktop and mobile navigation retain a red disconnected indicator, and the dialog auto-closes on reconnect and reappears after a later disconnect.

**Cache headers**: `spaHandler` in `internal/server/spa.go` sets `Cache-Control` headers — `public, max-age=31536000, immutable` for Vite hashed `assets/*`, `no-cache` for `sw.js`/`workbox-*.js`/`index.html` and SPA fallback responses.

**Terminal streaming**: `pipe-pane` fans output to all subscribed web clients via WebSocket. Pipe start is deferred until the first `resize` message so the tmux pane is correctly sized before output flows. `PipeOutput` clears any stale pipe-pane from a previous process before starting a new one. On subscribe, the server waits 150ms for SIGWINCH redraw, then sends a `CaptureWithEscapes` snapshot as backfill (`\n` → `\r\n` for xterm.js). After the live pipe starts, the server bounces the pane width by 1 column (shrink then restore) to force a full SIGWINCH redraw through the pipe, preventing the backfill snapshot and live stream from diverging. Output chunks sent synchronously (not `go c.send`) to preserve ordering. Escape sequence buffering (`findIncompleteEscape`) holds back incomplete CSI/OSC sequences at chunk boundaries to prevent xterm.js state corruption. Read buffer is 32KB. `refresh_pane` queries tmux cursor position via `display-message` and appends ANSI CUP to restore cursor after snapshot.

**Native Chimera synchronization**: A terminal-backed task Chimera agent exposes **Upgrade to native Chimera** in `PromptBar`. `POST /api/agents/{task_id}/chimera/discover` scans current lockfiles without restarting any process, requires an exact task-ID match at an HTTP loopback endpoint, verifies both instance liveness and the expected session, and persists only one uniquely valid candidate; missing or stale candidates remain terminal-backed with an actionable error, while ambiguity returns `409 Conflict`. Successful discovery broadcasts `agents_changed`, and the initiating page also refetches `/api/agents`, switching to `NativeAgentPanel` when `has_chimera_endpoint` becomes true. If the panel's initial snapshot cannot resolve that persisted endpoint/session, the server conditionally clears the exact still-matching binding and replay cursor, broadcasts `agents_changed`, and the same page remounts the tmux terminal/composer without a reload; later manual and background snapshot failures retain an already-loaded native conversation. The native overflow menu also exposes **Downgrade to tmux**, which performs the same durable clear without stopping the agent, and a matching live lockfile can be manually upgraded again. `NativeAgentPanel` hydrates from the Chimera session snapshot and reduces live envelopes through `web/src/lib/nativeAgentSync.ts`, which owns ordered item insertion, stable assistant/tool identities, bounded event-ID deduplication, and per-assistant streaming buffers. `subscribe_agent` carries the browser's last accepted `cursor`; the server retains a 1,000-event per-agent replay ring and upstream SSE connection for a 30-second disconnect grace period. Known cursors replay missed envelopes before live delivery. Unknown, expired, or cursorless reused streams emit `chimera_sync_required`, causing race-safe snapshot reconciliation. Events arriving during a snapshot fetch are queued and reduced afterward, failed refreshes retain the existing conversation, and completed runs trigger a debounced authoritative repair. Background repair keeps the feed mounted with a lightweight syncing indicator and preserves scroll position. The native panel overflow menu also provides **Refresh from snapshot** for manual recovery. Picking the agent that is already open, in the sidebar or the mobile picker, runs the same refresh (`useAgentReselected` in `web/src/hooks/useAgentSelection.tsx`), and the mobile app re-picks the open agent each time it returns to the foreground (see `mobile/README.md` § Returning from the background). `spawn_agent` calls use a dedicated expanded card that groups each child by Chimera's `parentCallId`, shows its requested agent/model/prompt, and streams forwarded child assistant, reasoning, and tool activity without mixing parallel children. Cursorless browsers loading during an active shared stream receive snapshot repair followed by retained events, so active child cards and captured activity are restored. Live child activity is retained through parent snapshot repair, but not across a full page reload after the shared stream's replay window has expired because Chimera does not persist forwarded `subagent_event` envelopes in the parent snapshot; completed cards then state that no live activity was captured.

**Native Claude Code sessions**: A Claude Code agent appears in the same `NativeAgentPanel` once its session's bridge is bound (`has_chimera_endpoint` true), with no Chimera involved: the bridge speaks the same protocol on the session's behalf. Tool cards, streaming, queued messages, interrupt, permission cards, subagent cards and context usage work as for Chimera; the panel's wording follows `agent_kind` ("Tool approval", "Feedback for Claude Code"). The model selector offers the session's own model plus `adapters.claude-code.models`, the model settings dialog sets effort, and both apply to that session only without touching Claude Code's saved defaults; Chimera modes are absent. A permission card stays answerable while Claude Code's own terminal dialog is open, and expires when the terminal answers first. A permission card offers the agent's own ways to allow when it lists any (**Allow once** beside Claude Code's "don't ask again"), and a plan awaiting approval is drawn as Markdown with a choice of how edits are handled afterwards. A question Claude asks (`AskUserQuestion`) opens a `NativeQuestionCard`: options, several answers where allowed, an answer typed by hand, or Dismiss. These cards are driven by the native protocol's `question_request` and `permission_request` fields, not by the agent kind, so any native agent that emits them gets the same cards. While a request is open the status bar reads **Waiting for you** in place of Idle or Working, and clicking it scrolls to the request. **Downgrade to tmux** works as for Chimera; a terminal-backed Claude Code agent offers **Upgrade to native panel**, which re-binds to the still-running bridge. See [Claude Code native integration](claude-code-native.md).

**Native Codex sessions**: A Codex agent Legato launched appears in the same `NativeAgentPanel` from the moment its pane starts, through the bridge `legato agent codex` runs beside its app server. Commands are `bash` cards; file changes are `patch` cards with a diff per file (added, deleted, changed, moved). A command approval offers Codex's own decisions as options (**Allow once**, **Allow for this session**, **Allow, and don't ask again for commands that start with …**); denying with feedback sends the feedback as the next message. A message sent before Codex's terminal is ready is shown at once and delivered when its conversation opens. The model selector lists what Codex itself reports, and a model or effort chosen there applies from the next turn Legato starts. Wording follows the agent ("Feedback for Codex"); `web/src/lib/agentKind.ts` holds `canBeNative(kind)` (which tools can be offered **Upgrade to native panel**) and `nativeToolName(kind)`. See [Codex native integration](codex-native.md).

**Terminal prompts in the native panel**: Some prompts never reach Legato as a request: an update notice, a trust question for a new directory or its hooks, a picker opened in the terminal. While a native panel is open it sends `detect_prompt` every two seconds, and a `prompt_state` of type `menu` (any numbered menu with a cursor, read from the pane by `internal/engine/prompt`) is drawn by `NativeTerminalPrompt` as **`<Tool>` is asking in its terminal**: the text above the menu, a button per option, **Cancel (Esc)** when the menu offers it, and **Open terminal**. A choice is sent as `send_keys` (`Down`/`Up` to the option, then `Enter`). The card is hidden while the agent has a permission or question request open, since the terminal is then showing that same request, and counts toward **Waiting for you**. It works for every native agent kind. A terminal-backed session shows the same menu in `PromptBar`'s action list.

**Artifacts and cards from agents**: An agent can show something through its Legato tools (`legato mcp serve`; see [Agent tools](agent-mcp.md)). A **card** (`show_card`, `show_components`) is drawn in the native conversation where the call was made, in place of a tool row, and stands alone as a `spawn_agent` call does: a placeholder while the call runs, then the card, with **Open in side panel**. An **artifact** (`show_artifact`) is a line in the conversation that opens the **Artifacts** panel: a resizable column beside the conversation on a wide screen, and a full-screen sheet above the bottom navigation below 1100 px of viewport (1500 px beside the swarm event log). The panel lists what the session showed as tabs, with a revision stepper, Copy source, Download and Remove. A new artifact from the agent in view opens the panel on it; one from another agent is counted on that agent's sidebar entry and opens when the person goes there; where the panel is a sheet it only marks the toolbar's **Artifacts** button, so it cannot land on top of what the person is typing. A terminal-backed session has no conversation feed, so its cards are in the panel too. HTML an agent wrote is drawn only inside `SandboxedHtml`: a `sandbox="allow-scripts"` frame with a content security policy that allows no network beyond loading from `agents.mcp.resource_domains`, and a **Made by the agent** label. A card or an artifact can put text in the person's message box (an `actions` button, or `legato.proposeMessage(text)`); a notice says so and nothing is sent until the person sends it. `agent_ui_changed` invalidates the session's item list and the item. An agent can put image files from disk in what it shows: Legato keeps its own copy of each and serves it from `/agent-ui-images/`, a click on an image opens it over the whole window (`ImageLightbox`), and the `image` and `image_grid` components do it with no HTML; see [Agent tools](agent-mcp.md) § Image files. A link of the form `/agents?task=<id>&artifact=<item-id>` selects the agent and opens the panel on that item, on a phone too, then drops both parameters from the address; the TUI shows such a link for what it cannot draw.

**Images an agent read**: A `read` call on an image file (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.bmp`) is a row the person can open: the image is drawn under it, and a click on the image shows it full size until Escape or another click. The agent saw the image; without this the person sees only its name. Nothing is fetched until the row is opened, and the file is read again each time, since a screenshot is often written again under the same name. The file is on the machine Legato runs on, so the browser asks Legato's server for it: authenticated `GET /api/agents/{task_id}/image?path=<path>` (`internal/server/agent_image.go`; `POST` to the same address stores a pasted image, see the next paragraph).

- Any path may be asked for, because an agent's screenshots are seldom inside its worktree. A relative path is taken from the session's working directory, which the session's native endpoint reports; without one a relative path is `404`.
- What limits the endpoint is what it gives out: only a regular file of at most 25 MiB whose *content* is PNG, JPEG, GIF, WebP or BMP. The name does not count: a text file called `secret.png` is refused (`415`). SVG is refused, because it is a document, and one opened from Legato's own address could run script there.
- The response is `no-store` and `nosniff`, with a sandboxing content security policy. The browser draws it from a blob address, which is released when the row closes.
- It works for every native session (Claude Code, whose `Read` paths are absolute, and Chimera, whose paths may be relative). Codex has no read tool; it reads files with shell commands.

**Pasting an image for an agent**: An image pasted into an agent's message box (the native composer, and the terminal session's `PromptBar`) reaches the agent as a file. An agent tool takes a message as text, and each tool has a different way to attach an image, or none; every agent can read a file. So the browser gives the image to Legato (`POST /api/agents/{task_id}/image`, the image as the body), Legato stores it and answers with the file's path, and the path is put in the message where the cursor is. The person writes around it and sends as usual; the agent reads the path with its own tools, and its `read` row then shows the image (see Images an agent read).

- The file goes to `<system temp dir>/legato-<uid>/pasted-images/<task-id>/pasted-<UTC time>-<random>.<ext>`. The temporary directory is the one place every agent tool lets its agent read: Chimera's `read` takes the working directory or `/tmp` and nothing else. It is not the worktree, where the files would show up as changes.
- Only content that is PNG, JPEG, GIF, WebP or BMP is stored (`415` otherwise), up to 10 MiB each (`413`). The folder is `0700` and the file `0600`. A task keeps its newest 20 pasted images; older ones are removed when a new one is stored, because the temporary directory is often memory.
- A thumbnail above the message box stands for each pasted path still in the message; it goes when the message is sent or the path is deleted. A refusal is shown there in the server's words and leaves the message alone.
- A paste that carries text is left to the message box, also when a picture of that text comes with it (a copy from a spreadsheet).
- Claude Code asks before it reads a file outside its working directory. For the session's own pasted images it does not: the `legato-tools` plugin answers that request itself (see [Claude Code native integration](claude-code-native.md) § Legato's tools in a session). Chimera reads the file without asking. A Claude Code session that started before this hook existed, or runs without the plugin (`agents.mcp.enabled: false`), raises the request once; **allow reading from that folder during this session** covers the rest, since a task's images share one folder.

`usePastedImages` (`web/src/hooks/usePastedImages.ts`) is the paste handling both message boxes share, and `PastedImageStrip` the thumbnails. Checked in a browser with Claude Code, Chimera, and a Chimera session driven through its terminal.

**Thinking in the native panel**: What an agent thought on its way to a reply or a tool call is a **Thinking** row: one quiet line that opens to all of it. While the thought is still arriving the line follows it; afterwards it shows how the thought began (a summary's title, for Codex). A thinking row is a step like a tool call: it joins the group of tool calls around it, so an agent that thinks between calls still gets one compact group, and a fold of earlier calls takes their thoughts with it. An edit that is the only tool call of its group still opens its diff, whatever was thought before it.

- It is part of the native protocol, not of one agent: `reasoning_text_delta {id, delta}` and `reasoning_text_done {id, text}` events, and in a snapshot a `{type: "reasoning", text}` part of an assistant message, ahead of that message's text and tool calls. `web/src/lib/nativeAgentSync.ts` reduces them to items of role `reasoning`; a thought replayed over a snapshot that already has it is not shown twice.
- How much there is to show is each tool's and each model's own matter:
  - **Chimera** streams what its model reasons, and keeps it in the session. Nothing to set up.
  - **Codex** has a summary of the model's reasoning only when Codex is told to make one: `model_reasoning_summary = "detailed"` (or `"concise"`) in `~/.codex/config.toml`, or `adapters.codex.launch_args: ["-c", "model_reasoning_summary=\"detailed\""]`. Without it Codex reports that the model reasoned and nothing of what. See [Codex native integration](codex-native.md) § Reasoning.
  - **Claude Code** models keep their thinking to themselves: the block they return is signed and, for Opus 5.5, Sonnet 5.5 and Haiku 5.5, empty. What does show is the short summary a model writes now and then during long work. See [Claude Code native integration](claude-code-native.md) § Thinking.

**Native composer prefixes**: The native panel mirrors Chimera TUI syntax for idle turns. `@path` grants read access and attaches a bounded file/directory snapshot (line-numbered files up to 2,000 lines / 100 KiB; directories up to 200 entries). `#path` grants write access and attaches the same snapshot. Attachment tokens are parsed and expanded server-side through the Chimera interaction adapter; only idle `SendMessage` triggers expansion, while `QueueMessage` sends plain text. `!command` executes a shell command in the session CWD with a 30-second timeout and 1 MiB output limit via `POST /api/agents/:task_id/chimera/bang`, appends the formatted result to Chimera session context, and resyncs the panel. While busy, `!` commands enter a visible browser-local queue and execute after `run_finished`. Tool calls made back to back, with no reply between them, are drawn as one compact group of one-line rows; a run longer than six shows its latest five under an **N earlier tool calls** row that lists the tools those calls used and expands the rest. A row opens for inspection on click. An edit that stands alone opens its diff by default; other tools, and every call inside a group, start collapsed. A `spawn_agent` call keeps its own subagent card and ends the group before it. The feed scrolls to the latest message on initial hydration and after explicit send/queue actions.

**Resize protocol**: Web clients send `resize` messages (initial + on container resize + 5s heartbeat for TTL). Server computes min of all web client sizes + attached tmux terminal clients (`tmux list-clients -t <session>`). Only resizes if dimensions actually changed (dedup via `appliedCols`/`appliedRows`). Stale clients expire after 10s TTL. On last client disconnect, resets `window-size` to `latest` so tmux auto-sizes from remaining terminal clients.

**Prompt detection**: `prompt.Detect` runs on captured pane output after 500ms debounce following output. Classifies as `tool_approval` (Yes/Always/No buttons), `plan_approval` (Accept/Reject), `free_text` (text input), or `menu` (any other numbered menu with a cursor on one option; one action per option). Only shown when agent activity is `"waiting"` (gated on hook state, avoids false positives during active output). Dismissed prompt type tracked in `dismissedPromptTypeRef` — suppresses re-detection of same prompt until user submits text, switches agents, or manually re-detects. Per-agent prompt detection toggle in overflow menu (overrides global default from `legato:prompt-detection` localStorage). Actions rendered as vertical keyboard-navigable list (`ActionList` component): j/k or arrows to navigate, Enter to confirm, Escape to dismiss. On-demand detection via `detect_prompt` WebSocket message (Re-detect prompt in overflow menu).

**Key sending**: `send_keys` WebSocket message. Text ending in `\n` → literal text via `tmux send-keys --` then named `Enter`. No `\n` → space-separated named keys sent in sequence (e.g. `"Down Enter"` → two `SendKey` calls). Used by prompt action buttons, Mode (BTab), Stop (Escape), and free text input.

**Shared snapshots and navigation API**: TanStack Query owns authoritative HTTP snapshots under keys prefixed by the selected server URL. Concurrent and later consumers share settings, board, queue, attention, and workflow snapshots rather than issuing per-hook requests. `GET /api/settings` is both the origin authentication probe and the shared capability/configuration snapshot (`ca_cert_available`, `working_dir`, `ntfy_configured`, `voice_enabled`, `worktrees_enabled`, and repository presets). `GET /api/navigation-summary` returns only the Attention, Review, Plans, workflow-attention, and active-agent counts used by Layout, so navigation never loads full collections. Review queue/count/tour GETs read the persisted projection and never reconcile Git state. Agents synchronize while authoring or marking a tour ready; humans can explicitly reconcile one tour with `POST /api/review/tours/{id}/sync` or **Sync changes** on the review page. `GET /api/ca-cert` serves the auto-generated CA certificate as a PEM download (`Content-Disposition: attachment; filename="legato-ca.pem"`). Returns 404 when using custom TLS config (no auto-generated CA). `Server.SetCACertPath(path)` wired in `main.go` from `resolveTLS` return value.

**WebSocket synchronization**: Resource messages are mapped centrally to server-scoped query keys and coalesced over 75 ms. Queue/list invalidation refreshes only observed snapshots, detail messages are ID-scoped, `cards_changed` refreshes board keys, and `workflow_changed` never refreshes definitions. A reconnect revalidates each observed snapshot once to recover missed events. While actively observed, navigation summary also refetches once per minute as a foreground convergence fallback for missed or absent events; other shared snapshots do not poll. HTTP remains authoritative; websocket messages synchronize the shared cache rather than replacing initial loads.

**Macros API and shortcuts**: `GET /api/macros` returns `{"macros": [{name, keys}, ...]}` from the configured `macros:` YAML list. Auth-protected like other `/api/*` routes. `Server.SetMacros([]macros.Macro)` is called from `cmd/legato/main.go` after `NewWithSwarm`. Both web agent views eagerly fetch macros via `apiFetch(baseUrl, "/api/macros")` on mount/base-URL change so the ordered list is ready before the menu first opens. On the Agents view, unmodified `M` opens the mounted agent surface's macro menu when focus is outside input, textarea, select, and content-editable controls; `1`–`9` select the first nine macros in API order, and Escape dismisses the menu. Modified, repeated, already-handled, unavailable-index, and editable-target key events are ignored, preserving modifier-plus-digit agent switching. Later macros remain clickable without number shortcuts. Terminal sessions submit macro text through their normal message transport; native Chimera sessions dispatch leading-`!` macros through the bang endpoint and ordinary macros through `agent_message`. Bang commands overlay the active tmux session environment onto the child process, so they receive the exact variables injected at agent launch (including future additions) rather than incidental server-process values; execution fails if that environment cannot be read.

**Sparkline data**: `/api/agents` now includes a per-agent `state_timeline` field — a string slice (one entry per bucket, values: `"working"`, `"waiting"`, `""` for idle). Driven by `Store.GetStateTimeline(taskID, window, buckets)`. Window defaults to 10 minutes / 10 buckets and is configured via `Server.SetSparklineWindow(window, buckets)` from the `agents.sparkline_window` config field. `AgentSidebar` renders the timeline as a row of colored divs in each agent card.

**Ensemble**: `/agents?view=ensemble` shows every running agent at once, in place of the agent list and the one agent in view (`AgentEnsemble`). It is the web counterpart of the TUI's ensemble (see [TUI](tui.md) § Ensemble).

- **Getting there.** The grid button in the agent list's header, the same button beside the agent picker on a phone, or `e` (ignored while typing, with a modifier held, or with a dialog open). **List**, or `e` again, goes back. The view is part of the address, so Back returns to it after an agent was opened from it.
- **Header.** Agents counted by what they are doing: needs you (waiting, or stopped on an error), running, in background, idle.
- **Tiles.** One for each running agent, the ones that need the person first; one column on a phone, up to four on a wide screen. A tile has the agent's ID, its kind badge and its state (with the time it has worked, while it runs), its task, what the agent is at, and a foot with its recent activity and how full its context is (yellow from 70%, red from 85%). A tile that needs the person has an amber frame. The whole tile opens its agent in the usual view.
- **What an agent is at.** A native agent (`has_chimera_endpoint`) shows the end of its conversation: what the person sent, what the agent said (plain text; the newest is bright and gets six lines, older ones two), each tool call as one line (done, failed, or running), a run of tool calls cut to its newest three under **N earlier calls**, and the open request (**Wants to run:**, **Asks you to approve a plan:**, **Asks:**). What Legato or another agent sent is labelled as theirs. An agent driven through its terminal shows the last lines of its pane. The newest is kept in view; what does not fit is cut at the top.
- **Reading it.** `useAgentGlance` asks for each tile every three seconds (a conversation) or five (a pane), only while the tile is on screen and the page is in front. A read that fails keeps what was read before it.
- While the ensemble is shown no terminal is mounted, so the page subscribes to no agent's stream and sends no resize.

`GET /api/agents/{task_id}/conversation[?limit=N]` (`internal/server/agent_conversation.go`) is what a tile of a native agent reads: `{task_id, status, entries[], permission, question, context_used, context_window}`, where an entry is `{kind: "user"|"assistant"|"tool", text, tool?, command?, state?}`. It is `service.AgentConversationReader.ConversationTail` as JSON (see [TUI](tui.md) § A conversation in a tile): the server reads the agent's snapshot, which for a long session is megabytes, and returns the newest `limit` entries (40 by default, 100 at most), a few kilobytes. `409` for an agent with no native endpoint (its pane is at `/api/agents/{task_id}/preview`), `404` for one that is not running, `502` when the endpoint does not answer.

**Agent management**: `POST /api/agents/spawn` creates ephemeral agent (title input, defaults to "Ephemeral session"). `POST /api/agents/kill` terminates an ordinary agent session; a conductor task ID routes through full swarm cancellation. Both broadcast `agents_changed`. Dead agent detection: `onStreamEnd` callback fires on pipe-pane EOF → `ReconcileSessions` updates DB → `agents_changed` broadcast → web sidebar filters to `status === "running"` only. Auto-disconnect from selected agent if it dies.

**Mobile support**: Custom touch-to-scroll handler intercepts `touchstart`/`touchmove` on terminal container, calculates swipe delta, calls `term.scrollLines()` directly (xterm.js built-in touch doesn't work on mobile browsers). `touchmove` uses `preventDefault` (non-passive) to block pull-to-refresh. `overscroll-behavior: none` on body as fallback. Floating scroll-to-bottom button appears when scrolled up from bottom (tracks `buffer.active.viewportY < baseY`).

**Collaborative plans**: `/plans` is the queue of proposed and changes-requested plans; `/plans/<plan-id>` renders the immutable Markdown revision with required choices, text-selection comments, revision history data, immediate Q&A, and approve/request-changes/reject actions. Fenced `mermaid` architecture diagrams and canonical `wireframe` Wiremark UI mockups render lazily on plan detail and in captured review-plan context, with expandable previews and readable source fallback; other Markdown surfaces do not enable Wiremark. Comments on either visual retain the exact original fence and byte offsets rather than generated SVG. `plan_changed` WebSocket messages refresh matching open plans and the queue badge. Comments remain attached to their submitted revision. Required agent-authored questions block approval until answered. See `docs/plans.md`.

**Review tours**: `/review` supports individual and select-all queue selection plus a confirmed **Remove selected** action for stale review packets. `POST /api/review/tours/bulk-delete` validates every selected tour and removes all of their review artifacts in one transaction; a missing tour leaves the entire selection untouched. Removal retains tasks, repositories, worktrees, agent records, and Git history. `/review/<tour-id>` subscribes to `review_changed` WebSocket events and re-fetches the open tour when the event's `tour_id` matches, including answers submitted by agents through `legato review answer`. Diff line-number gutters are selectable: click and drag across rows to select a contiguous range, or click one line and another line in the same hunk to extend it; selecting another hunk replaces the range. Questions send canonical file/hunk/index coordinates, which the server validates against the current step diff and resolves into a durable fenced `diff` block for the agent and Q&A transcript. Transcript messages render safe GitHub-flavored Markdown (plain text remains valid), and delivered questions give agents a quoted-heredoc `legato review answer <step-id> --file -` command that preserves Markdown without shell expansion. Retrying the latest question replaces its prior answer instead of adding a duplicate. Completed tours stay out of the queue until visible follow-up work exists; when new commits or annotations arrive after a chaptered review, those unreviewed follow-up steps appear alongside the previously reviewed chapters instead of being hidden. The Q&A pane defaults wider and can be resized from its left edge (or with Left/Right on the separator). Its multiline composer sends with Ctrl/Cmd+Enter and, when voice is enabled, can append an editable transcription-only draft without bypassing the review transcript. Each hunk has a local **Viewed** checkbox that collapses/restores its lines, and the step-level reviewed action remains sticky at the top of the scrolling diff pane.

### Board page

The board page (`BoardPage` in `web/src/pages/Board.tsx`) is a keyboard-driven kanban view backed by `GET /api/board`. It renders columns left-to-right with cards underneath, maintains a selected-card cursor, and supports workspace filtering via a dropdown. `/board?highlight_task=<task-id>` selects the matching card across columns, expands its mobile column, scrolls it into view, and applies a cyan ring distinct from agent activity. After eight seconds the highlight and only that query parameter are removed with history replacement; the same bounded cleanup applies when an archived or filtered task is not visible.

**Keyboard bindings.** `j`/`k` moves the cursor down/up within a column; `h`/`l` switches columns left/right. `n` opens the Create Task overlay (title, description, column, workspace). `x` archives the selected card if it is in the Done column. `Shift+X` opens the Bulk Archive overlay when the Done column has cards (shows count, `y` confirms). `i` opens the Import Remote Task overlay (live search via `SyncService`, j/k navigation, enter to import). `w` opens the workspace switcher (`GET /api/workspaces`, j/k navigation, enter to filter). `?` opens the Help overlay with keybinding reference.

**Mutation feedback and pointer movement.** Board cards support native desktop drag-and-drop between columns in addition to keyboard/click movement. The target column highlights while dragging and the move uses the same task PATCH endpoint as the move dialog. User-triggered mutations show accessible success/error toasts, preserve open form data after failures, and disable repeat submission while pending. Action dialogs render above an open task detail panel. Successful web mutations also broadcast `task_update` over IPC, while embedded TUIs subscribe directly to `EventCardMoved`, so card moves refresh running TUIs in both standalone-server and embedded-server deployments.

**Task worktrees.** When `worktrees.yggdrasil.enabled` is configured, task detail offers **Create worktree**. The modal mirrors the TUI `b` flow with repository presets plus editable primary directory, task-derived branch, and base branch fields. `POST /api/tasks/{id}/worktree` calls the shared `service.WorktreeWorkflow` and Yggdrasil runner; it does not implement a separate web lifecycle. Persisted worktree path/branch metadata is returned by task detail and displayed on later visits. **Open agent** prefers that path as its editable working-directory default, allowing worktree creation and agent launch entirely from the web UI.

**Data flow.** `useBoard()` observes the server-scoped board query. The central websocket coordinator coalesces `cards_changed` bursts and invalidates each active board key once; the hook also exposes `refresh()` for authoritative refetch after create/import/move/worktree creation and provider sync. The toolbar's **Sync providers** action calls authenticated `POST /api/board/sync`, disables and spins while the shared single-flight Jira/GitHub operation runs, explicitly refetches the active workspace afterward, and toasts success, unavailable sources, conflicts, or partial failures. `EventPRStatusUpdated` also becomes `cards_changed` so other connected boards converge. Board data includes PR metadata (check status, review decision, comment count, draft indicator) and swarm stats per card when those services are active.

**Per-card indicators.** Each card shows: priority-colored left border, task-provider icon (Jira, GitHub, local), warning dot if sync failed, workspace tag in "All" view, and swarm stats when active. Every linked PR gets one stable pull-request row with `#number`, explicit CI passed/failed/pending/no-checks state, approved/changes-requested/pending-review state, non-zero comment count, and an additive draft badge. The shared card component covers desktop and mobile.

**Overlay set.** Create overlay (`CreateTaskOverlay`), Import overlay (`ImportOverlay`), workspace switcher (`WorkspaceOverlay`), archive confirmation (`ArchiveOverlay`), link-PR modal (`LinkPRModal`), help (`HelpOverlay`), and a detail slide-out (`TaskDetail`) for viewing full card context. Only one overlay is active at a time; Escape dismisses. The detail pane shows effective description Markdown, remote metadata, PR branch info, and swarm step list with active step highlighted. Provider-backed tasks expose **Edit Legato details**: the modal receives raw `local_description_md`, provider `remote_description_md` remains read-only, and the pane refetches the server-composed `description_md` after save.

### Swarm controls

The web PWA supports the full user-driven swarm control surface:

**Starting a swarm.** The agents view has a "Start Swarm" flow that opens a working-directory input modal, calls `POST /api/swarm/start`, and spawns the conductor session. Board task detail also shows **Start swarm** with the parent task fixed and a directory default resolved as `task worktree → remembered task directory → configured default`. A successful task launch navigates to `/agents?task=<parent-id>` and selects the conductor when it appears. An existing conductor changes the task action to **Go to swarm**.

**Plan approval.** When the conductor calls `legato swarm propose-plan`, the server broadcasts a `plan_proposed` WebSocket event to all connected web clients. Each client opens a modal showing the plan summary and sub-task list. The user can:
- **Approve** (`y`) — sends a `plan_verdict` WebSocket message with status `"approved"`; the conductor proceeds to dispatch workers.
- **Reject with notes** (`n`) — opens a text input for notes, sends `plan_verdict` with status `"rejected"`; the conductor revises the plan based on the natural-language feedback.
- **Dismiss** (`Escape`) — closes the modal without sending a verdict; the conductor remains blocked on `BroadcastRequest` and the user can re-trigger proposal from the conductor pane or TUI.

The modal does not include in-browser YAML editing (v1). Users who need surgical edits either reject with detailed notes or fall back to the TUI overlay which supports `e` to open `$EDITOR`.

**Extension plans.** When a conductor calls `legato swarm extend-plan` (or the server receives `plan_extension_proposed` over WebSocket), the modal title changes to "Extension plan — append to existing swarm". The rest of the approval flow — approve, reject with notes, dismiss — is unchanged. Web clients track whether the current modal is an extension via the `mode` field on `plan_proposed` IPC events.

**Cancel swarm.** The board detail panel (`DetailPanel.tsx`) shows a red "Cancel swarm" button when the card has active swarm stats or a working directory. Clicking it opens `CancelSwarmModal.tsx`, which confirms that the action kills the conductor + all live workers, deletes sub-tasks, and clears swarm state. Killing a conductor from the Agents dot menu or right-click menu routes through the same full swarm cancellation. The card itself and its history remain.

**Per-worker action menu.** Each agent entry in the sidebar has an overflow `⋯` button that opens a role-appropriate menu:
- **Worker** → Send message (free-text input → `POST /api/swarm/message`), Close worker (`POST /api/swarm/close`)
- **Conductor** → Send message, Finish swarm (`POST /api/swarm/finish`)

**Swarm command center.** Selecting any swarm participant switches the Agents page from the solo layout to a swarm-level view. Desktop keeps the conductor in the primary pane and shows every status subtask in a scrollable worker area, including queued or terminal workers without sessions. Selecting a live worker expands one interactive worker pane beside the conductor. Compact tmux cards poll bounded plain-text captures from `GET /api/agents/{task_id}/preview`; they never subscribe to terminal output or report dimensions, so they cannot shrink the real tmux pane. Native Chimera compact cards use status metadata and expand into the existing native panel. On narrow screens, one participant picker controls one interactive pane. The shared prompt bar always targets the focused interactive participant.

**Swarm event log.** A collapsible "Swarm events" panel appears below the agent area when the focused agent is part of a swarm. It shows unacked event entries (`#42 [progress] worker "API" — text…`) fetched from `GET /api/swarm/inbox/<parent-id>`. New lifecycle, question, and debounced progress events publish `swarm_changed`, which causes a non-acknowledging peek. Clicking an entry expands the full payload. A "Drain" button marks events acknowledged. Events are never auto-drained because the conductor or another client can also be reading them.

**Keyboard agent switching**: Modifier key + digit (1-9) switches agents with glitch animation. `getSwitchModifier()` reads `legato:switch-modifier` from localStorage (defaults `"Alt"` on Mac, `"Control"` on Linux). Global `keydown`/`keyup`/`blur` listeners in `Agents.tsx` track `modifierHeld` state. `AgentSidebar` renders number badges when modifier held. Settings page has modifier key picker (Control/Alt/Meta).

**Draft persistence**: Per-agent text input drafts stored in localStorage (`legato:draft:<agentId>`). `PromptBar` saves draft on every keystroke, restores on agent switch, clears on submit or kill. Uses `prevAgentIdRef` + `inputRef` to handle agent switch save/load without stale closures.

**Frontend source**: `web/src/` — `pages/Agents.tsx` (main orchestrator), `pages/Settings.tsx`, `components/TerminalPanel.tsx`, `components/PromptBar.tsx`, `components/AgentSidebar.tsx`, `components/OfflineDialog.tsx`, `components/TokenPrompt.tsx`, `components/QRScanner.tsx`, `components/PlanApprovalModal.tsx` (HITL plan + extension approval), `components/board/DetailPanel.tsx`, `components/board/CancelSwarmModal.tsx`, `hooks/useWebSocket.ts`, `lib/auth.ts` (token helpers), `lib/utils.ts`. ### Attention dashboard

`/attention` is a grouped operational dashboard over the durable Attention registry. It always presents **Needs intervention**, **Ready for review**, and **Merge blockers** with section counts and compact section-level all-clear states; a larger global all-clear appears only when every section is empty. Cards retain urgency/source labels, reason and detail, source-owned execute actions, revision-scoped Dismiss, and direct navigation. Unknown future allowed signals fall back to Needs intervention. Actions wrap below card text on narrow screens, and loading/source/action-conflict errors remain visible and accessible.

The dashboard does not compose Board, Agents, and Review API calls in the browser. `GET /api/attention` remains authoritative, and `attention_changed` invalidates its shared query. Navigation badges, TUI, CLI, and Stream Deck consume the same expanded default signal policy while retaining generic list/count presentation.

## Web UI

Remote web interface for monitoring and interacting with agent sessions from any device (mobile, tablet, second screen). Built with React 19 + Vite + xterm.js + TailwindCSS. Compiled to `internal/server/static/dist/` and embedded in the Go binary via `embed.FS`. Installable as a PWA with offline support.

**Voice keyboard readiness**: The Agents page binds `v`/Escape in a layout effect using the current selection and voice setting directly, without a passive-effect mirror ref. A terminal session with a prompt bar can start dictation as soon as its selection is shown.

**Terminal prompt choices**: `PromptBar` lets native buttons handle Enter when a choice has keyboard focus. Its container handles Enter only when the container itself is focused. Arrow navigation moves focus with the highlighted choice, so Tab, arrows and Enter cannot activate a different approval; Dismiss never sends terminal keys.

**Modal contract**: `components/ui/useModalLayer.ts` owns the modal stack, background `inert`, body scroll lock, focus containment and restoration, and topmost-only Escape. Its named API is `{open, onClose, containerRef, dismissible?}`. Nested pickers consume Escape with `preventDefault` before the document handler. Keep desktop side columns nonmodal; each phone sheet uses its actual layout breakpoint. `ui/Dialog` uses the same hook and provides a bounded panel, scrolling body, and stable wrapping footer.

**Agent switching readiness**: The Agents page installs its modifier-plus-digit listener in a layout effect, so the displayed list order and key mapping change together. Its regression presses the shortcut at the first terminal commit.

**Search keyboard readiness**: `SearchModal` installs its result-navigation listener in a layout effect, so Enter selects the visible result in the same commit that displays it, including archived tasks. The BoardSearch regression presses Enter from a MutationObserver before passive effects run.

**The loop that holds a pull request.** `GET /api/review-loops?repo=<owner/name>&pr=<n>` (authenticated; `internal/server/review_loops.go`, `service.ReviewLoopLookup`, wired on both web servers in `cmd/legato/main.go`) reads the pull request's claim on the loop record (`store.ActiveReviewLoop`, the repository's case ignored), so it finds the loop whichever caller opened it, in a process with or without the review engine (spec LEG-559 § API contract). It answers `{loop: {loop_id, kind, run_id, step_path, phase, state, held, outcome, link}}` (`service.FoundReviewLoop`) or `{loop: null, agent_author}` when no loop holds it (a closed loop has let its claims go); a missing parameter, a `repo` that is not owner/name or a `pr` that is not a positive number is a `400` (`service.CheckReviewLoopQuery`). `kind` is `run`, `child_run` (the run has a parent run: a `workflow.run` step started it, LEG-489) or `handoff`; `run_id` and `step_path` are empty for a handoff. `link` is where the web UI shows the loop: `/workflows/runs/<run>` for a run's, `/board?highlight_task=<card>` for a handoff's. `held` says the operator stopped the loop's steward watching (Stop watching). `agent_author` is what a launcher starts `review-loop` with (spec LEG-559 D8): true only when Legato's author App opened the pull request, as the card that tracks it says (`service.ReviewAuthors.AgentAuthor`: `agentAuthoredPRs` on that card's tracked branch; `Server.SetReviewAuthors`; see [TUI](tui.md) § Review passes from the card menu); false for a pull request no card tracks, and on a server not given it. The card menu and the TUI read it (LEG-596).

Save (or Create) is on only when the check of the current text has no error. Refusals are handled by `WorkflowFileError.code`: `stale` shows the file's current text with **Reload** or **Keep my edits** (which takes the new digest), and `confirm_triggers` names the triggers and offers **Save and switch on** (`confirm_triggers: true`). The app's `BrowserRouter` has no `useBlocker`, so unsaved changes are guarded three ways. A `beforeunload` prompt covers a reload or a closed tab. A capturing click listener confirms before a link leaves the page (the nav included). Completion, hover and checks as you type come from `web/src/lib/workflowSchema.ts` over `web/src/generated/workflow-v2.schema.json` (and `workflow.schema.json` for a version 1 file), our own small reader of it (`codemirror-json-schema` brings shiki and markdown-it):

- `contextAt` finds the cursor's YAML path from indentation (block style).
- `keyCompletions` and `valueCompletions` give the keys a path takes (a step's `with` by its `type`, through the schema's `if`/`then`) and the values it takes: enums, booleans, and the non-internal step types with their titles.
- `schemaDiagnostics` checks with the `yaml` package's ranges. An unknown `with` key is a warning (LEG-461); types, enums, patterns, required keys and the exclusive groups are errors.

Expressions: `web/src/lib/workflowExpressions.ts` builds on the schema's `x-legato.expressions` (`ExpressionContexts()` in Go) and `task_fields`/`repository_fields`. It holds no rules of its own: each root pattern's placeholders (`<input>`, `<task input>`, `<earlier step>`, `<output>`, `<file output>`, `<path>`…) are filled from the document at the location (`locationOf(path)`: `run_title`, a step's `with`, a file output's `path`, a trigger's `inputs`). `references` lists what can be read there, and `checkExpression` gives the engine's verdict. `internal/engine/workflow/testdata/expressions.json` is a table of references that Go (`TestTheSharedExpressionTable`, through `Validate`) and Vitest both run, so the editor's verdicts can't drift from the engine's. `valuePathAt` finds the value a position is in, the key of a block scalar (`prompt: |`) included. The editor completes inside an open `${{` (`expressionCompletions`), shows what an expression reads on hover (`expressionAt`), and marks refused references (`expressionDiagnostics`) with the schema's checks. The builder's expression picker will use the same module. `editorDiagnostics.ts` turns the server's lines and columns into offsets, and on a line the server marks only its diagnostics show. Tests mock the lazy editor with a textarea (`WorkflowEdit.test.tsx`).

  - Common to all kinds: `enabled`, `confirm`, `max_runs_per_day`, and an inputs table with one row per workflow input. Its `ReferencePicker` gives `references` for `trigger.<kind>`.
  - `task.entered_column`: a column (board columns), `handed_off`, and `ConditionNode`, recursive over all and any groups, `not`, and field rows. A field row's field suggests `x-legato.condition_fields` (Go's `ConditionFields`) and `task.metadata.`; it has an operator (`equals`, `not_equals`, `exists`, `in`) and values of a type chosen beside them (`ConditionLeaf`, `operandOf`), so editing `"123"` keeps it text. An `in` list is one field per value, each with its own type (`InList`), so `[foo, true]` stays a text and a boolean and a value with a comma in it stays one value. The condition tree is written whole on each change.
  - `schedule`: **Every** (every, at, on for weekly; leaving weekly removes `on` in the same edit) or **Cron**, switched in one edit, plus the time zone and `catch_up`. The next three times come from the check (`POST /api/workflow-files/check` adds `schedule: {description, timezone, next}`, from `ScheduleTrigger.Next`, in `schedulePreview`).
  - Removing a trigger is `setTrigger(kind, null)`. `removePair` now also takes the comment lines written at the key's column just above it.
  - `TriggersEditor.test.tsx` builds the `triage` template's trigger (a column, inputs from `event.task` and `task.metadata.repository`, a condition on `task.metadata.triaged`). The result equals the template and passes the checks. It also covers a bad cron's server diagnostic on its field, a removal that leaves every other byte, the every/cron switch with the preview, and nested condition groups.

`CommitField` writes on blur or Enter, so a word is one undo step. It reports text it holds but hasn't written through the `PendingDrafts` context (`pendingDrafts.ts`), and the page counts that as unsaved. After Undo or Redo the history is `sealed`, so typing makes a new step instead of changing the one returned to. Choices are one field each (`Choices`), so a choice with a comma in it stays one. `shapeProblem` (in `workflowDocument.ts`) sends a file whose parts aren't of a workflow's shape (a step that is not a mapping, say) to YAML before the forms draw. A `Boundary` around the forms shows any other failure to draw, with **Edit as YAML**, and tries again when the text changes. Problems from the server's check show on the field whose path they are on, or under it (`problemsAt`). A file that doesn't parse, or that `parseWorkflow` marks read-only, shows why and **Edit as YAML** instead of the forms. `pages/__tests__/WorkflowBuilder.test.tsx` covers:

**Workflow document model** (`web/src/lib/workflowDocument.ts`, LEG-470, the policy LEG-462 decided) is what the builder edits through. Every operation splices the file's text at the `yaml` package's node ranges (`keepSourceTokens`), never `Document.toString()`, which reflows folded scalars. So the bytes of every node an operation does not touch, comments included, stay as they were, and a write of the value already there changes nothing.

- **Reads:** `parseWorkflow` gives `{errors, readOnly, values}`; then `metadata`, `inputsOf`, `stepsOf`, `stepById` and `triggersOf`.
- **Operations:** `setField(path, value)` (`undefined` removes; the maps on the way are made), `insertStep`, `moveStep`, `removeStep`, `renameStep` (rewrites `steps.<id>.outputs` inside `${{ }}`), `setTrigger(kind, spec|null)` (`on:` goes with its last trigger), `addInput`, `removeInput` and `renameInput` (rewrites `workflow.inputs.<name>` and the triggers' `inputs` keys). Each takes the text and returns `{text, undo: {label, before, after}}`.
- **Writing style:** a node it writes is in one style (`render`: 2-space indent, block collections, plain scalars where they read back the same, `|` for multi-line text). A flow collection around the change is rewritten whole in block style. A value's own comments survive its rewrite: a trailing comment after a one-line value or flow collection, a block scalar's header comment (`|- # why`), and a comment on the key's line above a block collection all go back on the key's line, or after the new value. A move to last place inserts after the last step, not at the end of the file, since fields may follow `steps:`.
- **Steps:** they are found by ID. A step's lines run from its dash, with the comment lines at the dash's column above it, to the next step's, so a step's comments move and go with it.
- **Refusals:** an operation on a file that doesn't parse throws `WorkflowDocumentError`. An anchor, alias or merge key refuses an operation only when it is in the item the operation touches (`writable(text, ...scopes)` and `guard`: the input, trigger, top-level field or top-level step of the path, or the flow collection rewritten around it), or is an anchor or an alias on a container the edit is inside, down the path as far as it exists (so adding an input to `inputs: *defs` is refused). The rest of the file stays editable. `parseWorkflow`'s `readOnly` still names the whole file's problem for the old builder.
- **Where things are** (LEG-503), for the outline, the YAML navigator and errors in place. An item is an `ItemRef`: `about` (a top-level field), `input`, `trigger` or `step`, known by its StepPath (`each/review`; a step's children are the list under its own `steps:`). A run's path with a loop pass (`each/2/review`) finds the same step: a numeric segment that names no step is skipped. `itemKey` is an item as a string (`step:each/review`).
  - `rangeOf(text, item, field?)` is the text of an item, or of a field in it (`["with", "prompt"]`). An input, trigger or field runs from its key, and a step from its dash, to the end of its value with an inline comment, without the line break. `stepYamlPath` is a StepPath's place, such as `["steps", 1, "steps", 0]`.
  - `pathAt(text, offset)` is the innermost item and field at a position, or null between items, in a comment above one, or in a file that doesn't parse.
  - `itemsOf(text)` lists the items in the file's order, nested steps after their parent, each with its range and `problem`: why the forms can't show it. That is an anchor, alias or merge key inside it, or a shape the forms can't draw (a step that isn't a mapping, a `with` that isn't one, a trigger's conditions). Each such item becomes an "Edited as YAML" row and the rest stay visual. Only a file that doesn't parse, or isn't a mapping, gives `file` and no items. A container that is the wrong shape, or a flow collection (`steps: [...]`), is an `about` item with the problem. `parseWorkflow`'s `readOnly` still covers the whole file for the current builder, until the outline uses `itemsOf` (LEG-505).
  - `itemText(text, item)` is an item's YAML out of its place, unindented: a step as a mapping without its dash, an input or a trigger as its key and value. `setItemText(text, item, edited)` writes it back at the item's indent, over the item's range alone, so the rest of the file stays byte for byte. That is the inspector's YAML tab (LEG-504). An empty item is refused: remove it instead.
  - `problemsByItem(text, diagnostics)` files the server's diagnostics under each item's key by their path (`steps[1].steps[0].with.prompt`; a trigger's dotted kind is matched against the file's own keys), or by their line and column when they have no path. Those that belong to no item go under `file`.

**Development hot reload**: `task run:hot` launches the stable `./legato --hot-reload` binary for the TUI and its optional in-process web server; `task server:hot` launches `./legato --hot-reload serve` and honors `LEGATO_SERVER_PORT`. The Unix foreground supervisor watches the resolved executable rather than source or `dist`, inherits args/env/CWD/stdio/terminal, and uses a private child marker to prevent recursion. A stable replacement triggers SIGTERM, complete old-child shutdown, then one new child; children never overlap. Missing/partial replacements leave the current child running. Once a stable build starts shutdown, the TUI gets a bounded graceful quit followed by Bubble Tea's terminal-restoring hard stop; the supervisor then force-stops and reaps any process that exceeds its wider deadline before starting the replacement. An immediately failing replacement leaves the supervisor waiting for a later build. `task build` reloads Go against the already embedded bundle; `task build:full` first emits and embeds a fresh web build identity. Hot mode resets transient TUI state and allows a brief web disconnect; it is not a daemon or zero-downtime deployment mechanism. A hot-reload child running from a checkout exposes `hot_reload_enabled` in authenticated `/api/settings` and accepts authenticated `POST /api/hot-reload/build`; Settings uses that capability to show a mobile-friendly **Rebuild and hot reload** action. The endpoint starts `task build:full` asynchronously from the executable's checkout directory, rejects concurrent builds, and redirects output to `.legato/run/hot-reload-build.log` so it cannot corrupt the TUI. Normal/non-checkout processes do not install the trigger and return no capability. `server:restart` remains a separate detached standalone-server helper.

**TLS**: Disabled by default for simple local-network development. Set `web.tls.enabled: true` for auto-generated HTTPS, or set both `web.tls.cert` and `web.tls.key` to enable HTTPS with explicit files. `Server.SetTLS(certFile, keyFile)` configures TLS before `Start()`/`Serve()`. `Serve()` calls `http.Server.ServeTLS` when TLS is set, plain `Serve` otherwise. Auto-generated certificates live at `~/.local/share/legato/certs/`; the server certificate is regenerated when it expires or no longer includes the configured hostname or current local IP addresses, while retaining the CA.

**Authentication**: Bearer token auth on all API/WebSocket requests. **Pairing by phrase**: a phone in the Legato app pairs by typing four words. The person opens a pairing request with `legato pair` or Settings › **Pair a device** (`PairDeviceDialog`), and the phone proves it knows the phrase without sending it. How the app does its side, and why it is safe, is in `mobile/README.md` § Pairing and servers.

- **The request** (`service.PairingService`, in memory). One at a time per server; opening another replaces it. Its phrase is 4 words from the EFF short word list (`internal/engine/pairing/words.txt`). It ends after 5 minutes (`expired`), after 5 exchanges that did not pair (`exhausted`), when cancelled (`cancelled`), or when a phone pairs (`paired`, with the name the phone gave). A restart of the server ends it.
- **For the person** (behind the token): `GET /api/pairing` (the request: `state`, `phrase`, `expires_at`, `attempts_left`, `device`, and `pair_uri` while it is open), `POST` opens one, `DELETE` cancels it. `pairing_changed` on the WebSocket says it changed.
- **The QR code** is `pair_uri`: `legato://pair?url=<address>&phrase=word-word-word-word`. It carries the phrase, which works once and for five minutes, never the token. The address is the one the browser asked on, unless that is a loopback one; then the first LAN address the server is announced on (`SetPairingAddresses`). With neither there is no `pair_uri`. The dialog draws it blurred until clicked (`uqr` encodes it); the app pairs from it without anything typed.
- **For the phone** (no token; the phrase is the check): `POST /api/pair/exchange {share}` → `{session, share}`, then `POST /api/pair/confirm {session, confirmation, phone}` → `{confirmation, sealed}`. Values are base64. It is SPAKE2 as RFC 9382 defines it (P-256, SHA-256, HKDF, HMAC; the phone is A, identities `legato-mobile` and `legato-server`, AAD `legato-pair-v1`), with the password scalar derived from the words by HKDF (`pairing.PhraseScalar`). `phone` and `sealed` are AES-256-GCM under keys derived from the exchange's key: the phone's name, and `{token, name, ca_certificate}`. The token is the one the server checks; `ca_certificate` is the generated CA, or the file of `web.tls.cert`. Errors: `410` no open request, `403` the phrase does not match (one attempt used), `400` a malformed step, `404` a server without pairing.
- `/api/meta` has `phrase_pairing: 1` when the server pairs by phrase. The server also announces itself on the local network (see `web.discovery` in [Config](config.md)) so the app can list it.
- **A main instance's request.** `POST /api/pairing {"purpose":"main"}` opens a request for a main instance instead of a phone; no body, or none with a purpose, is a phone's, as before. The request's view has `purpose` (`phone` or `main`); a main's has no `pair_uri` and has `address`, the address to type on the main. A main pairs with its own SPAKE2 identity (`legato-main`) and gets a token that can only hand off, never the web token. `PairDeviceDialog` takes `purpose` (`phone` by default) and shows it: its title, the address for a main, and a notice when a request opened elsewhere for the other purpose replaced its own. See [Integrations](integrations.md) § Main instances and workers.

**PWA**: Installable progressive web app via `vite-plugin-pwa` (Workbox). Service worker auto-updates (`registerType: 'autoUpdate'`), `skipWaiting: true` + `clientsClaim: true` for immediate activation on update. Each production Vite build generates one UUID, compiles it into the browser, and emits `dist/build-id` for Go embedding. Public no-cache `GET /frontend-meta` returns the serving binary's embedded ID independently of Go's local `dev` version. Initial WebSocket connection and every reconnect to the server that served the page compare the IDs (with another server chosen in the switcher there is no check: its build says nothing about this page, and a reload would load this one again): a mismatch updates registered workers, waits briefly for controller change, and reloads once. Session storage bounds automatic attempts; a repeated mismatch displays a manual **Reload update** action rather than looping. Same-build network reconnects never reload. Precaches app shell (HTML/CSS/JS/icons); Workbox skips a file over 2 MiB and the plugin then fails the build, so `build.rolldownOptions.output.codeSplitting` in `web/vite.config.ts` puts the libraries every page loads (React and its router, xterm, the Markdown stack) in chunks of their own. Name a library there only if it loads at start: a group takes a module however it is imported, so a catch-all would make mermaid's on-demand diagrams load with the app. Runtime caches API routes with NetworkFirst strategy. Navigations fall back to the cached app, except the addresses in `web/src/lib/serverPages.ts` (`navigateFallbackDenylist`), which the server answers itself: the image routes, and `/oauth/` (an integration's consent page sends the browser back to `/oauth/callback` with a code only the server can exchange). Manifest at `/manifest.webmanifest` (auto-injected by plugin). Icons: `web/public/pwa-192x192.png` and `pwa-512x512.png` (pre-generated from `favicon.svg`). PWA requires HTTPS on non-localhost — hence TLS auto-generation.

**Reconnecting and the offline dialog**: a phone that slept, or switched to another app, usually comes back to a closed WebSocket while the server is still there. So a drop is first *reconnecting*, and only later *lost*:

- **Reconnecting at once.** `useWebSocket` reconnects without waiting out its backoff when the page becomes visible (`visibilitychange`), the network comes back (`online`), the page is shown from the back-forward cache (`pageshow`), or the mobile app returns to the foreground (`legato:shell-return`). An open or opening socket is left alone. The page and its state stay as they are; the agents page and the panels subscribe again on the new connection.
- **Out of view.** `usePageInView` (`web/src/hooks/usePageInView.ts`) is false once the page has been hidden for 10 seconds (`HIDDEN_GRACE_MS`), or at once when the mobile app goes to the background (`legato:shell-leave`), and true again on `visibilitychange` to visible or `legato:shell-return`. While it is false the agents page unsubscribes its terminal streams and `NativeAgentPanel` unsubscribes its agent, so a hidden page or a phone with its screen off stops receiving them; on return they subscribe again, the native panel with its last cursor. The socket itself stays open, so board, agent-list and approval messages still arrive.
- **Reconnecting notice.** While disconnected and not yet lost, `OfflineDialog` (`web/src/components/OfflineDialog.tsx`, mounted in `Layout`) shows a small floating "Reconnecting…" (or "Connecting…" before the first connection) at the top of the page after 500 ms, so a quick reconnect shows nothing. The rail and the tab bar keep saying `sync`.
- **Lost.** With no connection for `lostAfterMs` (10 seconds) the hook sets `lost`: the server is likely down. Then the Connection Lost dialog appears over the page, with **Retry** (which reconnects at once, without reloading, so the page stays where it was), server switching, Settings/QR actions and a TLS hint for remote servers, and the rail and tab bar say a red `offline`. The dialog can be dismissed with its close control or Escape; it closes when the connection is back and opens again the next time it is lost.

**Cache headers**: `spaHandler` in `internal/server/spa.go` sets `Cache-Control` headers — `public, max-age=31536000, immutable` for Vite hashed `assets/*`, `no-cache` for `sw.js`/`workbox-*.js`/`index.html` and SPA fallback responses.

**Terminal streaming**: `pipe-pane` fans output to all subscribed web clients via WebSocket. Pipe start is deferred until the first `resize` message so the tmux pane is correctly sized before output flows. `PipeOutput` clears any stale pipe-pane from a previous process before starting a new one. On subscribe, the server waits 150ms for SIGWINCH redraw, then sends a `CaptureWithEscapes` snapshot as backfill (`\n` → `\r\n` for xterm.js). After the live pipe starts, the server bounces the pane width by 1 column (shrink then restore) to force a full SIGWINCH redraw through the pipe, preventing the backfill snapshot and live stream from diverging. Output chunks sent synchronously (not `go c.send`) to preserve ordering. Escape sequence buffering (`findIncompleteEscape`) holds back incomplete CSI/OSC sequences at chunk boundaries to prevent xterm.js state corruption. Read buffer is 32KB. `refresh_pane` queries tmux cursor position via `display-message` and appends ANSI CUP to restore cursor after snapshot.

**Native Chimera synchronization**: A terminal-backed task Chimera agent exposes **Upgrade to native Chimera** in `PromptBar`. `POST /api/agents/{task_id}/chimera/discover` scans current lockfiles without restarting any process, requires an exact task-ID match at an HTTP loopback endpoint, verifies both instance liveness and the expected session, and persists only one uniquely valid candidate; missing or stale candidates remain terminal-backed with an actionable error, while ambiguity returns `409 Conflict`. Successful discovery broadcasts `agents_changed`, and the initiating page also refetches `/api/agents`, switching to `NativeAgentPanel` when `has_chimera_endpoint` becomes true. If the panel's initial snapshot cannot resolve that persisted endpoint/session, the server conditionally clears the exact still-matching binding and replay cursor, broadcasts `agents_changed`, and the same page remounts the tmux terminal/composer without a reload; later manual and background snapshot failures retain an already-loaded native conversation. The native overflow menu also exposes **Downgrade to tmux**, which performs the same durable clear without stopping the agent, and a matching live lockfile can be manually upgraded again. `NativeAgentPanel` hydrates from the Chimera session snapshot and reduces live envelopes through `web/src/lib/nativeAgentSync.ts`, which owns ordered item insertion, stable assistant/tool identities, bounded event-ID deduplication, and per-assistant streaming buffers. `subscribe_agent` carries the browser's last accepted `cursor`; the server retains a 1,000-event per-agent replay ring and upstream SSE connection for a 30-second disconnect grace period. Known cursors replay missed envelopes before live delivery. Unknown, expired, or cursorless reused streams emit `chimera_sync_required`, causing race-safe snapshot reconciliation. Events arriving during a snapshot fetch are queued and reduced afterward, failed refreshes retain the existing conversation, and completed runs trigger a debounced authoritative repair. Background repair keeps the feed mounted with a lightweight syncing indicator and preserves scroll position. The native panel overflow menu also provides **Refresh from snapshot** for manual recovery. Picking the agent that is already open, in the sidebar or the mobile picker, runs the same refresh (`useAgentReselected` in `web/src/hooks/useAgentSelection.tsx`), and the mobile app re-picks the open agent each time it returns to the foreground (see `mobile/README.md` § Returning from the background). `spawn_agent` calls use a dedicated expanded card that groups each child by Chimera's `parentCallId`, shows its requested agent/model/prompt, and streams forwarded child assistant, reasoning, and tool activity without mixing parallel children. Cursorless browsers loading during an active shared stream receive snapshot repair followed by retained events, so active child cards and captured activity are restored. Live child activity is retained through parent snapshot repair, but not across a full page reload after the shared stream's replay window has expired because Chimera does not persist forwarded `subagent_event` envelopes in the parent snapshot; completed cards then state that no live activity was captured.

**Sub-agent tiles**: When a native session has subagents (a `spawn_agent` call, or one carrying `subagent` state), `AgentChatHeader` shows `SubagentSwitch` (group "Sub-agents": **Inline** / **Tiles** with the count and a live dot). A spawn rehydrated after a bridge restart has no `subagent` record, so it cannot be joined and shows `done`.

**Background shell tiles** (LEG-244): each background shell the agent started is a tile in the same deck, after its subagents (`components/tiles/shellTiles.tsx`, `components/tiles/ShellParts.tsx`), and counts toward the switch, which appears once the agent has a subagent or a shell; the deck is then called "Sub-agents and shells". A shell's tile: its description (else the command's first line) as title, `$ <command>` as meta, state `running`, `done` (exit 0, or an end with no code), `error` (any other code) or `killed` (a `TileState` of its own), the run time, `exit N` in the corner, the newest line it printed as the summary, and its output (`ShellOutput`: a `pre` with the terminal's escape sequences and carriage-return redraws taken out by `plainOutput`, read-only, with "Earlier output is not kept." when the tail was cut). In Tiles, the Bash call that started it keeps its row in its tool group, and a `SubagentLink` (`kind="shell"`) after the group opens the tile (`shellTileForCall`). Shells reach the panel in one shape (`lib/backgroundShells.ts`, `NativeBackgroundShell`: `shellId`, `callId`, `command`, `description`, `status` `running`/`exited`/`killed`, `exitCode`, `startedAt`, `endedAt`, `output {available, text, truncated}`) from two sources, merged with the endpoint's first (`mergeShells`): the native endpoint's snapshot `backgroundShells` and its `background_shell` (start or end, no output) and `background_shell_output` (`chunk`, `gap`: start over from it, `reset`) events, which `nativeAgentSync` folds into `NativeSyncState.backgroundShells` (output kept to `shellOutputLimit`, 32 KiB, as the bridge keeps; an output event whose `seq` is at or below the shell's `output.seq` is already held and skipped, so events replayed over a snapshot add nothing twice); and the agent's `background_shells` from `/api/agents` (`fromStored`, `output.available: false`), which `pages/Agents.tsx` passes as the panel's `backgroundShells`. Claude Code's come the first way, with output (see [Claude Code native integration](claude-code-native.md) § Background shells); Chimera's the second, without output, until Chimera lets a mod read a shell's output (CHIM-95), when its endpoint can serve them the first way and win. Codex reports none.

Inline cards and tiles share `subagentStatus` (then `subagentLive`, above): background `result.status: running`, terminal `result.reason`, tool exceptions and interruption all settle the same lifecycle. Chimera's mod supplies durable `subagentStates` on proxied snapshots; active-child panels repair on debounced `agents_changed` notices, including idle completions missing from upstream SSE. A snapshot's in-flight spawn timestamp is running even when startup SSE was missed. Interrupted tiles are terminal and go on the Finished shelf; an old replayed spawn cannot resurrect a completed child. See [Chimera native integration](chimera-native.md) for upstream gaps and fixture evidence.

Snapshot hydration keeps the latest exchange after retained historical tools. Idle legacy snapshots align their message slots with the tool-record suffix, not a compacted-away prefix. New Chimera snapshots join committed provider-ID occurrences and append only explicit pending-message tools (including finished siblings before SDK response attachment); replay still deduplicates by canonical call ID. New hosts mark legacy records settled on resume. Old busy hosts retain their earlier uncommitted-tool fallback; exact active-step correlation needs the paired Chimera update. No scroll-pinning or browser-only retention masks missing history. See [Chimera native integration](chimera-native.md) for protocol and rollout limits.

**Terminal prompts in the native panel**: Some prompts never reach Legato as a request: an update notice, a trust question for a new directory or its hooks, a picker opened in the terminal, or a question or permission prompt of an agent whose native hook is missing (started before a hook update). While a native panel is open it sends `detect_prompt` every two seconds, and a `prompt_state` of a choice type (`menu`, `tool_approval`, `plan_approval`, `question`, read from the pane by `internal/engine/prompt`) is drawn by `NativeTerminalPrompt` as **`<Tool>` is asking in its terminal**: the text above the options, a button per option, a text field for a row that takes text (`takes_text`, Claude Code's "Type something."), **Cancel (Esc)** when the prompt offers it, and **Open terminal**. A choice is sent as `answer_terminal_prompt` (`agent_id`, `request_id` prefixed `terminal-answer:`, `keys`, `prompt`: the prompt the card showed, and `content` for a text row), never as `send_keys`, which bound native sessions refuse. The server reads the screen again and presses the keys only when it still shows that same prompt (keys move from the cursor, so they mean the chosen option only there) and they are one of its actions; otherwise it answers `error` with `code` `prompt_changed` and the screen's `prompt`. A text row's keys move the cursor there, the text is typed (tmux `send-keys -l`, so a text such as `Enter` stays text), and Enter follows only when `text_submits` (in a multi-select typing ticks the row, and Enter would untick it). The keys go through `tmux.Manager.AnswerPrompt`, whose guard (`verifyPromptAnswer`) is the delivery guard without the native refusal: the tool itself must be in front. About 400 ms later the server reads the screen again and replies `terminal_prompt_answered` with it. The card (`useTerminalPrompt`, `lib/terminalAnswer.ts`) stays up, its buttons held (**Answering…**), until the screen moves on: it closes when nothing is asked, shows the next prompt when another one is (so a several-question form is walked tab by tab, then its review's **Submit answers**), and says the terminal didn't take the answer when the same prompt is still there. A refusal's `error` (with the agent and the request, as every `send_keys` error now carries) is shown on the card. The card is hidden while the agent has a permission or question request open, since the terminal is then showing that same request, and counts toward **Waiting for you**. It works for every native agent kind. A terminal-backed session shows the same menu in `PromptBar`'s action list.

**Review briefings on the branch**: A branch can carry a review briefing for the pull request it will become: HTML pages under `.review/<branch-slug>/`, written by an agent with the review-briefing skill and shown on GitHub by the PR Review Briefings extension. Legato shows them in the agent's **Artifacts** panel before the pull request exists.

- **Which files.** `internal/engine/reviewbriefing` reads the agent's checkout (the directory its execution started in, else the task's recorded working directory). The base is `origin/HEAD`, else `main`, else `master`. The files are those under `.review/` that differ between the merge-base and the working tree, plus untracked ones: committed or not, and never a folder another pull request left on the base branch. The rule is the extension's.
- **Tabs.** Each HTML page is a tab after the artifacts (`Review`, `Review · Risks`; the folder too when there is more than one), the branch's own folder first and `index.html` first in a folder. The panel opens on the briefing when the agent has shown no artifact. The footer names the file and the branch; a page has no revisions, Download or Remove. The tab's ID is `review:<path>`, which no item can have.
- **Drawing a page.** `GET /api/agents/{task_id}/review-briefing/page?path=` returns the page inside JSON, with every relative `src`/`href` to another file of the briefing put in as a `data:` URL (a link inside `.review/` that leads out of it is not followed). `buildBriefingDocument` puts the same content security policy as for agent HTML first in the page's own head, and nothing of Legato's theme: a briefing has its own, light and dark. A link to another page of the briefing opens its tab (`legato/open-page`); a web link asks first, as in agent HTML. Code links show their path, as a briefing does without the extension.
- **Keeping current.** Nothing reports a change in a checkout, so `useReviewBriefing` reads the list again every 15 seconds and when the window gets the focus. A page's `version` is a hash of its content, so a rebuilt page is read again. A page that appeared or changed since the panel was last open on that agent counts toward the **Artifacts** switch's new mark (`useUnseenBriefingPages`, remembered in this browser); it never opens the panel by itself.
- `GET /api/agents/{task_id}/review-briefing` answers `{branch, base, pages: [{path, folder, label, version}]}`, and `{pages: []}` for an agent with no checkout.

**Images an agent read**: A `read` call on an image file (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.bmp`) is a row the person can open: the image is drawn under it, and a click on the image shows it full size until Escape or another click. The agent saw the image; without this the person sees only its name. Nothing is fetched until the row is opened, and the file is read again each time, since a screenshot is often written again under the same name. The file is on the machine Legato runs on, so the browser asks Legato's server for it: authenticated `GET /api/agents/{task_id}/image?path=<path>` (`internal/server/agent_image.go`; `POST` to the same address stores a pasted image, see the next paragraph).

- Any path may be asked for, because an agent's screenshots are seldom inside its worktree. A relative path is taken from the session's working directory, which the session's native endpoint reports; without one a relative path is `404`.
- What limits the endpoint is what it gives out: only a regular file of at most 25 MiB whose *content* is PNG, JPEG, GIF, WebP or BMP. The name does not count: a text file called `secret.png` is refused (`415`). SVG is refused, because it is a document, and one opened from Legato's own address could run script there.
- The response is `no-store` and `nosniff`, with a sandboxing content security policy. The browser draws it from a blob address, which is released when the row closes.
- It works for every native session (Claude Code, whose `Read` paths are absolute, and Chimera, whose paths may be relative). Codex has no read tool; it reads files with shell commands.

**Pasting an image for an agent**: An image pasted into an agent's message box, chosen with its **Attach image** button, or dropped on its composer (the native composer, which the Reeve's conversation uses too, and the terminal session's `PromptBar`) reaches the agent as a file. An agent tool takes a message as text, and each tool has a different way to attach an image, or none; every agent can read a file. So the browser gives the image to Legato (`POST /api/agents/{task_id}/image`, the image as the body), Legato stores it and answers with the file's path, and the path is put in the message where the cursor is. The person writes around it and sends as usual; the agent reads the path with its own tools, and its `read` row then shows the image (see Images an agent read).

- The file goes to `<system temp dir>/legato-<uid>/pasted-images/<task-id>/pasted-<UTC time>-<random>.<ext>`. The temporary directory is the one place every agent tool lets its agent read: Chimera's `read` takes the working directory or `/tmp` and nothing else. It is not the worktree, where the files would show up as changes.
- Only content that is PNG, JPEG, GIF, WebP or BMP is stored (`415` otherwise), up to 10 MiB each (`413`). The folder is `0700` and the file `0600`. A task keeps its newest 20 pasted images; older ones are removed when a new one is stored, because the temporary directory is often memory.
- A path that would start the message is put in as `Image: <path>` (`insertImagePath` in `web/src/lib/agentImage.ts`). Claude Code refuses a plugin's prompt whose text starts with `/` ("a text beginning with / would run a command as the user", checked after trimming), so a bridged Claude Code session never got a message that began with the path (LEG-151). A path the person types at the start still fails, and shows as not sent.
- A message from a terminal session's `PromptBar` carries a `request_id` (`terminal-message-…`), and an `error` answer for it is a toast with the server's reason (`Agents.tsx`). When the page has no connection the message stays in the box (`onSubmitMessage` returns false) with a toast. The server logs every message it could not deliver (`handleAgentMessage`), and every `message_failed` of a native agent (`logDeliveryFailure` in `internal/server/agent_delivery.go`, fed by the approval watcher's stream of each running native agent, so with no page open too), its reason quoted and cut and the message cut to its first 60 characters.
- A thumbnail above the message box stands for each pasted path still in the message; it goes when the message is sent or the path is deleted. A refusal is shown there in the server's words and leaves the message alone.
- A paste's images are read from `clipboardData.items` (`getAsFile()`), else `files`, once each. Text that comes with an image (its file name; a copy of cells and a picture of them) is still pasted, and the image is added beside it. A paste of text alone is left to the message box.
- **WebKitGTK** (the desktop app on Linux) fires the paste of an image with `clipboardData` empty: no types, items or files, whatever else is on the clipboard (checked on 2.52 under KWin Wayland and X11, LEG-135). So a paste that carries nothing asks `navigator.clipboard.read()` for an `image/*` item, which WebKit answers inside a paste event without its paste prompt. It needs a secure page; over plain HTTP there is no `navigator.clipboard`, and the attach button and drop still work. A browser that puts the image in the event never gets here.
- **Attach image** (`AttachImageButton`, first in the composer's tool row) opens `<input type="file" accept="image/*" multiple>`: on a computer a file dialog; in the Android app the system's picker (`ServerPage.onShowFileChooser`, `params.createIntent()`: the photo library and files, no camera yet); in a phone's browser also the camera. A chosen file that is not an image is refused by name ("notes.txt is not an image").
- **Drop**: files dropped on the composer box are attached; a drag of text is left to the message box. The box's border takes the accent colour while files are over it. The desktop app turns Tauri's drag-drop handler off for server pages (`disable_drag_drop_handler`), or the drop never reaches the page. A file dropped anywhere else is claimed by `keepFileDropsOnThePage` (`lib/fileDrop.ts`, installed in `main.tsx`) and shown as not droppable, so it never opens in place of the page, as a browser and, with the handler off, the desktop app would.
- **A task away on a worker** has its agent there, where a path on the main names nothing, so the main refuses the image (`409`, "images can't reach the agent from here: task X is away on vm-1, so send the image from vm-1's own page"). The main has no chat for such an agent: its card links to the worker's page, whose own server stores the image beside the agent.
- **In the sandbox** the task's folder is mounted read-only at its own path, over the sandbox's `/tmp`, and other tasks' folders are not. **Thinking in the native panel**: What an agent thought on its way to a reply or a tool call is a **Thinking** row: one quiet line that opens to all of it. While the thought is still arriving the line follows it; afterwards it shows how the thought began (a summary's title, for Codex). A thinking row is a step like a tool call: it joins the group of tool calls around it, so an agent that thinks between calls still gets one compact group, and a fold of earlier calls takes their thoughts with it. An edit that is the only tool call of its group still opens its diff, whatever was thought before it.

- It is part of the native protocol, not of one agent: `reasoning_text_delta {id, delta}` and `reasoning_text_done {id, text}` events, and in a snapshot a `{type: "reasoning", text}` part of an assistant message, ahead of that message's text and tool calls. `web/src/lib/nativeAgentSync.ts` reduces them to items of role `reasoning`; a thought replayed over a snapshot that already has it is not shown twice.
- How much there is to show is each tool's and each model's own matter:
  - **Chimera** streams what its model reasons, and keeps it in the session. Nothing to set up.
  - **Codex** has a summary of the model's reasoning only when Codex is told to make one: `model_reasoning_summary = "detailed"` (or `"concise"`) in `~/.codex/config.toml`, or `adapters.codex.launch_args: ["-c", "model_reasoning_summary=\"detailed\""]`. Without it Codex reports that the model reasoned and nothing of what. See [Codex native integration](codex-native.md) § Reasoning.
  - **Claude Code** models keep their thinking to themselves: the block they return is signed and, for Opus 5.5, Sonnet 5.5 and Haiku 5.5, empty. What does show is the short summary a model writes now and then during long work. See [Claude Code native integration](claude-code-native.md) § Thinking.

**Native composer prefixes**: The native panel mirrors Chimera TUI syntax for idle turns. A path with spaces is written in double quotes (`@"My Vault/today.md"`) or with its spaces escaped (`@My\ Vault/today.md`). `@path` grants read access and attaches a bounded file/directory snapshot (line-numbered files up to 2,000 lines / 100 KiB; directories up to 200 entries). `#path` grants write access and attaches the same snapshot. Attachment tokens are parsed and expanded server-side through the Chimera interaction adapter; only idle `SendMessage` triggers expansion, while `QueueMessage` sends plain text. `!command` executes a shell command in the session CWD with a 30-second timeout and 1 MiB output limit via `POST /api/agents/:task_id/chimera/bang`, appends the formatted result to Chimera session context, and resyncs the panel. While busy, `!` commands enter a visible browser-local queue and execute after `run_finished`. Tool calls made back to back, with no reply between them, are drawn as one compact group of one-line rows; a run longer than six shows its latest five under an **N earlier tool calls** row that lists the tools those calls used and expands the rest. A row opens for inspection on click. An edit that stands alone opens its diff by default; other tools, and every call inside a group, start collapsed. A `spawn_agent` call keeps its own subagent card and ends the group before it. The feed scrolls to the latest message on initial hydration and after explicit send/queue actions.

**Resize protocol**: Web clients send `resize` messages (initial + on container resize + 5s heartbeat for TTL). Server computes min of all web client sizes + attached tmux terminal clients (`tmux list-clients -t <session>`). Only resizes if dimensions actually changed (dedup via `appliedCols`/`appliedRows`). Stale clients expire after 10s TTL. On last client disconnect, resets `window-size` to `latest` so tmux auto-sizes from remaining terminal clients.

**Prompt detection**: `prompt.Detect` runs on captured pane output after 500ms debounce following output, from the mirror stream or, for an agent in terminal mode, from its terminal (see [Terminal mode](#terminal-mode)). Classifies as `tool_approval` (Yes/Always/No buttons), `plan_approval` (Accept/Reject), `free_text` (text input), or `menu` (any other numbered menu with a cursor on one option; one action per option). Only shown when agent activity is `"waiting"` (gated on hook state, avoids false positives during active output). Dismissed prompt type tracked in `dismissedPromptTypeRef` — suppresses re-detection of same prompt until user submits text, switches agents, or manually re-detects. Per-agent prompt detection toggle in overflow menu (overrides global default from `legato:prompt-detection` localStorage). Actions rendered as vertical keyboard-navigable list (`ActionList` component): j/k or arrows to navigate, Enter to confirm, Escape to dismiss. On-demand detection via `detect_prompt` WebSocket message (Re-detect prompt in overflow menu).

**Key sending**: `send_keys` WebSocket message. All terminal sends use the foreground/lifecycle guard described in [Agent states](agent-states.md). Bound native text submissions and C-c use native message/interrupt routes; other raw native keys are refused, never typed. Text ending in `\n` → literal text via `tmux send-keys --` then named `Enter`. No `\n` → space-separated named keys sent in sequence (e.g. `"Down Enter"` → two `SendKey` calls). Used by prompt action buttons, Mode (BTab), Stop (Escape), and free text input.

**Runtime response validation**: Use Zod when frontend API boundaries need runtime schema checks, rather than duplicating interfaces in handwritten guards. Derive TypeScript types with `z.infer` from the same schema. `web/src/lib/jobClones.ts` validates the clone-list envelope and entries this way; malformed responses surface validation errors, not empty inventories. Object schemas tolerate extra server fields for forward compatibility. Validate at the boundary, not again in hooks or components consuming the parsed result. Existing API helpers need not be migrated as part of unrelated changes.

**WebSocket synchronization**: Resource messages are mapped centrally to server-scoped query keys (`invalidationsFor`, `web/src/lib/querySync.ts`) and coalesced per key (`coalesce`): a burst is one refetch once messages stop for 75 ms, and a stream that never stops still refetches every second (`MAX_WAIT_MS`). A reconnect revalidates each observed snapshot once to recover missed events. While actively observed, navigation summary also refetches once per minute as a foreground convergence fallback for missed or absent events; other shared snapshots do not poll. HTTP remains authoritative; websocket messages synchronize the shared cache rather than replacing initial loads.

`GET /api/agents/{task_id}/conversation[?limit=N]` (`internal/server/agent_conversation.go`) is what a tile of a native agent reads: `{task_id, status, entries[], permission, question, context_used, context_window}`, where an entry is `{kind: "user"|"assistant"|"tool", text, tool?, command?, state?, thinking?, subagent?}`, plus `live?` when the agent is writing. The extra fields are for a reader that wants more, and the entries are the same without them: `thinking` is the thought behind a step, on its first entry (from the snapshot's `reasoning` parts); `subagent` (`{purpose, status, tool?, text?}`) is the subagent a call started, with its newest call (from the call's `subagent.events`); `live` (`{thinking?, reply?}`) is what the agent is writing now, which no entry holds yet (the endpoint's `streaming`, else a stored thought with nothing after it while the agent is running). The ensemble does not show them; the glasses do. **Session history API** (`internal/server/session_history.go`, over `service.SessionHistoryService`; the Reeve reaches it with `legato_api`): `GET /api/sessions?q=&agent_kind=&state=&task=&repo=&since=&until=&cursor=&limit=` returns `{sessions, next_cursor}`, 50 entries unless `limit` says (200 at most). `q` is words: each becomes a quoted FTS5 phrase matched as a prefix, all required (`sessionSearch`; quotes, `*` and lone operators are dropped, so nothing typed is FTS5 syntax), ranked by bm25; without `q`, the most recently used first. `state` is `running`, `interrupted`, `ended` or `away`; `since` and `until` are RFC 3339 times on `last_seen_at`; the cursor is opaque (an offset). Each entry has the conversation's tool and provider session ID, task ID and title (the task's own while it exists), `task_exists`, `task_archived`, slot, `ephemeral`, `reeve`, folder, repository and branch, `state` with `end_reason`, first and last messages, first and last seen, `run_count`, `source`, `transcript_state`, and `restorable`, `new_task_only`, `reason`, `can_start_fresh` (`SessionHistoryService.restorability`, the checks a restore makes in its order: running, away, tool not configured, folder gone or transcript gone (both offer a fresh start); then a task gone or archived or a named slot's conversation is restorable into a new task only; a Reeve entry is restorable). `GET /api/sessions/{id}` adds `runs` (execution, start, end, end reason, `sandboxed` when known, engram, resources). `POST /api/sessions/{id}/restore` with `{target: "task"}` starts one again in its task (see [Claude Code native integration](claude-code-native.md) § Task launch resumption), and with `{target: "new_task"}` in a new task of the original's kind (`SessionHistoryOptions.NewTask`, `service.BoardNewTask`: an ephemeral task for an ephemeral original, else a local card titled as the original in its workspace when that still exists (`agent_conversations.workspace_id`) and the board's first column), to which the conversation moves before its agent starts; when the start fails, the task is removed and the conversation moves back. It answers `{status, task_id}`, the task the conversation runs in. With `fresh: true` (and `target`, optional `working_dir`) it starts a **new** conversation in its place instead (`SessionHistoryService.StartFresh`, `agentService.StartFresh`): the same tool, sandbox choice, engram (new session) and resources, in `working_dir`, else the old folder while it exists (`400` when neither is a folder), with a `[legato handover]` first message (`handoverNote`: the title, folder, repository and branch, when it last ran and why it ended, the first prompt and last message as clipped, and the transcript path while it is there). It is refused while the conversation runs, for a Reeve conversation, and as a restore is for an away task or a tool not configured; a task that cannot take it starts it in a new task. `can_start_fresh` is true for an entry whose folder or transcript is gone and for a Chimera one (whose store Legato cannot look into), false while it runs. The other guards apply to both; a Reeve conversation is never restored into a new task. A refusal is `409` with `{error, new_task_possible?, can_start_fresh?}`. `DELETE /api/sessions/{id}` forgets one: the entry, its runs and its search row, leaving the tool's transcript and the task's saved conversation; `409` for one running or interrupted. `400` for a query it cannot read, `404` for no such session, `503` without a history. The GETs are Read routes and Forget a Change route. Wired for both web servers by `wireSessionHistory` (`cmd/legato/session_history_runtime.go`), with whether a tool is configured (`AdapterFor`) and whether a task is away (`OpenAwayTask`).

**Remote** (`/remote`, `web/src/pages/RemotePage.tsx`): managed job clones on the currently selected Legato server, not a cloud-provider dashboard or a list of the person's repositories. Reached from the desktop rail and **More › Tools › Remote** on a phone; More stays active on this route. Settings › Agents keeps an always-visible **Open Remote** link at `#job-clones` for old links, with no duplicate clone inventory and no `fresh_clones_enabled` gate. That flag only controls the spawn dialog's Folder | Clone switch.

The inventory names each clone's repository, current branch, server path, linked tasks, tracked-agent occupancy, last use and scheduled removal when set. `unpushed` is the legacy wire name for **local tips absent from cache** (branch tips and detached HEAD), not proof of whether work reached GitHub: the cache may be stale. A comparison problem is shown as unavailable, never as a clean result. **Working-tree changes: not checked** means exactly that; neither modified nor untracked files are inspected. Refreshing the inventory does not fetch GitHub. Removal asks for confirmation, warns that the entire folder (including changed, untracked and ignored files) is deleted, and is disabled while an agent works in the clone. The dialog uses newer inventory details when available. Retention is unchanged: `repository_cache.keep_idle` (default 7 days, `0` disables idle cleanup), with a further 7 days for tips absent from cache and a task note; an existing removal deadline still expires. The page explains these limits under **About status and automatic cleanup**. This is not a guarantee that uncommitted files are preserved. `GET /api/job-clones` (`{clones: [...]}`, most recently used first), `DELETE /api/job-clones/{id}` (`204`; `409` while occupied; `404`); `internal/server/job_clones.go`.

`useJobClones` uses a server-scoped query key. Page entry, Refresh, successful removal, `agents_changed`, and reconnect refresh the inventory without polling. A server change closes confirmation; pending requests remain bound to their original server. List failures and malformed responses are errors, not empty inventories, including in spawn dialogs. A failed refresh retains the last successful inventory with a warning and its original check time.

**Repository guidance** (Settings › Repositories, `RepositoryGuidanceSettings`, `#repository-guidance`): the guidance agents get for the repository they work in (see [Configuration](config.md) § Config, `agents.guidance`), that of `config.yaml` first (marked, changed there), then that saved here, each with its repository (`host/owner/name`) and text. **Add guidance** takes a repository (`owner/name`, `host/owner/name` or a remote address) and the text; **Edit** changes a saved one's text; **Remove** (after asking) forgets one saved here. `GET /api/settings/repository-guidance` (`{guidance: [{repo, text, configured}]}`), `PUT` `{repo, text}` (sets it, replacing any; `400` for what is not a repository or empty text, `409` for a repository `config.yaml` sets), `DELETE ?repo=` (`404` for none saved here, `409` for `config.yaml`'s); `503` without the service; `internal/server/repository_guidance.go`.

**Repositories** (Settings › Repositories): every repository Legato offers, those of `config.yaml` first (marked, changed there), then those added here, each with its GitHub name, base branch and folder. **Add repository** takes a name, a GitHub repository (`owner/name`, or its address), a base branch and an optional folder on the server; **Remove** (after asking) removes one added here. A repository the GitHub credential does not list is marked **Can't be cloned** with the reason, which names `owner/*`. One it lists says how its copy in Legato's cache stands (`cache` in `/api/repositories`, live through `repository_cache`): **Not copied yet**, **Copying** or **Fetching** with git's progress and a bar, **Copied** with when it was last fetched, or **Copy failed** with git's reason. Legato copies each repository when it starts (the broker owner) and each one added here at once. A change refetches `/api/settings`, which the spawn dialogs and the workflow form read. `GET /api/repositories` (each with `configured`, and `clone_problem` when it cannot be cloned), `POST /api/repositories` (`400` in the service's words), `DELETE /api/repositories/{id}` (`404` for one not added here); `internal/server/repositories.go`. `/api/settings` and `/api/workflows` name the repositories as they are at each request.

**Skills** (Settings › Agents, `#skills`, `SkillsSettings` in `web/src/components/settings/`, `web/src/lib/skills.ts`): the skills folder, then a row per skill with its name, description (or its error, marked **error**), path and a toggle (**Give agents <name>**; none for a skill with an error). **Engram bindings** (Settings › Agents, `#engram-bindings`, `EngramBindingsSettings`): the probe's state (engram's version, binary and store; or "engram was not found", or off), then one row per place with bindings, shown by its key without the prefix (`github.com/cpave3/legato`, or a folder path) and its kind, with its bound engrams: the default marked **default**, one engram no longer lists marked **missing**. **Make default**, **Unbind** and **Clear the default**; no adding, since binding happens through the spawn dialog's Remember. `POST /api/agents/spawn` and `POST /api/tasks/{id}/agent` both expand a `working_dir` that starts with `~`. Either takes `repo` (`owner/name`), `ref` and `branch` instead of `working_dir`: the agent then starts in a fresh clone of the repository made for it, on `branch` (`legato/<task id>` when empty; GitHub's branch of that name when it exists, else made from `ref`, else from the default branch). A task that already has a live clone of `repo` works in that one again, on its branch unless `branch` names a new one. A chapter's narration is drawn as Markdown, as the TUI draws it. Narration, answers and the captured plan can show image files, drawn from Legato's copies (`/review-images/`, `/plan-images/`) and opened full size on a click; see [Plans](plans.md) § Image files. Transcript messages render safe GitHub-flavored Markdown (plain text remains valid), and delivered questions give agents a quoted-heredoc `legato review answer <step-id> --file -` command that preserves Markdown without shell expansion. Completed tours stay out of the queue until visible follow-up work exists; when new commits or annotations arrive after a chaptered review, those unreviewed follow-up steps appear alongside the previously reviewed chapters instead of being hidden. The Q&A pane defaults wider and can be resized from its left edge (or with Left/Right on the separator). Its multiline composer sends with Ctrl/Cmd+Enter and, when voice is enabled, can append an editable transcription-only draft without bypassing the review transcript. Each hunk has a local **Viewed** checkbox that collapses/restores its lines, and the step-level reviewed action remains sticky at the top of the scrolling diff pane.

### Terminal mode

An agent that runs in tmux (any agent without a native panel) opens on the Agents page as `LiveTerminal`: xterm.js with stdin on, connected to `GET /api/agents/{task_id}/terminal?cols=&rows=&token=` (`internal/server/terminal.go`). There is no switch: the read-only mirror (`TerminalPanel`: capture-pane snapshot + pipe-pane stream) is kept only for the participants of a swarm's command centre. The server attaches a real tmux client on a pty (`tmux.Manager.AttachPTY`, `internal/engine/tmux/attach_pty.go` with `openpty_linux.go`/`openpty_darwin.go`, `golang.org/x/sys/unix`, no cgo) and copies bytes both ways: binary frames are terminal bytes, a text frame `{"type":"resize","cols","rows"}` resizes the client. One client per connection; closing it detaches and leaves the session. tmux draws the screen and keeps the scrollback, so xterm's own `scrollback` is 0. **Refresh terminal** in the agent's menu reconnects it (a new client, which tmux redraws in full).

`AttachPTY` sets three options on the session: `status off` (so pty rows are window rows), `window-size latest` (the most recently active client wins, as in native tmux) and `mouse on` (the wheel enters copy-mode; touch drags are sent as SGR wheel reports). These stay set after the web client leaves, so a desktop `tmux attach` of the same session has mouse mode on and no status line. The route carries its token in the query like `/ws` (`isTerminalPath`). `cmd/legato/terminal_runtime.go` wires `SetTerminalAttacher`; without it the route answers 503.

**Prompts.** With no mirror stream, the terminal handler runs prompt detection itself: once its output has been quiet for `promptDetectDelay` (500 ms, the stream's delay too) it captures the pane and broadcasts `prompt_state` to every `/ws` client (`Server.announcePrompt`), which also applies the activity a blocking prompt implies, as the stream does.

**The frame.** The terminal sits inset in a frame (16 px from the edges, 8 px on a phone; 10 px corners, 8 on a phone) with a strip along its top: the tmux session name, and the size while it has focus (**Click to type**, **Tap to type** on a phone, without). Focused, the border takes the accent ring. When the socket drops, the strip says **Reconnecting** and the seconds to the next try (backoff 1 s doubling to 10 s), the screen dims and **Retry now** reconnects at once.

**Message box.** On a desktop outside a swarm there is no PromptBar: the terminal is the one place to type and the agent menu is in `AgentChatHeader`. A phone keeps the bar, with `TerminalKeys` above it: **Esc**, **⇧Tab**, **↑**, **↓** sent as `send_keys` (`Escape`, `BTab`, `Up`, `Down`), and **Ctrl**, which arms and sends the next character typed anywhere (a capturing `beforeinput` listener, so the message box and xterm's text box alike) as `C-<char>`. A swarm keeps the bar because it holds the menu there. Native (chimera/claude-bridge) agents keep their own panel.

### Route classes

Every method of every route has a class and a plain description, in `internal/server/route_class_table.go` (`routeClassTable`), beside the mux: **read** (changes nothing), **change** (needs an approval when an agent asks for it), **risky** (touches security, availability, or cannot be undone; can need a signed approval), **never** (refused whatever the approval: deciding approvals, answering an agent's permission prompt, enrolling or removing approval devices, reading or opening a pairing request and pairing (`/api/pairing` GET and POST, `/api/pair/*`: a request's phrase authenticates the exchange that hands out the web token), typing into an agent's terminal or running `!` commands in it, and `/ws`, which carries keys to terminals). The classes are the Reeve's (see the spec, LEG-106 Part 4).

- **Lookup.** `ClassifyRequest(r)` matches a request to its entry the way the server's mux matches it to a handler (each entry is registered as `METHOD pattern` on a `ServeMux` of its own). A `GET` (or `HEAD`) that no entry matches, or that only the catch-alls `/` and `/api/` match, is `read` with `Known: false`: Legato does not serve it, so it answers 404 (below) and reads nothing. That holds only when the path is not classed for another method (`servedForAnotherMethod`): a `GET` on a route the table has only `POST` for stays `risky`, since its handler would decide what a `GET` does. Any other request no entry matches is `risky` with `Known: false`. `PUT`/`DELETE /api/config/settings/{key}` take the setting's class from the registry, and `/api/config/lists/{list}/{name}` the list's.
- **The test.** The mux records every pattern it is given (`routeMux`, `Server.routes`). `TestEveryRouteHasAClass` fails for a served pattern with no entry, a method-carrying pattern whose method has none, or an entry for a pattern no longer served. A new route needs its entries. `TestEveryServedRouteHasAClassForGET` fails for a served pattern whose `GET` would pass as a route Legato does not serve, and `TestEveryGETIsAReadUnlessListedOnPurpose` for a `GET` entry that is not `read` and not in `getNotRead` with why (the pairing phrase, the terminal socket, `/ws`, the voice session, the OAuth callback).
- **Not served.** `/api/` itself is a route (`notServedHandler`): a path under it that nothing else serves answers `404 {error: "not_found", message}`, naming the manual's API page, and never the web UI's page.
- `RouteClasses()` lists the table. The manual's `reference/api` page is written from it (`apiReference`; see [The Reeve](reeve.md) § What it knows): after changing a route, run `go test ./internal/server -run TestTheAPIReferencePageIsCurrent -update`.

The selected card is lifted with an accent border. ### Handing off a task

A main instance's board hands a task to a paired worker and shows it away there ([Integrations](integrations.md) § Handing off a task; spec LEG-15 § Web UI, decisions LEG-8). Built in LEG-20: the form, the lane and the read-only panel. The folded rail, drag to hand off and the phone's Away section are LEG-28 (below); live state in the lane LEG-24; Return and Recall LEG-25 (§ Returning and recalling below); Take back LEG-26.

- **Board API.** `GET /api/board` lists `workers: [{instance_id, name, address, last_pull_at?}]`, the workers this main is paired with (`[]` when none; `Server.boardWorkers` from `SetWorkers`). An away card keeps its column in the API and carries `away`: `{worker_instance_id, worker, handoff_id, worker_task_id, purpose, kind, repo, branch, agent_kind?, left_column, handed_off_at, state?, failure?, state_at?, url?}` (`AwayResponse`, from `service.AwayTask`). `state` is the worker's state as last heard (`pending`, `in_progress`, `done`, `failed`, `returning`); today that is the state the worker accepted it in, which `HandOff` keeps as the away task's first `last_summary` (`service.HandoffSummary`), and LEG-24's summary rows replace. `url` opens the task on the worker: the summary's own link when it gives one, else `<worker address>/board?highlight_task=<worker task id>`. A handoff publishes `EventCardsRefreshed`, so every board refetches through `cards_changed`.
- **The route.** `POST /api/tasks/{id}/handoff` `{worker, purpose, kind?, branch?, repo, agent_kind}` (`branch` names the pushed branch for `kind: "pushed-branch"`) (`internal/server/away.go`, `SetMainHandoffs`, wired with `SetWorkers` by `wirePairing`) calls `TaskHandoffService.HandOff` and answers 201 `{away}`. A refusal is `{error}` in the service's words: 400 for a bad request, an unknown worker or no such task (404); 409 for a task already away, an agent running here or an old worker ("update the worker"); 422 for a worker's refusal ("vm-1 refused the handoff: this worker does not know the agent tool …") or a worker without the sandbox ("vm-1 cannot run agents in Legato's sandbox …"); 502 for a worker that did not answer ("vm-1 did not answer, so nothing was sent").
- **The lane.** `withAwayLane` (`web/src/lib/away.ts`) takes each away card out of its column and adds a column marked `away: true`, named **Away**, after the others, ordered by worker; it is there once a worker is paired. `BoardGrid` draws it as `AwayLane` (`web/src/components/board/AwayLane.tsx`): a header with the count, then a group per worker (`awayGroups`: each paired worker in the server's order, then any worker an away card names that is no longer paired), whose header has the worker's name and **Open** (its address). A group with nothing away says so. Each away task is the board's own card (`BoardCard`, its away variant when `card.away` is set; LEG-414): the header adds the worker (`cardSource`: `Burnlite · LEG-390 → vm-1`); its PRs are drawn as at home (one line, or the stack block) without the macro button, since the worker's author fixes them; and one strip at its foot, `awayStrip` (`web/src/lib/away.ts`), says the review while one runs, else the away state, in the card's words and glyphs: `◐ Review pass 2 · author fixing` with `3 blocking · 1 comment · 1 check` on the right; `◐ Review approved · waiting for 2 checks`; `✓ Review done · approved`; `◆ Review stuck after pass 3: <reason>` in full on the needs tint with an amber edge; `⚠ vm-1 unreachable since 21:40`, `✕ Lost on vm-1: <why>` and `⚠ vm-1 no longer accepts this main` on the error tint with a red edge; otherwise `awayLook`'s state (◌ Starting, ● Running, ◆ Needs you, ○ Idle, ■ Agent ended, ‖ Interrupted on worker, ✓ Done, ✕ Failed: reason, ↩ Coming back, → Handed off) with `from <column> · <time handed off>`. The card's actions (`AwayRowActions` with `recall={false}`) sit under the strip; Recall is in the card's ⋯ and right-click menu (**Recall…**, `RecallDialog`) for every away task that can be recalled, and the task panel keeps it. An away card cannot be dragged. Cards are part of the cursor model: `j`/`k`, a click and `Enter` select and open them as in a column. `AwayLane` takes `groupExtras(worker, cards)` and `rowActions(card)` for what LEG-24 and LEG-25 add (reachability, Return all done, Return, Recall, Take back). With nothing away the lane folds to a rail like an empty column (`isColumnCollapsed` treats it as one, so `z`, a click on the rail and `h`/`l` behave the same); `BoardGrid` draws that rail with `BoardColumn`'s, coloured as the lane (`border-lw-accent-ring`), and opens the lane again as soon as a task is away.
- **Drag to hand off (LEG-28).** A card dragged from a column onto the Away lane or its rail opens the Hand off form for it: `AwayLane`'s and the rail's `onCardDrop` (both from `useDropTarget` in `web/src/components/board/useDropTarget.ts`, which columns use too) reach `BoardGrid`'s `onCardHandOff`, and `Board.tsx` (`handleDragHandOff`) opens `HandOffModal` as the menu does. A drop never hands off by itself and never moves the card. A card already away is not offered the form again (lane rows are not draggable, and the handler ignores an away card); a card whose agent runs here opens the form with its notice and no **Hand off** button. The lane takes drops only while a worker is paired.
- **On a phone (LEG-28).** `MobileBoardList` leaves the Away lane out of its chips and draws `MobileAwaySection` (`web/src/components/board/MobileAwaySection.tsx`, region "Away on workers") above them: one folded line per worker that holds away tasks, "vm-1 · 6 away · 2 done" (the done count left out at none), with that worker's **Return all done (N)**. Tapping a line opens it (`aria-expanded`): the worker's `WorkerReach`, then its tasks, each the same away card as in the lane with its actions, and a long press opens its menu. Tapping a card opens its details (`onCardClick` with the Away lane's column index). A highlighted away task (`?highlight_task=`) opens its worker's line. With nothing away there is no section. An away card is drawn only in the lane or this section, never in the column it left.
- **Live state (LEG-24).** The main hears each away task change over its worker's Events connection ([Integrations](integrations.md) § Live away state) and publishes the usual board events, so the lane refetches through `cards_changed`. `away` also carries `activity`, `worker_column`, `worker_title`, `branches`, `lost`, `lost_at`, `worker_unreachable_since`, `worker_refused_at` and `view`; each of `workers` carries `unreachable_since` and `refused_at`. `awayLook` draws `view` first: Starting, Working, Needs you, Idle, Agent ended, Interrupted on worker (`interrupted`: the worker's summary reports `activity: "interrupted"` while the card has an interrupted agent and none running; Recall is offered, as for Agent ended), Done, Failed: reason, Coming back, Unreachable, Lost on worker, Not accepted; an older server's `state` alone still works. The pill's tooltip (`awayDetail`) says why: the lost reason, since when the worker is unreachable, that it no longer accepts this main. `BoardGrid` gives each group's header `WorkerReach` through `groupExtras` (`workerReach`: "pulled 2 min ago", "unreachable since 21:40", "no longer accepts this main; pair again", "not pulled yet"), which moves on every 30 seconds by itself. Settings › Connections › Workers says when each worker was last pulled and whether it is unreachable or refuses this main; a worker's Settings › Connections › Main instances shows each main's last pull (refreshed by its Events connection) and open handoffs. The board's sync also reconnects and pulls every worker.
- **PRs while away (LEG-29).** The main tracks an away task's PRs itself from the branches its worker reports ([PR tracking](pr-tracking.md) § Away tasks), so an away card carries `pull_requests` like any card. Its row in the lane sums them up under the state line (`awayPRSummary` in `web/src/lib/awayPullRequests.ts`, `data-testid="away-prs"`): "PR #12 · draft", "3 PRs · 1 merged · 1 draft · 1 ready · #14 CI failed", in red when a ready PR has what Attention calls a merge blocker. The task panel's away section lists each PR under **Pull requests** (`AwayPullRequests`, with `ChecksMark` and `ReviewMark`): number, draft, ready, merged or closed, checks, review, its branch; then each reported branch (`away.branches`) whose PR the main has not found as "no PR yet", or "No branch pushed yet". The panel's general PR row is left out for an away card. An Attention item about an away task (a Merge blocker) opens `/board?highlight_task=<id>`, which selects its row in the lane and shows its panel.
- **The form.** `HandOffModal` (`web/src/components/board/HandOffModal.tsx`) opens from the card's ⋯ and right-click menu (`CardContextMenu`'s **Hand off…**, shown when `canHandOff`) and from the task panel (**Hand off…**, `BoardTaskPanel`'s `onHandOff`). It reads `GET /api/settings/workers` (a worker without the sandbox is listed but cannot be chosen) and `GET /api/adapters` (the default tool first, never `shell`), and offers the settings' repositories that have a GitHub name (a field for `owner/name` when there are none). **No repository is preselected**: the select starts on a disabled "Choose a repository…", resets to it each time the form closes, and **Hand off** waits for a choice, so work cannot go to a repository the person did not pick. The layout fits a phone: the Purpose and Start from options stack below `sm` (side by side from it) and their notes wrap; fields are 16 px tall-target on a phone (no iOS zoom); the panel is at most the viewport high, its body scrolls and its footer stays in view. Purpose is Make a change or Find out; Start from lists `startChoices`: A new branch (`legato/<task id>`) or A pushed branch, which shows a **Branch** field and sends `kind: "pushed-branch"` with `branch` (trimmed; **Hand off** waits for a name). The worker fails the handoff later, not the form, when GitHub has no such branch: the lane's pill says "Failed: branch not on GitHub…". A task whose agent runs here gets a notice and no **Hand off** button. A refusal is shown in an alert, the form left open. **The worker's advert (LEG-227).** With a worker chosen, the form reads its `advert` from `GET /api/settings/workers` (`web/src/lib/workers.ts`): a worker with `cannot_take_handoffs` (or no sandbox) is listed with the reason and disabled (`handoffBlock`); the repositories it cannot clone are disabled with "<worker> can't clone it" and those only it names are added as "on <worker> only" (`advertCanClone`, `workerOnlyRepositories`; a `null` list is not second-guessed); the agent tools are those installed there that run with prompts off, its default first (`handoffTools`; this Legato's own without an advert), and the choice follows the worker's default until the person picks one (`toolChosen`); and a warning names the skills and MCP connections on here (`GET /api/settings/skills`, `GET /api/settings/mcp/connections`) that it lacks (`missingOnWorker`; a worker without Legato's agent tools is not warned of but blocked, since it refuses every handoff). Resources are not compared: they are machine-local (the milestone's decision), and a worker's resources of the same name may hold other paths, so a name match would claim a sameness it cannot know. Names a worker adds to the repository list must be a GitHub `owner/name`. `TaskHandoffService.HandOff` reads the advert again first (`WorkerService.RefreshAdvert`; a failed read keeps the stored one), since a worker without away tasks has no connection to refresh it, then refuses a repository the advert does not list before sending (`HandoffAdvert.CanClone`, `ErrWorkerRefused`, "vm-1 can't clone other/thing: its GitHub credentials do not list it"), for API clients such as the Reeve.
- **Read-only while away.** The task panel of an away card shows its state, worker, purpose, where it started, branch, repository, the column it left, when, and **Open on <worker>**; the description is headed "read-only while away", and the agent action, **Move** and **Hand off…** are gone. The menu of an away card offers **Open details** and **Open on <worker>**. `DetailPanel` takes `away`: a banner with the worker, the state and **Open on <worker>**, and no edit, move, delete, link-PR, worktree or agent controls. The board's own keys (`m`, `d`, `p`, `t`, and in details `t`, `e`, `m`, `D`) and a drag toast the refusal instead; the server refuses them too.

Settings › Connections › Workers explains handing off while no worker is paired (`WorkersSettings`).

### Returning and recalling

Away tasks come home from the Away lane and the task panel ([Integrations](integrations.md) § Return and recall, § Take back, Drop and Leave; built in LEG-25 and LEG-26).

- **What each row offers.** `awayActions(away)` (`web/src/lib/awayReturn.ts`) says which of Return and Recall a row shows, from `view` (else `state`): **Return** for `done` and `coming_back` (a return under way, pushed on); **Recall** for `failed` and `ended`, and, after a confirm dialog, for `starting`, `working`, `needs_you` and `idle`, whose agent may still be at work ("Recall K7Q2?": "Its agent on vm-1 may still be working. Recalling stops it and brings back what there is so far"; **Recall now**); only **Take back** for `unreachable`, `not_accepted` and `lost`, always after a confirm dialog ("Take back K7Q2?": why it cannot come back with its results, that its notes, branches and edits stay on the worker, and that the worker is told to stop its agent and archive its card when it can be reached; **Take back now**). A failed handoff offers only Recall. The main never takes a task back by itself.
- **Where.** `AwayRowActions` (`web/src/components/board/AwayActions.tsx`) is each lane card's `rowActions` (without Recall, which is in the card's menu) and the task panel's away section (`BoardTaskPanel`'s `awayActions`); `ReturnAllDoneButton`, "Return all done (N)", is in each worker group's header (`groupExtras`, after `WorkerReach`) while the group has a task done there (`doneOnWorker`), followed by `WorkerGroupMenu`, the group's ⋯ menu: **Open on worker** and **Remove…**, which asks with `removeWarning` and calls `removeWorker`. `BoardGrid` draws them when given `baseUrl`; `Board.tsx` passes it, and `onAwayNotice`, which toasts "K7Q2 is back in Done", "K7Q2 is back in Ready, without its results", "2 tasks back from vm-1", "Removed vm-1: 1 recalled, 1 taken back", or the refusal.
- **Calls.** `returnTask`, `recallTask`, `takeBackTask` and `returnAllDone` post to `POST /api/tasks/{id}/return`, `POST /api/tasks/{id}/recall`, `POST /api/tasks/{id}/take-back` and `POST /api/workers/{instance_id}/return-done` (`removeWorker` in `web/src/lib/workers.ts` sends `DELETE /api/settings/workers/{instance_id}`), and throw the server's words (shown under the buttons in an alert as well). Once a task is home, the server publishes `EventCardsRefreshed`, so the board refetches through `cards_changed` and the card is back in its column.
- **Notes.** A note that came back from a worker (`source` `worker`) is headed "From the worker" in the task's Notes tab (`TaskActivityTabs`), and on a worker, a note the main sent (`source` `main`) "From the main".

### Swarm controls

The web PWA supports the full user-driven swarm control surface:

**Starting a swarm.** The agents view has a "Start Swarm" flow that opens a working-directory input modal, calls `POST /api/swarm/start`, and spawns the conductor session. Board task detail also shows **Start swarm** with the parent task fixed and a directory default resolved as `task worktree → remembered task directory → configured default`. A successful task launch navigates to `/agents?task=<parent-id>` and selects the conductor when it appears. An existing conductor changes the task action to **Go to swarm**.

**Plan approval.** When the conductor calls `legato swarm propose-plan`, the server broadcasts a `plan_proposed` WebSocket event to all connected web clients. Each client opens a modal showing the plan summary and sub-task list. The user can:
- **Approve** (`y`) — sends a `plan_verdict` WebSocket message with status `"approved"`; the conductor proceeds to dispatch workers.
- **Reject with notes** (`n`) — opens a text input for notes, sends `plan_verdict` with status `"rejected"`; the conductor revises the plan based on the natural-language feedback.
- **Dismiss** (`Escape`) — closes the modal without sending a verdict; the conductor remains blocked on `BroadcastRequest` and the user can re-trigger proposal from the conductor pane or TUI.

The modal does not include in-browser YAML editing (v1). Users who need surgical edits either reject with detailed notes or fall back to the TUI overlay which supports `e` to open `$EDITOR`.

**Extension plans.** When a conductor calls `legato swarm extend-plan` (or the server receives `plan_extension_proposed` over WebSocket), the modal title changes to "Extension plan — append to existing swarm". The rest of the approval flow — approve, reject with notes, dismiss — is unchanged. Web clients track whether the current modal is an extension via the `mode` field on `plan_proposed` IPC events.

**Cancel swarm.** The board detail panel (`DetailPanel.tsx`) shows a red "Cancel swarm" button when the card has active swarm stats or a working directory. Clicking it opens `CancelSwarmModal.tsx`, which confirms that the action kills the conductor + all live workers, deletes sub-tasks, and clears swarm state. Killing a conductor from the Agents dot menu or right-click menu routes through the same full swarm cancellation. The card itself and its history remain.

**Per-worker action menu.** Each agent entry in the sidebar has an overflow `⋯` button that opens a role-appropriate menu:
- **Worker** → Send message (free-text input → `POST /api/swarm/message`), Close worker (`POST /api/swarm/close`)
- **Conductor** → Send message, Finish swarm (`POST /api/swarm/finish`)

**Swarm command center.** Selecting any swarm participant switches the Agents page from the solo layout to a swarm-level view. Desktop keeps the conductor in the primary pane and shows every status subtask in a scrollable worker area, including queued or terminal workers without sessions. Selecting a live worker expands one interactive worker pane beside the conductor. Compact tmux cards poll bounded plain-text captures from `GET /api/agents/{task_id}/preview`; they never subscribe to terminal output or report dimensions, so they cannot shrink the real tmux pane. Native Chimera compact cards use status metadata and expand into the existing native panel. On narrow screens, one participant picker controls one interactive pane. The shared prompt bar always targets the focused interactive participant.

**Swarm event log.** A collapsible "Swarm events" panel appears below the agent area when the focused agent is part of a swarm. It shows unacked event entries (`#42 [progress] worker "API" — text…`) fetched from `GET /api/swarm/inbox/<parent-id>`. New lifecycle, question, and debounced progress events publish `swarm_changed`, which causes a non-acknowledging peek. Clicking an entry expands the full payload. A "Drain" button marks events acknowledged. Events are never auto-drained because the conductor or another client can also be reading them.

**Agent groups** (LEG-134): the web counterpart of the TUI's `g`. A group is `tasks.task_group`, so every agent of a task is in it and the TUI and web agree. API (`internal/server/agent_groups.go`, `service.TaskGroups`, which the agent service implements): `/api/agents` carries `group` (absent for none); `PUT /api/agents/{task_id}/group` with `{"group": "name"}` or `{"group": null}` (a blank name is none; a name is one line of at most 60 characters with no control characters, else `400` (`service.ErrInvalidTaskGroup`); a slot's agent ID addresses its task; `404` for no task; `409` for a task away on a worker, which keeps its group as it keeps its workspace (`RefuseAway`); only the column is written, `store.SetTaskGroup`); `GET /api/agent-groups` answers `{defaults, groups}`, `groups.defaults` (`Server.SetGroupDefaults`) then the groups of tasks that are not archived, by name (`store.ListTaskGroups`); `PUT /api/agent-groups/{name}` `{"name": "new"}` renames, moving every task (`store.RenameTaskGroup`; a blank or invalid new name is `400`; a new name already in use merges the two groups); `DELETE /api/agent-groups/{name}` takes every task out. Each change broadcasts `agents_changed` and `task_update` over IPC (`notifyTaskChanged`), so a TUI in another process reloads its agents; the TUI in turn broadcasts `task_update` after `g` (`App.SetTaskChangedNotifier`), which the server running with it or `legato serve` turns into `agents_changed`.
Web: `agentGroupLayout` (`web/src/lib/agentGroups.ts`) lists blocks: known groups (defaults, then those made in this browser) even when empty, other groups in use by name, then Ungrouped when it has agents or an agent is being dragged; inside each, `agentSections` order, and `needsYou` (waiting or error). `useAgentGroups` (`web/src/components/agent-groups/useAgentGroups.tsx`) holds the mode (`legato:agent-groups:mode`; by default grouped once any agent has a group), the collapsed groups (`legato:agent-groups:collapsed`, Ungrouped as `"\u0000"`), the groups made here with no agent yet (`legato:agent-groups:made`), the move/rename/delete calls, and `dialogs`: `GroupNameDialog` (new, rename), `MoveToGroupDialog` (the groups, Ungrouped, **New group…**) and the delete confirmation, which says when the group is a default and so keeps its header. `AgentSidebar` with `grouping` draws `AgentGroupSection`s: a header button (`aria-expanded`, the count, and while collapsed a `N need you` badge), a `⋯` `GroupMenu` (Rename group, Collapse all others, Delete group), status sub-headings (`h3`), and HTML drag and drop (entries carry `application/x-legato-agent`; a section is the drop target, `data-drop-target` while over it; a drop on the agent's own group does nothing). **Move to group…** is in the right-click menu, `useTerminalMenu` (`onMoveToGroup`) and `NativeAgentPanel`'s menu, never for the Reeve. On a phone `AgentSelect` takes the same `grouping` and lists collapsible group headers.

**Keyboard agent switching**: Modifier key + digit (1-9) switches agents with glitch animation. `getSwitchModifier()` reads `legato:switch-modifier` from localStorage (defaults `"Alt"` on Mac, `"Control"` on Linux). Global `keydown`/`keyup`/`blur` listeners in `Agents.tsx` track `modifierHeld` state. `AgentSidebar` renders number badges when modifier held. ### Attention dashboard

`/attention` is a grouped operational dashboard over the durable Attention registry. It always presents **Needs intervention**, **Ready for review**, and **Merge blockers** with section counts and compact section-level all-clear states; a larger global all-clear appears only when every section is empty. Cards retain urgency/source labels, reason and detail, source-owned execute actions, revision-scoped Dismiss, and direct navigation. Unknown future allowed signals fall back to Needs intervention. A `task` navigation opens `/board?highlight_task=<id>` (`legatoHref`), which selects the task wherever it is on the board, an away task's row in the Away lane included. A task done on a worker (`handoff_done`) is in Ready for review, with Return, Open on <worker> (the action's `href`, in a new tab) and Open task; the other `handoff` signals are in Needs intervention, and Take back asks the action's `confirmation` first ([Attention](attention.md) § Handoff). Argus's cases (`argus_case` in Merge blockers, `argus_needs_you` in Needs intervention) open in Argus in a new tab and, on a task, also offer Open task (`/board?highlight_task=<id>`); a detail is Markdown without raw HTML or images, folded with More when long ([Integrations](integrations.md) § Cases in Attention). Actions wrap below card text on narrow screens, and loading/source/action-conflict errors remain visible and accessible.

The dashboard does not compose Board, Agents, and Review API calls in the browser. `GET /api/attention` remains authoritative, and `attention_changed` invalidates its shared query. Navigation badges, TUI, CLI, and Stream Deck consume the same expanded default signal policy while retaining generic list/count presentation.

- Agent actions in the sidebar and dialogs — `AgentContextMenu` (right-click on a sidebar agent) takes the same `AgentMenuEntry[]` as the More actions menu. `AgentsPage.contextMenuEntries` reuses the selected terminal agent's `useTerminalMenu` entries; for any other agent it builds the entries that name the agent by `taskId` (Rename, notify, upgrade/downgrade, Reload, Kill; plus Refresh from snapshot and Disconnect for the selected native agent, through `NativeAgentPanel`'s `resyncRef`). `useConfirm` (with `ui/ConfirmDialog`) replaces `window.confirm` on the agents page, `AgentActionMenu` and `AgentArtifactPanel`: `const { confirm, dialog } = useConfirm()`, render `dialog`, `await confirm({title, message, confirmLabel, destructive})`. Other existing confirmation flows keep their own entry points.
- **Agent info** — `AgentInfoDialog` (`web/src/components/AgentInfoDialog.tsx`), opened by the **Agent info** entry of the right-click menu (`contextMenuEntries`), `useTerminalMenu` (`onShowInfo`, so the header's and the phone `PromptBar`'s menus) and `NativeAgentPanel`'s menu; `AgentsPage` keeps the agent opened (`infoAgent`) and shows its current row from the agents list. It reads only `AgentInfo` and `GET /api/agents/{task_id}/resources`: `working_dir` (the execution's `working_dir`: the spawn's folder, a Yggdrasil worktree, a job clone's path or the Reeve's work folder; "No working directory is recorded" when absent) and `clone` (`repo`, `branch` it was made on, from the live `job_clones` row at that path), task, slot, tool, engram, native or terminal, role, group, status, started, sandbox, resources, execution, tmux session and workflow run. Each identifier is a `CopyField`: full value in monospace, `break-all`, a copy button (`Copied` / `Could not copy`); without the Clipboard API (plain HTTP) it tries `document.execCommand("copy")` and leaves the text selected with a `role="status"` hint. The model is not shown: Legato does not record it per execution.


### Interaction and recovery contracts

`useMenuLayer` handles anchored placement, measured bounds, visual-viewport/resize/scroll updates, outside dismissal and trigger restoration. Action/choice menus use Arrow/Home/End navigation and typeahead; nested levels consume Escape before the outer layer. Board cards have separate semantic primary and action buttons; Shift+F10 opens their action menu. Mobile More uses the modal contract; navigation marks the current page.

Operational pages show initial loading, empty and retryable failures distinctly. Attention and run pages retain cached content after refresh failure; workflow artifact failures can be retried. Learning and Audit discard responses for a stale server/filter/ID. Reports name increases/decreases in accessible text. Plan rejection and cleanup controls are available on phones; plan/review feedback sheets use the shared modal stack without making desktop columns modal. Artifact tabs follow tab/tabpanel keyboard relationships; resize listeners clean up on cancellation, blur and unmount.

Browser verification: build the current Go binary to a scratch path, then run `LEGATO_VERIFY_BIN=/absolute/path/to/legato node scripts/verify-web-ui.mjs` from the checkout. The harness owns its backend, database, Vite configuration, browser and tmux runtime, uses ephemeral ports, and removes its runtime afterward. Results/screenshots are in `/tmp/web-ui-excellence-evidence`. Skills and nested/busy dialogs use production-component fixtures with stub agent transport; they do not launch or verify an external agent. CSS viewport reduction is zoom-equivalent, not physical-device/virtual-keyboard or screen-reader coverage.

### Server preferred theme and Follow server

Settings › Appearance › This Legato mounts `ServerThemeSettings`, which edits **Preferred theme** through authenticated `GET`/`PUT /api/settings/theme`, including **No preference** (`id: ""`), expected-revision conflicts and visible load/save errors with **Reload preference**. `ServerThemeProvider` reads public metadata keyed by the active connection; `QuerySyncProvider` invalidates metadata/preference on `server_theme_changed` and reconnect. `appTheme.ts` keeps mode (`legato:theme-mode`) separate from the local fallback (`legato:app-theme`) and resolved ID (`legato:effective-app-theme`); `serverTheme.ts` caches snapshots per connection. Failed fetches retain only that connection's snapshot; older/no-preference/unsupported responses resolve to local fallback. Named choices exit Follow server; existing clients remain local. Native capability 2 owns resolution/delivery, while capability 1 hides Follow server instead of opting only the page in. Explicit terminal choices remain unchanged. See [Client themes](themes.md).

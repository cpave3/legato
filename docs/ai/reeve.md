# The Reeve

The Reeve is the agent of a Legato instance itself (see `GLOSSARY.md`): the person talks to it to run and configure that instance, not to work on a task. Spec: Burnlite milestone `LEG-106`. Site page: `using/reeve`.

## Sessions

- **A session is a hidden task** of kind `reeve` (`tasks.kind`, migration 101; `store.CreateReeveTask`, ephemeral, so it is off the board and out of every task listing). `reeve_sessions` holds each session's `state` (`running`, `suspended`, `ended`), `agent_kind`, `model`, `launch_args` (JSON), its API token and the token's hash, `started_by`, `created_at`, `updated_at`, `active_at` (for the idle suspend) and `ended_at`.
- **One running session per instance.** `ReeveService.Start` refuses with `ErrReeveRunning` while a session is `running` or `suspended` (`store.CurrentReeveSession`). `Resume` of another session is refused the same way.
- **Starting** (`ReeveService.Start`, `internal/service/reeve.go`): makes the task, a new API token, and spawns the agent through the agent service with the `reeve.*` settings read now (`ReeveDefaults`: `reeve.agent`, `reeve.model`, `reeve.launch_args`), overridden for one session by `ReeveStart.Agent` and `Model` (the Reeve's own start button; "Ask the Reeve" always uses the defaults). `AgentSpawnOptions.LaunchArgs` adds the launch arguments after the adapter's own. The brief, when there is one, is the launch prompt (the full prompt comes with R2).
- **Ending** (`End`): stops the agent, and `SetReeveSessionState(ended)` clears the API token and its hash, so it stops working at once. Killing the current session's agent is ending it: `POST /api/agents/kill` (the sidebar's **Kill agent**) and the TUI agents view's kill ask `ReeveService.StopAgent` first, which ends the session when the task is the current Reeve session's and leaves any other agent to the usual kill. The broker token is the execution's, revoked when the agent ends, as for every agent.
- **Resuming** (`Resume`): a new API token (for an ended session), the session's tool and model unless overridden, and the spawn with `SessionPolicy: resume`, so the conversation comes back.
- **Deleting** (`Delete`): only an ended session (`ErrReeveNotEnded`); removes its row and its task.

## What it knows

- **The launch prompt** (`ReeveLaunchPrompt`, `internal/service/reeve_prompt.go`), in the engram sessions spec's order:
  1. the engram's boot packet, which the spawn puts first (see § Its engram); when the engram did not boot, or the Reeve has none, `reeveNoEngram` stands in for it: a line saying the session starts without its engram, why, and that it writes nothing to one;
  2. `ReeveRolePrompt`: the Reeve's tools and when to use each, changes and approvals, the never list, the host shell only as a last resort, secrets only by name, not proposing a denied change again unless asked, and that its engram keeps what is worth remembering (and that secrets never are);
  3. the instance snapshot (`ReeveSnapshot`): the time, version and update mode, how it runs (`howThisRuns`: the TUI or `legato serve`, under systemd or the hot-reload supervisor), the instance ID, its workers with their reachability and its mains, open Attention items (eight at most), running agents, the last five error lines of the log, host operations (none yet) and approval levels;
  4. the brief (`## The brief`), when there is one; the first message then asks the Reeve to look into it.
- `ReeveLaunchPrompt(noEngram, snapshot, brief)` builds parts 2 to 4, with the no-engram line first only when the session has no engram to boot. The spawn takes it as `AgentSpawnOptions.LaunchPrompt`, which replaces the general prompt: no repository guidance, review prompt or learnings are added. Each agent tool gets it as it gets any launch prompt (`--append-system-prompt`, `developer_instructions`, `--prompt`).
- **A resumed session** is sent a fresh snapshot first (`ReeveResumeMessage`: `[legato] since you were last here: …`), then the brief if any.
- **Its tools** (`internal/cli/mcp_reeve.go`), served by `legato mcp serve` only to a session whose task is a Reeve's (`IsReeveTask`), and checked again on each call (`mustBeReeve`):
  - `docs` (`list`, `search`, `read`): the user manual, the `site/src/content/docs` pages built into the binary by the `site` package (`site.Pages`, `Search`, `Read`); not `docs/ai/`;
  - `instance_status`: the snapshot, fresh;
  - `read_logs`: the last lines of the log file (`<data_dir>/logs/legato.log`, and `.1` before it), filtered by a regular expression (`ReadLogLines`), 100 by default, 1000 at most;
  - `legato_api`: a call to this instance's API (`MCPReeve.APIBase`, the local web server) with the session's own token, answered with the status and body. Its token passes read routes only, so change and risky calls come back `403 needs_approval` until change sets exist.

## Its engram

One engram per instance, the Reeve's own, in a store apart from the person's, so it never shows in their `engram identity list` or in the spawn picker. Spec: LEG-106 Part 3 § Its engram.

- **Name and store** (`ReeveEngramFor`, `internal/service/reeve_engram.go`): `reeve-` and the first eight characters of the instance ID after its `srv-` prefix; `ENGRAM_HOME=<Reeve folder>/engram`. `reeveEngram` (`cmd/legato/reeve_runtime.go`) gives it to `ReeveServiceOptions.Engram`, or `ErrEngramsOff` when `engram.enabled` is off: the Reeve then starts with the no-engram line first in its launch prompt and no Attention item.
- **Through the spawn's engram steps** (see [Engram sessions](engram.md) § The spawn, with an engram): `ReeveService.spawn` sets `AgentSpawnOptions.Engram`, `EngramHome`, `EngramSeed` (`ReeveSeedTemplate`) and `EngramMissing` (`reeveNoEngram`). So the session key is the execution ID, a resume keeps it and gets no packet, the packet comes first, the sandbox mounts the binary and the store, and the engram and its store are recorded on the execution (`engram_home`). Bindings are never read or touched, and there is no picker.
- **Created by Legato**: the first boot finds no store, or no engram in it, and issues it with `engram identity new <name> --file -` and the seed; exit `5` (it exists) counts as done; any other failure is a boot failure.
- **Ending**: `End` of a running session kills its agent, which ends the engram session (`EndExecution`). The idle suspend kills the agent with the session kept (`withEngramSessionKept`), so the resume continues it; `End` of a suspended session ends it with `EndTaskEngramSession` (the task's latest execution that ran as an engram).
- **Boot failure**: the agent starts without the engram, with `reeveNoEngram(reason)` first in its launch prompt (or its first message, on a resume), writes nothing to an engram, and the `engram` Attention producer raises `engram_boot_failed` worded for the Reeve ("The Reeve's engram did not boot"), leading to Settings › Reeve's engram (`settings` / `reeve-engram`), since its task is hidden.
- **The seed** is engram's `identity.md` once the engram exists (`$ENGRAM_HOME/identities/<name>/identity.md`, engram's documented layout); Legato writes it only when issuing the engram and when a signed edit asks it to. `reeveSeedTemplates` lists every built-in seed shipped, the current one last: a seed that is one of them was never edited. `View` reports `edited`, and `newer` when the built-in seed changed since the seed was written: an older built-in seed, or an edit made when another template was current (its hash kept in `instance_values` under `reeve_seed_template`). Legato never puts a newer template in by itself. When the template changes, add the old one to `reeveSeedTemplates`.
- **Editing the seed** is one of the Reeve's own rules: `ProposeSeed` refuses with no device enrolled (`ErrNoDeviceEnrolled`) and submits a signed approval of source `reeve_seed` with the engram and the whole seed in its details (the tray shows the seed as its summary); its resolver rewrites `identity.md` after engram's header, through a temporary file, or issues the engram with the seed when it does not exist yet.
- **Memories and threads**: `View` lists them (`engram memories --all-scopes --json`, `engram thread list --json`, as the engram); `RemoveMemory` deletes one (`engram remove <id> --yes`), `CloseThread` closes one with the resolution "Removed by the person in Legato's Settings." Editing a memory stays with the engram CLI.
- **API**: `GET /api/reeve/engram` (`{enabled, error?, name, store, exists, seed: {text, edited, template, newer}, memories, threads}`, read), `PUT /api/reeve/engram/seed {seed}` (`202 {status: "needs_signature", approval_id}`, `409` with no device; risky), `DELETE /api/reeve/engram/memories/{id}` and `DELETE /api/reeve/engram/threads/{id}` (risky). Wired by `wireReeveEngram` for each web server.
- **Settings › Reeve › The Reeve's engram** (`ReeveEngramSettings.tsx`, `#reeve-engram`): its name and store, the seed in a text box (**Save the seed** asks for the signature), **Use the new built-in seed** when `newer`, and the memories and open threads, each with **Remove**. With engrams off it says why.

## Idle, and the next message

- **Suspend.** `runReeveIdle` (`cmd/legato/reeve_runtime.go`, in every process that serves the web UI) checks once a minute: a `running` session whose `active_at` is older than `reeve.idle_timeout` (a duration, `2h` when empty; `ReeveConfig.ReeveIdleTimeout`) is suspended (`ReeveService.SuspendIdle`): its agent stops with its engram session kept, its state is `suspended`, its API token stays (for resume only: nothing calls with it while no agent runs), and its pending approvals stay. A suspended session still counts as the instance's running one.
- **Activity** moves `active_at` on: the agent's activity changes (`EventAgentActivityChanged` for a reeve task), each `legato_api` call, each message, a start and a resume.
- **The next message** (`ReeveService.Message`; `POST /api/reeve/message {text}`): into the running session (`QueueMessage`), resuming a suspended one with the text after the fresh snapshot, or starting a session with it as the brief when none runs. It reads the session under the lock `Start` and `Resume` hold, so a message that comes while one runs (the voice status's warm-up) waits for it and goes to the session it made. A message to a session launched within the last 30 s (`reeveBindWait`) waits until its native endpoint is bound (`HasChimeraEndpoint`), as launch messages do, so it is not typed into a tool still starting.

## Where it runs

- **Always in Legato's sandbox.** `SpawnAgent` refuses a `reeve` task with `Unsandboxed` (Run without sandbox) or when the sandbox is off (`ErrReeveSandboxed`); `RestartAgentSwitchingSandbox` (the TUI's `U`, the web UI's `switch_sandbox`) refuses it too. Swarm and workflow agents were already pinned.
- **The Reeve's folder**: `$XDG_STATE_HOME/legato/reeve`, else `~/.local/state/legato/reeve` (`service.ReeveFolder`), given to the session read-write as a resource, with the working directory `<folder>/work` inside it. It is outside any repository and outside the data folder, which the sandbox refuses to show. It holds the Reeve's engram store, `<folder>/engram`, which the sandbox also mounts read-write, with the engram binary read-only first on `PATH`, as for any engram session.
- `LEGATO_REEVE=1` is in the session's environment.

## Tokens and what the Reeve may call

- **An API token** `lgr_<48 hex>` per session (`ReeveTokenPrefix`), kept with its SHA-256 in `reeve_sessions` and resolved by `ReeveService.Authenticate` (an ended session's token is gone). `serveReeveToken` (`internal/server/reeve.go`), reached from the auth middleware for a Bearer token with that prefix, classes the request (`ClassifyRequest`, see [Web UI](web-ui.md) § Route classes): **read** passes, with the session in the request's context (`ReeveCaller`); **never** is refused (`403`, code `never`); **change** and **risky** are refused (`403`, code `needs_approval`): the Reeve proposes changes as change sets, which Legato runs itself.
- No other session's token reaches the Reeve's routes; the web token does (the person).
- **Attention actions that decide approvals**: `POST /api/attention/{id}/actions/{action}` is a `change` route, but the `approvals` producer's actions decide an approval and the `devices` producer's act on approval devices. `ChangeSetService.decidesApproval` classes such a call `never` when the set is proposed, and refuses it again when it runs; an item that cannot be found is refused too.
- **Approvals it reads**: `GET /api/approvals` and `GET /api/approvals/{id}` answer a Reeve token with its change sets' calls stripped of what Legato read from the host to show the person: `diff` (an edited file's or config.yaml's) and `before` (a setting's value). Otherwise proposing a change it never meant to make would let it read any host file (`withoutHostContent`, `internal/server/approvals.go`). The person's view is whole.
- **Its sandbox's `legato` commands**: the broker's `cli.run` (`cliRunOp`, `cmd/legato/cli_forward.go`) runs a command for the Reeve's session only when `classifyLegatoCommand` classes it `read`; any other is refused (`forbidden`), since a change goes to the person through the `legato` tool or `propose_changes`.

## API and web

- `GET /api/reeve` (`{current, history, folder}`), `POST /api/reeve/sessions` (`{agent?, model?, brief?}`; `201`; `409` while one runs, or with the sandbox off), `POST /api/reeve/sessions/{task_id}/end`, `POST /api/reeve/sessions/{task_id}/resume` (`{agent?, model?}`), `DELETE /api/reeve/sessions/{task_id}` (`409` unless ended). Each change sends `agents_changed`.
- Settings › Reeve (`ReeveSettings.tsx`): the current session with **End session**, or **Start the Reeve** with optional agent tool and model for this session; the history with **Resume** (disabled while one runs) and **Delete**; and the `reeve.*` settings as registry rows.

## On the Agents page and the phone

- `/api/agents` marks the current session's agent `reeve: true` (`Server.reeveTaskID`). `GET /api/reeve` also gives `instance` (this machine's host name), `role` (`main`, `worker`, `main and worker`, `standalone`, from paired workers and mains) and `to_approve` (pending approvals of the Reeve's sessions).
- **Web** (`web/src/components/ReeveEntry.tsx`): `ReeveEntry` is pinned first in `AgentSidebar` (its `reeve` slot, above Starting and the groups; the Reeve's agent is left out of the groups) with `reeveWash`, a violet wash from the left edge and a faint violet border, apart from the selection accent. It shows the session's state and time, the agent tool and the activity bar, the instance's name and **N to approve**. With no session running it stays, quieter (`opacity-70`, "pick to start" or "pick to resume"), and picking it starts one (`POST /api/reeve/sessions`) or resumes the suspended one, then selects it. `useReeveOverview` reads `/api/reeve` without a query client and again when the Reeve's agent changes.
- **The conversation's status bar** (`ReeveStatus`, in `AgentChatHeader`'s notes for the native panel and the terminal view): **Reeve**, `sandboxed`, the instance with its role, and the engram its agent runs as (`GET /api/reeve`'s `engram`, from the current session's agent), or `no engram`.
- **The phone**: `AgentPickerBar` leads its list with the same `ReeveEntry` (`compact`), and `AgentSelect` lists the Reeve's agent first with the violet wash when it has no entry of its own.

## Levels and rules

- **Levels** (`service.ReeveLevel`, `internal/service/reeve_levels.go`): `free` (a read), `approve` (a tap), `signed` (an enrolled device), `verified` (signed, with a fingerprint or a PIN). `ReeveLevelFor(cfg.Reeve, class, call, enrolled)`: read is free; change is `reeve.levels.change` (default `approve`); risky is `reeve.levels.risky`, default `auto`: `signed` once a device is enrolled, else `approve`. Then the last rule of `reeve.rules` whose pattern matches the call (`METHOD /path` or a `legato` subcommand, `*` for any run of characters, case ignored) sets the level, up or down, never below `approve`. A signed level with no device enrolled stays signed: such a change is refused, never downgraded to a tap. `StrictestLevel` is a change set's level.
- **The Reeve's own rules**: `reeve.levels.*` and `reeve.rules` (and later host operations on or off, and the peer setting) are marked `OwnRule` in the registry. `SettingsService.Set`, `Reset`, `SetEntry` and `DeleteEntry` refuse them (`ErrOwnRule`) unless applying a signed approval. `ReeveRules.Propose` checks the change, refuses it when no device is enrolled (`ErrNoDeviceEnrolled`), and submits a signed approval of source `reeve_rules`; its resolver applies the change once allowed. `PUT`/`DELETE` of such a setting or entry answer `202 {status: "needs_signature", approval_id}`, or `409` with no device; Settings marks those rows **signed** and says to approve on the phone or with a passkey. The Reeve's seed is one of its own rules too, kept by engram rather than the registry, with its own signed approval (`reeve_seed`; see § Its engram).

## Change sets

- **Proposing** (`ChangeSetService.Propose`, `internal/service/reeve_changes.go`): the `propose_changes` tool takes a one-line reason and ordered calls (`{kind: api, method, path, body}`, `{kind: restart}`); a change made with `legato_api` (its `403 needs_approval`) becomes a set of one, its reason the call. `Describe` first refuses an API call that is not a plain route (`checkAPICall`: a method of GET, POST, PUT, PATCH or DELETE; a path under `/api/` with no space or control character, that parses and is already clean, with no `//`, `.` or `..`), then classes each call by the route class table (`classifyCall`, `server.ClassifyRequest`), refuses the whole set for a `never` call (`ErrNeverCall`), gives each call its level (`ReeveLevelFor`) and, for a setting (`PUT`/`DELETE /api/config/settings/{key}`), its value before and after, computed now, with `applies_at_restart` for a restart-mode setting and the running agents a new-agents-mode setting does not reach. The set's level is its strictest call's; a signed level with no device enrolled refuses the set (`ErrNoDeviceEnrolled`).
- **The approval**: one approval of source `reeve_change_set` (source key the set's ID, `cs-<10 hex>`; task the Reeve's session), `signed` for a signed level and `verified` for a verified one, with every call in its details (`ChangeSetDetails`), so a signature covers exactly what will run. The set is kept in `reeve_change_sets` (migration 102: `id`, `task_id`, `approval_id`, `reason`, `level`, `calls`, `state`, `results`, `waiting`). `Propose` waits up to 60 s for the decision (`ApprovalService.Wait`) and answers `approved`, `denied` (with the note) or `pending`.
- **Running**: the resolver moves an allowed set to `queued`. The process that serves the broker runs queued sets every 2 s (`RunQueued`, `whileBrokerOwner`), each once (claimed by moving it to `running`), from the approval's details, never from the Reeve: calls in order, a restart last, stopping at the first failure (the rest `skipped`), with no rollback. An API call runs against this instance's web API with the web token (`localAPI`), which never follows a redirect: an answer of 3xx fails the call. The set ends `done`, `failed` or `restarting`, with each call's result in `results`, and the Reeve is sent `ChangeSetReport` (`[legato] Change set … : N of M ran …`): each call's state, why a failed call failed, and a host call's output whether it ran or failed (up to `reeve.host_output_cap`, then where the whole output is kept); the output of other calls that ran is left out, since a `legato` command's may hold a token. A restart then runs `restartAll`; Part 2's rollback covers it.
- **Denial**: the set is `denied`; when `propose_changes` is no longer waiting (`waiting` is 0) the Reeve is sent the person's note and told not to propose the same change again in the session unless asked.
- **Ending a session** expires its pending approvals (`ApprovalService.ExpireTask`) and its pending sets; suspending it does not. Messages reach the set's own session only while it is the current one (`notifyReeve`), resuming it when suspended.

## The change-set card, and the line in the conversation

- **The card** (`web/src/components/ChangeSetCard.tsx`, in `ApprovalTray` for source `reeve_change_set`): the source and instance, the set's ID, its number of changes and the level it needs; the reason as the title; each change with its kind (`change`, `risky`, `host as root`), its route or tool, written out in full: the method and path, `legato` with every argument (quoted where it has spaces), the shell command, the file written, or the service with its action and whether it is a system one, its description, a before-and-after for a setting, "Applies at restart", the running agents a new-agents setting does not reach, and its body; and "Legato runs exactly this, in order, stopping at the first failure." The tray's own buttons decide it: one approve button at the set's level (**◈ Approve and sign** through the phone or a passkey when signed, **Approve** otherwise) and **Deny…** with a note.
- **The line** (`ChangeSetLines.tsx`, in the native panel of a Reeve session, under its header): each of the session's last four sets with its reason and state (waiting for your approval, running, done with how many of how many ran, failed, denied), from `GET /api/reeve/sessions/{task_id}/change-sets`, read again as the agent's activity changes.

## Restart, config edits and secrets as tools

- **`restart_legato`** proposes a set of one `restart` call (`reason`).
- **`propose_config_edit`** (`set`: dotted keys and values, `remove`: dotted keys) proposes a `config_edit` call then a `restart` marked `optional`. `Describe` checks the edit (`CheckConfigEdit`, `internal/service/config_edit.go`): it applies the edits to the file in memory through `yaml.v3` nodes and loads the result with `config.LoadBytes` (Load's own rules); an edit that does not load refuses the set. An edit that touches one of the Reeve's own rules (its key, a parent of it such as `reeve` or `reeve.levels`, or a part of it; `editsOwnRule`) needs a signature, as from Settings: it is refused with no device enrolled (`ErrNoDeviceEnrolled`) and is at least `signed` otherwise. The call carries the line diff (`lineDiff`) and `check: "loads"`, shown on the card. A set with an optional restart offers **Approve without the restart** (`OptionNoRestart`): the set is queued as `queued_no_restart` and the restart is `skipped`, so the edit waits for the next restart. Running, the edit is written with `config.EditFile` (comments and order kept, a timestamped backup), then the restart runs last; Part 2's rollback covers a start that fails on the new file.
- **"Legato is back"** (`ChangeSetService.ReportRestarts`): a set that ended in a restart is left `restarting`. The process that serves the broker after the restart (it started after the set's last update, `processStart`) moves it to `done` (or `failed` when the latest restart record was rolled back) and sends the session the restart's time and version, who asked for it and why, each step's result (applied, skipped, or rolled back), and the settings now in effect (those of the set that apply at restart, and any others that were waiting). Each set is reported once.
- **`request_secret`** (`name`, `purpose`; `ReeveSecrets`, `internal/service/reeve_secrets.go`): an approval of source `reeve_secret` with the name and purpose, never a value. The tray shows `SecretRequestForm`: a password field and **Store the secret**, which posts the value to `POST /api/reeve/secrets/{approval_id}` (classed `never`, so the Reeve can never supply a value itself). `Fulfil` puts it in Legato's sealed secret store (`legatoSecretSink`) and closes the request with the reference as the decision's note; a plain allow is refused (`Validate`). The tool waits 60 s and answers the reference (`legato://<name>`), declined, or pending. The value is never in the approval's record or the conversation. 1Password is not written to: Legato's 1Password support only reads.

## The `legato` tool

- **Classes.** Every leaf subcommand of the CLI has a class and a plain description in `cmd/legato/reeve_command_table.go` (`legatoCommandClasses`); `TestEveryLegatoSubcommandHasAClass` fails for a command without one, or for a class of a command that no longer exists. `never`: an agent tool's own hooks and bridges (`agent state`, `agent bridge`, `mcp serve`, `clone setup`, …), commands that hand out secrets or act for an agent session (`credential get|exec|request|git|gh-token`, `auth token`), the web token and devices (`auth regenerate`, `device reset`), servers and interactive commands (`serve`, `pair`), and an agent's own workflow steps. `agent message` is a change: it is how the Reeve messages agents the normal way. A command the table does not class, or args naming none, is `never` (`classifyLegatoCommand`).
- **Running** (`runLegatoCommand`): this process's own binary (`launchExecutable`) with the args, no shell, in the home folder, without any agent session's variables (`hostCommandEnv`), for at most two minutes, the output cut at 64 KB.
- **The tool** (`legato`, `MCPReeve.Legato`): a `read` command runs at once and answers its exit code and output; a `change` or `risky` one becomes a change set of one `legato` call (`ChangeCall.Args`), at its class's level (`ReeveLevelFor` with the call `legato <args>`); a `never` one is refused. In a set, a `legato` call fails on a non-zero exit, and its output is the result's detail.

## Host operations

- **On or off**: `reeve.host_operations` (on when unset), one of the Reeve's own rules (changed only with a signature). Off, `host_shell`, `edit_file` and `manage_service` are not offered (`MCPReeve.HostOperations`) and `Describe` refuses host calls (`ErrHostOperationsOff`); the API and the `legato` tool work either way.
- **The calls** (`internal/service/reeve_host.go`), all risky, each at least an approval: `host_shell` (`command`, run with `sh -c`, shown word for word), `edit_file` (`file`, its whole new `content`; the card shows a diff; a file or content larger than 1 MiB (`MaxEditFileBytes`) is refused, and a diff whose line-by-line match would take more than 4 million pairs of lines (`maxDiffWork`) is shown as the old lines out and the new in; written atomically, the mode kept, the old file kept as `<file>.<UTC time>.bak`), `manage_service` (`unit`, `action` of start, stop, restart, status or logs, `system` for a system unit: `systemctl [--user] <action> <unit>`, `journalctl [--user] -n 200 -u <unit>` for logs). `as_root` makes a call need a signed and verified approval, always, whatever the levels and rules say; with no device enrolled it is refused.
- **How they run** (`runHostCommand`, `cmd/legato/host_exec.go`), in the process that serves the broker, from the approval's details: as Legato's user, in its home folder, with a small fixed environment (`HOME`, a system `PATH` with the user's own bin folders, `LANG=C.UTF-8`, `USER`, `LOGNAME`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`), not Legato's. A call not as root runs through the legato binary itself with `LEGATO_HOST_EXEC=1` (`hostExec`, checked first in `main`), which sets `no_new_privs` on Linux (`host_exec_linux.go`; nothing to do elsewhere) and then runs `sh -c`, so `sudo` cannot elevate. A call as root runs with `sudo -n --`, which works only where the user may sudo without a password. Each runs in a process group of its own, which is killed whole at `reeve.host_timeout` (10 minutes), and its output is read for at most two seconds after that (`hostOutputWait`), so a child that keeps the output open does not hold the change set (a command as root runs under sudo, whose root children Legato cannot signal; its wait is still bounded); the Reeve is given `reeve.host_output_cap` bytes of output (64 KiB), and the whole output past it is kept in `<Reeve folder>/host-output/<set>-<n>.log`, which its sandbox can read. Nothing depends on spotting `sudo` in the command.
- **Audit**: each host action is appended to the hash-chained `credential_audit` (event `host`, empty credential): the command, file or unit (`resource`), the kind (`operation`), the approval, who decided with which device (`decided_by`) and verification, and in `detail` whether it ran as root, the exit code, the state and the SHA-256 of the output.
- The snapshot says whether host operations are on, and the approval levels.

## Voice

The Reeve can speak out loud with the tool `speak` (`internal/cli/mcp_reeve.go`; queue in `internal/service/reeve_speech.go`, `ReeveSpeech`).

- **Settings** (`reeve.voice.*`, `config.ReeveVoiceConfig`, all live, read for each line): `enabled` (off by default; it offers the tool, and off also mutes lines already queued; class `change`), `command` (run as `<command> "<text>" <out-file>`, writes the audio), `credential` (a credential name, given to the command in `credential_env`, which is `<NAME>_API_KEY` when empty), `player` (`<player> <file>`; `pw-play`, else `ffplay -nodisp -autoexit`, when empty). Command, credential and player are `risky`: they choose what runs on the host and which secret it gets.
- **The tool** is offered only to the Reeve's session while `enabled` is on (`MCPReeve.Speech`, listed when the session's MCP server starts, so a session started before the voice was turned on lacks it), checked again on each call (`mustBeReeve`, then `Enabled`). It takes `text`, refuses empty text and text over `MaxSpokenChars` (400 characters: "say less"), queues the line and answers `queued` at once. Its description teaches writing for the ear; "voice mode" is the person asking the Reeve to call it for each reply.
- **The queue** runs in the process that serves the broker, where the Reeve's tools run (`processSpeech`, `cmd/legato/reeve_voice_runtime.go`): the Reeve's sandbox cannot reach the sound system. At most 16 lines wait. One goroutine makes each line's audio while another plays the line before it, so lines play in order, one at a time. The command runs with Legato's environment (plus `XDG_RUNTIME_DIR` = `/run/user/<uid>` when it is missing), in its own folder when given as a path, for at most a minute; the player for at most five minutes. A line that fails to be made or played is logged (its length and the command's error, the key replaced by `[credential]`, never the text) and the queue carries on.
- **Audio** is written to `<data_dir>/reeve-voice/line-<n>.mp3` and removed once played or failed; the folder is cleared when the queue starts, so nothing is kept after a crash.
- **The credential** is read with `CredentialBroker.UseForLegato`: Legato's own use, which the person allowed by naming it in a setting. No rule is asked and no approval raised; each use is audited (`use`, detail "Legato's own use · the Reeve's voice", the characters as its amount) against the Reeve's session. The Reeve never holds the value.
- To switch from ElevenLabs (`reeve-say.sh`) to Piper, set `command` to a Piper script and clear `credential`; no code changes.
- **`LastError`** is why the last line was not made or played, cleared when a line plays. The voice status gives it.

## Hands-free voice

A spoken back-and-forth with the main's Reeve from the desktop and Android apps (Burnlite `LEG-118`; design `docs/analysis/reeve-voice-conversation.md`). `service.ReeveVoice` (`internal/service/reeve_voice.go`) holds it; `wireReeveVoice` (`cmd/legato/reeve_voice_runtime.go`) serves it on both web servers.

- **Transcription in `legato serve`.** `newVoiceService` builds `VoiceService` when `voice.enabled` and `voice.whisper_url` are set at start (both take a restart), for `legato serve` as for the TUI, so `/api/voice/transcribe` works on serve too. A `VoiceService` without tmux transcribes but cannot type into a pane. `voice.whisper_url` can name the Wyoming Whisper that Home Assistant Assist already uses (`tcp://<host>:10300`); that server takes one request at a time, so Legato's and Assist's wait for each other.
- **The status route**, `GET /api/reeve/voice` (class read, web token): `VoiceReadiness` with the instance (`InstanceID`, the host name, `InstanceRole`), the Reeve's session state and whether its agent is `working`, speech (`reeve.voice.enabled`, whether a command is set, `ReeveSpeech.LastError`, cleared only by a line newer than the one that failed), transcription (built in this process, and whether Whisper answered a Wyoming `describe` within 1 s: `whisper.Client.Describe`, `VoiceService.Probe`; false when it was not asked), the open voice session, then `ready`, `reason` and `setting`. It never gives the command line, the credential or the Whisper address. The reasons, first match wins:
  1. "Transcription is off on <name>" (`voice.enabled`; `voice.whisper_url` when only the address is missing).
  2. "Whisper isn't answering on <name>" (`voice.whisper_url`).
  3. "The Reeve's voice is off on <name>" (`reeve.voice.enabled`).
  4. "The Reeve has no voice command on <name>" (`reeve.voice.command`).
  5. "The Reeve can't start on <name>" (this server has no Reeve), or "…: the sandbox is off" (`agents.sandbox.enabled` was off at start; the Reeve runs only in the sandbox; `ReeveVoiceOptions.CanStart`).

  The client adds its own: it cannot reach the server, or has no microphone.
- **Warming up.** When the voice is ready and the Reeve's session is suspended, the status call resumes it in the background (`started_by` `voice`), so the resume happens while the person speaks. A turn sent meanwhile waits for it (see The next message).
- **Settings** (live, read at each turn): `reeve.voice.pause` (the quiet that ends a turn, 1 s, kept to 0.3–2 s, `PauseDuration`), `reeve.voice.follow_up` (how long the session listens for a reply after the Reeve has spoken, 6 s, 0 for a single turn), `reeve.voice.partials` (words so far, on unless set to false).

### The voice session

`GET /api/reeve/voice/session` (class change) is a WebSocket with the web token in `?token=`, as `/ws`. Text frames are JSON (`service.VoiceIn` from the device, `service.VoiceOut` from the main); binary frames are audio, 16 kHz mono s16le PCM, at most a second each. The first frame must be `hello {device, client, play}`, within 10 s, or the socket closes with policy violation. `internal/server/reeve_voice_session.go` is the socket; `service.VoiceSession` (`reeve_voice_session.go`) the conversation, run on one loop so it needs no locks: audio, messages, transcripts, deliveries and a poll (500 ms) all go through it.

- **One session at a time.** `ReeveVoice.Open` ends an open one with `ended {reason: "taken over by <device>"}`. The status route reports the open session's device.
- **The device sends** `listen` (start a turn), `send` (send now), `cancel` (drop the turn), `stop` (while thinking, `InterruptAgent` on the Reeve; while speaking, drop the lines), `playing`/`played {line}`, `bye`.
- **The main sends** `state {state, reason}` (`idle`, `listening`, `thinking`, `speaking`; idle reasons `no_speech`, `nothing_heard`, `cancelled`, `no_answer`, `failed`), `pause {ms, of}`, `partial {text}`, `heard {text}`, `activity {text}`, `line {id, text, url}`, `written`, `ended {reason}`.
- **The end of the turn** is `internal/engine/endofturn`'s detector, fed every frame while listening: `Pause` events drive the pause bar; at the 400 ms `Boundary` the turn so far is transcribed (speculative), `Resumed` drops that text, and at `TurnEnded` the speculative text is sent when it still covers the turn, else the turn is transcribed then. The session counts its own waits in samples: 8 s with no speech goes idle (`no_speech`), and in the follow-up window `follow_up` does. Partial words: the turn so far, at most once a second, only while Whisper is idle, for the first 20 s.
- **Delivery.** The text goes to `ReeveService.Message` (by `voice:<device>`), which starts or resumes the Reeve as a typed message does. The device gets `heard`, then `thinking`. For 2 s after a send the session keeps listening: speech that starts then (before the Reeve answers) is a second message.
- **While thinking**, the poll reads the Reeve's agent activity and its conversation tail: the newest tool call (but `speak`) is sent as `activity`. Once the agent has been `working` and stops, its turn is over: with no line said, `written` and idle. No answer within 2 minutes is `no_answer`.
- **Audio is ignored** while idle, speaking (no echo cancellation in v1), or thinking past the 2 s window.
- **Timings** of each turn are logged from the end of speech: transcript, delivered, first `speak`, line made, playback started.
- **Fixtures** shared with the desktop's Rust tests and the web's TypeScript tests: `internal/server/testdata/voice-session/messages.json` (every message, round-tripped by the Go types) and `turn.json` (one turn, replayed over a real socket).

## Ask the Reeve

Attention items, a failed provider sync on the board, and agents that need the person have **Ask the Reeve** in the web UI and on the phone: a session starts with a brief of what it is, its IDs and its error line, or, with a session there, the person adds the brief to it or ends it and starts fresh. See [Web UI](web-ui.md) § The Reeve on the Agents page.

## Reeve to Reeve

A Reeve can message the Reeve of another instance this one is paired with (`internal/service/reeve_peers.go`, `ReevePeerService`). It only asks: whatever the other Reeve changes is its own change set, approved by its own person.

- **Who it can reach** (`List`, `GET /api/reeve/peers` → `{peers: [{instance_id, name, via, address?}]}`): its workers (`via: worker`, over `WorkerService.Client` and the main's token), its mains (`via: main`) and instances paired in Settings › Reeve (`via: pairing`), and a prime that messaged it from behind NAT (`via: prime`). A main and a worker are reached without another pairing.
- **Pairing two Reeves**: on one instance, a pairing request of purpose `reeve` (`POST /api/pairing {"purpose":"reeve"}`, Settings › Reeve › Reeve pairings › **Let another instance pair with this one**; the view shows `address`, as for a main). The other pairs with its address and phrase (`POST /api/reeve/peers {address, phrase}`, `Pair`): SPAKE2 as a main does, and the token it gets is of kind `reeve_peer` holding `reeve` alone (`IntegrationTokenService.CreateReevePeer`, which revokes earlier ones for that instance). The token is kept sealed as `legato://reeve-peer-<instance ID>`, the peer in `reeve_peers` (migration 103). `DELETE /api/reeve/peers/{instance_id}` removes a pairing (risky).
- **A message** (`Send`; the tool `message_reeve`, which lists the peers when called with no `to`) goes to `POST /api/integrations/reeve/messages` with `{from, text, reply?}`; the route needs the scope `reeve` and takes who sent it from the token's instance, never the body. The first message to a peer carries a reply contact: this instance's address, CA and a `reeve_peer` token for it, so the other Reeve can answer; later ones only the address (`reeve_peers.reply_given`). A prime the other side cannot reach (NAT) gets its answer queued (`reeve_outbox`, `QueueReeveReply`) and handed back with the answer to its next message (`PeerAnswer.Replies`).
- **Receiving** (`Receive`, then `ReeveService.PeerMessage`): the message goes into the running session, framed `[from the Reeve on <name> · <role>] …` (`PeerFrame`), resuming a suspended one. With none running, `reeve.peer` decides: `start` (default) starts a session with it as the brief; `ask` keeps it in `reeve_inbox` and raises the Attention item `reeve_peer` ("The Reeve on <name> wants to talk", **Let it talk** → `LetPeerTalk`), answering `waiting`; `refuse` answers 409 `refused`. `reeve.peer` is one of the Reeve's own rules (changed with a signature).
- **Their change sets in this tray**: each instance answers `GET /api/integrations/reeve/approvals` (scope `reeve`) with its pending `reeve_change_set` approvals; this server asks every peer every 30 seconds and the web tray lists them, decided on their instance. See [Approvals](approvals.md) § Where the person sees them.
- **Classes**: the message route is `change`; pairing, removing and the per-main toggle are `risky`; listing and the approvals routes are `read`.
- Wired by `cmd/legato/reeve_peers_runtime.go` (`newReevePeers`, `wireReevePeers`) for each web server, and for the tool in the broker host (`reeveTools`, sending only).

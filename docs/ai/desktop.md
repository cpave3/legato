# Desktop app

`desktop/` is Legato's desktop app: Tauri 2 (Rust) with a React and TypeScript shell. It shows every paired Legato server in one window, pairs by phrase with the server's certificate pinned, and signs approvals with a security key, or on a Mac with Touch ID. The person's page is `site/src/content/docs/running/desktop-app.md`; how to build and run it is in `desktop/README.md`.

## The window

`src-tauri/src/app.rs`. One frameless window (`decorations(false)`) holds:

- **The shell** (`src/`, React): the title bar, the dock, the Servers & keys panel and the approval sheet, across the whole window. It is the only webview with IPC (`capabilities/shell.json` names the `shell` webview; server pages are remote and get nothing).
- **A webview per server** (`server-<id>`), made the first time the server is shown and kept, over the content area: right of the dock (68px), under the title bar (40px), short of the right and bottom edges by 4px, where the shell's resize strips are. Only the active one is shown; `set_content_visible(false)` hides it while the shell draws a panel or the sheet over the content area.
- **Linux layout.** Tauri packs a window's webviews into a vertical `gtk::Box`, one under the other, and wry moves a webview only inside a `gtk::Fixed`. So `overlay::install` puts a `gtk::Overlay` in the window's box, and `overlay::adopt` moves the shell into it as its base and each server webview over it with margins; GTK keeps them laid out as the window resizes, and `relayout` does nothing on Linux. Elsewhere `relayout` sets positions and sizes on `WindowEvent::Resized`.
- **A server's page** gets an initialization script for its own origin: the token in `localStorage["legato:token:local"]`, as the web UI keeps it, and no service worker (`register` rejects; existing registrations are removed and the page reloaded once). The web UI's service worker took over requests from the second load, and its requests did not get the pinned certificate's allowance, so they hung.
- **Pinned TLS in the page** (Linux): `load-failed-with-tls-errors` on the WebKitGTK view checks the presented certificate with `Pin::trusts` and, when it holds, `allow_tls_certificate_for_host` and reloads. WebKit applies the allowance to the host's later loads, the WebSocket included. macOS's WKWebView has no hook in wry yet, so there a page loads only when the system trusts the server's certificate.
- **A page macOS would not load** (`systrust.rs`). Before the shell shows an https server on a Mac, `page_trusted` fetches the certificate the server presents (checked against the pin, `legato::presented_certificate`) and asks `security verify-cert -p ssl -s <host>` whether the system trusts it, with the pinned CA given to build the chain but not as an anchor. Positive answers are kept for the session. When it does not, the shell draws `TrustScreen` in place of the page: **Trust it on this Mac** (`trust_server_certificate`: `security add-trusted-cert -r trustRoot -p ssl -s <host>` into the login keychain, so the CA is a root for TLS to that host only; macOS asks for the password; then the check again and a reload), **Save the certificate** (`save_server_certificate`: the pinned CA to `~/Downloads/<server> Legato CA.cer`, shown in Finder; `open_certificate` opens it in Keychain Access), the steps to trust it by hand, and **Check again**. A check that fails (the server is down) shows the page as before. Elsewhere `page_trusted` is always true.
- **A server that is down** (`src/pageState.ts`, `OfflineScreen`). The shell draws its own offline screen in place of the page (the server's tile, its address, the reason `poll` gave, **Try again**, which polls now, as the title bar's reload does then) and hides the webview, when `poll` says the server does not answer or its page did not load (`screenFor`). No webview is made for a server known to be down. A page that loaded keeps its state while its server is down and is shown again as it is, since the web UI reconnects by itself. A page that did not load is loaded again when the server answers (`recovered`, at most once a poll: `load_server_page`, at the address that failed when it is the server's own, `links::page_to_load`, else the root). On Linux the webview says so: `load-failed` (not a cancelled navigation or a policy error) emits `page-load-failed` `{server, uri}` to the shell and WebKit's error page is not drawn. Elsewhere a page made before its server's state was known, whose first state is down, is taken as failed (`failedAtStart`).

The shell's parts: `TitleBar` (drag region, server name, reload, the update pill, `N to sign`, window buttons), `Dock` (tiles in the server's tint with an online dot and a count of its open approvals; `+`; at the foot the approvals button with every server's count, and the key button), `ApprovalsPanel` (every server's open approvals, as the Android app's Approvals screen: a signed one opens the sheet, any other opens its server's page on it, `open_approval_in_page`, at `/?approval=<id>`, where its tray answers it), `ServersPanel` (servers: rename, remove; keys: plugged in or not, each server's status, enrol, revoke, add; this app's version and updates), `PairForm`, `ApprovalSheet` (it takes an approval's ID and fetches the request itself; while `prepare` answers `NO_KEY_PLUGGED` it asks again every 1.5 seconds, so plugging the key in carries on; closing it says how it came out). A refused signature made with a touch alone gets `webauthn::explain_refusal`'s hint: go-webauthn reports a missing user verification only as "Error validating the authenticator response", which a Legato from before touch-only signing gives. The server in front tints the chrome (`--server-tint`: a wash over the title bar, the dock and the edges, the page's border); panels stay neutral. Tiles reorder by pointer drag (`Dock.tsx`: pointer events, not HTML5 drag, which Tauri's webview does not give; a 6px move starts it, the order follows the pointer, the click after a drag is swallowed); `reorder_servers` saves it through `Store::reorder_servers`, which is the order of `servers` in the state file. `poll` (every 3 seconds) gives each server's state, tint (kept in the state file for when it is down) and open approvals; `N to sign` counts the signed ones.

## The bridge between a page and the shell

`bridge.rs`, the contract the Android app has with the web UI (`mobile/.../PageContract.kt`, `web/src/lib/mobileShell.ts`). A server page's top frame gets `window.legatoShell = {approval: 1, enroll: 1, workers: 1, key}` and a `window.ReactNativeWebView.postMessage` of the app's (`bridge::script`, a random key per page). The web UI then treats the page as the app's: its tray offers **◈ Approve and sign** on a signed approval, which posts `{legatoShell: "approval", key, id}`; Settings › Devices posts `enroll`. The page has no IPC, so the script turns a message with its key into a navigation to `legato-desktop://approval?key=…&id=…` (or `…//enroll?key=…`), which the webview's `on_navigation` reads (`bridge::read`, which refuses another key) and cancels, and emits to the shell as `page-message`. The shell opens the sheet on the approval (reading only its ID: it fetches the request itself, so the page cannot change what is signed), or Servers & keys for `enroll`. When the sheet closes, `page_approval_done` runs `bridge::result_script` in the page: `legato:shell-approval` with `{id, status: decided | cancelled | error, option?, error?}`, which the tray waits for. Being the app also turns off the web UI's browser notifications. The script is checked in Node by the Rust tests.

`links.rs`: a server's webview never leaves its server. `on_navigation` and `on_new_window` (`target=_blank`, `window.open`; the latter always denied) ask `links::classify` and hand any other `http(s)` origin, `mailto:` or `tel:` link to the system's default handler (`open_in_browser`: `xdg-open`, `open`, `rundll32`; no shell), cancelling the navigation. `about:`, `blob:`, `data:` and the bridge scheme stay. The Android app does the same with `allowNavigation`. A subframe's navigation reaches `on_navigation` too, so an agent's HTML frame that loads another site's page is opened in the browser instead.

**Dictation.** A page over plain HTTP has no microphone, and WebKitGTK gives none to any page by default, so the app records for the page as the Android app does. When `voice::system_recorder` finds `parecord` (else `arecord`) on the `PATH`, Linux only, the page is also told `voice: 1`. `useVoiceRecorder` then posts `{legatoShell: "voice", key, action: start | stop | cancel}`, which reaches the app as `legato-desktop://voice?key=…&action=…`. `record_for_page` (`app.rs`) runs the recorder writing 16 kHz mono 16-bit samples to its output (`voice::Recorder`, which links no audio library), and `bridge::voice_script` answers the page with `legato:shell-voice` events: `started`, `level` every 150 ms (the newest tenth of a second in decibels, -50 dB to full scale, as the Android app shows it: without a browser's automatic gain, speech sits near -30 dB), `audio` (the whole recording as a WAV, base64, `mime: audio/wav`), `cancelled`, or `error` (the recorder's last line when it ends by itself). The page reads the WAV's samples as they are, without `decodeAudioData` (the AppImage carries WebKitGTK without GStreamer's plugins, `bundleMediaFramework: false`, and there it never settles), and transcribes them through its server as usual. Each request, the recorder used, the size of the recording and every event but levels are printed as `[voice] <server>: …` lines on the app's output. One recording at a time: starting one cancels another page's. A recording no page stops ends after ten minutes, and removing a server ends its own. Without a recorder, or on a Mac, the page is not told, and dictation behaves as in a browser.

**Adding a worker** (`workers.rs`). The page is also told `workers: 1`. Settings › Handoff › Workers › Add a worker posts `{legatoShell|type: "workerCandidates", key, id}` and `{…: "openWorkerPairing", key, id, server, main}`; the script sends them as `legato-desktop://workers?key=…&id=<JSON>` and `…//worker-pairing?key=…&id=<JSON>&server=…&main=…` (the id JSON-encoded, so a string or a number comes back as it went). `answer_worker_candidates` (`app.rs`) answers with `workers::candidates`: every server but the page's, `{key: id, name, url}`. `pair_worker_for_page` refuses at once a server the app does not know or the page's own ("This app has no such server.") and one whose keyring token is gone (`workers::no_token`), then asks with the system's dialog (`tauri-plugin-dialog`, `MessageDialogButtons::OkCancelCustom("Make it a worker", "Cancel")`, parent the window): "Make <server> a worker of <main>? …", `main` being the page's name for its server, trimmed and cut to 80 characters, else the app's name for it (`workers::main_name`). On yes, `workers::open_main_request` posts `/api/pairing {"purpose":"main"}` with that server's `Client` (its token and pin) and answers `{id, address: <the app's URL for it>, phrase, expires_at}`. A refusal is the server's words (`HTTP n` without any is "The server answered n."); no answer is "Could not reach <name>: …" (`Client::reach` tells the two apart); an answer without `purpose: "main"` (a Legato from before handoff opened a phone's request) is withdrawn with `DELETE /api/pairing` and is "This server is too old to be a worker. Update Legato on it, then try again.", as the Android app says. Answers go back as `legato:shell-worker` events (`bridge::worker_script`): `{id, servers}`, the pairing, `{id, cancelled: true}` or `{id, error}`. Each step is printed as a `[worker] <server>: …` line.

## Links from the system

`applink.rs`, with `tauri-plugin-deep-link` and `tauri-plugin-single-instance` (its `deep-link` feature passes a link a second start was given to the app that runs, and focuses it). The system hands the app `legato-desktop://import?provider=<provider>&key=<KEY>`, which the browser extension opens to import a ticket (`openImportsInDesktop`; see `browser-extension/README.md`). On Linux the app registers the scheme at each start (`register_all`: a `legato-desktop-handler.desktop` in `~/.local/share/applications` naming the running binary, or `$APPIMAGE`), since an AppImage is not installed; a Mac takes it from the bundle's `plugins.deep-link` in `tauri.conf.json`. A page's own `legato-desktop:` addresses (`bridge`) never reach the system.

- `applink::read` accepts only that shape: provider `[a-z][a-z0-9-]*`, key `[A-Z][A-Z0-9_]*-[0-9]+` (upper-cased); any other link is ignored. `handle_link` queues it in `Desktop.imports`, emits `import-request` to the shell and brings the window to the front; the shell takes the queue (`take_import_requests`, also at its start, for a link that started the app).
- The shell asks with `ImportSheet` (every server, the one in front first, with **Don't ask again: import into the server in front**), or, when `import_target` is `current` (`store::ImportTarget`, kept in the state file, `import_preference`/`set_import_preference`, shown in Servers & keys as **Ask which server to import a ticket into**), imports into the server in front at once; a refusal there opens the sheet with the server's reason.
- `import_ticket` is `POST /api/remote/import {ticket_id, provider}` with that server's token; `open_task_in_page` then puts the server in front at `/board?highlight_task=<task>`.
- The dev build and the AppImage share the app's identifier, so with single-instance one does not start while the other runs, and the last to start owns the links.

## Talking to the Reeve

Hands-free voice with the main's Reeve (Burnlite `LEG-118`; design `docs/analysis/reeve-voice-conversation.md`, server side [The Reeve](reeve.md) § Hands-free voice).

### The key

`voicekey.rs` decides everything about the key; `voicekey_portal.rs` (Linux) only talks to the portal; `app.rs` wires them (`start_voice_key`, `voice_key_input`, `voice_key`).

- **Which way** (`voicekey::backend`, given `voice.key_backend`): the app grabs the key itself with `tauri-plugin-global-shortcut` (`Backend::Grab`) on X11, macOS, Windows, and on a Wayland session (`XDG_SESSION_TYPE=wayland`, else `WAYLAND_DISPLAY`) with XWayland (`DISPLAY` set), unless the state file has `voice.key_backend: portal`, which uses the XDG desktop portal's GlobalShortcuts. A Wayland session without `DISPLAY` uses the portal; anything else has only the link. The choice is read at start (`set_voice_key_backend` saves it and the settings offer **Restart now**, `restart_app`), and the plugin is added only when grabbing, so the grab and the portal are never both bound (one press would count twice). `voicekey::can_choose` (Wayland with XWayland) shows the choice in Servers & keys. A way that fails falls back to the link, never to the other way; a portal whose signals end later (the portal died) clears the key and sets `problem`.
- **The grab** (`grab_keys`): two keys, talk and cancel, `voicekey::default_keys` unless the person chose others (`voice.talk_key`, `voice.cancel_key`, kept only when not the default): `Ctrl+Alt+Space` and `Ctrl+Alt+Shift+Space`, on a Mac `Ctrl+Shift+Space` and `Ctrl+Alt+Shift+Space`. Not Super: KWin and GNOME keep many Meta keys. On Linux `global-hotkey` grabs on the X server (`XGrabKey`, NumLock and CapsLock variants, detectable auto-repeat) and reports `Pressed` and `Released`; on a Wayland desktop that is XWayland, which gets keys typed in Wayland windows only as the compositor passes them: KDE's System Settings › Application Permissions › Legacy X11 App Support, by default keys typed with Ctrl, Alt or Meta held. Cameron's Psittac grabs `Alt+P` the same way on the same KDE. `global-hotkey` sends a key's next press only after its release, so a release the compositor withheld would leave the key dead until it is grabbed again (changing it, or a restart); the log shows each press and release. Servers & keys records a new key by pressing it (`src/keys.ts`, `recordedKey`: the modifiers held and the DOM's `code`, `Ctrl+Alt+KeyV`); `set_voice_keys` writes it as the plugin reads it (`voicekey::accelerator`: modifiers Ctrl, Alt, Shift, Super in that order, `KeyV` as `V`, `Digit1` as `1`, checked by the plugin's parser; refused with no Ctrl, Alt or Super, which would take the key from every app and which KDE would not pass; `chosen_keys` refuses talk and cancel the same), grabs them at once in place of the old ones, keeps the old ones when a new one cannot be taken, and saves them; `null` is the default.
- **The log** (the app's output, `[voice key]`): the way and why (`the app grabs the key itself (voice.key_backend grab, set in Servers & keys)`, `the key is the desktop's GlobalShortcuts portal`), each key registered or not and on which X display (`grab: registered Ctrl+Alt+Space (talk) on X display :0`, `grab: could not register …: <error>`), each press and release (`grab: Ctrl+Alt+Space pressed`, `… released`), and what it asked (`Talk from the grab`). A key not registered is also the settings' `problem`.
- **The portal** (`ashpd`, pure Rust over zbus, `tokio`): the app writes `~/.local/share/applications/dev.legato.desktop.desktop` (`voicekey::desktop_entry`: `Name=Legato`, `NoDisplay=true`, `Exec` the AppImage or the binary, quoted with `%` as `%%`) and registers that ID with `org.freedesktop.host.portal.Registry` (`ashpd::register_host_app`), so KDE lists the shortcuts under Legato. One session for the app's life: `ListShortcuts`, then `BindShortcuts` only when `talk` or `cancel` is missing (`voicekey::needs_binding`; KDE bug 498575), with `talk` ("Talk to the Reeve", preferred `LOGO+ALT+space`) and `cancel` ("Stop talking to the Reeve", no preferred key). The first bind shows KDE's own dialog. `Activated`/`Deactivated` become presses and releases; `ShortcutsChanged` updates the key's text. **Change the key…** is `ConfigureShortcuts` (portal version 2, `can_change`). On Cameron's Bazzite KDE the binding was never stored (no `dev.legato.desktop` in `kglobalshortcutsrc`, and `xdg-desktop-portal-kde` aborted while the dialog should have shown), which is why the grab is the default.
- **The link**: `legato-desktop://voice` (`?action=cancel` for cancel) and `legato-desktop --voice` (`--voice=cancel`), through the deep-link and single-instance plugins (`voicekey::read_link`, `read_args`). Any other `voice` link is ignored; a page's own `voice?key=…` addresses never reach the system. A link has no release, so it is a press whatever the mode. Any page can open the link, as it can the import link; the browser asks first.
- **Hold to talk** (`voicekey::Keys`, off by default, `voice.hold_to_talk` in the state file, `set_hold_to_talk`): off, a press is `talk` and its release nothing; on, a press is `hold` and its release `release`. Presses less than `REPEAT_GAP` (1 s) apart with no release between are a key repeating while held, and ask once; a press later than that is a new press, so a release that never comes (a portal that sends no `Deactivated`, a screen lock) does not leave the key dead. `cancel` forgets a held key: its release asks nothing. A release with no press asks nothing.
- **Events.** `voice-key` `{key: "talk" | "hold" | "release" | "cancel", from: "grab" | "portal" | "link"}`, to every webview, of which only the app's own can listen (see the widget's events), and the key is handed to the conversation (`voice_command`), which it starts when there is none. A conversation started before the first ask of the servers has finished (a cold start with `--voice` or the link) waits up to 10 seconds for it (`Desktop.voice_targets_known`), so the main is known. `voice-key-changed` carries `KeyInfo` `{backend, choice, can_choose, key, talk, cancel, hold_to_talk, can_change, problem, link}`, which `voice_key_info` also answers; `key` is the bound key as the person reads it (`voicekey::key_text`: `Ctrl+Alt+Space`, on a Mac `⌃⇧Space`), for the widget. The shell shows it in Servers & keys › **Talking to the Reeve** (`VoiceSection.tsx`).
- **Checked headless**: the app in a headless KWin with an Xvfb as its `DISPLAY`, keys pressed with `xdotool` (XTEST): both keys registered, `Pressed` and `Released` reported for each, cancel told from talk, a second press talks again. KWin's own XWayland would not start in the sandbox, so what KWin passes to XWayland was not seen.
- **Not checked here**: that KWin passes `Ctrl+Alt+Space` and its release to XWayland on Cameron's desktop; with the portal, that KDE lists the shortcut under Legato, keeps it across restarts (so later starts list and do not bind), and sends `Deactivated` on release.

### The conversation

The desktop is the two-way voice channel: it streams the microphone to the main, plays the Reeve's lines, and tells the widget what to show. `voicemain.rs` chooses the main, `voiceproto.rs` is the protocol, `voiceclient.rs` the conversation, and `app.rs` (`voice_command`, `converse`, `PlayLines`, `refresh_voice_targets`) the wiring.

- **Which main** (`voicemain::choose`): each server's `GET /api/reeve/voice` gives its instance (ID, name, role), kept in `Desktop.voice_targets` (a server that does not answer keeps what it said last). Exactly one `role == "main"` is it; else the only server; else the instance the person chose, `voice.server` in the state file (Servers & keys › **Talking to the Reeve** › the radio list, `voice_targets`, `set_voice_server`); else nobody, and the key says to choose. Asked at start, every 10 minutes, and after pairing or removing a server (`voice-targets-changed`).
- **On the key** with no conversation, `converse` asks the main's status within 2 seconds. Not ready (`voicemain::not_ready`: "Can't reach <name>", the server's own `reason`, or "No microphone on this computer" without `parecord`/`arecord`) emits `voice-state` `not_ready` with the line and the server's `setting`, and records nothing. A key while a conversation runs is handed to it; a key during the status call or the connect waits in the channel. The recorder starts before the session opens.
- **The session**: `Client::websocket` (`legato.rs`) opens `wss://…/api/reeve/voice/session?token=<web token>` over the same pinned rustls configuration as every request (`tokio-rustls` with `ring`, then `tokio-tungstenite`'s handshake; `ws://` for an `http` server), with the app's `Origin`. The connect, TLS and upgrade together get `CONNECT_TIMEOUT` (5 s). While it runs, the app pings every 5 seconds and ends the conversation (`idle`, `voiceclient::LOST`) when nothing, a pong included, has come for 15 (`Liveness`); the main's WebSocket answers pings as it reads. A frame or message that cannot be sent ends it the same way. `hello {device: "<host> (desktop app)", client: "desktop", play}` (`play` when `pw-play`, `paplay` or on a Mac `afplay` is installed), then `listen` once the main says `idle`.
- **The microphone**: `voice::Recorder::stream` runs the same recorder as dictation (16 kHz mono s16le, `parecord --latency-msec=50`) and hands each piece on as it arrives; `voice::Framer` cuts it into 50 ms frames (`FRAME_SAMPLES`). Every frame's level goes to the widget; a frame goes to the main while it is `listening` or `thinking` (the main takes speech that carries on just after a send), is kept (up to 10 s) while the app has asked it to listen and it has not said `listening` yet, sent as soon as it does (`Conversation::audio`, `Audio::Hold`, `Effect::FlushAudio`), and is dropped while a line plays or for 300 ms after (`voiceclient::Mute`, `AFTER_PLAYING`). Dictation keeps `Recorder::start`, which keeps the samples.
- **Lines**: `line {id, text, url}` is queued; one plays at a time, in order. `playing {line}` is sent and the microphone muted, `PlayLines` fetches `url` with the token over the pinned TLS (`Client::bytes`), writes it to a temporary file only its owner can read (`0600`, `write_private`) and runs the player to the end, then `played {line}`. Stopping drops the task, which kills the player (`kill_on_drop`) and removes the file.
- **Commands** (`voiceclient::Command`; the widget's `voice_action` with `talk`, `stop`, `reply`, `send`, `cancel`, `end`): the key starts listening when idle, sends while listening (hold to talk: the release sends), and is Reply while speaking; Reply stops playback, drops the lines and sends `listen`; Send now is `send`; Stop is `cancel` while listening, else `stop` (playback stopped, lines dropped); Cancel drops the turn (`cancel` or `stop`) and ends with `bye`; End (the widget closed) is `bye`. What acts on listening and comes before the main says `listening` (the key again, its release, Send now, Stop) is remembered and done when it does, after the kept audio: a short phrase said with hold to talk is not lost. The follow-up is the main's: after the last line it says `listening`, and the app streams.
- **The end**: `idle` once the main has been past it (follow-up with no speech, nothing heard, no answer) ends the conversation with `bye`, except the `idle` that answers the person's Stop: that keeps it, as the web UI's sheet does (the main answers `stop` with `idle`, `cancelled` or no reason; `internal/service/reeve_voice_session.go` `onStop`), and `voice-state` `idle` with no reason is sent. `ended {reason}` ends it without `bye`; so does a lost connection. A recorder that stops ends it with what the recorder said last (`Recorder::why_stopped`, its stderr). The recorder is ended with the conversation.
- **The widget's events**, emitted with `emit` to every webview. Only the app's own pages can listen: a server's page has no capability, so no `core:event` permission, and is never told what is said to the Reeve (the widget holds no token). A target would not keep them out: in Tauri 2 a JS `listen()` has the target `Any`, which every emit matches. The app's log has the states and line IDs, never what was said.

  | Event | Payload |
  | --- | --- |
  | `voice-state` | `{state, reason, setting}`: `connecting` (reason: the main's name), `not_ready` (reason: the line to show; setting: the server's setting to open), `listening`, `thinking`, `speaking`, `idle` (reason: how it ended: the main's idle reason, `cancelled`, `bye`, an `ended` reason, or a lost connection) |
  | `voice-level` | `{level}`: the microphone, 0 to 1 in decibels from -50 dB, every 50 ms frame |
  | `voice-pause` | `{ms, of}`: the pause bar |
  | `voice-caption` | `{kind, text}`: `partial`, `heard`, `activity`, `written` (text empty) |
  | `voice-line` | `{id, text, status}`: `queued`, `playing`, `played`, `dropped` |
  | `voice-key` | `{key, from}` (see The key) |
  | `voice-key-changed` | `KeyInfo` |
  | `voice-targets-changed` | `VoiceTargets` `{servers: [{server, name, instance}], talking_to, must_choose, chosen}` |

- **Tests**: the protocol against `internal/server/testdata/voice-session/messages.json` (every message written or read as it is there); `turn.json` replayed by a stand-in main (`tokio-tungstenite` on a local port) against `run` and `Client::websocket`, with tone and quiet fed in pieces of any size; lines played in order and acknowledged; the session over a pinned certificate and refused over another; the conversation's choices and the mute alone (`Conversation`, `Mute`); a main that stops answering pings, one that answers them, a recorder that stops, a server that never finishes the upgrade.
- **Not checked here** (the session client): a real main (the session, `pw-play` of the main's MP3 or WAV: `pw-play` and `paplay` read through libsndfile, which reads MP3 from 1.1), and a real microphone. No window shows the conversation until the widget (`LEG-127`); the `[voice]` lines on the app's output follow it.

### The widget

`voicewidget.rs` (geometry, choices, `layer_shell`), `app.rs` (`make_voice_widget`, `show_widget_as_it_should`, `place_widget`, the `voice_*` commands) and the page `src/voice/` (`voice.html`, the second Vite entry).

- **The window**: `voice`, made at start from `voice.html`: undecorated, transparent, no shadow, not resizable, out of the taskbar, always on top, on every workspace, `focused(false)` and `focusable(false)` (tao's `accept_focus` false), made hidden and shown once placed. Its capability is `capabilities/voice.json` (`core:event:default`, `core:app:default`, and `allow-<command>` for only the commands the page calls: `voice_action`, `voice_status`, `voice_key_info`, `voice_open_settings`, `voice_widget_size`, `voice_widget_menu`, `voice_widget_drag_start`, `voice_widget_drag_move`, `voice_widget_drag_end`, `voice_widget_layout`). `build.rs` lists every app command in `tauri_build::AppManifest::commands`, which makes `allow-`/`deny-` permissions for each (in `permissions/autogenerated/`, not committed), so a command is callable only where a capability allows it; `capabilities/shell.json` allows all of them. A test in `app.rs` keeps `COMMANDS` the same as `generate_handler!`; it holds no token and hears the `voice-*` events, which only the app's own pages can listen to (see The conversation). The page tells its size (`voice_widget_size`, from a `ResizeObserver`), so the window is the size of what it draws and no transparent margin takes clicks; each new size places it again, so the whole widget stays on the screen as it grows. The size is kept to `voicewidget::limits` of the monitor it is on: at most `MAX_SIZE` (480 by 640 logical), less on a screen too small for that with 16 px on both sides, at least 40 by 40.
- **Its layout** (`WidgetLayout`): `voice_widget_layout` answers, and the `voice-widget-layout` event says when it changes (`tell_layout`, from `place_widget`), `{width, height, anchor}`: those limits and where it keeps to. The page's root (`.voice-widget`, `src/voice/widget.css`) is a flex column with `--widget-max-w`/`--widget-max-h` from it and `data-anchor`, its children aligned to the anchor's side (end for the right-hand anchors, centre for `top` and `bottom`). Every child keeps its size except the one marked `data-widget-feed`, which scrolls in the height left (`min-height: 0`): the capsule or card never shrinks or leaves the screen, whatever the feed holds.
- **Where it keeps to** (`voice.anchor`, `store::Anchor`; `corner` in a file from before edges, read as its alias): a corner (`bottom-right` by default, `bottom-left`, `top-right`, `top-left`) or an edge it is centred on (`top`, `bottom`, `left`, `right`), and `voice.offset` `{x, y}`, the logical distance from the anchored left-or-right edge and top-or-bottom edge (an axis it is centred on has none), absent for the default 16 px (`MARGIN`). `voicewidget::margins` keeps the saved offset so the whole widget, at the size the page last asked for, is inside the work area (a card that grows from a capsule dropped near an edge is pushed in, the saved offset unchanged), and falls back to the 16 px margin when the saved spot is off this screen (a monitor unplugged). `origin` is the widget's top-left for those margins, `place` the window position (physical, from the logical size times the scale, not the window's own size, which on Linux changes only once the compositor has answered). Choosing an anchor (the menu's **Place**, Servers & keys) forgets the offset.
- **Dragging** (`src/voice/drag.ts`, `useWidgetDrag`, on the page's root; `voice_widget_drag_*`): a left-button press that moves `DRAG_FROM` (4) px is a drag, and its click is swallowed (`onClickCapture`), so a click on the capsule still talks; nothing inside `[data-no-drag]` starts one (the approvals list's buttons and scrollbar). Start takes the widget's top-left within the monitor's work area (`Drag`). The window moves under the pointer, so each `pointermove`'s client position less where the pointer took hold is how far it still has to go: `voice_widget_drag_move {dx, dy}` moves it that much (`voicewidget::drag_to`, kept on the monitor it started on), one move in flight at a time, and moves while one is in flight are dropped (measured from where the window was). On a layer surface it is anchored to a corner while dragged (`drag_corner`: its own, or for an edge a corner on that edge's side) with margins from those edges (`margins_for`), so they start as they were and the surface does not jump; on X11 `set_position`. The drop (`voice_widget_drag_end`, also on `pointercancel` and `lostpointercapture`) is where it is shown: `voicewidget::drop_at` picks the nearest corner, or the edge whose middle tenth its centre is in (`CENTRE_BAND`; in the middle of the screen, the nearest edge), with the offset that keeps it there, saves both, places it and sends `voice-widget-changed`. An ordinary window on Wayland (`Floating`) is handed to the compositor (`start_dragging`, xdg move) and its spot is not kept.
- **Placement** (`voicewidget::placement`; Wayland is the GTK window's display being a `GdkWaylandDisplay`, not the environment, so `GDK_BACKEND=x11` is placed as X11): on Wayland a layer surface when `gtk-layer-shell` loads and the compositor has the protocol, else an ordinary window the compositor places (`Floating`); on X11 and macOS the app places it (`Placed`, `voicewidget::place`). A layer surface gets its anchor, margins and size (`layer_shell::place`) before it is first shown and again only when they change (`WidgetState.applied`). Its size is the window's size request (`layer_shell::request`): gtk-layer-shell sends the request after the first configure, and a window holding only a web view requests none, so without one the surface is configured and never drawn, on GTK's main thread (`run_on_main_thread`), since a conversation runs on tokio's. GTK on Wayland knows no panels, so the work area there is the whole monitor, while a layer surface's margins count from inside panels with an exclusive zone: a widget dropped across the screen from the edge it was anchored to may land off by the panel's height, and a card next to a panel may reach under it by as much. macOS: TODO, a non-activating `NSPanel` (`tauri-nspanel`) at floating level on every space, and `macOSPrivateApi` for the transparent window.
- **Layer shell** (`voicewidget::layer_shell`, Linux): `libgtk-layer-shell.so.0` opened at run time with `libloading`, never linked, so a build or a computer without it still runs; `$APPDIR/usr/lib/libgtk-layer-shell.so.0` first, the AppImage's own, else the system's by name. `gtk_layer_is_supported`, then on tao's `gtk::ApplicationWindow` before it is shown (tao only realizes a window when it is shown, so a window made with `visible(false)` is still unrealized; `attach` refuses a realized one and the widget falls back): the empty title bar tao gives an undecorated Wayland window removed, the size request set (`FIRST_SIZE`), `init_for_window`, namespace `legato-voice`, layer Top, exclusive zone 0, keyboard mode None (pointer clicks still reach it). `place` sets each edge's anchor (`voicewidget::anchors`: two for a corner, one for an edge, along which layer shell centres it) and margin (the offset on anchored edges, 0 on the rest). Needs gtk-layer-shell 0.6 or later (`gtk_layer_set_keyboard_mode`). The `Gtk-WARNING: gtk_window_set_titlebar() called on a realized window` at start is tao's, for the main window (undecorated, shown as it is made), with or without layer shell; it says nothing about the widget.
- **Carrying the library in the AppImage**: `scripts/layer-shell.sh` (`build.beforeBundleCommand`, so every `tauri build` runs it; nothing off Linux x86_64, nothing when already there) downloads Ubuntu 26.04's `libgtk-layer-shell0_0.10.1-1_amd64.deb`, checks its SHA-256, and unpacks the library and its copyright into `src-tauri/target/layer-shell/` (with a `version` file, so a change of version fetches again); `bundle.linux.appimage.files` puts them at `usr/lib/libgtk-layer-shell.so.0` and `usr/share/doc/libgtk-layer-shell0/copyright` in the AppImage. gtk-layer-shell reads GTK's private structs, so it must know the GTK the AppImage carries, which is the build machine's: 0.10.1 knows GTK up to 3.24.52 (Fedora 44's). 0.8.2 knew 3.24.39, and on 3.24.52 it crashed in its popup grab code (`gdk_window_get_priv_grab_seat`, a garbage `transient_for`) after some minutes. When the build machine's GTK passes the version the carried one knows, take a newer one (its changelog's "Compat: bump supported GTK"). GTK 3's gtk-layer-shell wraps nothing of `libwayland-client`, so opening it after GTK has started works. It needs only GTK 3, GLib, `libwayland-client` and libc (glibc 2.4 symbols). The build needs `curl`, `ar`, `tar` with zstd and `sha256sum`.
- **What it draws** (`src/voice/model.ts`, `Widget.tsx`): the view cut to its latest words (`capped`: the words so far 180 characters, what was sent 140, the Reeve's activity 60, how it ended 140, each `tail`ed from the start of a word after an ellipsis; of the Reeve's lines the one playing, cut to 180, and as many to come as fit in what is left), so a long dictation keeps the card to a few lines instead of growing past the screen; the conversation keeps the whole text. `VoiceCapsule` and `VoiceCard` from `web/src/voice/` (Vite alias `@web-voice`, `server.fs.allow`, `resolve.dedupe` of React; `tsconfig` `paths` points React's types at this app's copy, so `web/` needs no `node_modules`). Tailwind 4 draws them in this window only (`src/voice/widget.css`: `@import "tailwindcss"`, `@source` of `web/src/voice`); Geist Mono is bundled (`@fontsource/geist-mono`). The model maps the events: `connecting` and `idle` the capsule; `not_ready` the amber capsule with the reason and **Open settings** (`voice_open_settings`: the main's page at `/settings#setting-<key>` in the main window, in front, `shell-show-server` to the shell); `listening`/`thinking`/`speaking` the card, its "<key> to send" the bound key's text; `idle` with something to say (nothing heard, no answer, failed, taken over, answered in writing) the card for 6 seconds or until Close; `bye`, `cancelled` and a plain end the capsule; `idle` with no reason (the person stopped the Reeve, and the app keeps the conversation) keeps the card, at rest, with Close and Talk. At rest it asks `voice_status` (the same check as the key, `ready_main`, recording nothing) at start, every 30 seconds and when the servers change.
- **Its buttons**: a click on the capsule is the key (`voice_action talk`); the card's Send now, Cancel, Stop, Reply and Close are `send`, `cancel`, `stop`, `reply`, `end`. A right click asks `voice_widget_menu`: a native menu with **Hide**, **Place** (the four corners, then the four edges, the current one checked) and **Settings…** (the main window's Servers & keys, `shell-open-panel`).
- **Shown**: unless the person hid it (Hide, or Servers & keys › **Show the voice widget**, `voice.widget_hidden`), and then still while a conversation runs (an `idle` with no reason, a conversation kept after Stop, included), for 8 seconds when the key says why it cannot (`NOT_READY_FOR`), and for 6 seconds after a conversation that ended with something to say, as long as the page's card (`ENDED_FOR`; not after `bye`, `cancelled`, or `done` with nothing written) (`voicewidget::showing`, `shows`). Where it keeps to is also in Servers & keys, which says when it was dropped on a spot of its own.
- **Motion**: the shared components stop their animations under `prefers-reduced-motion`.
- **Checked headless**: `scripts/layer-shell-check.sh` runs the built app in a headless KWin (`kwin_wayland --virtual`) with the carried library, on its own session bus and in scratch folders, and passes when the widget's layer surface is anchored, configured and given a buffer (it read 0 buffers before the size request). It sees no pixels and sends no input.
- **Not checked here**: how the layer surface resizes as the page grows from capsule to card (the size request changes, which gtk-layer-shell sends as `set_size`; checked only in a small GTK probe); the right-click menu's popup from a layer surface, where 0.8.2 crashed; the always-on-top window on X11; transparency; the native menu's popup position; whether a drag on a layer surface follows the pointer smoothly (each move waits for the last); a drop on KWin next to a panel (the panel offset above).

## Pairing

`src-tauri/src/pairing.rs` is SPAKE2 (RFC 9382, P-256/SHA-256/HKDF/HMAC) as `internal/engine/pairing` has it, the app as party A with the phone's identities, and `legato.rs::pair` the two requests (`POST /api/pair/exchange`, `/api/pair/confirm`). `tests/fixtures/pairing-exchange.json` is written by `go test ./internal/engine/pairing -update`, which fails when the desktop's copy differs; `resources/pairing-words.txt` is checked by a Rust test against the digest `internal/engine/pairing/phrase_test.go` holds. A phrase is read word by word by its first three letters.

Over HTTPS the certificate presented during pairing is recorded (`PinVerifier` with no pin) and must afterwards be the one the server sealed (`ca_certificate`) or be issued by it for the host, else pairing fails. The sealed certificate is the server's pin from then on.

## Talking to a server

`legato.rs::Client`: reqwest with a rustls configuration whose only verifier is `PinVerifier` (`pin.rs`: the presented leaf is the pinned certificate, or webpki finds it issued by the pinned one for the host). An `https` server without a pin is refused. Every request carries `Origin: https://legato-desktop.invalid`, which `/api/devices/passkey/options` takes as the page's origin.

## Keys

The app is its own WebAuthn client (WebKitGTK has none), over CTAP2 with `ctap-hid-fido2` (`fido.rs`), and `webauthn.rs` builds what a browser would send.

- **One credential per key.** `add_key` makes a non-resident credential on the one plugged-in key for relying party `legato-desktop.invalid` (a touch, and the key's PIN only when it insists: CTAP error `0x36`). The app keeps the credential ID and the authenticator data.
- **Enrolled on every server** by `enroll`: the server's options, client data with its challenge and the app's origin, and a `none` attestation over the kept authenticator data. No touch is needed, since the credential exists. A server keeps the origin and relying party and checks them; a server with enrolled devices makes the new one `pending` behind a `devices` approval. Pairing a server enrolls every key.
- **Signing**: `prepare` finds a plugged-in key the server knows (each plugged-in key is asked, without a touch, `up=false`, whether it holds each credential), fetches `/api/approvals/{id}/challenge` for that device and keeps the request on the Rust side. `sign` checks the option is one of the request's allow options, builds the message a phone signs (`webauthn::signed_message`), asks the key for an assertion over the SHA-256 of it with a touch and no PIN, and posts the decision `by: "desktop"`. Legato records `verification: presence` (see [Approvals](approvals.md)). The sheet draws the request from what `prepare` returned, so the page cannot change what is signed.
- **Revoking** asks every server to remove the key's device (each a signed approval) and forgets the key. `keys` drops an enrolment the server no longer lists.

### Touch ID

`src-tauri/src/touchid.rs`. On a Mac the app is the authenticator: a P-256 key in the Secure Enclave with the access control `privateKeyUsage` and `biometryCurrentSet`, so it signs only after a fingerprint. `touchid::make` asks the chip for a key and builds the authenticator data a platform authenticator gives (rpIdHash of `legato-desktop.invalid`, flags UP, UV and AT, counter 0, AAGUID zero, the credential ID, which is the SHA-256 of the public key, and the key as a COSE_Key); no fingerprint is asked for. It is enrolled as a security key's credential is, a `none` attestation over that data, with `authenticatorAttachment: platform` and transport `internal`, so Legato lists it as a `passkey`. `touchid::sign` signs the authenticator data (UP, UV, counter 0) and the client data's hash; the dialog reads "Legato is trying to sign “<title>” on <server>". Legato records `verification: verified`. The counter stays 0, which WebAuthn takes as "no counter".

- **The chip** is behind the `Enclave` trait. On a Mac it is `touchid/`, a Swift package of three C functions (`legato_touchid_available`, `_create`, `_sign`; buffers are the caller's; 0 worked, 1 failed with words, 2 cancelled) that `build.rs` builds and links with `swift-rs` when the build machine is a Mac. The key is CryptoKit's `dataRepresentation`, a blob only this Mac's chip can use, not a Keychain item: so no entitlement or developer account is needed, and every build of the app can use it (checked on a Mac with two ad hoc builds with the hardened runtime, as the release signs it). Any program running as the person can ask the chip to sign with the blob, as any can ask a security key, but not without a fingerprint.
- **One per Mac** (`add_touch_id`). `touch_id` says whether this computer can (`this_mac`: a Secure Enclave and Touch ID set up), and the panel offers **Add Touch ID** only then.
- **Signing** prefers Touch ID when the server knows it and this Mac has it, else a plugged-in security key it knows. `prepare` says which (`with`), and the sheet asks for a fingerprint or a touch.
- Adding or removing a fingerprint in System Settings invalidates the key for good (`biometryCurrentSet`): remove it and add Touch ID again.

## What the app keeps

`store.rs`: `~/.config/legato-desktop/state.json` (mode `0600`, written beside and renamed over; `LEGATO_DESKTOP_STATE` names another file): each server's name, address (the servers in the dock's order), sealed certificate, tint and the device each key is on it; each key's name, credential ID and authenticator data, and a Touch ID key's Secure Enclave blob (`enclave`); `import_target` (`ask` or `current`), and `voice` (`hold_to_talk`; `server`, the instance ID of the Reeve the person chose to talk to). Tokens are in the desktop's keyring (`keyring`: Secret Service on Linux, Keychain on macOS) under service `dev.legato.desktop`, account the server's ID. Removing a server deletes its token. WebKit's data (cookies, storage) is in `~/.local/share/dev.legato.desktop/`.

## Network discovery

`discovery.rs` browses `_legato._tcp` with `mdns-sd` from start, asking again every 5 seconds for the first minute and every minute after (an early query can go unanswered, and the library's own backoff is long). A server's address is its IPv4 address (else IPv6), its port, and `https` when its `scheme` TXT record says so, as `mobile/.../Discovery.kt`. `discovered` leaves out paired servers.

## Releases and updates

The release workflow builds the app when `scripts/desktop-changed.sh` says so (the `desktop` input: `always`, `never`, or `auto`: `desktop/` changed since the newest stable release that carries the AppImage), on `ubuntu-24.04` (`legato-desktop-x86_64.AppImage`, `legato-desktop-SHA256SUMS`; the AppImage carries that machine's WebKitGTK and needs glibc 2.39 or later: 22.04's WebKitGTK crashed its page process on a Legato page that 2.52 shows) and `macos-15` (`legato-desktop-macos-arm64.dmg` to install from, `legato-desktop-macos-arm64.app.tar.gz` to update from, `legato-desktop-macos-SHA256SUMS`; ad hoc signed, not notarized; the tar made with `COPYFILE_DISABLE=1`, so no `._` files), with build provenance, attached to the release Legato's job published. The version is the release's: `LEGATO_DESKTOP_VERSION` at build time (`updates::version`, else `dev`) and the bundle's version through `--config`.

`updates.rs`: `check_update` (at start, every 6 hours, and **Check for updates** in the Servers panel's "This app" section; nothing for `dev`) lists the repository's releases and takes the newest stable one with this platform's build and its checksums (`this_platform`, `newest_with`: `LINUX` or `MACOS`), since not every release has a desktop build and each platform's job can fail alone. It says whether this copy can install it, and if not why (`reason`). `apply_update` downloads the build and the checksums and checks the SHA-256. Like Legato's own updater, the checksum comes from the same release.

- **Linux**, only when started as an AppImage (`$APPIMAGE`): `install` writes it beside the running one, keeps the old one as `.prev` and renames the new one over it; `restart_app` starts it and exits.
- **A Mac**: `app_bundle` finds the running `….app` from the executable's path, and refuses one macOS runs from a hidden read-only copy (`/AppTranslocation/`, opened from Downloads with the quarantine flag) or from the disk image (`/Volumes/`): the person moves it to Applications first. `install_bundle` unpacks the archive (`tar` and `flate2`) into `.legato-update-<random>` beside the app, checks it holds `Legato.app/Contents/MacOS/`, keeps the old app as `.Legato.app.prev` (hidden, replacing an older one) and renames the new one into place; a bad archive leaves the app as it was. `restart_app` runs `open -n` on the bundle and exits. A file the app downloads itself carries no quarantine flag, so Gatekeeper does not check the new copy again. macOS 13 and later may refuse an app without a developer team changing an app bundle (App Management): the rename then fails with a permission error, which says to allow Legato in System Settings › Privacy & Security › App Management. Untested on a Mac until a release carries the archive; to try it, build an older version on the Mac (`LEGATO_DESKTOP_VERSION=v0.0.1 pnpm tauri build --bundles app` in `desktop/`), put it in Applications and update.

## Tests

`task desktop:test`: `node --test "tests/*.test.ts"` (`desktop/tests/`, outside `src` so `tsc -b` does not need Node's types: which screen the content area holds and which failed pages load again, `src/pageState.ts`), `vitest run` (the voice widget's page in jsdom with Tauri's events and commands mocked, its model, the transcript cap and the drag gesture: `src/voice/widget.test.tsx`), `cargo test --lib` (the page's script and events run in Node, opening a worker's pairing request against a small HTTP server in the test, the recorder with `sh` standing in for `parecord` (and streaming), the key's choices (`voicekey`), the voice protocol against the server's fixtures and a session against a stand-in main (`voiceproto`, `voiceclient`), choosing the main (`voicemain`), the widget's anchors, margins, drag and drop and choices (`voicewidget`), pairing against the shared fixture, the pin check against certificates `rcgen` makes, the WebAuthn messages, Touch ID's authenticator data and signatures with a software key in place of the chip, the state file, discovery's addresses, the updater's choice, checksum and swap) and `tsc -b`. `tests/fixtures/touch-id-key.json` records what the app builds for a known key (`LEGATO_UPDATE_FIXTURES=1 cargo test --lib` rewrites it); `internal/service`'s `TestADesktopTouchIDKeyEnrollsAndSignsAsVerified` enrolls and signs with those bytes through Legato's own checks. The Swift in `touchid/` builds only on a Mac. The window, the keys and pairing with a server are checked by running the app against a scratch Legato (`task desktop:dev`, `LEGATO_DESKTOP_STATE` on a scratch file).

## Known limits

- macOS: no pinned TLS in server pages (the trust screen has the Mac trust the CA instead); updating itself only from Applications; the app is untested on a Mac (Touch ID's Secure Enclave key was tried there alone). No Windows build.
- One key at a time is added; signing finds the right key among several plugged in.
- The server webview is hidden while a panel or the sheet is open, rather than drawn under it.
- Dictation and talking to the Reeve need `parecord` or `arecord` on Linux; the app does not record on a Mac.

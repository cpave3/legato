# Settings in the database

Settings live in `config.yaml` and, for every setting that is not file-only, in the database too. The file pins; the database fills in. Site page: `reference/configuration` § Settings in the file and in the database.

## The registry

`config/settings.go` declares every setting that can live in the database (`config.Settings()`, `LookupSetting`). Each `config.Setting` has:

- `Key`: the dotted name of `config.yaml` (`agents.reviews`), resolved to a field of `config.Config` by its `yaml` tags (`settingField`, `SettingValue`; a `*bool` reads as its documented default when nil, `pointerDefault`).
- `Kind` (`bool`, `string`, `int`, `enum` with `Enum`, `duration`, `strings`) and an optional `Check`: `DecodeSetting` checks a JSON value by them.
- `Class`: `read`, `change` or `risky` (the Reeve's classes, see Part 4 of the spec, and `docs/ai/reeve.md` once it exists).
- `Mode`: `live` (read on each use: `web.tint`, `updates.mode`, `burnlite.projects`), `new_agents`, or `restart` (wired into services at start). A setting is `live` only where it is already read on each use; nothing was rewired to make one live.
- `Secret`: the value is the name of a secret, never the secret.
- `Section` and `Group`: its one home in web Settings (§ Sections and groups).
- `Help`: one line on what the setting does, including what empty or off means. It replaced `Description`; the API still sends it as `description` too, for one release (set by `init`, never written in the registry).
- `Unit`: `seconds`, `ms` or `bytes` for a whole number counted in one (a test holds every `int` named `_seconds`, `_ms`, `_bytes` to it); a `duration` needs none.
- `DefaultLabel`: what the setting is when unset, when that is not its zero value (`4`, `engram on PATH`).

The words are the operator's, written once here for the web, the Reeve and `config show --json`: a `Title` is a plain label with no group prefix and no unit (the group heading and `Unit` say those; `TestEverySettingHasHelpAndAPlainLabel`), and every setting has `Help`. A `DefaultLabel` is given only when the registry's own default is the zero value (`TestADefaultLabelIsGivenOnlyWhenUnsetIsTheZeroValue`), and agrees with the runtime: `TestADefaultLabelIsWhatTheRuntimeUses` (config's accessors) and `TestTheRegistrysDefaultLabelsAreWhatTheServicesUse` (`internal/service`: the swarm limits `DefaultSwarmMax*`, the kickoff delay, the update mode, the Reeve's peer rule and name). A number's `DefaultLabel` is the number in its `Unit`, for the web to format.

### Sections and groups

`config/settings_layout.go` places each setting: `settingLayout` maps a key, or a prefix ending in `.`, to its section, group and unit; `init` copies the place onto each `Setting` and panics at start when a setting has none, so a new setting must be placed. `SettingSections()` lists the 15 section IDs that hold registry settings, in nav order: `appearance`, `attention`, `input`, `agents`, `repositories`, `sandbox`, `reeve`, `swarms`, `review-passes`, `learn`, `board`, `integrations`, `security`, `connections`, `system` (Macros, the sixteenth section, is its own page). A feature's own switch (`swarm.enabled`, `review_passes.enabled`, `learning.enabled`, `agents.sandbox.enabled`) is in the group `config.GroupLead` (`On or off`), which the web shows first with no heading. Lists, file-only keys and the web's cards are placed by the web catalog (`web/src/lib/settingsCatalog.ts`).

`config.FileOnlySettings()` lists the file-only settings (`db`, `data_dir`, `secrets.master_key`, `secrets.onepassword`, `web.enabled`, `web.port`, `web.tls`, `web.public_url`, `approval_devices.android_app_digests`); `IsFileOnly` says whether a key is or is under one. A test fails if one is registered.

Every single value of `config.Config` is registered (a list of strings, such as `jira.project_keys`, is one value of kind `strings`). `TestEverySettingIsRegisteredOrFileOnly` (`config/settings_coverage_test.go`) walks `config.Config` by its `yaml` tags and fails for a field that is neither registered, file-only, nor a list of named entries (`config.EntryLists`: kept in tables of their own, see § Lists). `config.Config` gained `Web.Tint` and `Updates.Mode` for the two that were instance values only. Nil sections on a key's way (`integrations.argus`) are read as zero values and made when a value is set (`section`).

Modes are honest: `live` only for `web.tint`, `updates.mode`, `burnlite.projects` and the rail's switches `web.rail.*` (read through the settings service's `Effective` on each `GET /api/attention?view=rail`; see [Attention](attention.md) § The rail view), which their services read on each use; everything else is `restart`, since it is read once when services are built. Classes: settings that touch security (tokens, the sandbox, credential channels, the GitHub sign-in, network announcement, updates) are `risky`; the rest `change`.

**Secrets.** A setting marked `Secret` (`jira.api_token`, `github.token`, `notifications.ntfy.token`, `manticore.api_key`) takes only a secret's name in the database: `legato://<name>` (Legato's sealed store) or `op://<vault>/<item>/<field>` (1Password); `DecodeSetting` refuses anything else. `ApplySettings` reads the secret through a `SecretResolver` (`settingSecrets` in `cmd/legato/database.go`: `configuredSecretStore` for `legato://`, `credential.OnePasswordStore` for `op://`) and sets the value in the process's configuration; a secret that cannot be read leaves the setting empty and is logged. `List` and `Get` show the name, and never a secret given in `config.yaml` (`(set in config.yaml)`). `${ENV}` references stay valid in the file, where they are pins. Each secret setting that names a secret carries `secret_status` (`stored` or `missing`, never the value): for a name saved here, whether the process's resolver (`SetSecretResolver`, `settingSecrets` in `cmd/legato/database.go`, wired by `settingsFor`) can read it, each answer kept 30 seconds; for one `config.yaml` gives, whether it has a value. The web row shows **Stored** or **Not found**, and for a `legato://` name the command that stores or replaces it, `legato secret add <name>`, with Copy. It does not offer the Reeve's secret form: anyone with the web token may answer an open request (`ReeveSecrets.Fulfil` needs no signature), so a route that opened one from the browser would let a browser write a secret by itself.

## Layering

- **Pins.** `config.Load` records every dotted path the file gives a value (`pinnedKeys`: mappings walked, lists and scalars as leaves; `null` gives none). `Config.Pinned(key)` is true for that path or for any path above it that is a leaf (a list given whole). `PinnedKeys` lists the registered ones.
- **Overlay.** `config.Overlay(cfg, values)` applies JSON values by key to the settings the file does not pin, then runs `validate`: the same checks and normalization `Load` runs on a file (`Load` now calls it too). Its error is `Load`'s error for the same configuration. `config.OverlayAll(cfg, values, entries)` applies the values and the list entries first and validates once, so a value may name an entry kept in the database (`default_workspace` a workspace added there); `ApplySettings`, `Effective`, `Check` and `Reset` use it.
- **Storage.** Migration 098 adds `settings` (`key` primary, `value` JSON, `updated_at`, `updated_by`) and moves the instance values `web.tint`, `updates.mode` and `burnlite.projects` into it, keeping their values. Store: `ListSettings`, `SettingValues`, `GetSetting`, `SetSetting`, `DeleteSetting`. A pinned value is never written here.
- **The effective configuration.** `service.ApplySettings(ctx, db, cfg, resolve)` overlays the database's values on a configuration loaded from the file, in place. `openStore` (`cmd/legato/database.go`) calls it, so the TUI, `legato serve` and every short-lived command that opens the store read the same effective configuration. When the overlay would be invalid (the file changed since a value was saved), it is skipped and logged: the file's configuration applies, and a database value never stops Legato from starting.

## The service

`service.SettingsService` (`internal/service/settings.go`):

- `Effective`: the file, then the database.
- `List`, `Get`: each setting with `value`, `source` (`default`, `config.yaml`, `database`), `pinned`, `updated_at`, `updated_by`.
- `Check`, `Set`: the value by its own rule (`DecodeSetting`), then refused when pinned (`ErrSettingPinned`), then the whole configuration (the file, every database value and list entry, the change) through `OverlayAll`. `Set` keeps the canonical JSON.
- `Reset`: deletes the database value (checked the same way).
- `RestoreSettings`: a `SettingsRestorer` for restart rollback.
- `StringSetting`: the `TintStore` shape (`GetInstanceValue`/`SetInstanceValue` by key) over the settings, which `TintService` and `UpdateService` now take instead of the instance values.

Burnlite's projects: `service.BurnliteProjects` and `SaveBurnliteProjects` read and write the `burnlite.projects` setting; the runtime passes the configured projects only when the file pins them (`pinnedBurnliteProjects`).

## Sources, the API and the CLI

- **Waiting for a restart.** Each process makes one `SettingsService` per store at start (`settingsFor` in `cmd/legato/settings_runtime.go`), which calls `MarkStarted`: the values it started with. A `restart`-mode setting whose effective value differs from that is `pending_restart` (compared before a pinned secret is masked as `(set in config.yaml)`, so an unchanged one never waits) ("applies at restart"); `PendingRestart` lists them; such a setting carries its `started_value`. `MarkStarted` also keeps each list's entries saved here, and `Lists` names the entries of a restart list added, changed or removed since in `pending_entries`. `OnChange` hooks run after each `Set` or `Reset`; `wireSettings` publishes `EventSettingsChanged` on them.
- **The restart bar and Undo** (web). While anything waits, `RestartBar` (`web/src/components/settings/RestartSettings.tsx`) sits under the Settings header on every section: it names up to three waiting changes (`waitingChanges` in `web/src/lib/pendingRestart.ts`, "Swarms › Workers at once"), counts the rest, and has **Restart Legato** (`POST /api/restart`, after a confirm). System › Restart (`RestartCard`) lists each with its value then and now ("4 → 6") and **Undo**: a `DELETE` (reset) when the started value is the default (`undoIsReset`), else a `PUT` of `started_value`; list entries are named without Undo. There is no undo route: the API's `started_value` and `default` are enough.
- **Attention.** The `settings` producer (`SettingsAttentionAdapter`, signal `settings_restart`) raises one item, "Restart to apply N changes", while any wait, with **Restart Legato** (an `execute` action that runs `restartAll`) and **Open settings**. Its revision is the waiting keys, so a dismissed item comes back when another change waits.
- **API** (`internal/server/settings_registry.go`): `GET /api/config/settings` (`{settings: [SettingValue], file_only: [...]}`: each setting's `key`, `title`, `section`, `group`, `help` (and `description`, its old name), `unit`, `default_label`, `default`, `kind`, `enum`, `class`, `mode`, `secret`, `value`, `source`, `pinned`, `pending_restart`, `started_value` while it waits, `updated_at`, `updated_by`; and `file_only_values`); `PUT /api/config/settings/{key}` (`{value}`; `200` with the new `SettingValue`; `404` not a setting, `409` pinned, `400` a refused value with its reason); `DELETE /api/config/settings/{key}` (reset). A change broadcasts `settings_changed`.
- **CLI.** `legato config show [--sources] [--json]` prints `key: value` for every setting; `--sources` adds `(default)`, `(config.yaml, pinned)` or `(set here)`. That text is held by a golden file (`cmd/legato/testdata/config_show_sources.golden`); `--json` carries every field of the registry.

## Lists

A list of named entries is the file's entries, each pinned and matched by name ignoring case, plus the database's. Saving an entry whose name the file has is refused (`config.ErrEntryPinned`).

- **Lists kept in `setting_entries`** (migration 099: `list`, `name`, `value` JSON in `config.yaml`'s shape, `updated_at`, `updated_by`; key `(list, name)`): `config.EntryListDefs()` — `workspaces`, `macros`, `adapters` (a map: its keys name entries), `credentials`, `credential_sources` (named by `vault`), `agents.tmux_options` (map), `agents.sandbox.mounts` (named by `path`), `swarm.prompts` (map). One table holds them all, keyed by list, rather than a table each: the entries are configuration in `config.yaml`'s shape, and one table keeps the overlay generic. Classes: credentials, credential sources and sandbox mounts are `risky`; the rest `change`. Modes: `restart`, except `agents.tmux_options` (`new_agents`) and `macros` (`live`: `MacroService` reads them at each use; the list also shows the built-in macros, see [Configuration](config.md)).
- **Lists with tables of their own** keep them and the same rule (`config.EntryLists` lists all): repository presets (`repository_presets`, refusing a name of `config.yaml`'s `repositories`), repository guidance (`repository_guidance`, refusing a configured repository), resources (`resources`, refusing a configured name), directory presets (a configured path is answered with the configured preset), and the board's columns (`column_mappings`, made from `board.columns` by `legato columns sync`).
- **Config.** `Load` records each entry list's names as the file gives them (`recordFileEntries`; `Config.PinnedEntry`, `FileEntries`). `config.OverlayEntries` adds the database's entries (decoded from JSON by their `yaml` tags; the name set from the key) and runs `validate`. `EntryValue` reads one entry back in its YAML shape.
- **Service.** `ApplySettings` and `Effective` overlay the values, then the entries. `SettingsService.Lists` (each list with its entries and their `source`; a secret written in the file is shown as `(set in config.yaml)`), `SetEntry` and `CheckEntry` (refused when pinned, or when the whole configuration would be invalid), `DeleteEntry`.
- **Entry shapes.** `agents.tmux_options` entries are JSON strings, matching the configuration's string-valued map. Other entry lists take objects. `CheckEntry` validates the declared shape before applying the full configuration; a tmux option such as `history-limit` keeps `"50000"` as a string.
- **API.** `GET /api/config/lists`; `PUT /api/config/lists/{list}/{name}` (`{value}`; `409` for a name the file has, `400` with the reason for a refused entry); `DELETE /api/config/lists/{list}/{name}` (`404` for none). Each change broadcasts `settings_changed`.
- **Web.** Settings › System (`components/settings/ListSettings.tsx`): each list as a card, the file's entries with a lock, the database's with **Edit** and **Remove**, and **Add**, which takes a name and the entry's fields as JSON in `config.yaml`'s shape.

## Writing config.yaml, and the move

- **The writer** (`config/writer.go`). `EditFile(path, edit)` parses the file into `yaml.v3` nodes, applies `edit`, and writes it back atomically (a temporary file renamed over it), after copying the old file to `config.yaml.<UTC time>.bak` (`BackupPath`). Comments, order and every value not edited stay as they were; an `${ENV}` reference stays one. Helpers: `RemoveKey` (and the sections and lists it leaves empty), `SetKey` (keeping the key's place and comments), `RemoveListEntry` (by name field, or a map key). `EditBytes` does the same on bytes, for a check or a diff before writing; `EditFile` writes what it gives.
- **Keys into lists** (`config/writer_keys.go`): a key's part may be followed by selectors, `[2]` (an index from 0), `[name=github]` (the one mapping entry whose field has that value, case ignored; none or several is an error naming the list) and, for `SetKey` only, `[+]` (a new entry at the end; a new mapping when more of the key follows). So `credentials[name=github].policy[1].operation` names one rule's operation. Dots inside brackets do not split the key. `SetKey` never makes an entry up: a list or entry that is not there is an error, unless `[+]`. `RemoveKey` removes an entry, or a key inside one. `PlainKey` is a key without its selectors (`reeve.rules.level`).
- **Only the text that changed** (`config/writer_patch.go`). Re-encoding through `yaml.v3` keeps comments and order but rewrites some formatting (a flow mapping `{ a: 1 }` comes back `{a: 1}`) on every line. So `EditBytes` compares the edited nodes with the original's (`patchDocument`): when every change is a single-line scalar replaced in place (written in the old value's quoting when both are strings) or entries added after the last of a block list (one line in flow style when the last entry is, else a block at its indent), it makes just those changes to the original text. Any other change (a key added or removed, an entry removed, a multi-line scalar) re-encodes the document as before.
- **What can move** (`service.SettingsMover.Movable`): every registered setting the file pins, except a secret setting and one whose value in the file reads an environment variable (moving it would freeze the variable's value); and every entry the file gives of an entry list, except a list that reads a variable and an ordered list (`EntryList.Ordered`: `reeve.rules`, where the last rule that matches wins; the database's entries are added after the file's, sorted by name, so a moved rule would change which one wins). Then `keepFileLoadable` keeps only what can leave with the file still loading by itself (`config.LoadBytes` on the rewritten bytes), since a start runs `config.Load` before it opens the database: `manticore.url` stays while the secret `manticore.api_key` does. It takes what can go in passes, so a pair that must leave together (a workspace and the `default_workspace` naming it) still goes.
- **A move** (`SettingsMover.Move`): refused while a restart is pending (`ErrRestartPending`), and refused when `config.yaml` would not load without what it names ("would not load without them"). It copies each value into `settings` and each entry into `setting_entries`, keeping the old database values (an entry the file shadowed included, so a rollback restores it rather than deleting it); rewrites `config.yaml` without them (with its backup); and records the restart (`RestartRollback.Begin`) with the backup and the old values (`RestartSetting.List` set for an entry). The caller restarts: a start that fails puts back both the file and the database (`SettingsService.RestoreSettings`, which the runtime's rollback now gets). A start whose `config.yaml` does not load (`RollBackUnloadable`, before any configuration) puts the database's values back too, from the restart record.
- **What a move records.** Each `RestartSetting` of the restart record has `Old` (the database's value before, which a rollback puts back) and `New` (the value the move wrote: config.yaml's). An entry is written under the name the database already keeps it by, case ignored (`storedEntryName`), so an older row of the same name in another case does not stay beside it. The file's value always wins over an older database value (`TestMovingPinnedSettingsKeepsTheFilesValuesOverOlderDatabaseOnes`).
- **A config edit that removes a pin** (the Reeve's `propose_config_edit`) is a move too: see [The Reeve](reeve.md) § `propose_config_edit`. Before LEG-164 it only rewrote the file, so the database's older values took over.
- **The offer.** The `settings-move` Attention producer (`SettingsMoveAttentionAdapter`, signal `settings_move`) raises one item while anything can move, "Move N settings from config.yaml into the database", navigating to Settings › System › `#move`. Its revision never changes (`offer-1`), so once dismissed it stays dismissed.
- **API.** `GET /api/config/move` (`{settings, entries: [{list, name}]}`); `POST /api/config/move` with the same shape (`202 {restart}`, then `restartAll`; `409` while a restart is pending; `400` with the reason for anything that cannot move).
- **Web.** `MoveSettings.tsx`: every movable setting and entry, ticked; untick to keep pinned; **Move N to the database and restart**. Each pinned, non-secret registry row has **Move to the database (restarts Legato)**.

## Fresh installs

- `config.WriteFirstConfig(path)` writes, when there is no file, one that sets nothing: comments pointing to Settings and `legato config show --sources`, and the file-only settings commented out. `loadConfig` (TUI and `legato serve`) calls it before loading. A file already there is never touched; one written by provisioning pins what it holds.
- The setup wizard (`internal/setup`) with `WithSettings(sink)` saves Jira's settings in the database (`jira.base_url`, `jira.email`, `jira.project_keys`) and the token in Legato's secret store as `jira-api-token`, naming it in `jira.api_token`. The columns were always the database's (`column_mappings`). The TUI re-applies the settings after the wizard, so its sync starts with them.

## Export

`SettingsService.Export(ctx, pinned)` writes the settings set in the database (single values by key, list entries under their list, through `config.SetKey` on a new document) as YAML shaped like `config.yaml`, with a header comment. With `pinned`, the settings and entries `config.yaml` pins are included. Secrets are names: a database secret setting is a name already; a pinned one is written only when the file's value is a `legato://` or `op://` reference (read from the file itself, since the listing hides a pinned secret), and a credential whose secret is not a reference is left out. The export loads as a `config.yaml`. `legato config export [--pinned]` prints it; `GET /api/config/export[?pinned=1]` serves it as `legato-settings.yaml`; Settings › System › **Export settings** (`ExportSettings.tsx`, with **Include settings from config.yaml**) downloads it.

## Import

`ChangeSetService.ProposeImport(ctx, data, by)` loads a file shaped like `config.yaml` (`config.LoadBytes`; one that does not load is refused) and turns it into one change set, proposed without waiting: a `PUT /api/config/settings/{key}` for each registered setting the file gives (`Config.PinnedSettingsAndOthers`), and a `PUT /api/config/lists/{list}/{name}` for each list entry. File-only keys are left out and listed (`skipped`). The set has no Reeve session (`task_id` `""`), so its results are not messaged; the person sees it in the tray as a change set at its strictest call's level, and the broker's process runs it once approved. `legato config import <file> [--json]` proposes it (and broadcasts `approval_changed`); `POST /api/config/import` (the file as the body; `202` with `{id, approval_id, level, calls, skipped}`) serves Settings › System › **Import settings…**.

## MQTT restart settings

All nine `integrations.mqtt.*` settings use `ModeRestart`; normal pins and database overlays apply. `enabled`, `theme_control`, `broker`, `credential`, `discovery_prefix`, `base_topic`, and `attention_details` use `ClassRisky` for network access, publication scope, or retained detail. `device_name` and `include_reeve` use `ClassChange`. The credential setting names a credential, not a secret reference; generic settings loading never resolves the broker login. Runtime-derived topic/name defaults are not stored as settings. See [Configuration](config.md) § Home Assistant MQTT.

Settings → Integrations → **Home Assistant over MQTT** (`web/src/components/settings/MQTTSettings.tsx`, mounted by `SettingsPage`) exposes these nine keys through `RegistrySettings`; no separate persistence, client validation, credential resolution or restart action is added. The wrapper supplies setup/default/retention guidance and registry loading/error/retry feedback. Text fields keep the registry's explicit Apply/Cancel save behavior; pins, reset, save refusals, own-rule approvals and pending-restart badges remain registry-owned. Narrow registry rows wrap dotted keys and put controls on their own line on phones.

The MQTT credential field accepts only the credential **name** (empty means anonymous). Setup points to Settings › Security › Credentials for a `profile: mqtt`, `type: userpass`, `secret: legato://<name>` entry, never the login itself. The Reeve's existing `request_secret` approval-tray form can store username/password JSON without exposing it to agents; that form stores type `value`, so the credential entry must explicitly set `type: userpass` (the broker applies the declared type after opening the sealed value). The secret CLI can instead store it directly as `userpass`. No live broker configuration or connection is tested by saving settings. Site setup: `integrations/home-assistant`.


## Web editors and navigation

Settings has 16 sections in six nav groups (You, Agents, Features, Services, Access, System), each with headed groups. `web/src/lib/settingsCatalog.ts` holds the sections (`settingsSections`: ID, title, nav group, group order, Macros's `href`), and places what the registry does not: the cards (`settingsCards`), the lists (`listPlaces`; `listsWithCards` are drawn by a card of their own) and the file-only keys (`fileOnlyPlace`). A registry setting is placed by the API's `section` and `group` (`settingPlace`); one whose section the web does not know (a newer server) goes to System › Other settings. A feature's own switch (group `On or off`, `leadGroup`) comes first with no heading. A few settings are drawn by a card of their own instead of a row (`hasOwnCard`: `web.tint`, `updates.mode`, `web.rail.*`, `integrations.mqtt.*`). `SettingsSectionView` (`web/src/components/settings/SettingsSection.tsx`) draws a section: per group, its cards, rows, lists and file-only keys; an empty group is left out. The cards of the page are in `SettingsCards.tsx` and the page wires each by its catalog ID.

Routing: `#<section>` and `#<section>/<group slug>` (a group's element is `<section>--<slug>`, `groupElementId`). `settingsDestination(fragment, registry, fileOnly)` maps every old fragment to the new home: `#setting-<key>` (by the registry, so once it has loaded), `#list-<key>`, card IDs, the old categories (`#preferences` → Appearance, `#server` → System, …) and aliases (`#handoff`, `#integration-token-overview`, `#list-macros` → the Macros page). A row keeps the ID `setting-<key>`; a section's element is `section-<id>`. Nav state: On/Off from `agents.sandbox.enabled`, `swarm.enabled`, `review_passes.enabled`, `learning.enabled`; a dot on Security while `/api/devices` lists none; a count on System of the settings `pending_restart`. Below `lg`, `/settings` is the grouped list of sections with their state in words, and a section is a page of its own with Back and a row of its group links. Burnlite's OAuth callback returns to `/settings#burnlite`.

The row (`RegistrySettingRow` in `web/src/components/settings/RegistrySettings.tsx`, the canvas's Row-States board): the label and `help`; the source chip only when not the default (`SourceChip`: **Set here** with **Reset to <default>**, from the API's `default`; **config.yaml** with a lock); **Restart to apply** while `pending_restart`; **Signed** for an own rule; the control by kind (`int` with its `unit` beside, bytes shown as KB or MB by `byteUnit` in `lib/settingValues.ts` and saved as bytes; an unset number with a `default_label` is empty with that label as its placeholder; a default is greyed). Save and Cancel show only while a typed value differs; Enter saves, Esc cancels; switches and menus save at once. After saving: **Saved.** (fades), or **Saved. Legato uses X until it restarts.** from the API's `started_value`. A pinned row is read-only with a ⋯ menu (`PinnedMenu`): **Move out of config.yaml** (when `/api/config/move` lists it, with its confirm) and **Copy key**. The key shows on hover and focus (select to copy), or on every row with **Show config keys** at the foot of the nav (`showKeys.ts`, `legato:settings-show-keys`, read and written in try/catch). A group's heading says **Applies now**, **Applies to new agents** or **Applies at restart** when its settings share a mode (`modeLabel`); else each row says its own. File-only settings are `FileOnlyRow`s in their topic, with their value from `file_only_values` (`SettingsService.FileOnlyValues`: a secret's only as its kind or whether it is set) and **config.yaml only**.

`GET /api/config/settings` gives each setting its `default` (the value with nothing set; empty for a secret) and, while `pending_restart`, its `started_value`; and beside `file_only`, `file_only_values`.

Registry text fields save with Save or Enter; booleans/enums save immediately. Both registry and entry editors retain rejected drafts and detect external updates before overwriting. **Use <theirs>** accepts the server's value; **Keep <yours>** rebases the draft explicitly. Source/pin/reset, signed approval proposals and restart-required feedback are distinct. File-only entries remain read-only. List entries are edited with forms (`web/src/lib/listForms.ts`: `listForms` per list, typed fields with label, help and Optional; `formFor` gives an unknown list its name field and YAML alone): `EntryForm` in `components/settings/ListSettings.tsx` writes each field into the entry's value and keeps keys it does not know; **Edit as YAML** (`entryYaml`/`parseEntryYaml`, js-yaml) edits the whole entry in config.yaml's shape (a list of objects with its name field among the others, a map list with the name as its key) and back. Config.yaml's entries are read-only with a lock; a refused save keeps the draft with the server's reason; an entry changed elsewhere while edited asks **Use theirs** or **Keep mine**. Each list has its empty state and its add button ("No workspaces.", **New workspace**). JSON editing is gone. `adapters` shows each agent as a card of its own with a summary ("2 tiers · 3 models · connected to Legato"); its form has launch arguments, a tiers table (`TiersInput`: name, what the conductor is told, launch arguments one per line; a tier's other fields kept; rows keep what was typed, a new tier gets an unused name, and two tiers of one name block Save, as two roles of one name do in `PairsInput`), models (Claude Code only), Connect to Legato (`native_bridge`, Claude Code and Codex) and modes (Chimera only, `PairsInput`): a field with `only` shows for those agents alone. `swarm.prompts` takes a role and a prompt per agent. `reeve.rules` lists its entries numbered in the order they apply and says the last match wins (the database's after the file's, in name order, as `config.applyEntries` adds them; `SettingsService.Lists` returns an `Ordered` list in that order); a change still goes for a signature.

`SettingsPage.test.tsx` checks that every registered key, file-only key and named list has exactly one row, against `web/src/pages/__tests__/fixtures/settings-registry.json`, a copy of the registry. `TestTheWebSettingsRegistryFixtureIsCurrent` (`config/`) fails when the copy is out of date: after changing the registry, run `go test ./config -run TestTheWebSettingsRegistryFixtureIsCurrent -update`. The web test used to run `go run` itself, which compiled Go inside its timeout and failed CI's `web` job on a slow runner.

## Preferred server theme

**Preferred theme** is separate from the generic configuration registry: `ThemePreferenceService` owns the current database row and revision, with authenticated `GET`/`PUT /api/settings/theme`. Empty ID means **No preference**. Saves apply after commit without a restart and notify followers through `server_theme_changed`; they do not change browser/native local choices. **Follow server** is a client flag, not a registry setting. The risky `integrations.mqtt.theme_control` opt-in is restart-only and independent of aggregate `enabled`; saving it does not enable control live. Only the operator chooses when to restart. See [Client themes](themes.md).

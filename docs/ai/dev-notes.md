## Development Notes

- Legato builds without C: `task build` and `task install` set `CGO_ENABLED=0`, so `./legato` is one static binary that cross-compiles with `GOOS`/`GOARCH` alone. `TestLegatoBuildsWithoutC` (`cmd/legato`, skipped with `-short`) fails when a dependency starts to need C; put such code in a separate binary, as the credential-plugins plan does for PKCS#11. `TestLegatoBuildsForEveryReleasePlatform` (also skipped with `-short`) builds for each platform `task release:dist` lists, read from the Taskfile, so code that compiles only on Linux fails there and not in the release; give such code a file per OS (`openpty_linux.go`, `openpty_darwin.go`). `task test:race` still needs C, since the race detector uses it
- Tests use real SQLite databases in `t.TempDir()` — no mocks for storage
- Event bus tests use real channels — no mocks
- Config tests use `t.Setenv()` for env var isolation
- Jira client tests use `net/http/httptest` servers — no real API calls
- Sync service tests use a `mockProvider` implementing `TicketProvider` — not the real Jira client
- `sync_log` uses `datetime('now')` which has second precision — queries use `id DESC` as tiebreaker for ordering
- TUI tests: test model state via `Update()`, not rendered ANSI output — lipgloss strips styles in non-TTY test environments
- Bubbletea async data loading: never replace the entire model in a `DataLoadedMsg` — only copy data fields, or dimensions set by `WindowSizeMsg` get wiped
- `tea.Model` interface requires `Update` to return `(tea.Model, tea.Cmd)` — concrete types need type assertions in tests
- `cmd/validate/service-smoke/` — standalone service layer smoke test (renamed from phase2)
- Glamour: must use `glamour.WithStyles(styles.DarkStyleConfig)`, NOT `WithAutoStyle()` — auto-style probes terminal background via stdin/stdout which deadlocks in bubbletea's alt-screen mode
- Clipboard: `Copy()` uses `cmd.Start()` + `StdinPipe()`, NOT `cmd.Run()` — `wl-copy` on Wayland stays alive to serve paste requests, so `Run()` blocks forever
- Detail view loads cards synchronously via `GetCard()` in the `OpenDetailMsg` handler (hits local SQLite, not remote API). `e` opens `$EDITOR` for Legato-owned description details on every task (via `tea.ExecProcess`); `t` opens title edit only for local tasks. Provider-backed editors are seeded from `LocalDescriptionMD`, never the effective combined document.
- Hotkeys: add static bindings in `internal/tui/hotkey/defaults.go`, then handle the typed action ID in its declared root/page/overlay target. Dispatch, full help, page shortlists, status bars, and inline hints query this registry; do not add parallel key-label arrays. Capability gates remove bindings from both dispatch and display. Per-item predicates hide compact hints but still allow dispatch when the action must return user-fixable feedback
- Hotkey precedence: active overlays receive input before pages; focused text-entry overlays and review/plan input modes consume printable keys before globals, while menu overlays may yield `?` to help. Parent/global collisions require `YieldToSpecific`. Move/workspace content-derived letters remain dynamic and must query `Registry.IsReserved` for their overlay scope
- Overlay system: only one overlay is active at a time (`overlayType` + `activeOverlay tea.Model`). `?` replaces menu overlays with help but is typed into focused overlay inputs; `esc` dismisses according to the active overlay/mode
- Move overlay shortcuts: first letter of column name lowercased (`b`=Backlog, `r`=Ready, `d`=Doing, `v`=Review, `x`=Done); falls back to number keys on conflict. `w` opens workspace assignment overlay (`MoveWorkspaceOverlay`) for the same task — lists "None" + workspaces, marks current, emits `WorkspaceAssignedMsg{TaskID, WorkspaceID}`. App calls `UpdateTaskWorkspace` on selection
- Search overlay: typing appends to query, produces `SearchQueryChangedMsg` → app calls `BoardService.SearchCards` → returns `SearchResultsMsg` → overlay updates results; `enter` closes overlay and calls `board.NavigateTo(cardID)`
- Create overlay: `n` opens from board view; title input + description input with `focusField` cycling (tab: title → column → workspace → description); `h`/`l` cycles columns/workspaces when focused, `ctrl+j` inserts newline in description, ctrl+p cycles priority (none/low/medium/high); workspace pre-filled with active workspace (None if All/Unassigned view); enter submits `CreateTaskMsg` (with description + workspaceID), esc cancels
- Title edit overlay: `t` from detail view (local tasks only); pre-filled text input, enter saves via `BoardService.UpdateTaskTitle`, esc cancels
- Card context overlay: `c` from a selected board card opens Open details, Move, Delete, and Workflows. Basic operations emit the existing board messages; Workflows lists definitions with exactly one task input and gathers remaining typed inputs through `TaskWorkflowLauncher`, which also lists a review item for each open pull request of the card (`reviewPassOptions`, LEG-596): **Open review loop · #N** when a loop holds it, whatever started it (`TaskWorkflowOption.Loop`, from `ReviewLoopLookup`; the TUI opens its link in the web UI), else **Review passes · #N · agent|person**, which starts the built-in `review-loop` with `repo`, `pr_number` and `agent_author` derived (`ReviewAuthors`, over `agentAuthoredPRs`: true only when Legato's author App opened the pull request, spec LEG-559 D8), after **Review passes · stack #a–#z** (scope `stack`) when the card has several open pull requests in one repository and none is held (each item then scope `pr`). `Start` refuses a held pull request naming its loop and link before making a run, and returns a run refused at once the same way (`*WorkflowStepError` with its code and link). The start only writes the run, so it runs whether or not the process has the review engine. They are offered only while some Legato on the data folder runs the review engine; otherwise the menu says why instead (`ReviewUnavailable`, `GET /api/review-engine`; see [TUI](tui.md) § Review passes from the card menu). The web card menu has the same items (`CardContextMenu` `reviewPasses`, `reviewLoops`, `onReviewPasses`, `onOpenReviewLoop`, and `reviewUnavailable` for the reason; Board looks each pull request up at `GET /api/review-loops`, opens the loop's link, else `RunWorkflowDialog` on `review-loop` with those values read-only).
- Delete overlay: `d` from board, `D` from detail; shows task title, warns if remote-tracking ("removes local reference only"); `y` confirms, `n`/`esc` cancels. Confirm calls `BoardService.DeleteTask`, returns to board from detail view
- Archive overlay: `X` (shift-x) from board opens archive confirmation if Done column has cards; shows "Archive N done cards?", `y` confirms → `ArchiveConfirmedMsg` → `BoardService.ArchiveDoneCards()` → board refresh, `n`/`esc` cancels. No-op if Done column is empty. Done column identified by name (case-insensitive match on "Done"), not by position — boards may have columns after Done (e.g. Unmapped)
- Card archiving: `store.ArchiveTask(id)` sets `archived_at = datetime('now')`, `store.ArchiveTasksByStatus(status)` bulk archives. All listing queries (`ListTasksByStatus`, `ListTasksByStatusAndWorkspace`) filter `AND archived_at IS NULL`. `BoardService.ArchiveTask(id)` validates task is in Done column before archiving. No unarchive in v1 — data preserved in DB for future restore feature
- Import overlay: `i` from board (no-op without SyncService); fixed-size panel (60% width, 10 result rows + scroll indicator); typing triggers `SyncService.SearchRemote` (min 2 chars); j/k navigates, enter imports via `SyncService.ImportRemoteTask` (with active workspace ID if viewing a specific workspace), esc cancels. Errors shown in red instead of silent "no results"
- Workspace overlay: `w` from board opens workspace switcher listing "All", "Unassigned", and each configured workspace (with color dot). j/k navigates, single-letter shortcuts, enter selects, esc dismisses. Returns `WorkspaceSelectedMsg` with `store.WorkspaceView`. Board filters cards via `ListCardsByWorkspace`. Workspace tags shown on cards in "All" view only. Status bar shows active workspace name in configured color. Create overlay includes workspace picker (h/l cycling, pre-filled with active workspace)
- Workspace data flow: `workspaces` config → `SeedWorkspaces` at startup → `workspaces` SQLite table → `tasks.workspace_id` FK. `store.WorkspaceView` enum: `ViewAll`/`ViewUnassigned`/`ViewWorkspace(id)`. `ListTasksByStatusAndWorkspace` handles SQL filtering; `ViewAll` excludes the reserved **Workflows** workspace, while `ViewWorkspace(id)` explicitly opts into it. Board model holds `workspaceView` and `workspaces` state. `NewApp` takes `[]service.Workspace` param. Workspace assignment works for both local and remote tasks (workspaces are a local organizational concept)
- Card warning indicators: `CardData.Warning` bool → renders warning icon; sourced from `sync_log` where most recent entry for task is `push_failed`
- Error event classification: sync service classifies errors by message content (auth/rate-limit/offline) and publishes typed events; app converts to `statusbar.ErrorMsg`
- Messages Legato sends to an agent: every message that the operator did not type (a notice, a resume note, a relayed event, a verdict, anything a timer, a service or another agent caused) must open with a `[legato <kind>]` tag, such as `[legato interrupted]` or `[legato review pass]`; another agent's words open with `[legato peer <task-id>]`. It reaches the agent as a user turn, and the tag is the only thing that makes the web UI draw it as Legato's own message (`web/src/lib/legatoMessage.ts`, the teal `Legato · <kind>` bubble) instead of as the operator's. A kind that only tells of something that happened can be drawn as one collapsed line instead (`eventLabels` in that file, `service.LegatoEvent` for the TUI; today `[legato change set]` and `[legato restart]`). Never send untagged automated text, at launch (`AgentSpawnOptions.Prompt`) or later (`SendMessage`). Put the tag in the message's constant or builder, and assert it in the test that sends the message. In any text an agent reads, the human is "the operator" (`GLOSSARY.md`), never "the person" or "the user". **One exception: macros are never tagged.** A macro (`service.MacroService`, built-ins included) is the operator's own words, so whether sent from a picker or started on a card it reaches the agent untagged, as if typed
- Server: `internal/server/` consumes `BoardService`, `AgentService`, and `TmuxManager` interfaces + `engine/prompt` for detection — no TUI imports, independently startable; tests use `httptest.NewRecorder`, `mockTmuxManager`, and `mockBoardService`. Stream lifecycle tests cover subscribe/unsubscribe, pipe reset on failure, cancel abort. `findIncompleteEscape` has table-driven tests for CSI/OSC/bare-ESC edge cases. `log.SetOutput(io.Discard)` before bubbletea alt-screen to prevent server log writes from corrupting TUI. `SetTLS(cert, key)` enables HTTPS — `Serve()` calls `ServeTLS` when configured. SPA handler sets cache headers (immutable for hashed assets, no-cache for SW/index.html)
- Agent sessions: tmux sessions named `legato-<TASK_ID>`, tracked in `agent_sessions` SQLite table (task_id column). Tmux manager (`internal/engine/tmux/`) uses `exec.LookPath` injection for testability. Integration tests skip when tmux not installed (`skipWithoutTmux`). SpawnAgent verifies tmux session is actually alive before returning "already running" error (prevents stale DB state). `ListAgents()` calls `PaneCommands()` to override `Command` with live foreground process name (e.g., `claude`, `vim`) for running sessions; falls back to DB value for dead sessions or on tmux query error. `AgentSession.Title` populated via `store.GetTask()` lookup per session (gracefully empty if task deleted)
- Agent service tests use `mockTmux` implementing `TmuxManager` interface + real SQLite — same pattern as sync service with `mockProvider`
- Agent view: `viewAgents` enum value, toggled via `A` key from board. `agents.Model.Update` returns `(Model, tea.Cmd)` (concrete type, same as board — not `tea.Model`). Polling via `agentTickMsg` at 200ms; capture output forwarded as `CaptureOutputMsg`
- Agent attach: `tea.ExecProcess` suspends bubbletea, runs `tmux attach-session` with escape key set to `Ctrl+]` (configurable via `agents.escape_key` in config). On detach, refreshes agent list
- Agent card indicator: `CardData.AgentActive` bool and `AgentState` → the strip at the foot of a board card (`running`, `needs you`, `idle`, ...). Populated by app querying `AgentService.ListAgents()` on `DataLoadedMsg`, not by BoardService. The same list is handed to the agents view, so its record of what changed grows while the board is in front
- Data model: provider-agnostic `tasks` table with nullable `provider`/`remote_id`/`remote_meta` for synced tasks, nullable `workspace_id` FK to `workspaces`. `Card.Title` (not Summary), `Card.WorkspaceName`/`WorkspaceColor` populated in All view. `CardDetail.RemoteMeta` map for provider-specific fields, `CardDetail.WorkspaceID *int`. `service.Card.IssueType` extracted from remote_meta at read time
- Local task creation: `BoardService.CreateTask(title, description, column, priority, workspaceID)` generates 8-char alphanumeric ID, inserts task with description and optional workspace, publishes refresh event
- Task editing: `BoardService.UpdateTaskDescription(id, description)` updates Legato-owned `description`/`description_md` for local and provider-backed tasks; `UpdateTaskTitle` still rejects provider-backed tasks. Provider Markdown is stored in `remote_description_md`, and effective detail is composed at the service boundary.
- Editor config: `config.ResolveEditor(cfg)` → config `editor` field → `$VISUAL` → `$EDITOR` → `vi`. Used by detail view `e` keybinding to open external editor for description editing via `tea.ExecProcess`
- Task deletion: `BoardService.DeleteTask(id)` verifies existence, deletes from store, publishes `EventCardsRefreshed`. Works for both local and remote-tracking tasks (remote-tracking only removes local ref)
- Provider icons: a card names where its task comes from at the end of its first line (◈ jira, ◉ github, `local`). The glyphs are configurable via `icons` config field (`"unicode"` default, `"nerdfonts"` for Nerd Font glyphs). `theme.NewIcons(mode)` returns icon set, passed through `NewApp` → `board.New` → `RenderCard`
- Board rendering: see [TUI](tui.md). Views give a block a solid background with `theme.Fill`, which puts the background back after every styled span, so **do not set `.Background` on the spans inside a card or a panel**; render them with foreground colors and fill the block. Every view must return exactly the size it was given, or panels joined side by side break apart
- First-run setup: `loadConfig` writes `config.WriteFirstConfig` when there is no `config.yaml` (comments only: a pointer to Settings and the file-only settings, commented out; it pins nothing); `config.Load` without a file gives what an empty file gives. When `column_mappings` is empty, `main.go` runs the guided setup, `setupFlow(...).Run` (`setup.Flow`, also `legato setup`; see [CLI](cli.md) § Subcommands): it seeds the default columns through the `ColumnSeeder` interface (backed by `StoreAdapter`), runs the checks, chooses the default agent tool and a ticket tracker. Jira's settings go to the database through the `SettingsSink` and the token to Legato's secret store as `jira-api-token` (`jira.api_token: legato://jira-api-token`); nothing is written to `config.yaml`. A stopped or failed setup never ends Legato: the board opens. `legato serve` runs no setup: it seeds `board.columns` on a board with none (`setup.SeedColumnsIfEmpty`), so a headless worker can take handoffs
- Jira client: uses `/rest/api/3/search/jql` endpoint (not the removed `/rest/api/3/search`)
- `NewSyncService` takes `projectKeys []string` for scoping remote searches
- `NewApp` takes `SyncService` (nil-safe), `PRTrackingService` (nil-safe), `theme.Icons`, `editor string` (resolved via `config.ResolveEditor`), `[]service.Workspace` (loaded from DB), and a variadic trailing `*service.SwarmService` (nil-safe — when omitted, capability-gated `S`/`C` swarm bindings and swarm UI are hidden); `board.New` takes `theme.Icons`; `detail.New`/`detail.NewLoading` take `editor string`
- Swarm tests: `internal/service/swarm_test.go` and `swarm_testhelpers_test.go` use the existing `mockTmux` from `agent_test.go` plus a temporary repo root for `ScopeOverlaps` calls. Conflict tests must touch a real file under both scopes' intersection (the tree walk drives overlap detection — empty repos always report no overlap). The CLI swarm tests in `internal/cli/swarm_test.go` define a `stubTmux` that records spawn calls but no-ops on attach/capture
- Swarm in-detail navigation uses `J`/`K` (uppercase) instead of `j`/`k` because lowercase is reserved for viewport scrolling. The spec called for `j`/`k` but the conflict is unavoidable without a focus-mode toggle, which is over-scoped for v1
- Swarm sub-task IDs are `st-<10-hex>` (13 chars) generated via `crypto/rand` in `service.generateSubtaskID`. The `reviewer_agent_id` column on `swarm_subtasks` is a v0 schema remnant retained for migration compatibility; v1 uses the single `builder_agent_id` slot
- CI: `.github/workflows/ci.yml` runs on every pull request (in a GitHub stack, its heavy jobs on the top PR only: see the next note) and push to `main`: `scripts/migration-order.sh` (job `migrations`: a new migration must sort after the newest in the latest release tag and, on a pull request, on its base branch; see [Database](database.md)), `scripts/case-clashes.sh` (no two tracked paths may differ only in case, nor two JS/TS modules as an import names them, without the extension: macOS and Windows would see one, as the v0.15.0 macOS desktop build did with `Approvals.tsx` and `approvals.ts`; tested by `cmd/legato/case_clashes_test.go`), `go vet` and `go test -short ./...` (with tmux and node installed, so agent-session and plan-validator tests run), then the two build tests `-short` skips (`TestLegatoBuildsWithoutC`, `TestLegatoBuildsForEveryReleasePlatform`), the web UI's `pnpm run build` (the `theme-utilities.css` check, `tsc -b`, `vite build`: what `task release:dist` runs as `web:build`) and `pnpm run test`, and the `packages/` workspace's `pnpm run check` (lint, types and tests of every app there; job `packages`). Vitest's test and hook timeouts are 20s and Testing Library's `findBy`/`waitFor` give up after 15s (`web/vite.config.ts`, `web/src/test/setup.ts`): pages that render long tables into jsdom missed the defaults on a loaded machine. `internal/testenv` keeps each package's isolated home under `/tmp`, so on a machine whose `/tmp` is a small RAM disk the full Go suite can fail with "disk is full" (several packages install the plan validator's npm packages at once, with `npm ci` from the lockfile in `internal/engine/planvalidate/node/`; see [Plans](plans.md)); CI runners do not have this problem
- CI on a GitHub stack (LEG-629): only a stack's top PR runs `ci.yml`'s heavy jobs, `go`, `web`, `packages` and `docs` (the docs site's PR build, moved from `docs.yml`, which now builds and publishes main only; it builds when the PR, or on the top of a stack the whole stack since `stack.base.ref`, changes `site/`, `GLOSSARY.md`, `config/`, `internal/tui/hotkey/` or the two workflows, and otherwise passes at once). Each has the gate `github.event_name != 'pull_request' || !github.event.pull_request.stack || github.event.pull_request.stack.position == github.event.pull_request.stack.size`, so main and a PR outside a stack build in full. `paths` and `migrations` run on every PR: they take seconds, and a single layer can break them on its own (`migrations` compares each PR with its own base). Drafts build like any other PR, unlike autopilot's, since agents open draft PRs and their review loops count the checks. The commit status `ci/stack` (`scripts/stack-status.cjs`, tested by `scripts/stack-status.test.cjs` through `cmd/legato/stack_status_test.go`; `cmd/legato/ci_workflow_test.go` holds the workflow files to the design; the jobs with `statuses: write` check the script out from the default branch, never the PR's, so changing what posts `ci/stack` takes the right to change workflows or to merge, not only to push a branch, and post nothing while the default branch has none) stands for a lower PR's CI: job `stack` posts it at the start of every PR's run (`success` "Gated by its own checks" on the top and on an unstacked PR, with `pending` on the PRs below the top; `pending` "Waiting for the last PR in the stack" on a lower PR that has none yet); job `stack-status` (needs every other job, skipped when the run is cancelled) posts the top's result, unless the PR has a newer head or is no longer the top by then, on each lower PR whose head the top's build contains (`success` when it passed and the top is approved, or no approval is required; `pending` "Waiting for approval"; `failure`); `.github/workflows/stack.yml` re-posts it on a review of the top and, when a top PR closes unmerged, marks the new top and the PRs below it pending with what to do. How a stack is built:
  - Open its PRs as drafts, link them (`gh stack link`; its bottom PR must be based on `main`: with the bottom on another branch, `gh stack link --base <branch>` made no stack, LEG-629), then mark them ready (the `create-stack-prs` skill does this). Linking fires no workflow; `ready_for_review` does, with the stack in the payload, and cancels the opening run through the concurrency group.
  - A push to a lower layer alone leaves its `ci/stack` pending ("Waiting for the last PR in the stack") until the top is restacked and pushed: the top's build must contain that head.
  - GitHub keeps a PR closed unmerged in its stack (and merged ones too, so as the bottom layers merge the top stays the top). When the top closes unmerged, the PR below it stays below the stack's size, so its heavy jobs keep skipping: dissolve the stack (Unstack) and link it again without the closed PR, then push to the new top. A re-run does not help: it replays the old payload, with the old position.
  - Required checks: nothing is required on `main` today. Should branch protection come, require `ci/stack`, `paths`, `migrations`, `go`, `web`, `packages` and `docs` (a job its `if:` skips reports success, so `ci/stack` carries a lower PR's result and the heavy jobs carry the top's), never `docs.yml`'s `build` or anything of `stack.yml`, and only once open stacks have rebased onto a main with `ci/stack`. `review_passes.required_checks` should name the same list (see [Integrations](integrations.md) § Required checks). A steward or a review loop reads a lower PR's CI as `ci/stack`, `paths` and `migrations`; its skipped `go`/`web`/`packages` test nothing, and `ci/stack`'s link leads to the top's run
- Log file: every Legato process (`legato serve`, the TUI, a hot-reload child) writes its `log` output to `<data_dir>/logs/legato.log` through `internal/engine/logfile` (rotated past 10 MB, three old files kept as `.1`–`.3`; several processes append to one file and each notices another's rotation). `startLogFile` in `cmd/legato/logfile_runtime.go` sets it up: serve also keeps stderr, the TUI writes only to the file (it used to discard its log)
